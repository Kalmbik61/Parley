# Браузер Parley, этап D: сверочный спайк (ввод в `<webview>`, хранилище, файлы, скрипты)

**Дата:** 2026-10-20. **Electron:** 44.4.5 (Chrome из той же сборки). **Машина:** macOS 15.3.1 (24D70), Apple M4 Pro, Node 22.23.3; окна проб — на главном экране 3440×1440, DPR 1. Playwright 1.63.0 (`_electron`). Codex CLI 0.162.0 (только справка и документация, без запуска модели).
**План:** `docs/specs/2026-10-20-browser-agent-control-plan.md`, задача 1 и раздел «Ветки спайка».
**Скрипты:** scratchpad сессии, в репозиторий не входят: `lib-d.cjs` (стенд), `spike-d.cjs` (вопросы), `run.cjs` (прогон без Playwright), `pw-d.cjs` (прогон через Playwright), `other-app.cjs` (второе приложение спереди), `winlist` (Swift: окна процесса на экране, без записи экрана), `summarize.cjs`.

## Как устроена проба

- Окно `BrowserWindow` 1200×800 (`webviewTag`, `contextIsolation`, `sandbox`), сверху `<textarea id="chat">`, под ним `<webview id="w1" partition="persist:spike-d">` 1000×600. Как у Parley: `will-attach-webview` снимает preload и ставит `disableDialogs`; разрешения раздела — отказ (`setPermissionRequestHandler`/`setPermissionCheckHandler`); гость стартует с `about:blank`, отладчик подключается до `loadURL` (вариант D этапа 0).
- Гость — локальный HTTP на 127.0.0.1: форма (`#plain`, `#second`, кнопка submit), управляемое поле React 18 (UMD из `packages/desktop/node_modules`), `contenteditable`, `<select>` из трёх, чекбокс, `<input type=file multiple>`, ссылка `download` на `/file.csv` (`Content-Disposition: attachment`), кнопка-счётчик, кнопка с `while (true) {}`, `localStorage`/`sessionStorage`; страница пишет `focus`/`blur`/`keydown`/`input` в журнал.
- **Каждый случай — в свежем `<webview>`** (старый удаляется из DOM): фокус, одолженный раньше, не переносится на следующий случай.
- **Состояния фокуса окна:** `focused` — окно спереди и ключевое (`app.focus({ steal: true })`, `win.isFocused()` true); `otherWin` — спереди другое окно того же приложения; `otherApp` — спереди отдельный процесс Electron (другое приложение); для мыши ещё `occluded` (окно целиком закрыто чужим окном, `document.visibilityState` окна `hidden`) и `minimized`. Фактическое состояние записывалось в каждом случае.
- **«Человек» — модель, а не настоящая клавиатура и мышь.** Реального ввода ОС у пробы нет. Нажатия и клики человека моделировались двумя способами: (а) CDP окна-хозяина (`win.webContents.debugger`, `Input.dispatchKeyEvent`/`dispatchMouseEvent`) — без эмуляции фокуса; (б) Playwright `_electron`: `window.keyboard.type` / `window.mouse.click` (через обратный вызов драйвера). Оба пути маршрутизируются браузерным процессом в сфокусированный виджет так же, как события ОС после `RenderWidgetHostView` окна, но это не замер настоящей клавиатуры.
- Человек за машиной работал во время проб, и окно пробы забирало у него фокус: в одном пробном прогоне его нажатия попали в `chat` пробы. Поэтому в зачётных прогонах `before-input-event` окна и гостей вне собственных отправок пробы считался «чужим»; случаи с чужими событиями помечены, ни один вывод на них не держится (итоги в них те же).
- **Прогоны:** каждый вопрос — 3 прогона (отдельный процесс Electron на прогон), в трёх состояниях фокуса, где это сказано; В16 — одно действие на процесс (открытое меню `<select>` иначе портит следующий случай).

### Сверх вопросов таблицы

- **Набор клавиш `guest.sendInputEvent` без фокуса гостя** (В2, 18/18, `send` и `send` + эмуляция фокуса): текст — `char` на кодовую точку, работает и кириллица, и `✓😀`; Backspace, стрелки, Tab (фокус к следующему полю страницы) — `keyDown`/`keyUp`; **Enter — только `keyDown` + `char '\r'` + `keyUp`** (без `char` форма не отправляется 0/18); управляемое поле React — значение и `onChange` на каждый символ; `contenteditable` — работает; **⌘A не выделяет** (ни `sendInputEvent` с `meta`, ни `webContents.selectAll()`; 0/18 и 0/18); `webContents.insertText()` вставляет без фокуса 18/18. С `Emulation.setFocusEmulationEnabled` поле получает событие `focus` от `DOM.focus` (без эмуляции — нет). Путь одолженного фокуса (CDP) для сравнения: ⌘A с `commands: ['selectAll']` выделяет 3/3, Enter с `text '\r'` отправляет форму 3/3.
- **Мышь и фокус окна.** После клика агента окно возвращает фокус (`prev.focus()`) — следующие нажатия человека идут в `chat`, а клавиши агента через `guest.sendInputEvent` — по-прежнему в поле страницы: 9/9 raw, 9/9 pw. Страница при этом видит `blur` (без эмуляции фокуса).
- **Окно не на экране.** Окно закрыто чужим окном целиком, свёрнуто или спереди другое приложение: CDP-клик 9/9, клик `guest.sendInputEvent` 9/9, клавиши `guest.sendInputEvent` 9/9.
- **Зависание шага CDP-мыши.** `Input.dispatchMouseEvent` ждёт ответа страницы: клик, обработчик которого не возвращается (кнопка с `while (true) {}`), держит `mouseReleased` до срока 3/3. Ещё два зависания на 5 с без видимой причины — в двух пробных прогонах (около 60 кликов), в зачётных — ни одного.
- **`viewPoint` (точка клика для окна) по снимку окна-хозяина** (красная кнопка, 3/3 в каждом режиме): формула задачи 9 (`fit === null ? × zoom : × scale`) верна без эмуляции (масштаб 1 и 2) и при эмуляции без масштаба страницы; при эмуляции не мобильной **с** масштабом страницы кнопка на экране в `× scale × zoom` (0,864 вместо 0,6); при мобильной эмуляции страницы без `<meta viewport>` — около `× 0,21` вместо `× 0,739` (страница уменьшена своим масштабом). Сам клик CDP при этом попадает (В6).
- **Playwright:** под Playwright гость ни разу не увидел `blur` и `document.hasFocus()` у него всегда true — Playwright включает эмуляцию фокуса и у `<webview>`. E2E этапа D не может проверить `blur` страницы.
- **`browser:focus` стража** (существующая функция, не этап D): `focus` WebContents гостя не пришёл ни в одном случае, включая модель клика человека при ключевом окне. На macOS клик в страницу, похоже, вкладку активной этим путём не делает (E2E `browser-page.spec.ts:162` шлёт `emit('focus')` вручную). Проверить настоящим кликом — человеку.

## Вне таблицы — нужно решение человека

1. **В2 «иначе» и В3 «по умолчанию» вместе.** Строка В2 при «иначе» убирает механизм фокуса целиком (задачи 5, 15b, 20 «как в В1»: нет `focus` в `AgentActivity`, `requestFocus`, `agentFocusReady`, обработки в окне). Но В3 — «да»: любой клик агента (CDP и `sendInputEvent`) уводит фокус окна на `<webview>`, и без возврата следующие нажатия человека уйдут в страницу (Фокус ревью 1). План (задача 9) для В3 «да» одалживает фокус и мыши — этот механизм строка В2 и удаляет. Ещё: при пути `sendInputEvent` у ⌘A (`selectAll`) нет рабочего способа без фокуса, а клавиатура CDP без фокуса уходит в поле человека (В1). Варианты:
   - **А. Оставить план как есть** (CDP-клавиатура с одолженным фокусом для клавиш и мыши, возврат фокуса окном, `setFocusEmulationEnabled`): замерено и работает (В4 (1) 72/72). Минус — во время ввода агента нажатия человека шли бы в страницу (держит правило тишины M3).
   - **Б. Смешанный путь:** клавиши и текст — `guest.sendInputEvent` (без фокуса; Enter — `char '\r'`; пересылка сочетаний `FORWARDED` выключена на время ввода агента или `bad_request`, как в строке В2), мышь — CDP с одолженным фокусом и возвратом (механизм фокуса остаётся только для мыши). ⌘A — одолжить фокус на одно нажатие (CDP `commands: ['selectAll']`) или функция Parley над элементом (`select()`/`Range`; **не проверено**), или убрать ⌘A из `press` и сказать в скилле, как очистить поле.
   - **В. Всё через `guest.sendInputEvent`** (и мышь): фокус окна мышь всё равно уводит (В3, 18/18), координаты вида при эмуляции ненадёжны (см. `viewPoint`) — не советую.
2. **В15 (1): фокус на скрытый `<webview>` ставится** (27/27), и клавиши — агента и человека — уходят в скрытую страницу (18/18). Механизм M2 (`ok = document.activeElement === <webview>` → `tab_hidden`) скрытую страницу не распознает. В строке В15 столбец «иначе» есть только для клика. Варианты: (а) окно отвечает `ok = видна && activeElement === <webview>` (видимость окно знает само; задача 20); (б) main отказывает `tab_hidden` по `record.visible === false` до просьбы о фокусе (задачи 15b, 17); (в) разрешить ввод в скрытую страницу — клавиши действительно доходят, но человек их не видит (Фокус ревью 2 придётся переписать).
3. **В4 (2): `hostWebContents.focus()` не нужен и вреден.** Без него нажатие человека после возврата фокуса идёт в `chat` (36/36); с ним при другом окне Parley спереди окно этой страницы становится ключевым — фокус ОС отнимается у человека (6/6 raw, 5/6 pw). Строка таблицы для (2) не даёт «иначе». Вариант: не звать `host.focus()` (возврат — только `focus()` прежнего элемента в окне); то же про `guest.focus()` — он тоже делает окно ключевым.
4. **`viewPoint`** (не вопрос таблицы, задачи 9 и 20): при эмуляции с масштабом страницы точка должна быть `× scale × zoom`; при мобильной эмуляции страницы без `<meta viewport>` ни одна из формул не верна (нужен масштаб страницы, например `Page.getLayoutMetrics`, — не проверено). Варианты: поправить формулу для эмуляции с масштабом и принять сдвиг точки у мобильных страниц без `viewport`; или считать точку по `Page.getLayoutMetrics`.

## Рецепт ввода (что замерено)

- **Клавиатура, путь плана (А):** окно запоминает `document.activeElement` и зовёт `w1.focus()`; main — `DOM.focus` цели (или клик), `Emulation.setFocusEmulationEnabled({ enabled: true })` (страница не видит `blur`), `Input.insertText` для текста, `Input.dispatchKeyEvent` для клавиш (Enter — `text: '\r'`; ⌘A — `commands: ['selectAll']`); по концу операции окно зовёт `prev.focus()` — **без** `win.webContents.focus()`. Нажатия человека после этого — в `chat` (72/72). Без одолженного фокуса CDP-клавиатура попадает в поле человека (27/27) — ни одного `Input.*` клавиатуры без фокуса.
- **Клавиатура без фокуса (Б, если выберут):** `DOM.focus` цели, затем `guest.sendInputEvent`: текст — `{ type: 'char', keyCode: <символ> }` на кодовую точку; Backspace/Tab/стрелки — `keyDown` + `keyUp`; Enter — `keyDown` + `char '\r'` + `keyUp`; ⌘A — нет. `before-input-event` гостя видит эти нажатия: часы тишины их должны пропускать (`ignore`), пересылка сочетаний — выключена на время ввода агента.
- **Мышь (оба пути):** CDP `Input.dispatchMouseEvent` (`mouseMoved`, `mousePressed`, `mouseReleased`) в центр `DOM.getBoxModel` после `DOM.scrollIntoViewIfNeeded` × `k = эмуляция ? (мобильная ? scale / zoom : scale) : 1`; клик уводит фокус окна на `<webview>` — окно возвращает его `prev.focus()`. Клики доходят при окне не в фокусе, закрытом, свёрнутом и у скрытой страницы. По `<select>` не кликать (системное меню, Escape его не закрывает). Шаг мыши ждёт ответа страницы — нужен свой срок на шаг и обрыв по `signal`.

## Риски

- Проба не трогала настоящую клавиатуру и мышь ОС: «человек» — CDP окна и Playwright. Маршрут после `RenderWidgetHostView` у них тот же, что у ОС, но фокус ОС-окна и `browser:focus` при настоящем клике проверяет только человек.
- E2E этапа D (Playwright) не видит `blur` страницы и не меряет настоящую клавиатуру; тесты Фокуса ревью 1 в 22a проверяют маршрут, а не ОС.
- Клик агента по `<select>` оставляет системное меню на экране человека даже после закрытия страницы.
- Скрипт агента с `execCommand('copy')` в течение ~5 с после клика агента перезаписывает буфер обмена человека (В17, принятый риск).
- Зависший промис в `browser_evaluate` держит вызов CDP до срока команды `sendAgentScript` (15 с); страница не страдает.
- Во время проб окно забирало фокус у человека, работавшего за машиной; зачётные прогоны отделяли его нажатия, но вмешательство мышью отследить нельзя (одиночные отклонения в долях отмечены).
