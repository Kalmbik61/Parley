2. **Прогон 2 — ошибка в `plan.ts` `foreign()`.** Раз `/opt/parley-relay/.env` есть, любой порт, который держит

3. Даже без ошибки режим `proxy` даёт сниппет на `127.0.0.1:8787`: веб-сервер в Docker до такого адреса не

Сервер s-38 починил руками (раздел 6.5) — это и есть целевое поведение для такого сервера.

## 2. Новое правило: мастер правит чужой веб-сервер

Прежнее правило 6.7 «Чужие конфиги мастер не правит» и строка «Кроме `/opt/parley-relay`, правил `ufw` и пакетов
Docker мастер на сервере ничего не трогает» отменяются. Человек попросил одну кнопку, поэтому мастер теперь сам
добавляет relay в веб-сервер человека. Новое правило:

**Мастер меняет конфигурацию веб-сервера человека только одной из двух правок:**
- **свой файл** `parley-relay<суффикс>` в каталоге, который сервер уже подключает (`import` у Caddy,
  `include …/*.conf` у nginx);
- **свой блок** в конце главного Caddyfile между строками `# BEGIN parley-relay …` и `# END parley-relay` — только
  если у Caddy нет такого каталога.

**Гарантии.**
1. **Всё видно до Run.** Экран плана перечисляет каждый чужой файл, который мастер добавит или изменит: путь на
   сервере, действие (добавить файл, заменить свой файл, дописать блок, убрать свой файл, убрать свой блок),
   содержимое целиком, путь резервной копии, команды проверки и перезагрузки. Также — подключение relay к чужой
   сети Docker (имя сети и псевдоним).
2. **Чужие строки не трогаются.** Мастер не меняет и не удаляет ни одной строки, которую не писал. «Свой» файл
   определяется по имени и содержимому (раздел 5.3). Файл с нашим именем, но не наш, — план не выполняется.
3. **Ровно те байты, что в плане.** Перед записью мастер сверяет sha256 целевого файла с тем, что видела разведка.
   Файл изменился между разведкой и Run — правка не делается, шаг падает с текстом «файл изменился, запустите
   мастер снова».
4. **Проверка до перезагрузки.** После записи — штатная проверка самого сервера (`caddy validate` в контейнере,
   `nginx -t` и `nginx -T`), затем мягкая перезагрузка (`caddy reload`, `nginx -s reload`). Caddy под systemd
   перезагружается только `systemctl reload caddy` — в окружении юнита (раздел 5.2); загрузка конфигурации у
   Caddy атомарна, плохая отклоняется целиком. Остановки и перезапуска чужого контейнера или службы нет.
5. **Автоматический откат.** Проверка или перезагрузка не прошли → файл восстанавливается из копии байт в байт
   (новый файл удаляется), работающий сервер остаётся на прежней конфигурации: Caddy при неудачной загрузке
   оставляет старую; nginx до сигнала перезагрузки проверен `nginx -t` (о провале самой перезагрузки
   `nginx -s reload` не сообщает — защита только `nginx -t`). Правка, как и любая команда мастера, выполняется на
   сервере отдельно от канала SSH: обрыв её не прерывает (раздел 7.3).
6. **Копия остаётся.** Перед правкой — копия в `/var/backups/parley-relay/` (вне `/opt/parley-relay`: «Remove relay»
   её не удаляет).
7. **Удаление чистое.** «Remove relay» убирает только наш файл или наш блок (с той же проверкой, перезагрузкой и
   откатом), затем наши контейнеры. Не прошла проверка после удаления нашей правки → файл возвращается, удаление
   останавливается до контейнеров: сайт человека не остаётся со ссылкой в пустоту.
8. Если хоть одно условие раздела 4 не выполнено, мастер ничего не правит и даёт прежний ручной путь (раскладка 5)
   с объяснением, что занято, чем и почему не получилось.

Строка заметок плана говорит то же коротко, например: «Parley adds one site file to your Caddy
(/opt/evdev-site/caddy/parley-relay.caddy). A backup is kept in /var/backups/parley-relay/. If the check or the
reload fails, the file is restored and your server keeps its current configuration. The reload applies your
server's whole configuration as it is on disk now.»

## 3. Разведка

Разведка по-прежнему только читает. Новые команды — фиксированные строки; значения, пришедшие с сервера (id
контейнеров, пути, имена сетей), перед попаданием в любую команду проходят строгие шаблоны (раздел 3.4) и
`shQuote`.

### 3.1 Контейнеры Docker

Если Docker есть:

```
docker ps -q | xargs -r docker inspect --format '<шаблон>'
```

Шаблон печатает одну строку JSON на контейнер: `Id`, `Name`, `Config.Image`, `Config.Labels`, `Path`, `Args`,
`Config.WorkingDir`, `Mounts` (Type, Source, Destination, RW), `NetworkSettings.Ports`,
`NetworkSettings.Networks` (нужны имена сетей), `HostConfig.NetworkMode`. Разбор — в TypeScript на Маке.

### 3.2 Кто держит порт (исправление `foreign()`)

- **Наш контейнер** — у которого метка `com.docker.compose.project=parley-relay`. Не имя процесса и не наличие
  `.env`.
- **Занятый порт** — объединение двух источников: слушатели `ss -ltnp` и опубликованные порты (`HostPort`) всех
  запущенных контейнеров. Второй источник нужен там, где Docker публикует порты без `docker-proxy`
  (userland-proxy выключен): `ss` такой порт не показывает, а `up` всё равно упадёт.
- Держатель порта: контейнер, который его публикует (наш или чужой); иначе процессы из `ss`; `docker-proxy` без
  найденного контейнера — «чужой контейнер Docker».
- Наши контейнеры порт не занимают. Наличие `.env` на это больше не влияет.

### 3.3 Веб-сервер на 80/443

Для держателя порта 80 (и 443) разведка выясняет, можно ли добавить в него сайт:

- **Caddy в Docker** — контейнер публикует 80 (и 443), `docker exec <id> caddy version` отвечает. Файл
  конфигурации — из `--config` в `Path`/`Args`; нет `--config` при `caddy run` → `<WorkingDir>/Caddyfile`.
  `--resume`, адаптер не `caddyfile` → не поддерживается.
- **nginx в Docker** — контейнер публикует 80, `docker exec <id> nginx -v` отвечает; конфигурация —
  `docker exec <id> nginx -T`.
- **Caddy или nginx на хосте** — только под systemd: `systemctl is-active caddy` / `nginx` → `active`, в `ss`
  порт держит процесс `caddy` / `nginx`. Caddy: файл из `systemctl show -p ExecStart --value caddy` (`--config`;
  `--resume` → не поддерживается), и у юнита есть перезагрузка (`systemctl show -p ExecReload --value caddy` не
  пуст); nginx: `nginx -T`. Сервер без systemd (или контейнер с `network_mode: host`) — раскладка 5.
- **Apache, Traefik и прочие** — раскладка 5.

Файлы конфигурации читаются на хосте (`cat <путь на хосте>`), путь в контейнере переводится в путь на хосте по
`Mounts` (bind или volume, самый длинный подходящий `Destination`). Режим `:ro` не мешает: мастер пишет файл на
хосте, а контейнер его только читает. Файл не на смонтированном томе — править нечего, раскладка 5. В командах
внутри контейнера (`caddy validate --config`, проверка `nginx -T`) — путь в контейнере, в записи и копии — путь
на хосте; план хранит оба.

Что извлекается:
- **Caddyfile.** Строки `import <путь-с-маской>` верхнего уровня (глубина скобок 0, путь содержит `/` или `*`,
  относительный — от каталога Caddyfile). Подходит маска вида `<каталог>/*<суффикс>`, суффикс
  `[A-Za-z0-9._-]{0,32}`. Блок глобальных опций (первый блок `{ … }` без адреса): `admin off` → перезагрузка
  невозможна, раскладка 5; `admin <host:port>` → этот адрес; нет `admin` → `127.0.0.1:2019`. На course-VPS
  `localhost` в контейнере резолвится в `::1`, и `caddy reload` без `--address` получает отказ: адрес
  передаётся всегда.
- **nginx -T.** Главный файл (первый блок `# configuration file …:`): строки `include <каталог>/*.conf;` внутри
  `http { … }`. Предпочтение — каталогу, оканчивающемуся на `conf.d`.
- **Наши правки, если уже есть:** файл `parley-relay<суффикс>` в найденном каталоге, блок между маркерами в
  Caddyfile, `parley-relay.conf` в каталоге nginx (раздел 5.3).
- **Сеть.** У контейнера-сервера — пользовательская сеть (не `bridge`, `host`, `none`), выбранная
  детерминированно: та, в которой уже есть наш relay (ручная раскладка course-VPS), иначе первая по имени. Только
  `bridge` — раскладка 5 (в сети по умолчанию нет имён контейнеров).
- **Имена в чужой сети.** Наши контейнеры видны в чужой сети под именами `parley-relay` и `parley-relay-acme`
  (раздел 6.1). Если в выбранной сети эти имена уже носит чужой контейнер (имя, псевдоним, `DNSNames`) —
  план блокируется с текстом: иначе Docker DNS раздавал бы запросы по кругу между ним и нашим.
- **Незавершённая команда прошлого прогона** (раздел 7.3): её процесс ещё жив → план блокируется («A command of
  the previous run is still running on the server: <что>. Wait a minute and run the wizard again.»).

### 3.4 Шаблоны для значений с сервера

| Значение | Шаблон |
|---|---|
| id контейнера | `^[0-9a-f]{64}$` (в командах — только id) |
| имя контейнера (только показ) | `^/?[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` |
| имя сети | `^[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` |
| путь | `^/([A-Za-z0-9._@+-]+/)*[A-Za-z0-9._@+-]+$`, без сегментов `.` и `..`, до 256 символов |
| адрес admin Caddy | `host:port`, host — IPv4, `localhost` или имя по шаблону хоста из `input.ts` |

Не прошло — этот веб-сервер считается неподдерживаемым (раскладка 5 с причиной), а не ошибкой прогона.

Порт relay на петле (`RELAY_PROXY_PORT`, 4а и 5) — первый свободный из 8787, 18787, 28787; порт HTTP своего Caddy

**Раскладка 5 лучше прежней.** Текст называет держателя («Port 80 is used by Apache (apache2)», «… by the Docker

### 4.1 Решение по nginx (пункт 3 брифа)

Выбран **свой Caddy на 8443, а nginx на 80 только пересылает HTTP нашего имени этому Caddy**. Сертификат
получает и продлевает наш Caddy (HTTP-01 через nginx; TLS-ALPN выключен, раз 443 чужой), relay доступен по
`https://имя:8443`.

Почему не certbot: нужна выдача через webroot или плагин nginx, перезагрузка nginx при каждом продлении и cron
или таймер на сервере — это вторая система на чужом сервере и правка блока TLS в nginx. Почему не «вне объёма»:
nginx — самый частый сервер на VPS. Правка в nginx при выбранном пути — один блок `server` только на порту 80,
без TLS-директив, по одному имени, с runtime-резолвом апстрима; это наименьшая поверхность. Цена: порт 8443 в
адресе и его нужно открыть у провайдера (строка в плане, как в 1б).

Блок для nginx в Docker:

```
# parley-relay: added by the Parley relay setup wizard. Remove it with the wizard (Remove relay).
# Port 80 of <имя> goes to the relay's own Caddy, which gets the certificate and serves https://<имя>:8443.
server {
    listen 80;
    server_name <имя>;
    resolver 127.0.0.11 valid=30s;
    set $parley_relay_acme http://parley-relay-acme:80;
    location / {
        proxy_pass $parley_relay_acme;
        proxy_set_header Host $host;
    }
}
```

`resolver` + переменная: nginx ищет контейнер при запросе, а не при загрузке. Иначе `nginx -t` падал бы, пока
нашего Caddy нет, и после пересоздания контейнера nginx ходил бы на старый IP. Для nginx на хосте —
`proxy_pass http://127.0.0.1:<RELAY_ACME_PORT>;` без resolver.

Конфликт имён: `nginx -t` предупреждает `conflicting server name "<имя>"` (предупреждение, а не ошибка) — для
мастера это провал проверки и откат: такой блок nginx проигнорировал бы.

### 4.2 Apache и прочие

Apache, Traefik, HAProxy и т.п. — раскладка 5: сниппет Apache (как сейчас) или общий текст, без правки. Причина:
у каждого свой язык конфигурации и своя модель TLS, а у человека один реальный случай — Caddy в Docker.

## 5. Правка чужого веб-сервера

### 5.1 Содержимое наших правок

Caddy в Docker (раскладка 2), файл или блок:

```
# parley-relay: added by the Parley relay setup wizard. Remove it with the wizard (Remove relay).
<имя> {
	reverse_proxy parley-relay:8787
}
```

Caddy на хосте (4а) — `reverse_proxy 127.0.0.1:<RELAY_PROXY_PORT>`. Блок в конце Caddyfile обёрнут строками
`# BEGIN parley-relay (added by the Parley relay setup wizard; remove it with the wizard)` и
`# END parley-relay`, перед блоком — пустая строка. nginx — раздел 4.1. Имя файла: маска `<каталог>/*<суффикс>` →
`<каталог>/parley-relay<суффикс>`; nginx — `<каталог>/parley-relay.conf`.

### 5.2 Транзакция на сервере

Каждая правка (добавить, заменить, дописать, убрать) — один скрипт из фиксированного шаблона под `set -eu`;
переменные части — `shQuote`. Порядок:

1. sha256 цели (или «нет файла») совпадает с тем, что видела разведка; иначе выход без изменений. На файловой
   системе цели свободно не меньше 1 МиБ; иначе выход без изменений.
2. Копия: `cp -p <путь на хосте> /var/backups/parley-relay/<время>-<имя>` или отметка «файла не было». Копия не
   удалась → выход до записи.
3. Запись **на месте** (`cat … > цель`, `>>` для блока): у файла, смонтированного в контейнер по одному
   (bind одного файла), должен сохраниться inode, иначе контейнер увидит старый файл. После записи sha256 цели
   равен ожидаемому, иначе — восстановление (п. 6). Удаление своего блока — перезапись на месте содержимым без
   блока, вычисленным на Маке из прочитанного файла.
4. Проверка (пути — в контейнере для Docker, на хосте для host): Caddy в Docker —
   `docker exec <id> caddy validate --config <файл> --adapter caddyfile`; Caddy под systemd — отдельной проверки
   нет, её делает атомарная загрузка п. 5 (`caddy validate` из SSH не видит окружения юнита и для
   `{$VAR}` дал бы неверный ответ); nginx — `nginx -t` без строки `conflicting server name "<имя>"`, затем
   `nginx -T` содержит `# configuration file <наш файл>:` (наш файл действительно подключён; при удалении — не
   содержит).
5. Перезагрузка: Caddy в Docker — `docker exec <id> caddy reload --config <файл> --adapter caddyfile
   --address <admin>`; Caddy под systemd — `systemctl reload caddy`; nginx — `nginx -s reload` (в Docker — через
   `docker exec`).
6. Провал 3, 4 или 5 → восстановление из копии на месте (или удаление нового файла), код выхода ненулевой,
   текст — «check failed: the file was restored» / «reload failed: the file was restored».

Дописанный блок и его удаление обратимы байт в байт: если у файла не было `\n` в конце, мастер дописывает его
и отмечает это в строке `# BEGIN parley-relay …`; удаление снимает блок, пустую строку перед ним и, по отметке,
этот `\n`. Тест: «дописать → убрать» возвращает исходный sha256 для файла с `\n` в конце и без.

Скрипт выполняется как любая команда мастера — отдельно от канала SSH (раздел 7.3): обрыв соединения не
прерывает его на середине, правка доходит до конца или до отката. Шаг правки не прерывается отменой (7.2).

### 5.3 Что считается «нашим»

- Файл `parley-relay<суффикс>` в каталоге импорта или `parley-relay.conf` в каталоге nginx — наш, если в нём есть
  строка `# parley-relay:` или апстрим `parley-relay:8787`, `parley-relay-acme` или `127.0.0.1:<наш порт из .env>`.
  Так узнаётся и ручной файл course-VPS (`reverse_proxy parley-relay:8787`, без маркера).
- Блок между `# BEGIN parley-relay` и `# END parley-relay` в Caddyfile. Нашёлся только один маркер или их больше
  двух — план блокируется с текстом.
- Файл с нашим именем, но без этих признаков, — чужой: план блокируется («… exists and was not written by
  Parley»).

## 6. Шаги по раскладкам

### 6.1 Установка

Шаги — те же «проверка → действие». Новое: `image` качает все образы раскладки (relay и, где он есть, Caddy) с
прогрессом (раздел 7), `start` — `docker compose … up -d --remove-orphans --quiet-pull`, `web` — транзакция 5.2.

| Раскладка | Шаги |
|---|---|
| `caddy` | docker, dir, files, image, ufw (80, 443/8443), start |
| `caddy-site` docker | docker, dir, files, image, start, web |
| `caddy-site` host | docker, dir, files, image, start, web |
| `nginx-acme` docker/host | docker, dir, files, image, ufw (8443), web, start |
| `proxy` | docker, dir, files, image, start |

`caddy-site`: `web` после `start` — Caddy человека получает сертификат и начинает проксировать, когда relay уже
отвечает. `nginx-acme`: `web` до `start` — наш Caddy просит сертификат сразу при старте, и к этому моменту nginx
уже должен пересылать наш порт 80 (иначе неудачная проверка Let's Encrypt и бэкофф; блок с `resolver` проходит
`nginx -t` и без нашего контейнера).

Проверка шага `web` («already done»): sha256 нашего файла (или блока) равен ожидаемому **и** работающий сервер
знает наш сайт: nginx — `nginx -T` содержит наш файл; Caddy — ответ admin API `GET /config/` (в контейнере через
`wget -qO-`, на хосте через `curl -s`) содержит наше имя. Проверку нечем выполнить (нет `wget`/`curl`) — шаг
выполняется (validate и reload мягкие и повторяемые).

Файлы `/opt/parley-relay/` (фиксированные шаблоны, меняются только значения в `.env`):
- `caddy` — `compose.yml` и `Caddyfile`, как сейчас (копии `packages/relay/deploy/`);
- `caddy-site` docker — `compose.yml`: только сервис **`parley-relay`** (не `relay`: compose делает имя сервиса
  DNS-именем в каждой сети сервиса, а у человека может быть свой `relay`), `expose: 8787`, внешняя сеть
  `name: ${RELAY_NETWORK}`;
- `caddy-site` host и `proxy` без сети — `COMPOSE_PROXY` (как сейчас); `proxy` с сетью — как `caddy-site` docker;
- `nginx-acme` — сервисы `parley-relay` и **`parley-relay-acme`** (Caddy); Caddy публикует `${RELAY_HTTPS_PORT}:443`;
  в docker — во внешней сети nginx, в host — `127.0.0.1:${RELAY_ACME_PORT}:80`. Свой `Caddyfile` с
  `tls { issuer acme { disable_tlsalpn_challenge } }` и `reverse_proxy parley-relay:8787`.

Проверка шага `start` ищет сервис раскладки (`grep -qx parley-relay` или `relay`). Переход на шаблон с другим
именем сервиса пересоздаёт контейнер (`--remove-orphans` убирает прежний); том `relay-data` тот же, данные целы.

`.env` — память мастера. К прежним ключам добавляются (читаются обратно разведкой и проходят шаблоны 3.4):
`RELAY_WEB_RUNTIME` (`docker` | `host`), `RELAY_WEB_FILE` (путь на хосте), `RELAY_WEB_EDIT` (`file` | `block`),
`RELAY_NETWORK`, `RELAY_ACME_PORT`.

ufw: правило 8443 для `nginx-acme`, если ufw активен; для `caddy-site` новых портов нет.

### 6.2 Повтор и обновление

Повтор = обновление (как сейчас): разведка заново, решение заново.

**Источник истины — живая разведка** для всех действий (установка, откат, удаление): наши контейнеры (по метке
проекта), наши правки в чужом сервере (по 5.3) и его состояние. `RELAY_MODE` и прочие ключи `.env` — подсказка.
На course-VPS `.env` говорит `caddy` (прогон 2), а на деле работает ручная раскладка 2.

Правило перехода между раскладками:

- **Наша правка в чужом сервере есть**, а новое решение кладёт её в другой файл или в раскладку без правки →
  план блокируется: «Parley's site is in <файл> of <сервер>, but the server now looks different (<что видно>).
  Remove the relay first, then install again.» Мастер не переносит правку сам.
- **Работающая ручная установка `proxy` сохраняется.** `.env` говорит `proxy`, и `https://<адрес>/v1/health` с
  Мака уже отвечает (одна попытка во время разведки, таймаут 5 с) → раскладка остаётся `proxy`, повтор только
  обновляет образ; строка в плане: «Your web server already serves the relay at <адрес>; Parley keeps this
  layout.» Иначе сниппет человека (0.28.1) молча перестал бы работать, а адрес сменился бы.
- **Правки нет, и прежняя раскладка не работает** (`caddy`, неотвечающий `proxy`, старый `.env`) → переход
  разрешён: `files` переписывает файлы (прежние — в `previous/`), `start` с `--remove-orphans` убирает наш
  лишний контейнер. Если меняется адрес — строка в плане «The relay address changes from X to Y; pair your phone
  again.»

### 6.3 Откат

«Roll back» возвращает прошлый образ и файлы `/opt/parley-relay/` только в пределах той же раскладки:
`previous/.env` и `.env` с одинаковыми `RELAY_MODE`, `RELAY_DOMAIN`, `RELAY_WEB_FILE`, `RELAY_NETWORK`,
`RELAY_PROXY_PORT`, `RELAY_ACME_PORT`, и `.env` совпадает с живой разведкой. Иначе план блокируется («The
previous version used a different layout; install again instead»). Чужой файл откат не трогает: в одной
раскладке он тот же.

### 6.4 Удаление

| Раскладка | Шаги |
|---|---|
| наших правок в чужом сервере нет (`caddy`, `proxy`) | down, ufw, files (как сейчас) |
| наша правка найдена разведкой (любая раскладка, в том числе ручная course-VPS при `.env` с `caddy`) | web-undo (транзакция 5.2: убрать наш файл или блок), down, ufw, files |

Строка таблицы выбирается по живой разведке (6.2), а не по `RELAY_MODE`. Копии в `/var/backups/parley-relay/`
удаление не трогает. С «Also delete the relay data» дополнительно удаляются оставшиеся тома проекта

## 7. Образ: прогресс и отмена

### 7.1 Прогресс

Шаг `image` для каждого образа:

```
if command -v curl >/dev/null 2>&1 && [ -S /var/run/docker.sock ]; then
  curl -sS --no-buffer --unix-socket /var/run/docker.sock -X POST 'http://localhost/images/create?fromImage=<репозиторий>&tag=<тег или digest>';
else docker pull <образ>; fi; docker image inspect <образ> >/dev/null
```

Engine API отдаёт строки JSON (`status`, `id`, `progressDetail.current/total`, `error`) — разбор надёжнее, чем
полосы `docker pull` в псевдотерминале. Итог шага решает `docker image inspect` (ошибка в потоке API приходит с
HTTP 200). Нет `curl` или сокета — `docker pull`, тогда прогресс только по слоям.

Параметры запроса из ссылки на образ: есть digest → `fromImage=<репозиторий без тега>` и `tag=sha256:<hex>`
(текстовый тег отбрасывается: `caddy:2.11.7@sha256:…` → `fromImage=caddy&tag=sha256:…`); нет digest →
`tag=<тег>` или `latest`. Пустой `tag` не отправляется никогда (он тянет все теги). Значения URL-кодируются.

Main разбирает строки шага `image`: слоёв всего и готово («Pull complete», «Already exists»), байт всего и
скачано (сумма по слоям). В окно — событие `progress` не чаще 4 раз в секунду; строки JSON в окно и в лог как
есть не идут: в лог — итог каждые 10 % или 15 с и последняя строка `Status: …`, ошибки — целиком. Окно:
«Downloading the relay image: 41.2 of 82.0 MB · 3 of 8 layers» и полоса; без байтов — только слои.

`up -d --quiet-pull` и предварительная загрузка Caddy в шаге `image` убирают поток «Downloading 1.049MB» из шага
`start`.

### 7.2 Отмена

- Шаг `image` прерываемый: Cancel вторым каналом SSH завершает группу процессов текущей команды
  (`kill -TERM -- -<pid>` по файлу `$D/pid` раздела 7.3). `curl` к Engine API рвёт запрос, `docker pull` выходит;
  отменяет ли движок Docker загрузку на своей стороне, не проверено (особенно с хранилищем containerd) — окно
  этого не обещает: «Cancelled. A download may finish on the server by itself; running the setup again picks it
  up.» Скачанные слои остаются, повтор продолжит. Шаг — `stopped`.
- Прочие шаги (apt, compose, правка 5.2) не прерываются: окно сразу пишет «Cancelling after this step…», кнопка
  Cancel неактивна, по концу шага оставшиеся шаги — `stopped`.
- Итог отмены — новая фаза `cancelled`, не `failed` и не красным: «Cancelled. Run the setup again to finish:
  finished steps are skipped.»
- Ненулевой код команды, которую прервали мы, — `stopped`, а не `failed`.
- Отмена во время проверки здоровья прекращает ожидание: фаза `cancelled` с шагом `health` и кнопкой Check.

### 7.3 Команды на сервере не зависят от канала SSH

Без псевдотерминала `sshd` при обрыве не шлёт SIGHUP, но закрывает трубы, и следующая запись процесса даёт
SIGPIPE: `apt-get` погиб бы посреди `dpkg` («dpkg was interrupted»), `compose up` — между контейнерами. Сон
Мака, смена сети и выход из приложения во время прогона — обычные случаи, поэтому каждая команда шага (не
проверка) запускается на сервере отдельно от канала:

```
D=/var/tmp/parley-relay-setup; mkdir -p -m 0700 "$D"; rm -f "$D/<id>.code"
setsid flock -n "$D/lock" sh -c 'echo "<id>" > "$D/active"; <команда>; echo $? > "$D/<id>.code"; rm -f "$D/active"' \
  > "$D/<id>.log" 2>&1 < /dev/null &
p=$!; echo "$p" > "$D/pid"
tail -n +1 -f --pid="$p" "$D/<id>.log"; [ -f "$D/<id>.code" ] && exit "$(cat "$D/<id>.code")"; exit 255
```

Состоянием владеет фоновая часть: она держит `flock` на `$D/lock` всё время работы, сама пишет код и сама
снимает `active`. Передняя часть только показывает журнал: при обрыве канала она умирает или доходит до конца,
ничего не снимая. Окно получает строки `tail`; обрыв канала убивает только `tail`, команда доходит до конца.
Каталог — вне `/opt/parley-relay` (его ещё нет до шага `dir` и его удаляет Remove).

Разведка: `flock -n "$D/lock" true` не прошёл → команда прошлого прогона жива → план блокируется (раздел 3.3),
что именно — из `$D/active`. Блокировка снимается ядром со смертью процесса и после перезагрузки, поэтому pid и
`kill -0` не нужны (pid переиспользуется). Прошёл, а `active` есть → команда умерла посреди работы; хвост её
журнала (`tail -n 20`) — в заметках плана. Отмена прерываемого шага: `kill -TERM -- -<pid из $D/pid>`
(`setsid` делает процесс лидером новой группы). Итог при обрыве:
«The connection to the server was lost. Commands keep running on the server and finish on their own; run the
wizard again in a minute.» `setsid`, `tail --pid` — util-linux и coreutils, есть на Ubuntu 22.04/24.04 и Debian 12.

## 8. Окно: прогон живёт в main

### 8.1 Запись прогона

Прогон (от Run до итога) живёт в main-процессе, в сервисе мастера, а не в состоянии React. Запись:

```ts
interface RelayRunView {
  seq: number;              // номер последнего применённого события
  intent: SetupIntent;
  host: string;
  plan: RelayPlanView;      // выполняемый план (заголовок и чужие правки)
  steps: Array<{ id: string; title: string; status: 'pending' | StepStatus; lines: string[] }>; // ≤ 200 строк на шаг
  progress: RelayPullProgress | null;
  cancelling: boolean;
  phase: RelaySetupPhase;   // { phase: 'running' } во время прогона, итоговая фаза — после
}
```

Секретов в записи нет (строки уже замаскированы). Новые вызовы: `state` → запись или `null`; `dismiss` → забыть
запись (во время прогона — отказ). `run` больше не ждёт конца: отвечает `{ phase: 'running' }`, итог приходит
событием и через `state`. События получают `seq`; новые события — `progress`, `cancelling`, `phase` (итог,
и после Check). Порядок в окне при открытии: сначала подписка на события (они копятся в буфер), затем `state`,
затем применить буфер с `seq` больше снимка и дальше — по мере прихода. Иначе события между ответом `state` и
подпиской терялись бы (особенно после перезагрузки окна). `check` (повтор проверки здоровья) обновляет итог
записи.

### 8.2 Закрытие и возврат

- Окно мастера закрывается **только крестиком**: ни клик по фону, ни Esc его не закрывают (во всех фазах).
- До Run (форма, ключ сервера, пароль, план) крестик и Cancel — как сейчас: отмена сеанса, соединение и учётные
  данные сбрасываются.
- Во время прогона крестик только прячет окно, прогон идёт дальше. Cancel в подвале — отмена (7.2).
- После итога крестик прячет окно, запись остаётся. Подвал итога: **Close** — забыть запись и закрыть; **New
  setup** — забыть запись и показать форму.
- Settings → Remote access → «Set up on my server…» при живой записи открывает её (живой лог или итог с логом),
  а не форму.
- **Перезагрузка окна** запись не теряет: она в main. **Выход из приложения** (и перезапуск) её теряет:
  запись не сохраняется на диск, SSH закрывается на событии `quit` (а не на `before-quit`: на `before-quit` и
  `will-quit` висят сторожа, которые могут выход отменить, — отменённый выход прогон не трогает). Команда на
  сервере при этом доходит до конца (7.3). **Перезапуск хоста** Parley на запись не влияет: мастер живёт в main
  окна, не в хосте; если хост лежит в момент `configure`, итог — `configured: false`, как сейчас.

## 12. Риски

- `TRUST_PROXY: '1'` в чужой сети: контейнер человека в той же сети может прислать relay поддельный
  `X-Forwarded-For` (влияет только на учёт по IP). Relay и так рассчитан на интернет.
- Подключённый к чужой сети relay мешает её удалить: `docker compose down` проекта человека не может убрать сеть,
  пока в ней наш контейнер (поведение и код выхода фиксирует стенд S1); если человек пересоздаст сеть, наш
  контейнер не поднимется после перезагрузки сервера, пока мастер не запустят снова. Так же устроена и ручная
  раскладка course-VPS.
- `caddy reload` и `nginx -s reload` применяют всю конфигурацию человека с диска, включая его неприменённые
  правки (строка в карточке правки, раздел 2).
- `docker exec` наследует окружение контейнера (`Config.Env`), но не переменные, которые выставляет скрипт
  entrypoint: `caddy validate` в таком контейнере может разойтись с работающим Caddy. Официальный образ Caddy
  entrypoint-скрипта не имеет.
- Наш сайт в чужом Caddy получает сертификат средствами этого Caddy: если у него выключен автоматический HTTPS,
  проверка здоровья не пройдёт, итог — «failed: health» с Check, правка остаётся (её убирает Remove).
- Формат потока Engine API может отличаться у новых версий Docker (хранилище containerd): разбор терпим к
  неизвестным статусам, а итог шага решает `docker image inspect`.
