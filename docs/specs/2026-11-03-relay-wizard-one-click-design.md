## 2. Новое правило: мастер правит чужой веб-сервер

Прежнее правило 6.7 «Чужие конфиги мастер не правит» и строка «Кроме `/opt/parley-relay`, правил `ufw` и пакетов
Docker мастер на сервере ничего не трогает» отменяются. Человек попросил одну кнопку, поэтому мастер теперь сам
добавляет relay в веб-сервер человека. Новое правило:

**Мастер меняет конфигурацию веб-сервера человека только одной из двух правок:**
- **свой файл** `parley-relay<суффикс>` в каталоге, который сервер уже подключает (`import` у Caddy,
  `include …/*.conf` у nginx);
- **свой блок** в конце главного Caddyfile между строками `# BEGIN parley-relay …` и `# END parley-relay` — только
  если у Caddy нет такого каталога.

**Гарантии.**
1. **Всё видно до Run.** Экран плана перечисляет каждый чужой файл, который мастер добавит или изменит: путь на
   сервере, действие (добавить файл, заменить свой файл, дописать блок, убрать свой файл, убрать свой блок),
   содержимое целиком, путь резервной копии, команды проверки и перезагрузки. Также — подключение relay к чужой
   сети Docker (имя сети и псевдоним).
2. **Чужие строки не трогаются.** Мастер не меняет и не удаляет ни одной строки, которую не писал. «Свой» файл
   определяется по имени и содержимому (раздел 5.3). Файл с нашим именем, но не наш, — план не выполняется.
3. **Ровно те байты, что в плане.** Перед записью мастер сверяет sha256 целевого файла с тем, что видела разведка.
   Файл изменился между разведкой и Run — правка не делается, шаг падает с текстом «файл изменился, запустите
   мастер снова».
4. **Проверка до перезагрузки.** После записи — штатная проверка самого сервера (`caddy validate`, `nginx -t` и
   `nginx -T`), затем мягкая перезагрузка (`caddy reload`, `nginx -s reload`). Остановки и перезапуска чужого
   контейнера или службы нет.
5. **Автоматический откат.** Проверка или перезагрузка не прошли → файл восстанавливается из копии байт в байт
   (новый файл удаляется), работающий сервер остаётся на прежней конфигурации. Caddy и nginx при неудачной
   перезагрузке продолжают работать со старой конфигурацией. Правка выполняется на сервере одним скриптом с
   выводом в файл: обрыв SSH её не прерывает (раздел 5.2).
6. **Копия остаётся.** Перед правкой — копия в `/opt/parley-relay/backup/`.
7. **Удаление чистое.** «Remove relay» убирает только наш файл или наш блок (с той же проверкой, перезагрузкой и
   откатом), затем наши контейнеры. Не прошла проверка после удаления нашей правки → файл возвращается, удаление
   останавливается до контейнеров: сайт человека не остаётся со ссылкой в пустоту.
8. Если хоть одно условие раздела 4 не выполнено, мастер ничего не правит и даёт прежний ручной путь (раскладка 5)
   с объяснением, что занято, чем и почему не получилось.

Строка заметок плана говорит то же коротко, например: «Parley adds one site file to your Caddy
(/opt/evdev-site/caddy/parley-relay.caddy). A backup is kept in /opt/parley-relay/backup/. If the check or the
reload fails, the file is restored and your server keeps its current configuration.»

## 3. Разведка

Разведка по-прежнему только читает. Новые команды — фиксированные строки; значения, пришедшие с сервера (id
контейнеров, пути, имена сетей), перед попаданием в любую команду проходят строгие шаблоны (раздел 3.4) и
`shQuote`.

### 3.1 Контейнеры Docker

Если Docker есть:

```
docker ps -q | xargs -r docker inspect --format '<шаблон>'
```

Шаблон печатает одну строку JSON на контейнер: `Id`, `Name`, `Config.Image`, `Config.Labels`, `Path`, `Args`,
`Config.WorkingDir`, `Mounts` (Type, Source, Destination, RW), `NetworkSettings.Ports`,
`NetworkSettings.Networks` (нужны имена сетей), `HostConfig.NetworkMode`. Разбор — в TypeScript на Маке.

### 3.2 Кто держит порт (исправление `foreign()`)

- **Наш контейнер** — у которого метка `com.docker.compose.project=parley-relay`. Не имя процесса и не наличие
  `.env`.
- **Занятый порт** — объединение двух источников: слушатели `ss -ltnp` и опубликованные порты (`HostPort`) всех
  запущенных контейнеров. Второй источник нужен там, где Docker публикует порты без `docker-proxy`
  (userland-proxy выключен): `ss` такой порт не показывает, а `up` всё равно упадёт.
- Держатель порта: контейнер, который его публикует (наш или чужой); иначе процессы из `ss`; `docker-proxy` без
  найденного контейнера — «чужой контейнер Docker».
- Наши контейнеры порт не занимают. Наличие `.env` на это больше не влияет.

### 3.3 Веб-сервер на 80/443

Для держателя порта 80 (и 443) разведка выясняет, можно ли добавить в него сайт:

- **Caddy в Docker** — контейнер публикует 80 (и 443), `docker exec <id> caddy version` отвечает. Файл
  конфигурации — из `--config` в `Path`/`Args`; нет `--config` при `caddy run` → `<WorkingDir>/Caddyfile`.
  `--resume`, адаптер не `caddyfile` → не поддерживается.
- **nginx в Docker** — контейнер публикует 80, `docker exec <id> nginx -v` отвечает; конфигурация —
  `docker exec <id> nginx -T`.
- **Caddy или nginx на хосте** — только под systemd: `systemctl is-active caddy` / `nginx` → `active`, в `ss`
  порт держит процесс `caddy` / `nginx`. Caddy: файл из `systemctl show -p ExecStart --value caddy` (`--config`);
  nginx: `nginx -T`. Сервер без systemd (или контейнер с `network_mode: host`) — раскладка 5.
- **Apache, Traefik и прочие** — раскладка 5.

Файлы конфигурации читаются на хосте (`cat <путь на хосте>`), путь в контейнере переводится в путь на хосте по
`Mounts` (bind или volume, `RW: true`, самый длинный подходящий `Destination`). Файл не на смонтированном томе —
править нечего, раскладка 5.

Что извлекается:
- **Caddyfile.** Строки `import <путь-с-маской>` верхнего уровня (глубина скобок 0, путь содержит `/` или `*`,
  относительный — от каталога Caddyfile). Подходит маска вида `<каталог>/*<суффикс>`, суффикс
  `[A-Za-z0-9._-]{0,32}`. Блок глобальных опций (первый блок `{ … }` без адреса): `admin off` → перезагрузка
  невозможна, раскладка 5; `admin <host:port>` → этот адрес; нет `admin` → `127.0.0.1:2019`. На course-VPS
  `localhost` в контейнере резолвится в `::1`, и `caddy reload` без `--address` получает отказ: адрес
  передаётся всегда.
- **nginx -T.** Главный файл (первый блок `# configuration file …:`): строки `include <каталог>/*.conf;` внутри
  `http { … }`. Предпочтение — каталогу, оканчивающемуся на `conf.d`.
- **Наши правки, если уже есть:** файл `parley-relay<суффикс>` в найденном каталоге, блок между маркерами в
  Caddyfile, `parley-relay.conf` в каталоге nginx (раздел 5.3).
- **Сеть.** У контейнера-сервера — первая пользовательская сеть (не `bridge`, `host`, `none`). Только `bridge` —
  раскладка 5 (в сети по умолчанию нет имён контейнеров).

### 3.4 Шаблоны для значений с сервера

| Значение | Шаблон |
|---|---|
| id контейнера | `^[0-9a-f]{64}$` (в командах — только id) |
| имя контейнера (только показ) | `^/?[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` |
| имя сети | `^[A-Za-z0-9][A-Za-z0-9_.-]{0,127}$` |
| путь | `^/([A-Za-z0-9._@+-]+/)*[A-Za-z0-9._@+-]+$`, без сегментов `.` и `..`, до 256 символов |
| адрес admin Caddy | `host:port`, host — IPv4, `localhost` или имя по шаблону хоста из `input.ts` |

Не прошло — этот веб-сервер считается неподдерживаемым (раскладка 5 с причиной), а не ошибкой прогона.

(наши контейнеры не в счёт).

| № | Кто держит 80 / 443 | Раскладка (`RELAY_MODE`) | Что ставится | Адрес |
|---|---|---|---|---|

| 3 | контейнер nginx держит 80; `conf.d` подключён в `http` и на томе; пользовательская сеть; 8443 свободен | `nginx-acme`, runtime `docker` | relay + свой Caddy на 8443 в сети nginx (псевдоним `parley-relay-acme`); в nginx — блок на 80 для нашего имени | `имя:8443` |

Порт relay на петле (`RELAY_PROXY_PORT`, 4а и 5) — первый свободный из 8787, 18787, 28787; порт HTTP своего Caddy
на петле (`RELAY_ACME_PORT`, 4б) — первый свободный из 18080, 28080. Свободных нет — раскладка 5 (для 4б) или
блок «нет свободного порта» (для 5, как сейчас).

**Раскладка 5 лучше прежней.** Текст называет держателя («Port 80 is used by Apache (apache2)», «… by the Docker
container shop-nginx-1 (nginx), but its conf.d is not on a mounted volume») и причину. Держатель — контейнер в
пользовательской сети → relay подключается к этой сети, и сниппет ведёт на `parley-relay:8787`, а не на петлю
(ошибка 3 раздела 1). Иначе — петля, как сейчас.

### 4.1 Решение по nginx (пункт 3 брифа)

Выбран **свой Caddy на 8443, а nginx на 80 только пересылает HTTP нашего имени этому Caddy**. Сертификат
получает и продлевает наш Caddy (HTTP-01 через nginx; TLS-ALPN выключен, раз 443 чужой), relay доступен по
`https://имя:8443`.

Почему не certbot: нужна выдача через webroot или плагин nginx, перезагрузка nginx при каждом продлении и cron
или таймер на сервере — это вторая система на чужом сервере и правка блока TLS в nginx. Почему не «вне объёма»:
nginx — самый частый сервер на VPS. Правка в nginx при выбранном пути — один блок `server` только на порту 80,
без TLS-директив, по одному имени, с runtime-резолвом апстрима; это наименьшая поверхность. Цена: порт 8443 в
адресе и его нужно открыть у провайдера (строка в плане, как в 1б).

Блок для nginx в Docker:

```
# parley-relay: added by the Parley relay setup wizard. Remove it with the wizard (Remove relay).
# Port 80 of <имя> goes to the relay's own Caddy, which gets the certificate and serves https://<имя>:8443.
server {
    listen 80;
    server_name <имя>;
    resolver 127.0.0.11 valid=30s;
    set $parley_relay_acme http://parley-relay-acme:80;
    location / {
        proxy_pass $parley_relay_acme;
        proxy_set_header Host $host;
    }
}
```

`resolver` + переменная: nginx ищет контейнер при запросе, а не при загрузке. Иначе `nginx -t` падал бы, пока
нашего Caddy нет, и после пересоздания контейнера nginx ходил бы на старый IP. Для nginx на хосте —
`proxy_pass http://127.0.0.1:<RELAY_ACME_PORT>;` без resolver.

Конфликт имён: `nginx -t` предупреждает `conflicting server name "<имя>"` (предупреждение, а не ошибка) — для
мастера это провал проверки и откат: такой блок nginx проигнорировал бы.

### 4.2 Apache и прочие

Apache, Traefik, HAProxy и т.п. — раскладка 5: сниппет Apache (как сейчас) или общий текст, без правки. Причина:
у каждого свой язык конфигурации и своя модель TLS, а у человека один реальный случай — Caddy в Docker.

## 5. Правка чужого веб-сервера

### 5.1 Содержимое наших правок

Caddy в Docker (раскладка 2), файл или блок:

```
# parley-relay: added by the Parley relay setup wizard. Remove it with the wizard (Remove relay).
<имя> {
	reverse_proxy parley-relay:8787
}
```

Caddy на хосте (4а) — `reverse_proxy 127.0.0.1:<RELAY_PROXY_PORT>`. Блок в конце Caddyfile обёрнут строками
`# BEGIN parley-relay (added by the Parley relay setup wizard; remove it with the wizard)` и
`# END parley-relay`, перед блоком — пустая строка. nginx — раздел 4.1. Имя файла: маска `<каталог>/*<суффикс>` →
`<каталог>/parley-relay<суффикс>`; nginx — `<каталог>/parley-relay.conf`.

### 5.2 Транзакция на сервере

Каждая правка (добавить, заменить, дописать, убрать) — один скрипт из фиксированного шаблона; переменные части —
`shQuote`. Порядок:

1. sha256 цели (или «нет файла») совпадает с тем, что видела разведка; иначе выход без изменений.
2. Копия: `cp -p цель /opt/parley-relay/backup/<время>-<имя>` или отметка «файла не было».
3. Запись **на месте** (`cat … > цель`, `>>` для блока): у файла, смонтированного в контейнер по одному
   (bind одного файла), должен сохраниться inode, иначе контейнер увидит старый файл. Удаление своего блока —
   перезапись на месте содержимым без блока, вычисленным на Маке из прочитанного файла.
4. Проверка: Caddy — `caddy validate --config <файл> --adapter caddyfile` (в Docker — `docker exec <id> …`); nginx
   — `nginx -t` без строки `conflicting server name "<имя>"`, затем `nginx -T` содержит
   `# configuration file <наш файл>:` (наш файл действительно подключён; при удалении — не содержит).
5. Перезагрузка: `caddy reload --config <файл> --adapter caddyfile --address <admin>`; nginx —
   `nginx -s reload`.
6. Провал 4 или 5 → восстановление из копии на месте (или удаление нового файла), код выхода ненулевой, текст —
   «check failed: the file was restored» / «reload failed: the file was restored».

Запуск: `sh -c '<скрипт>' > /opt/parley-relay/web-edit.log 2>&1; c=$?; cat /opt/parley-relay/web-edit.log; exit $c`.
Вывод скрипта идёт в файл, а не в канал SSH, поэтому обрыв соединения не убивает скрипт на середине: правка
доходит до конца или до отката. Шаг правки не прерывается отменой (раздел 7.2).

### 5.3 Что считается «нашим»

- Файл `parley-relay<суффикс>` в каталоге импорта или `parley-relay.conf` в каталоге nginx — наш, если в нём есть
  строка `# parley-relay:` или апстрим `parley-relay:8787`, `parley-relay-acme` или `127.0.0.1:<наш порт из .env>`.
  Так узнаётся и ручной файл course-VPS (`reverse_proxy parley-relay:8787`, без маркера).
- Блок между `# BEGIN parley-relay` и `# END parley-relay` в Caddyfile. Нашёлся только один маркер или их больше
  двух — план блокируется с текстом.
- Файл с нашим именем, но без этих признаков, — чужой: план блокируется («… exists and was not written by
  Parley»).

## 6. Шаги по раскладкам

### 6.1 Установка

Шаги — те же «проверка → действие». Новое: `image` качает все образы раскладки (relay и, где он есть, Caddy) с
прогрессом (раздел 7), `start` — `docker compose … up -d --remove-orphans --quiet-pull`, `web` — транзакция 5.2.

| Раскладка | Шаги |
|---|---|
| `caddy` | docker, dir, files, image, ufw (80, 443/8443), start |
| `caddy-site` docker | docker, dir, files, image, start, web |
| `caddy-site` host | docker, dir, files, image, start, web |
| `nginx-acme` docker/host | docker, dir, files, image, ufw (8443), start, web |
| `proxy` | docker, dir, files, image, start |

`web` идёт после `start`: Caddy получает сертификат и начинает проксировать, когда relay уже отвечает.
Проверка шага `web` — sha256 нашего файла (или блока) равен ожидаемому → «already done».

Файлы `/opt/parley-relay/` (фиксированные шаблоны, меняются только значения в `.env`):
- `caddy` — `compose.yml` и `Caddyfile`, как сейчас (копии `packages/relay/deploy/`);
- `caddy-site` docker — `compose.yml`: только relay, `expose: 8787`, внешняя сеть `name: ${RELAY_NETWORK}` с
  псевдонимом `parley-relay`;
- `caddy-site` host и `proxy` без сети — `COMPOSE_PROXY` (как сейчас); `proxy` с сетью — как `caddy-site` docker;
- `nginx-acme` — relay и Caddy; Caddy публикует `${RELAY_HTTPS_PORT}:443`; в docker — внешняя сеть nginx с
  псевдонимом `parley-relay-acme`, в host — `127.0.0.1:${RELAY_ACME_PORT}:80`. Свой `Caddyfile` с

`.env` — память мастера. К прежним ключам добавляются (читаются обратно разведкой и проходят шаблоны 3.4):
`RELAY_WEB_RUNTIME` (`docker` | `host`), `RELAY_WEB_CONTAINER` (имя, для показа), `RELAY_WEB_FILE` (путь на хосте),
`RELAY_WEB_EDIT` (`file` | `block`), `RELAY_NETWORK`, `RELAY_ACME_PORT`.

ufw: правило 8443 для `nginx-acme`, если ufw активен; для `caddy-site` новых портов нет.

### 6.2 Повтор и обновление

Повтор = обновление (как сейчас): разведка заново, решение заново. Правило перехода между раскладками:

- **Наша правка в чужом сервере есть** (найдена разведкой или записана в `.env`), а новое решение кладёт её в
  другой файл или в раскладку без правки → план блокируется: «Parley's site is in <файл> of <сервер>, but the
  server now looks different (<что видно>). Remove the relay first, then install again.» Мастер не переносит
  правку сам.
- **Правки нет** (прежняя раскладка `caddy` или `proxy`, или `.env` старый) → переход разрешён: `files`
  переписывает файлы (прежние — в `previous/`), `start` с `--remove-orphans` убирает наш лишний контейнер Caddy.
- `RELAY_MODE` в `.env` — подсказка, а не истина: решает живая разведка. На course-VPS `.env` говорит `caddy`
  (прогон 2), а на деле работает ручная раскладка 2.

### 6.3 Откат

«Roll back» возвращает прошлый образ и файлы `/opt/parley-relay/` только в пределах той же раскладки:
`previous/.env` и `.env` с одинаковыми `RELAY_MODE`, `RELAY_WEB_FILE`, `RELAY_NETWORK`. Иначе план блокируется
(«The previous version used a different layout; install again instead»). Чужой файл откат не трогает: в одной
раскладке он тот же.

## 7. Образ: прогресс и отмена

### 7.1 Прогресс

Шаг `image` для каждого образа:

```
if command -v curl >/dev/null 2>&1 && [ -S /var/run/docker.sock ]; then
  curl -sS --no-buffer --unix-socket /var/run/docker.sock -X POST 'http://localhost/images/create?fromImage=<репозиторий>&tag=<тег или digest>';
else docker pull <образ>; fi; docker image inspect <образ> >/dev/null
```

Engine API отдаёт строки JSON (`status`, `id`, `progressDetail.current/total`, `error`) — разбор надёжнее, чем
полосы `docker pull` в псевдотерминале. Итог шага решает `docker image inspect` (ошибка в потоке API приходит с
HTTP 200). Нет `curl` или сокета — `docker pull`, тогда прогресс только по слоям.

Main разбирает строки шага `image`: слоёв всего и готово («Pull complete», «Already exists»), байт всего и
скачано (сумма по слоям). В окно — событие `progress` не чаще 4 раз в секунду; строки JSON в окно и в лог как
есть не идут: в лог — итог каждые 10 % или 15 с и последняя строка `Status: …`, ошибки — целиком. Окно:
«Downloading the relay image: 41.2 of 82.0 MB · 3 of 8 layers» и полоса; без байтов — только слои.

`up -d --quiet-pull` и предварительная загрузка Caddy в шаге `image` убирают поток «Downloading 1.049MB» из шага
`start`.

### 7.2 Отмена

- Шаг `image` прерываемый: Cancel закрывает канал SSH текущей команды. `curl` или `docker pull` получает обрыв
  записи, движок Docker отменяет загрузку; скачанные слои остаются, повтор продолжит. Шаг — `stopped`.
- Прочие шаги (apt, compose, правка 5.2) не прерываются: окно сразу пишет «Cancelling after this step…», кнопка
  Cancel неактивна, по концу шага оставшиеся шаги — `stopped`.
- Итог отмены — новая фаза `cancelled`, не `failed` и не красным: «Cancelled. Run the setup again to finish:
  finished steps are skipped.»
- Ненулевой код команды, которую прервали мы, — `stopped`, а не `failed`.
- Отмена во время проверки здоровья прекращает ожидание: фаза `cancelled` с шагом `health` и кнопкой Check.

## 8. Окно: прогон живёт в main

### 8.1 Запись прогона

Прогон (от Run до итога) живёт в main-процессе, в сервисе мастера, а не в состоянии React. Запись:

```ts
interface RelayRunView {
  seq: number;              // номер последнего применённого события
  intent: SetupIntent;
  host: string;
  plan: RelayPlanView;      // выполняемый план (заголовок и чужие правки)
  steps: Array<{ id: string; title: string; status: 'pending' | StepStatus; lines: string[] }>; // ≤ 200 строк на шаг
  progress: RelayPullProgress | null;
  cancelling: boolean;
  phase: RelaySetupPhase;   // { phase: 'running' } во время прогона, итоговая фаза — после
}
```

Секретов в записи нет (строки уже замаскированы). Новые вызовы: `state` → запись или `null`; `dismiss` → забыть
запись (во время прогона — отказ). `run` больше не ждёт конца: отвечает `{ phase: 'running' }`, итог приходит
событием и через `state`. События получают `seq`; новые события — `progress`, `cancelling`, `phase` (итог,
и после Check). Окно берёт `state` при открытии и применяет события с `seq` больше снимка.
`check` (повтор проверки здоровья) обновляет итог записи.

### 8.2 Закрытие и возврат

- Окно мастера закрывается **только крестиком**: ни клик по фону, ни Esc его не закрывают (во всех фазах).
- До Run (форма, ключ сервера, пароль, план) крестик и Cancel — как сейчас: отмена сеанса, соединение и учётные
  данные сбрасываются.
- Во время прогона крестик только прячет окно, прогон идёт дальше. Cancel в подвале — отмена (7.2).
- После итога крестик прячет окно, запись остаётся. Подвал итога: **Close** — забыть запись и закрыть; **New
  setup** — забыть запись и показать форму.
- Settings → Remote access → «Set up on my server…» при живой записи открывает её (живой лог или итог с логом),
  а не форму.
- **Перезагрузка окна** запись не теряет: она в main. **Выход из приложения** (и перезапуск) её теряет:
  `before-quit` закрывает SSH, запись не сохраняется на диск; команда на сервере может доработать сама (правка
  5.2 — доработает всегда). **Перезапуск хоста** Parley на запись не влияет: мастер живёт в main окна, не в
  хосте; если хост лежит в момент `configure`, итог — `configured: false`, как сейчас.

## 12. Риски

- `TRUST_PROXY: '1'` в чужой сети: контейнер человека в той же сети может прислать relay поддельный
  `X-Forwarded-For` (влияет только на учёт по IP). Relay и так рассчитан на интернет.
- Псевдоним `parley-relay` в чужой сети может совпасть с чужим именем — тогда проверка здоровья не пройдёт;
  разведка показывает контейнеры сети, но такой случай не блокирует.
- Наш сайт в чужом Caddy получает сертификат средствами этого Caddy: если у него выключен автоматический HTTPS,
  проверка здоровья не пройдёт, итог — «failed: health» с Check, правка остаётся (её убирает Remove).
- Формат потока Engine API может отличаться у новых версий Docker (хранилище containerd): разбор терпим к
  неизвестным статусам, а итог шага решает `docker image inspect`.
