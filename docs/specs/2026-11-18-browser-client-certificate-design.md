# Браузер Parley: клиентский сертификат по выбору человека (SSO с mTLS)

**Дата:** 2026-11-18. **Статус:** решения Р3, Р4 и стенд подтверждены человеком 2026-11-18; план принят, спайк сделан, раздел 2а — поправка по его итогам. **Основа кода:** origin/master 196850cf (v0.37.1), Electron 44.4.5.
**Меняет:** `docs/specs/2026-09-26-desktop-orca-ui-design.md`, раздел 12.2 («сертификат клиента не отдаётся»).

## 1. Что сломано

Вход через SSO, где сервер просит клиентский сертификат (mTLS), во встроенном браузере не завершается. Причина в коде и она намеренная:

```ts
// packages/desktop/src/main/browser/guard.ts:253
deps.app.on('select-client-certificate', (event, _contents, _url, _list, callback) => {
  event.preventDefault();
  callback();
});
```

Спека 12.2 объясняет зачем: без обработчика Electron отдал бы сайту первый сертификат из хранилища — личность человека без вопроса. Отказ закрыл этот риск, но вместе с ним и законный вход. Находка другого агента (сбой `auth.example.com:6443/login/check/` в сборке 0.36.0) с кодом сходится.

Исправление: не «отдавать», а **спрашивать человека**.

## 2. Решения

Р3, Р4 и Р7 подтверждены человеком 2026-11-18. Р1, Р2, Р5, Р6 приняты мной по умолчанию; человек может отменить любое до начала работ.

- **Р1. Выбирает только человек.** Инструмента для агента нет. Агент видит лишь «страница ждёт выбора сертификата».
- **Р2. Первый раз спрашиваем всегда**, даже если сертификат в списке один. Личность сайту без вопроса не уходит — смысл 12.2 сохраняется.
- **Р3. Выбор запоминается по `хост:порт`** (подтверждено). Без галочки — до выхода из Parley. С галочкой «Remember for this site» — на диске, в настройках окна. Хранится отпечаток сертификата, не ключ.
- **Р4. Запомненный выбор действует и для страниц агента** (подтверждено: одна галочка, без отдельной «для агентов»). Иначе агент не завершит SSO, ради чего всё делается. Текст галочки говорит об этом прямо.
- **Р5. Только гости раздела браузера.** Запрос от главного окна, острова и любых других `webContents` — отказ, как сейчас.
- **Р6. «Clear browsing data» стирает запомненные выборы.**
- **Р7. Локальный стенд mTLS разрешён — во временной связке ключей** (подтверждено). Связка создаётся на время спайка и убирается после него; основная связка человека не меняется.

## 2а. Поправка после спайка (2026-11-18)

Замеры — `docs/research/2026-11-18-browser-client-certificate-spike.md`. Где разделы 2–5 расходятся с этим разделом, верен он.

- **Ключ.** Событие отдаёт `хост:порт` готовым, без схемы.
- **Память (Р3).** Ответ на `хост:порт` — сертификат или отказ — Chromium помнит до выхода из Parley и повторно в этом запуске не спрашивает; сбросить это нельзя ничем, кроме перезапуска. Поэтому Parley хранит только выборы с галочкой (на диске); выбор без галочки живёт в самом Chromium до выхода.
- **Итог добавочных замеров (2026-11-18):** отмена — ветка «не сейчас»; при пустом списке событие не приходит, ветка «список пуст» убрана. Если подходящего сертификата в связках нет, Parley о запросе не узнаёт и ничего не показывает.
- **Отмена.** По замеру вопроса 7 (план, поправка 1) — одна из двух веток. «Не сейчас»: отмена, `Escape`, уход со страницы и закрытие вкладки оставляют запрос без ответа, и сайт спросит снова при следующем запросе. «Отказ»: отмена — отказ до перезапуска Parley, слой предупреждает об этом, `Escape` слой не закрывает.
- **Пустой список.** По замеру вопроса 6: если событие при пустом списке не приходит, ветка «список пуст» и уведомление убираются — Parley о таком запросе не узнаёт.
- **«Clear browsing data» (Р6).** Стирает сохранённые выборы; сайт, на который в этом запуске уже ответили, спросит снова только после перезапуска.
- **Окно macOS.** После выбора macOS спрашивает доступ к ключу; страница ждёт без срока, Parley окна не видит. Слой выбора говорит о нём строкой; в навыке — строка для агента.
- **Находка с CORS.** Предзапрос CORS несёт сертификат, так что ошибка CORS на `:6443` — скорее следствие отказа от сертификата, чем отдельная причина. На настоящем сервере не проверено.

## 3. Поведение

Событие: `select-client-certificate(event, webContents, url, list, callback)`. Всегда `event.preventDefault()`.

| Условие | Ответ |
|---|---|
| `webContents` — не гость раздела браузера | `callback()` без сертификата |
| `list` пуст | `callback()`; над вкладкой — уведомление «`хост:порт` asked for a client certificate, but macOS Keychain has none that Parley can use.» |
| Для `хост:порт` запомнен отпечаток и он есть в `list` | `callback(сертификат)` без вопроса |
| Запомненный отпечаток в `list` не найден (истёк, удалён) | запись снимается, дальше — как без неё |
| Иначе | запрос человеку (ниже) |

### 3.1. Запрос человеку

Слой над вкладкой, по образцу `AuthPrompt.tsx` (HTTP basic-auth): не системный диалог и не `alert`.

- Заголовок: `auth.example.com:6443 asks for a certificate that identifies you.` Если хост запроса не совпадает с хостом страницы — вторая строка: `Requested by the page example.com.` (так человек видит запрос от скрипта страницы на другой порт или поддомен).
- Список сертификатов из `list`: имя субъекта, издатель, срок действия, серийный номер. Один сертификат — выбран заранее, но кнопку всё равно нажимает человек.
- Галочка: `Remember for this site. Agents working in Parley's browser will be identified by it too.`
- Кнопки: `Use certificate`, `Cancel`. `Escape` — отмена.

Отмена → `callback()` без сертификата; ничего не запоминается.

Вкладка ушла со страницы или закрыта, пока запрос висит, — запрос снимается с `callback()` (как `finish` у basic-auth).

### 3.2. Несколько запросов сразу

- У гостя один слой за раз.
- Запросы к тому же `хост:порт`, пришедшие, пока человек выбирает, ждут этого же ответа и получают тот же сертификат.
- Запросы к другому `хост:порт` встают в очередь и показываются по одному.

### 3.3. Агент

- Пока запрос висит, `settleLoad` не ждёт загрузку до потолка, а отвечает сразу — тем же механизмом, что для basic-auth (`isPending`/`onPending`). В заметках ответа: `The site asks for a client certificate: ask the human to choose it in the browser panel.`
- Выбрать, подтвердить или обойти запрос агент не может: ни `browser_action`, ни `browser_evaluate` до слоя окна не дотягиваются (слой — в окне Parley, не в странице).
- В навыке `parley-browser`: строка в Troubleshooting про эту заметку.

### 3.4. Журнал

В журнал окна — одна строка на событие: `хост:порт`, число сертификатов в `list`, исход (`asked`, `remembered`, `empty`, `denied-not-guest`, `cancelled`, `chosen`). Без имён субъектов и отпечатков. Этого хватает, чтобы на стенде отличить «список пуст» от «человек не выбрал».

## 4. Безопасность

- Приватный ключ Parley не видит: он остаётся в Связке ключей macOS; Parley держит только объект `Certificate` и его отпечаток.
- При первом использовании ключа macOS может показать свой запрос доступа к ключу. Это ожидаемо, и это вопрос системы, не Parley.
- Риск Р4 назван прямо: после «Remember» агент на этом сайте действует от имени человека. Сдерживают: выбор сделан человеком для конкретного `хост:порт`; Stop и пауза панели; «Clear browsing data».
- Список сертификатов уходит только окну-хозяину гостя, ответ принимается только от него (как `browser:auth-response`).

## 5. Чего мы не знаем

Это надо выяснить до или во время приёмки; ответы могут поправить раздел 3.

1. **Что приходит в `list`** в dev-окне и в собранном подписанном приложении: видны ли сертификаты аппаратного ключа или стороннего поставщика (в находке — «токен»). Если список пуст — дело в доступе к Связке ключей, и код раздела 3 входа не починит.
2. **Запрос от скрипта страницы на другой порт.** В находке падает `fetch` на `:6443` с ошибкой CORS. Насколько я помню, Chromium не шлёт клиентский сертификат в предварительном запросе CORS (`OPTIONS`); если сервер требует сертификат уже на рукопожатии TLS, такой запрос не пройдёт ни в одном браузере на Chromium. Проверка: тот же вход в Chrome на той же машине. Работает в Chrome — должен заработать и у нас после выбора сертификата.
3. **Кэш выбора в Chromium.** Сессия сама помнит выбор для `хост:порт` до перезапуска; неизвестно, помнит ли она отказ и как его сбросить без перезапуска (нужно для «Cancel», затем повторной попытки).
4. **Запрос macOS к ключу** в dev-Electron против собранного приложения.

Пункты 2–4 и первая половина пункта 1 закрывает спайк на локальном стенде (задача 0, решение Р7). Стенд не покажет одного: виден ли Parley сертификат «токен» с машины, где случился сбой, — это остаётся живой приёмке (задача 6).

### 5.1. Стенд спайка

- **Связка.** `security create-keychain` создаёт временную связку с паролем спайка; в неё импортируется тестовая пара «сертификат + ключ» (`.p12`), выпущенная своим тестовым центром. Связка добавляется в список поиска пользователя (`security list-keychains -d user -s …`), прежний список записывается до изменения.
- **Сервер.** Node `https` на `127.0.0.1`, два порта: страница на одном, адрес `check` с `requestCert: true` — на другом. Так воспроизводится запрос скрипта на другой порт из находки, с `credentials: 'include'` и без.
- **Окно.** Свой стенд Electron 44.4.5 по образцу спайка 2026-10-20 (`<webview>`, тот же раздел, страж как у Parley, отладчик до `loadURL`), а не сборка Parley. Самоподписанный сертификат сервера принимает только стенд.
- **Уборка — часть приёмки.** Список поиска возвращается к записанному, временная связка удаляется (`security delete-keychain`), тестовые файлы стираются. `security list-keychains -d user` до и после совпадают дословно.

Отчёт: `docs/research/2026-11-…-browser-client-certificate-spike.md`, вопрос — замер — вывод, по образцу `2026-10-20-browser-agent-control-spike.md`.
