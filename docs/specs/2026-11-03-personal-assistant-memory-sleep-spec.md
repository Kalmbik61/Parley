# Parley — Спецификация №2
# Parley Personal Assistant v1: ассистент специалиста, долгосрочная память и цикл «сна»

**Версия:** 1.0 (product + technical design, ready for decomposition)  
**Дата:** 2026-11-03  
**Модель поставки:** открытый/общедоступный Parley Remote & Desktop с собственным хостом и подключёнными пользователем провайдерами. В первой версии **никакого Parley Cloud и обязательной платной подписки на самого ассистента**.  
**Целевая аудитория v1:** разработчики, технические лидеры, CTO, проектные руководители, power users, одновременно ведущие много работ, решений и агентных сессий.  
**Позиционирование:** «Parley — персональный AI-ассистент, которому поручают работу, а не просто задают вопросы».

## 0. Принципиальные решения

1. **Один Assistant Core, несколько интерфейсов.** Desktop island, текстовый чат, мобильный Voice и Telegram не заводят разные «личности»; они обращаются к одному сервису и к одной последовательной истории запросов/задач.
2. **Оркестрация отдельно от интерфейса.** Задачи выполняет существующий Parley Assistant из выбранного CLI-провайдера/подписки; голосовая модель не владеет бизнес-логикой и не получает право бесконтрольно выполнять команды.
3. **Память принадлежит Parley, а не Claude/Codex/GPT.** Смена модели не стирает контекст и не открывает доступ к чужим данным.
4. **«Сон» — самостоятельный процесс консолидации памяти.** Не путать с уже описанным в Parley «сном CLI-сессий», который освобождает RAM. Новый `Memory Sleep` обрабатывает события дня, пересматривает знания и актуальность, формирует краткие версии и предлагает изменения.
5. **Память с источником, областью доступа и историей изменений.** Ошибочные выводы не становятся фактами; противоречия не решаются незаметно; личные данные не попадают в проектные репозитории.
6. **Прозрачная автономность.** Ассистент может самостоятельно анализировать и готовить предложения, но полномочия для отправки сообщений, изменения проектов и других действий определяет host policy; существующие карточки подтверждения сохраняются.
7. **Local-first.** Первое поколение живёт на Mac/хосте пользователя; удалённые клиентские устройства — интерфейсы, не место для хранения постоянных прав и секретов.

## 1. Зачем это пользователю

Специалист ведёт несколько проектов/команд и множество AI-сессий. Сегодня ему приходится держать в голове: что поручено, что заблокировано, какие решения уже приняты, что обещал проверить, какие выводы из ошибок должны сохраниться после перезапуска агента. Разговорный Assistant решает лишь часть проблемы; без долговременной памяти каждое утро он снова «новый».

**North-star сценарий:** пользователь в мобильном приложении говорит: «Парли, дай утреннюю сводку: что поменялось за ночь, какие проекты застряли, что я обещал сделать и что ты считаешь главным сегодня?» Ассистент использует структурированную память и текущее состояние хоста, не фантазирует о неизвестных данных, называет источники, предлагает конкретные шаги; на запуск работы просит подтверждение.

**Цели v1:**

- Единый текстовый/голосовой Assistant с общей историей между каналами.
- Системный ежедневный обзор текущих работ, ожидающих решений, напоминаний и завершённых задач.
- Личная долгосрочная память предпочтений, фактов и договорённостей; отдельная память каждого проекта.
- Ежедневный `Memory Sleep`: извлечение кандидатов, консолидация, обнаружение устаревших фактов и конфликтов, компактизация, review/rollback.
- Постановка и контроль поручений с устойчивым `taskId`, очередью, отчётом о ходе, дедлайном и уведомлениями.
- Соблюдение прав: ассистент готовит действия и передаёт их в host через подтверждённые инструменты.

**Не цели v1:** покупка билетов/товаров, хранение паспортов и карт, голосовая биометрическая идентификация, enterprise-SSO, облачный хост на каждого клиента, использование чужих подписок, самостоятельные внешние транзакции, мобильное приложение без собственного Parley-host.

## 2. Опора на текущий репозиторий

Нельзя переписывать существующие слои без реальной необходимости. Перед составлением implementation-plan проверить состояние `master` на дату старта.

- `packages/host/src/assistant/assistant-service.ts` — общий помощник на CLI, выбранном пользователем, карточки proposed actions, разговоры и события `assistant.changed`.
- `packages/host/src/assistant/*` — чтение overview, find, reminders, управление планами и работами, action proposals.
- `packages/host/src/assistant/assistant-endpoint.ts` — локальная граница инструментов. **Расширять узкими проверяемыми tool calls**, не давать произвольный shell.
- `packages/core/src/work/project-memory.ts`, `memory-suggestions.ts`, `packages/protocol/src/memory.ts` — **существующая** проектная память и предложения.
- `.parley/memory.md` — разделяемая проектная память в git, с принятием человеком. Это **не хранилище личной памяти**.
- `packages/host/src/telegram/*`, `packages/remote-client`, `packages/mobile`, `packages/remote` — существующие каналы.
- `docs/specs/2026-10-30-agent-sleep-and-capacity-design.md` — экономия памяти при ожидании CLI; это не то же самое, что консолидация долгосрочной памяти.
- `docs/specs/2026-10-03-memory-journal-design.md` — история решений и память по проектам; новую память интегрировать с этим слоем, не дублировать ручные факты.
- `docs/specs/2026-10-19-assistant-control-telegram-design.md` — существующая политика подтверждений и напоминаний.

**Термины:** `Assistant Conversation` (диалог человека), `Task` (поручение), `Memory` (долговременный факт), `Episode` (записанный контекст/событие), `Memory Sleep` (задача консолидации), `CLI Session Sleep` (освобождение процесса). В UI и коде их не смешивать.

## 3. Концепция пользователя: один Parley, много контекстов

Ассистент может общаться с пользователем «о себе», о состоянии Parley, о рабочих проектах и, позднее, о бытовых вопросах. В первой версии в центре — профессиональный контекст, но схема должна не препятствовать будущему бытовому.

### 3.1 Разделение областей (Memory Scope)

- `personal` — предпочтения владельца, общие правила общения, собственные поручения, личная информация.
- `workspace:<id>` — рабочая область (например, «Работа A»), доступ только на основании membership/policy.
- `project:<id>` — проектные решения/уроки/ограничения; проектная память может быть общей для команды, но личная память не экспортируется в git.
- `conversation:<id>` — короткоживущий контекст отдельного диалога.

Каждая запись имеет владельца, scope, ACL, источник и политику времени хранения. **Знание из личного scope никогда не копируется в workspace/project без явного согласия.** Если завтра будут корпоративные и личные режимы, они будут различаться политиками доступа, а не отдельными «памятями» от разных LLM.

### 3.2 Онбординг v1

1. Установить Parley Desktop (или подключить уже существующий host), выбрать рабочую модель Assistant из настроенных официальных CLI.
2. Мобильное приложение: QR-pairing с подтверждением на Mac; после pairing виден Assistant first screen (спека №1).
3. Отдельные настройки с явным opt-in: «Сохранять историю для памяти», «Запоминать личные предпочтения», «Ежедневная консолидация», «Использовать выбранную модель и лимиты подписки на ночную обработку».
4. Объяснить: память хранится на хосте, что сохраняется, что никогда не запоминается, как просмотреть/исправить/удалить.
5. Пользователь может отключить все функции памяти и по-прежнему использовать Assistant с текущим контекстом.

## 4. Функциональность ассистента

### 4.1 Работа с текущими делами

**Read operations** — без отдельного LLM, если результат детерминирован:

- количество активных/спящих агентов и ожидающих слотов;
- текущие комнаты, решения, просроченные задачи, лимиты провайдеров;
- изменения за день, сводка результатов независимых verifier;
- краткая история и ссылки на первичные записи.

**Reasoning operations** — через выбранного CLI Assistant с доступом только к разрешённым tool endpoints:

- разобраться в причине задержки или нестыковки между участниками комнаты;
- сравнить варианты плана, найти риск, предложить переприоритизацию;
- составить сводку по нескольким проектам;
- предложить сообщения/создание комнат/дополнительную проверку.

**Write operations** — через существующие предложения и подтверждения:

- письма агентам и комнатам;
- создание работы, сессии или комнаты;
- разрешение/возврат решения комнаты;
- изменения бэклога/плана по явным полномочиям пользователя.

В MVP не делать общий `execute_anything`. В каждом инструменте — zod-schema, whitelist, project access check, idempotency key, audit record и канал подтверждения.

### 4.2 Проактивные помощники

Необходимы две категории:

1. **Explicit reminder** — «через 15 минут проверь комнату Auth»; использует существующий reminder host, может сделать обзор и уведомить по выбранному каналу.
2. **Daily digest** — «Что изменилось с прошлого отчёта» по журналу хоста/сохранённым задачам. Не создаёт внешних сообщений/задач без отдельного согласия.

Любой scheduled job сохраняется на хосте, запускается после рестарта, имеет `scheduledFor`, `lastRun`, `nextRun`, `status`, `idempotencyKey`. При отключённом Mac нельзя обещать выполнение «ровно в 03:00»: пропущенная обработка выполняется при следующем старте по catch-up policy.

### 4.3 Лента поручений

Каждое поручение — самостоятельная сущность, даже если возникло из одного голосового предложения:

- статус `draft | awaiting_confirmation | queued | running | blocked | completed | failed | cancelled`;
- `owner`, `scope`, `originChannel`, `sourceConversationId`, `createdAt`, `dueAt?`, `createdByActor`;
- связи с комнатами/сессиями, ожиданием подтверждений и документированными источниками;
- ревизии статусов и журнал результатов независимой проверки;
- `resume` после перезапуска только когда реальное состояние проверено; отсутствие подтверждения не считать успехом.

В мобильном UI отображать «Поручения» и «Требуют моего решения», а не только скрытую беседу.

## 5. Модель долговременной памяти

### 5.1 Слои

```text
Signals: transcripts / confirmed user messages / work events / decisions / reminders
    │
    ▼
Episodic Journal (история с источниками, датами, scope, retention)
    │
    ▼
Memory Candidates (черновики, оценка, provenance, конфликт)
    │   nightly Memory Sleep + пользовательский review
    ▼
Long-Term Memory (актуальные факты, цели, предпочтения, обязательства)
    │
    ▼
Retrieval Context (минимальный набор релевантных записей для конкретной задачи)
    │
    ▼
Assistant / CLI orchestration
```

**Короткая память:** ограниченная история текущего разговора и job context.  
**Эпизодическая память:** хронологические события и доказательства, retention policy.  
**Семантическая память:** долгоживущие сведения с версией и источником.  
**Процедурная память:** явные предпочтения/правила пользователя («по умолчанию сначала дай краткую сводку»). Не превращать это в возможность обхода security policy.

### 5.2 Какие знания сохраняем

Позитивные примеры:

- пользователь просил всегда показывать 3 приоритетных риска в утренней сводке;
- проект Auth имеет релизную дату, подтверждённую в плане;
- в комнате принято решение о выборе архитектуры с id и ревизией;
- владелец явно поручил повторно проверить проблему до пятницы;
- проверенная закономерность: тесты на определённом шаге не запускались, а проверка ошибочно прошла.

Отрицательные примеры — **не сохранять автоматически**:

- догадка LLM без подтверждённого источника;
- случайные фразы других людей в логах или содержимое недоверенного сайта;
- API-ключи, bearer токены, cookies, CVV, приватные ключи и одноразовые коды;
- полная копия секретного документа вместо ссылки/краткого метаданного;
- чувствительная личная информация, которая не нужна задаче или не разрешена настройками.

### 5.3 Структура записи

```ts
type MemoryRecord = {
  id: string;
  ownerId: string;
  scope: { type: 'personal'|'workspace'|'project'; id?: string };
  kind: 'fact'|'preference'|'agreement'|'goal'|'lesson'|'commitment';
  statement: string;                  // атомарное, проверяемое утверждение
  details?: string;
  tags: string[];
  provenance: Array<{
    sourceType: 'human'|'decision'|'task'|'session'|'tool'|'external';
    sourceId: string;
    observedAt: string;
  }>;
  evidenceStrength: 'explicit_human'|'verified'|'inferred';
  confidence: number;                // 0..1, не единственный критерий принятия
  validFrom?: string;
  validUntil?: string;
  status: 'candidate'|'active'|'disputed'|'superseded'|'archived';
  supersedesId?: string;
  revision: number;
  visibility: 'private'|'workspace'|'project';
  createdAt: string;
  updatedAt: string;
  reviewedAt?: string;
};

type EpisodicEvent = {
  eventId: string;
  scope: string;
  occurredAt: string;
  actor: 'human'|'agent'|'system';
  sourceRef: string;
  type: string;
  summary: string;
  piiClass: 'none'|'personal'|'sensitive'|'secret';
};
```

**Persistence v1:** собственная local SQLite database на хосте (не репозиторий, не Telegram, не память CLI). FTS5 — минимальный локальный поиск; embeddings/vector index необязательны в v1, добавлять при доказанной потребности. Для секретов — отдельные API ОС/Keychain; в БД — минимизация полей, права файлов, encryption at rest по выбранному уровню угроз, резервное копирование/удаление. Все схемы с миграциями и версиями.

### 5.4 Правила актуализации

- Новое утверждение не переписывает старое молча. Если подтверждено, создаётся новая ревизия или `supersedesId`; старое доступно в истории изменений.
- Факт из прямого высказывания пользователя имеет больший приоритет, чем вывод из поведения модели, **но** не может подменять security policy.
- Конфликт из двух авторитетных источников → статус `disputed` + видимое пользователю предложение разрешить конфликт.
- Изменение срока/задачи в Parley map при наличии надёжного источника может обновлять служебную память автоматически; изменения личных предпочтений и договорённостей требуют подтверждения при неопределённости.
- Удаление по запросу пользователя затрагивает active record и разрешённые производные summaries/indices, с отдельной прозрачной политикой бэкапов.
- Внешняя информация всегда несёт источник и время проверки; устаревшая информация не выдаётся за свежую.

### 5.5 Контекстный retrieval

Только при нужной задаче — не подмешивать **всю память** во все обращения.

1. Определить scope и права пользователя на запрос.
2. Определить intent, временной период и необходимые виды знаний.
3. Получить по FTS, metadata/time, затем rerank локальными правилами/моделью при необходимости.
4. Фильтровать `status=active`, срок годности и видимость.
5. Собрать компактный контекст с `memoryId`, источником, `asOf` и ограничением токенов.
6. Отделить **memory facts** от **live facts**: на «как сейчас идёт работа?» обращаться к хосту за свежим состоянием, не отвечать из ночного summary.

На UI «Почему Parley это помнит?» → исходный разговор/решение/поручение, управление правкой и забыванием.

## 6. «Сон» ассистента — Memory Sleep

### 6.1 Концепция

Не биологическая имитация сна, а **контролируемый, наблюдаемый и обратимый процесс консолидации**. Проводится один раз в сутки, например в 03:00 по часовому поясу пользователя. Время настраивается. Если Mac выключен/спит или CLI-провайдер исчерпал лимит — не запускать искусственно и не будить Mac; перенести на доступное окно.

**Отдельный тип job** `memory_consolidation`, не смешанный с `sessions.sleeping`. Новый job может выполняться на подключённой CLI-модели либо на детерминированных правилах, а платные API не подключаются незаметно.

### 6.2 Пайплайн

```text
[1. Cutoff / Snapshot]
    ↓
[2. Collect episodes since last successful checkpoint]
    ↓
[3. Redact secrets / scope partition / dedupe]
    ↓
[4. Extract atomic memory candidates]
    ↓
[5. Compare with existing active memories and project state]
    ↓
[6. Identify: new / reinforce / corrected / contradicted / obsolete]
    ↓
[7. Build change proposal + daily digest]
    ↓
[8. Validate constraints, evidence, budget]
    ↓
[9. Auto-commit safe system facts; human review for disputed/personal changes]
    ↓
[10. Rebuild compact retrieval index + log transaction / checkpoint]
```

**1 — Snapshot:** записать watermark `lastProcessedEventId` и `cutoffAt`; использовать неизменяемый диапазон событий для одного прогона. Нельзя менять базовый набор посреди LLM-анализа.

**2 — Capture:** читать только разрешённые события: выбранные пользовательские высказывания, решения комнат, завершённые задачи и verifier results, reminders и явно записанные мысли. Данные из другой рабочей области не попадают в текущую.

**3 — Sanitization:** удалить секреты/временные токены/лишние PII до отправки на модель; source refs вместо полного сырого содержимого; не отправлять в стороннюю модель документ, которому пользователь не разрешил такое использование.

**4 — Extraction:** каждая кандидатура атомарна, содержит `statement`, `provenance`, тип, временную применимость, основания и рекомендованное действие; модель не пишет непосредственно в БД.

**5 — Reconcile:** сравнить с активными фактами и current state; найти дубликаты, усиление, отрицание, новые сроки, устаревание. Нельзя считать рефлексию модели первичным доказательством.

**6 — Propose:** итогом являются `MemoryChangeProposal` и `DailyDigest`, а не готовый `UPDATE memories`.

**7 — Commit:** обычные системные статусы задач/комнат с подтверждёнными event refs могут обновляться по policy, но личные факты, сомнительные изменения и конфликтные сведения отправляются в review. **Ручные записи пользователя никогда не переписываются автоматически.** Применение через optimistic locking `expectedRevision` и одну транзакцию.

**8 — Compact:** создаётся новая компактная сводка для поиска/подмешивания, но не уничтожаются источники, пока не истечёт явно заданный retention. Отдельная диагностика «что изменилось за сон».

**9 — Checkpoint:** только после commit успешно записать `lastProcessedEventId`, `promptVersion`, `modelProvider`, `duration`, `usage`, количество кандидатов, обновлений, конфликтов; отчёт об ошибках и retry без двойного применения.

### 6.3 Контракт сна

```ts
type MemorySleepRun = {
  runId: string;
  ownerId: string;
  fromEventId: string | null;
  toEventId: string;
  cutoffAt: string;
  providerId?: string;
  state: 'queued'|'collecting'|'extracting'|'reconciling'|'review'|'completed'|'failed'|'skipped';
  budget: { maxTokens?: number; maxDurationSec: number; maxCostUsd?: number };
  stats: { candidates: number; autoApplied: number; requiresReview: number; conflicts: number };
  errorCode?: string;
};

type MemoryChangeProposal = {
  proposalId: string;
  operation: 'add'|'reinforce'|'supersede'|'mark_disputed'|'archive';
  targetMemoryId?: string;
  expectedRevision?: number;
  statement: string;
  rationale: string;
  evidenceRefs: string[];
  scope: string;
  requiresHumanReview: boolean;
};
```

### 6.4 Анти-паттерны и предохранители

- «Сон» не запускает work/room/CLI сессии ради собственной инициативы, не отправляет сообщения людям, не покупает и не удаляет ничего.
- Не менять подтверждённое человеком знание по недостоверному summary.
- Не допускать бесконечной рекурсии «сам изучает собственные summary» — использовать новые внешние эпизоды и указатели на реальные первичные источники.
- Не разрешать LLM самому объявлять факт verified; его verify определяется источником, проверкой хоста или человеком.
- Контент чужих документов/комнат/Telegram — данные, а не системные инструкции; память не расширяет разрешения.
- Если sleep failed — прежняя память остаётся целой; retry повторяет **то же** окно событий.
- Если слишком дорого по лимитам — пропустить или частично обработать пакет с checkpoint, предупредить в отчёте, не прятать потерю покрытия.

### 6.5 UI «Память и сон»

**Settings → Assistant → Memory:** переключатели и scope, время сна, модель-провайдер, бюджет, удержание истории, кнопка «Запустить консолидацию сейчас», «Экспортировать», «Удалить».  
**Memory Center:** актуальные факты, поиск, источник, версия, время, ручная правка, «забыть».  
**Sleep report:** `Вчера обработано 148 событий; добавлено 8 фактов; уточнено 3; 2 конфликта требуют решения`. Данные — лишь пример UI, считать из реального run.  
**Needs review:** карточка `Old deadline: 15 Nov → proposed: 19 Nov` с источниками и `Accept / Reject`; до подтверждения в retrieval отмечать конфликт/неуверенность.

## 7. Assistant engine: единый контекст и жизненный цикл

### 7.1 Assistant Conversations vs Agent Jobs

`Conversation` — персистентная история человека, связанная с его `ownerId`; канал (desktop/mobile/Telegram) — атрибут сообщения. `Task` — самостоятельная работа с собственным lifecycle. Модель/процесс может перезапускаться, но `conversationId`, `taskId`, память и permissions остаются.

- Не держать один бесконечный CLI-процесс ради памяти — CLI-сессии можно переиспользовать/пересоздавать согласно затратам и cache, но постоянное состояние хранить в host.
- Конфликт ввода Desktop и Telegram: serialize per conversation или ввод с упорядоченными `messageId`, `turnId`, `revision`, без гонки двух подтверждений.
- Существующий таймаут разговора (15 минут idle) может завершать **текущую CLI-сессию**, но не сбрасывает долгосрочную память или реальные поручения.
- При изменении провайдера/модели подтягивать только разрешённую релевантную память и краткую историю, не переносить credentials.

### 7.2 Контекст на один запрос

```text
[System/policy instructions]
[Parley host capability summary]
[User settings + authorized scopes]
[Relevant durable memories WITH provenance and validity]
[Fresh host state / project summary]
[Last turns of conversation + active task refs]
[User request]
```

Не отправлять полный `memory.md`, все комнаты или длинные логи по умолчанию. Большой материал по отдельному tool call с лимитом и источником.

### 7.3 Suggested tool interface (MCP / Assistant)

- `assistant_get_overview(scope?, since?)` — детерминированное чтение.
- `assistant_get_task(taskId)` / `assistant_list_tasks(status?)` — поручения.
- `assistant_propose_action(action, params, reason)` — существующие карточки; новый слой адаптации, не прямой command execution.
- `assistant_schedule_check(targetRef, time, reportPolicy)` — из существующего reminder.
- `memory_search(query, scope, asOf?, limit?)` — ACL и source refs.
- `memory_propose(statement, kind, scope, evidenceRefs)` — создавать кандидата.
- `memory_get(recordId)` / `memory_review(proposalId, decision)` — человек или авторизованный host, модель без прав review.
- `memory_sleep_get(runId)` / `memory_sleep_start(policy)` — ручной запуск только после пользовательской авторизации.

Избегать копирования `memory_read` проектного MCP: вынести общую абстракцию source/retrieval, но сохранить существующие права на `.parley/memory.md`.

## 8. Безопасность, приватность, управление памятью

### 8.1 Модель угроз

1. Украденный разблокированный телефон с удалённым доступом.
2. Prompt injection из содержимого GitHub issue, лога, веб-страницы, письма агента.
3. Cross-scope утечка личной памяти в проект/команду.
4. Неподтверждённое агентное изменение/отправка сообщения.
5. Неверная память после устаревания, повторное удаление или ложное «сделано».
6. Злоупотребление лимитом CLI и API при массовой ночной консолидации.

### 8.2 Политики

- Пользователь/хост — единственный authority на права и подтверждения. Языковая модель не может расширить allowlist.
- На мобильных устройствах revocable pairing, E2EE Noise; для важного действия — дополнительное подтверждение с контекстом; Face ID/passkey как **будущее отдельное расширение**, не голосовой биометрический идентификатор.
- Не сохранять секреты в LLM prompts или memory. External API credentials — только в разрешённых изолированных секретных хранилищах.
- Внешние провайдеры получают только минимально необходимые фрагменты пользовательского контекста после информированного согласия.
- Пользователь видит и управляет: что запомнено, откуда, когда обновилось, почему это показывается и что удалено.
- Редактирование памяти не должно само по себе удалять реальные задачи или решения из журнала. Отдельная команда и подтверждение.
- Audit без чувствительного текста, но с `actor`, `action`, `scope`, `entityId`, `revision`, `timestamp`, `decision`.
- Никаких silent background LLM calls до explicit opt-in для Memory Sleep.

## 9. Производительность, цена, автономность

- Не запускать оркестратор по каждому запросу read-only, сохранять отдельную быструю host-path.
- Сон запускается с budget/time/capacity cap; низкий приоритет в очереди против задач человека, при высокой RAM/CPU нагрузке откладывается.
- Если пользователь недоступен или Mac спит, ближайший запуск после пробуждения; без накопления десятков ночных job. Catch-up объединяет промежуток с точным диапазоном event IDs.
- Частичную обработку фиксировать. После сбоя можно продолжить/повторить без дублей.
- Предусмотреть статистику: `memory_precision_review`, `false_memory_reports`, `stale_memory_rate`, `sleep_coverage`, `sleep_tokens`, `time_to_daily_digest`, `task_completion_with_evidence`.
- Не давать SLA «ассистент всегда на связи», пока работа зависит от конкретного пользовательского Mac.

## 10. Потоки пользовательского опыта

### Сценарий A — утренний брифинг

**Пользователь:** «Парли, что нужно моего внимания сегодня?»  
**Host:** собирает live inbox, reminders, подтверждённые итоги вчерашних задач, текущие лимиты, память о приоритетах.  
**Assistant:** «Две комнаты ждут решения; проект X заблокирован из-за входа провайдера; по задаче Y проверка не прошла. Вчера ты просил утром вернуться к бюджету. Показать сначала блокировки?»  
**UI:** карточки первичных источников и кнопки действий. Ничего не исполнять из текста сводки.

### Сценарий B — поручение и долгий контроль

**Пользователь:** «Проверь 12 комнат и найди те, где верификация могла пройти ошибочно».  
**Assistant:** создаёт `taskId`, предлагает план с границами. Пользователь подтверждает.  
**Host:** запускает проверку на выбранном CLI, мониторит состояние, сохраняет evidence и прогресс.  
**UI:** человек закрывает голос, потом видит итог и ссылки на комнаты. Никаких повторных выполнений при reconnect.

### Сценарий C — обновление памяти во сне

Вчера в проекте приняли дату релиза 19 ноября вместо 15-го. В памяти есть старое подтверждённое значение «15 ноября».

- `Memory Sleep` обнаруживает новую подтверждённую версию решения, сравнивает scope/evidence.
- Старый факт `superseded` только по разрешённой политике и достаточному источнику; пользовательские ручные сведения отправляются на review.
- В отчёте: «Дата релиза изменилась: 15 → 19 ноября. Источник: решение комнаты r-… rev 3».
- Утренний ассистент использует новый факт только после его принятия по соответствующей политике; пока есть конфликт, честно его отмечает.

### Сценарий D — память «я обещал»

Пользователь сказал: «Напомни мне до пятницы согласовать архитектуру». Ассистент создаёт напоминание с явным подтверждением времени (включая timezone), а в памяти сохраняет обязательство со ссылкой на reminder/task. При исполнении reminder статус обязательства обновляется; `Memory Sleep` не создаёт повторное напоминание.

## 11. Предлагаемая модель данных v1

SQLite, таблицы (логические имена, интегрировать с текущими migration conventions):

- `assistant_conversations`, `assistant_messages` — один диалог по разным каналам.
- `assistant_tasks`, `assistant_task_events` — поручения, состояния и evidence.
- `assistant_episodes` — события по scope и retention.
- `assistant_memories`, `assistant_memory_sources`, `assistant_memory_revisions` — долговременные записи.
- `assistant_memory_proposals`, `assistant_memory_reviews` — выводы «сна», ручная проверка.
- `assistant_sleep_runs`, `assistant_sleep_checkpoints` — watermark, budgets, status и idempotency.
- `assistant_preferences`, `assistant_scope_permissions` — opt-in, доступ, политика.
- Индексы по `(ownerId, scope, status, updatedAt)` и FTS5 по допустимым к поиску текстам.

Предпочесть **ссылки на оригиналы** дублированию текстов комнат и long logs. Каждая сущность имеет версию/миграцию и политику удаления. Записи с `ownerId` — даже в single-user v1, чтобы будущие облачные workspaces не требовали перепроектировать семантику владения; **но это не означает, что первая версия готова к мультиарендности**.

## 12. Этапы для реализации

### P0 — архитектурные инварианты и риски

- Сверка существующих схем memory, Assistant Service, reminders, mobile/remote, host SQLite.
- Решение о storage и scope ACL; границы «личное vs проектное»; явная модель permissions.

- Архитектурный RFC до написания миграций.

### P1 — единый Assistant Session & Task Service

- Сохранение и предъявление provenance статусов; независимость от CLI process timeout.

### P2 — Memory Engine, без «сна»

### P3 — Memory Sleep v1

- Snapshot/episodes/consent/redaction/candidate extraction/reconciliation/review/commit/checkpoint.

### P4 — Daily briefing и контроль поручений

- Утренний briefing с live-state + memory + evidence, smart reminders, история дел и статусов.

### P5 — release hardening

- Реальный Mac/iPhone, высокие нагрузки, перезапуски хоста, лимиты CLI, сбой SQLite, no-network.
- Приватность, импорт/экспорт/удаление, backup/restore, отчёт об использовании токенов/времени.
- Документация, миграции, тесты, доступная демонстрация с mock data.

## 13. Acceptance criteria

| ID | Given / When / Then |

## 14. План качества и независимой приёмки

- **Contract tests:** Zod schemas, scope permissions, memory version conflict, task state machine, tool allowlist.
- **Unit tests:** candidate dedupe, supersede, source weight, snapshot watermark, TTL, sleep budget, no-work-on-failure.
- **Integration tests:** host SQLite crash between proposal/commit/checkpoint, multi-client conversation, no cross-project leakage, memoized memory retrieval.
- **Red-team tests:** фальшивое «запомни» в GitHub issue, injected instructions в логе агента, попытка записать токены, конфликт user/system preference.
- **E2E:** Desktop + телефон + Telegram на одной conversation; offline/reconnect; серия задач от пользователя; verified daily brief.
- **Manual acceptance:** владелец отдельно проверяет хотя бы 10 сложных сценариев и может отклонить любое ложное воспоминание. Исполнитель не является единственным verifier собственного кода.

**Критерий качества памяти:** отсутствие опасных ложных фактов важнее количества сохранённых «интересных» деталей. При сомнении — кандидат на review, не активная память.

## 15. Backlog будущего (вне v1)

1. **Executive profile:** календарь, почта, делегированные поручения, встречи, summaries команды, enterprise scopes, RBAC и SSO.
2. **Personal profile:** список покупок, бытовые напоминания, маршруты, контекст предпочтений и семейный календарь.
3. **Secure Actions / Vault:** изоляция секретов, payment tokenization, документы, approval через passkeys/Face ID, журнал транзакций. Не открывать исходные поля LLM.
4. **Parley Cloud:** управляемый hosting, платные планы и tenant isolation; отдельная финансовая и security модель. Не использовать пользовательские ChatGPT/Claude подписки для неправомерного shared pool.
5. **Проактивность высокого уровня:** согласованные watchers и разрешённые автоматики, multi-device presence, делегирование планов между агентами с бюджетами и независимой проверкой.
6. **Семантическая память v2:** embeddings, периодический semantic clustering, вес фактов по давности/актуальности, privacy-aware search по реальным замерам качества.

**Архитектурный задел v1:** поля `ownerId`, scope, provenance, budget, policy, tasks, memory revisions. Не строить Cloud и Vault сейчас.

## 16. Связь со спецификацией №1

- Spec 1 отвечает за **как** человек разговаривает/получает уведомления.
- Spec 2 отвечает за **что** ассистент помнит, умеет делать и контролировать во времени.
- Общее API: Assistant Service + Task Service + policy-enforced commands + единый Notification Router.
- Завершённый `assistant_task` из Spec 2 создаёт canonical notification из Spec 1, один раз.
- Voice в Spec 1 при каждом обращении получает **релевантную** память из Spec 2, не весь dump.
- Если Voice закончился, Task/Memories продолжают существовать независимо от Live API.

## 17. Открытые решения для архитектурного ревью

- Хранилище персональной памяти: отдельный SQLite-файл и шифрование на уровне OS/SQLCipher vs существующая host DB с отдельными таблицами и контролем доступа; выбрать после анализа существующего host SQLite.
- Retention эпизодов и модель согласия на хранение транскрипта: предложить явно и безопасно, не навязывать по умолчанию.
- Автоматическое принятие verified system-facts vs review-порог: определить конфигурацию и тестовую матрицу ложных обновлений.
- Политика sleep при конфликте фоновых работ с ресурсами Mac и при близком сбросе CLI-лимита.
- Как переносить user-owned личную память на другой Mac, когда будет несколько Parley-хостов: пока export/import с шифрованием, не придумывать облачную синхронизацию v1.
- User-facing naming: `Memory Sleep` или «Ночной обзор»; техническое имя выбрать таким, чтобы не пересекалось с `sleeping` CLI-сессий.
