## 1. Goal and evidence boundary

Reduce the context and orchestration cost of related Parley tool calls by letting an agent discover a small API, run bounded code against authorized methods, and return a selected result. Preserve the original session identity, tool semantics, the human-selected policy boundary in §5.1, room rules, budgets, and capability coverage through explicit residual tools or provider classic fallback.

Two possible savings need separate measurements: fewer tool definitions exposed to the model, and fewer intermediate results returned to it. [Anthropic's example](https://www.anthropic.com/research/code-execution-with-mcp) motivates discovery and local result processing; its reported 150,000-to-2,000-token example is not a Parley measurement or forecast. The current Codex session already has a native code orchestration tool. A benchmark must therefore measure incremental Parley benefit against the deployed native baseline, including deferred tool discovery where present.

The work here is source inspection, measurement, and document production only. Provider billable input, cached input, output, hidden context wrapping, per-turn schema injection, actual monetary savings, latency changes, security isolation, and packaged runtime behavior are **not measured**. Never multiply the complete schema corpus by every turn and present the result as observed provider usage.

## 4. Proposed API and data contracts

Names below are proposed. Three small MCP declarations avoid embedding the full generated API in the execute schema:

```ts
code_search({ query, cursor?, limit? })
code_docs({ names, cursor? })
code_execute({ code, apiRevision })
```

`code_search` returns method names, short descriptions, effect class, availability, documentation revision, completeness, and pagination cursor; cap the serialized page at 8 KiB. `code_docs` returns selected `.d.ts` declarations, examples, effects, input constraints, output guarantees, and availability; at most five names and 16 KiB per page. Generated declarations appear on demand, never as an entire execute-tool description. Cursor semantics and errors must remain explicit.

The catalog is generated from the actual session's tool list, intersected with an explicit broker allowlist. It is not a second handwritten list of every tool. The initial proposed cohort is `get_map`, `read_room`, `read_guide`, `list_roles`, `backlog_list`. Later cohorts require individually accepted T11 migrations; documentation visibility is not execution permission. These are **business-read-only**, not guaranteed storage-pure: existing thread binding/audit may write metadata. `check_inbox` and `wait_for(inbox)` mark messages read and are excluded; the F3 design (m-7405/m-7406) admits them through a two-phase host inbox (peek, then an ack at the answer edge). `find_skill` has a miss counter; the F4 design (m-7375, m-7384) admits it as a read with an advisory side effect. Session creation, report, close, room decisions, attempt/plan mutations, memory changes, and browser methods are excluded. The F1 design (m-7387/m-7388) later admits room decisions, attempt/plan mutations, memory and backlog changes, room creation and membership, and `send_message`, each as a write under its consent gate.

The execution input is one async function, written as declaration-guided JavaScript using a JavaScript-compatible TypeScript subset:

```js
async () => {
  const result = await parley.get_map({ session: "s-01" });
```
