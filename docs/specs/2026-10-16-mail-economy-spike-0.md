**Выводы 0.2.**

1. Правила A1 работают: письма короче на 91 %, документы ушли в файлы, карта не растёт. Критерий «−35 % токенов писем» выполнен с запасом.
2. Критерий «−20 % входных токенов комнаты» **не выполнен**: −10 %, и в основном за счёт простоя Codex в A. Письма — 0,08 % входных токенов комнаты (4 тыс. из 5,3 млн). Токены комнаты = число ходов × контекст хода: ведущий 37–39 ходов по 90 тыс. — 3,3 млн, и длина писем на это не влияет.
3. Рычаги экономии, которых в спеке нет: (а) **число ходов** — каждое письмо, указатель и возврат `wait_for` будят агента на полный ход; «принял, жду» и опрос впустую стоят по 90 тыс. каждый; (б) **контекст хода** — 56 тыс. до первого действия (CLAUDE.md с OMC, гид, бриф, скиллы) и рост до 90–100 тыс. за ход. Уменьшить ходы и стартовый контекст — отдельная спека (см. спека, «Итоги спайка»).
4. Типизированные письма (A3) ради токенов не нужны: тело письма ничего не решает. Если делать — ради карточек в окне.
5. Для хоста ценность A1 остаётся: письма не раздувают карту (часть B).

**Вопрос.** Сколько входных токенов экономят правила A1 на реальной комнате при той же задаче и том же составе, и не хуже ли результат.

**Как.**

1. Задача — повторяемая и короткая: ревью одного документа или одного PR силами комнаты из трёх агентов (ведущий + два ревьюера), одинаковые провайдеры и модели в обоих прогонах. Результат — один файл-отчёт.
2. **Прогон A (как сейчас):** комната создаётся обычным способом, задача — одним письмом человека.
3. **Прогон B (с правилами):** то же, но письмо человека начинается с блока правил A1 (письма до 1200 символов; документы — файлами, в письме путь; без цитат; отвечать только на вопросы; комнату не перечитывать). Код не меняется — правило доставляется задачей, а не гидом; это нижняя оценка эффекта, гид действует сильнее.
4. Окно времени каждого прогона фиксируется: от создания комнаты до `report` ведущего.

**Что мерить.**

- Письма: число, символы, токены — скриптом 0.1 с фильтром по `work` и `at` в окне прогона.
- Токены сессий — из транскриптов провайдеров за окно прогона:
  - Claude и GLM: `~/.claude/projects/<slug проекта>/<id сессии>.jsonl`, записи с `usage` (`input_tokens`, `cache_creation_input_tokens`, `cache_read_input_tokens`, `output_tokens`); id сессии провайдера — `providerSessionId` в карте;
  - Codex: `~/.codex/sessions/**/rollout-*.jsonl`, записи `token_count`.
  - Скрипт ниже суммирует по сессии за окно. Альтернатива — ветка расхода токенов комнаты (`feat/room-token-usage`, worktree `modest-hofstadter-608d75`, не влита): её dev-сборка показывает те же цифры в окне.
- Качество: человек сравнивает два отчёта по одному списку вопросов (полнота, точность, лишнее). Если B хуже — правила переписать, не ослабляя.

**Критерий успеха.** Токены писем в B на ≥ 35 % меньше, входные токены сессий комнаты (сумма `input + cache_creation + cache_read`) на ≥ 20 % меньше, результат не хуже. Выход-токены сравниваются отдельно: правила должны их тоже снизить.

**Бюджет.** Два прогона комнаты на три агента; оценка по журналу расхода прошлых комнат заполняется перед запуском. Тесты и E2E не гоняются.

**Скрипт суммы токенов за окно** (`node usage-window.cjs <from ISO> <to ISO> <providerSessionId...>`):

## 0.3 Потолок письма на сервере

**Вопрос.** Проверяет ли MCP-сервер `maxLength: 4096` у `send_message`. По картам — нет: письма на 54 КБ прошли.

**Как.** Модульный тест в `core/src/mcp/tools.test.ts` рядом с тестами `send_message`: текст 4097 символов → ошибка с текстом про файл и путь; 1500 → письмо записано, в ответе предупреждение; 800 → без замечаний. Сейчас первый случай упадёт (письмо примется) — это и есть подтверждение дефекта; после A2 тест зелёный.

**Критерий.** Три теста зелёные после A2; `grep` по картам через две недели не находит писем агентов длиннее 4096.
