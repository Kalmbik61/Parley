# Диагностика и разгрузка хоста — дизайн

Дата: 2026-10-16. Статус: черновик на утверждение.

## Зачем

Parley лагает: комната создана, а её сессии стартуют через минуты; сообщение отправлено, а агент получает его позже; Chat показывает «Working…», когда ответ уже в терминале. Замер 2026-10-16: собранный хост (один процесс Node, без worker-потоков) ест 77 % CPU и ~490 МБ при ~15 живых сессиях CLI. Сессия, разбиравшая лаги, упёрлась в предел логов: «хост занят тяжёлым вычислением, каким — по логам не понять, нужен профиль».

Две задачи в одном документе, потому что первая — инструмент для второй:

- **A.** У каждого пользователя Parley должна быть кнопка, которая собирает один файл с логами хоста, картиной ресурсов и журналом задержек. Пользователь присылает файл автору, и случай разбирается без переписки.
- **B.** Хост перестаёт захлёбываться при 15–30 сессиях. Правки идут по цифрам из A, а не по догадкам. Переписывание на другой язык не рассматривается: Orca с теми же node-pty и `@xterm/headless` держит 200 сессий на Node за счёт ограничений и разделения, а не языка (см. память `orca-terminal-load-mechanisms-2026-10-16`).

## Что есть сейчас (факты из кода, origin/master 8099d2f6)

Локальный `master` на 20 коммитов отстаёт от `origin/master`; логи времени 0.13.1 (`timing.ts`, `loop-delay.ts`) есть только там. Работа ведётся от `origin/master`.

- Лог хоста: `packages/host/src/log.ts` — `appendFileSync`, одна JSON-строка на запись `{"time","level","msg",...data}`, ротация при 5 МиБ в `host.log.1`, одно поколение. Путь `~/.parley/host/host.log` (`paths.ts:19-27`), рядом `host.err` — stderr хоста без ограничения размера (`desktop/src/main/host-launcher.ts:101-115`). У Electron main своего лог-файла нет.
- Уже логируются: `создание сессии: время шагов`, `запуск сессии: время шагов` (`sessions-service.ts:692,786`), `лента: снимок` (`feed-service.ts:1141,1168`), `медленный запрос` при ≥ 1 с (`server.ts:206`), `хост: цикл событий запаздывал` раз в 60 с при max ≥ 250 мс (`loop-delay.ts:25`).
- Не логируются: время от spawn до готовности CLI; доставка сообщения в PTY (`pty/send.ts`, `type-and-submit.ts`); доставка письма комнаты будильником (`wake-service.ts:427`); первая дельта ленты после отправки. Показателей CPU/RSS хоста нет нигде; `monitorEventLoopDelay` пишет только в лог.
- RPC: NDJSON по unix-сокету, метод = zod-схема в `protocol/src/methods.ts` + тип результата + обработчик в `host/src/methods/*` + регистрация в `methods/index.ts` + `bridge.call` в окне; шаблон — `host.info`. Окно гейтит новые методы через `useHostSupports`.
- Строка статуса: `desktop/src/renderer/shell/StatusBar.tsx`; правая группа `:251-280` (внимание, связь, «Host is outdated», тумблер wake); поповер — `ProviderSegment` на Radix `Popover`, `side="top"`.
- PTY: каждый чанк синхронно пишется в headless xterm (`pty-manager.ts:163-177`), scrollback 5000 (`screen.ts:33`), снимок при `pty.attach` — полная сериализация; клиент с буфером > 4 МиБ отбрасывается с `pty.resync` (`methods/pty.ts:58-72`); `pause()/resume()` node-pty не используются.
- Лента: seed Claude читает весь JSONL-транскрипт через readline в главном потоке (`feed-service.ts:251,632,802`); Codex опрашивается раз в 2 с на каждую живую сессию (`:774`); контекст — раз в 5 с, лимиты — раз в 30 с.
- Окно умеет `shell.showItemInFolder` (`main/index.ts:586`), `app.getPath('downloads')`; zip-библиотек в зависимостях нет; Node в хосте 22.23, Electron 44 (Node ≥ 22), значит `zlib.crc32` и `deflateRawSync` доступны.

## Цели

1. Кнопка «Diagnostics» справа в строке статуса. Одно нажатие → zip в `~/Downloads`, показанный в Finder. Ничего не отправляется само.
2. По файлу видно: версии; сколько сессий и каких; CPU и память хоста и его детей (claude/codex) как в `ps`; лаг цикла событий; история этих показателей за часы, а не только момент.
3. По файлу видно задержки действий человека: запросил → исполнено, с длительностью, для создания комнаты и сессий, готовности CLI, отправки сообщения в Chat и в комнату, начала ответа.
4. Из того же меню записывается CPU-профиль хоста на 20 с и кладётся в архив — это ответ на «нужен профиль».
5. Хост при 15 живых, но бездействующих сессиях ест < 10 % CPU; p99 лага цикла событий < 50 мс; «отправил в Chat → текст набран в PTY» < 300 мс; «создать сессию → процесс запущен» < 2 с без worktree.

## Не-цели

- Телеметрия, автоотправка, сервер приёма логов.
- Лог-файл Electron main (кроме кольца RPC, см. A4).
- Профилирование окна/рендерера.
- Linux/Windows: архив собирается кроссплатформенно, но проверяется только на macOS.
- Переезд хоста на Go/Rust или вынос PTY в отдельный демон.

## Анти-цели

- Кнопка диагностики сама подвешивает окно или хост: сборка архива в main асинхронная и потоковая, `ps` через `spawn`, никаких `execSync`/`readFileSync` на мегабайтах.
- В архив попадают тексты сообщений, содержимое терминалов, ключи провайдеров или `providers.json` — никогда.
- Правки части B без измерения «до/после» тем же архивом.

## Ограничения

- Всё, что пишет хост, — в свои каталоги (`~/.parley/host/…`); архив — в `~/Downloads` по явному действию пользователя.
- Старый хост с новым окном: кнопка работает (логи + `ps`), часть «хост» в архиве помечена `host did not respond`, окно предлагает «Restart host…».
- Тексты UI по-английски; документация и комментарии — по-русски.
- Исполнение — мелкими кусками (Workflow на Sonnet), диф читает ведущий. Недельный лимит: необязательное откладывать.

## Часть A. Диагностический снимок

### A1. Кнопка

В правой группе `StatusBar.tsx` между «Host is outdated» и тумблером wake: сегмент с иконкой стетоскопа/жизненной линии и подписью `Diagnostics` (на узком окне — только иконка). Поповер `side="top"`, как у провайдеров:

- **Save diagnostics** — собирает архив сразу.
- **Record 20-second profile, then save** — запускает профиль хоста, показывает обратный отсчёт в самом сегменте («Profiling 12 s…»), по окончании собирает архив с профилем.
- Строка-подсказка: `Includes host logs, process list and timings. No message text, terminal output or keys. The file is saved to Downloads; attach it to a GitHub issue.`

Готово: toast «Diagnostics saved» с кнопкой **Show in Finder**. Та же команда — в палитре (`host.diagnostics`).

### A2. Состав архива `parley-diagnostics-YYYYMMDD-HHMMSS.zip`

| Файл | Откуда | Содержимое |
|---|---|---|
| `README.txt` | окно | что внутри, оговорка о приватности, куда прислать |
| `host.log`, `host.log.1`, `host.err` | файлы `~/.parley/host/` | как есть (до 10 МиБ логов + stderr) |
| `host-info.json` | RPC `host.diagnostics` | версии хоста/Node/платформы, pid, startedAt, uptime, состояние `health` (CPU %, память, лаг цикла событий текущего окна max/p99/mean, счётчики: `ptys` — живые PTY, `attached` — подписки на поток терминала, `feedSubs` — подписки на ленту, `works`, `rooms`, `clients`), список сессий: ref, provider, activity, pid, startedAt, attached да/нет; список файлов профилей и состояние профилировщика |
| `app-info.json` | окно | версии app/Electron/Chromium/OS/arch, число окон, DPR, аптайм окна, состояние связи с хостом, был ли ответ хоста |
| `processes.txt` | окно, `spawn('ps', ['-axo', 'pid,ppid,%cpu,%mem,rss,etime,comm'])` | дерево хоста и его потомков (фильтр по pid хоста и ppid-цепочке) + `uptime` (load average), ncpu, memsize. Только `comm` (исполняемый файл), без аргументов: в argv claude/codex лежат бриф сессии (`{prompt}`, `{systemPrompt}`), а у их потомков (MCP-серверы) — токены. Сопоставление pid → сессия берётся из `host-info.json` |
| `actions.jsonl` | окно, кольцо RPC (A4) | последние 1000 вызовов окна к хосту: время, метод, ms, ok/error |
| `host-*.cpuprofile` | `~/.parley/host/diagnostics/` | профили за последние 24 ч (A5) |

### A3. Строка состояния хоста в логе

Хост раз в 30 с пишет `host: состояние` с `{cpuPct, rssMb, heapMb, extMb, loop:{maxMs,p99Ms,meanMs}, ptys, attached, feedSubs, works, rooms, clients}` (тип `HealthSample` в протоколе). Лаг берётся из `monitorEventLoopDelay` за вычетом его разрешения 20 мс: гистограмма Node хранит интервал между срабатываниями таймера, и без поправки здоровый хост показывал бы «лаг» около 21 мс. `cpuPct` — из `process.cpuUsage()` дельтой к стене за окно. Строка ≈ 200 байт; при ротации 5 МиБ это сутки истории даже под шумом. Таймер `unref()`. Эта же функция отдаёт мгновенные значения для `host.diagnostics`.

Порог предупреждения лага цикла событий остаётся 250 мс/60 с (`loop-delay.ts`), но в строку состояния попадают max и p99 каждого 30-секундного окна, чтобы динамика была видна и без предупреждений.

### A4. Журнал задержек

Общая форма записей — обычные строки `host.log` с единым полем `op` и `ms`, чтобы их можно было выбрать одним grep. Добавляются там, где сейчас дыры:

| Момент | Где | Запись |
|---|---|---|
| CLI готов | `activity-service.ts`: первый хук после spawn (`hookedSince`) или `TerminalReady` у Codex | `op:"session.ready"`, `{ref, provider, readyMs}` от `handle.startedAt` |
| Сообщение в Chat | `pty/send.ts` → `type-and-submit.ts` | `op:"pty.send"`, `{ref, chars, queueMs, typeMs, enterMs, outcome}` — без текста. `queueMs = now − params.requestedAt`: обработчик в хосте синхронный до `pty.write`, поэтому ожидание в очереди цикла событий изнутри не видно; его даёт метка клиента |
| Письмо комнаты | `wake-service.ts:beginAttempt` | `op:"mail.deliver"`, `{roomId, to, letterId, sinceSentMs, mode:"pointer"\|"resume", ms, outcome}` |
| Ответ начался | `feed-service.ts:flush` | `op:"feed.firstDelta"`, `{ref, sinceSendMs}` — по метке `lastSendAt` сессии, которую ставит `pty/send`; пишется один раз на отправку |
| Комната создана | `rooms-service.ts:createHumanRoom` | `op:"room.create"`, `{roomId, members, ms}` |

**Метка `requestedAt`.** В `pty.send` (и `rooms.send`) добавляется необязательное поле `requestedAt` (мс эпохи, одна машина — одни часы). Рендерер ставит его в момент нажатия Send, то есть при постановке в `chat/chat-outbox.ts` и `room-outbox.ts`, а не при вызове `bridge.call`: outbox шлёт строго по одному и ждёт Enter предыдущего, и эта очередь — вероятное место жалобы «отправил, а агент получил позже». Старый хост поле отбрасывает (zod не strict), новый хост без поля пишет `queueMs: null`.

Сторона «запросил» — кольцо RPC в окне: `HostConnection.call` (`host-connection.ts:437`) кладёт в кольцо на 1000 записей `{t, method, ms, ok, ref?}` для всех методов. Так в архиве видна обработка каждого вызова со стороны main, а не только «медленный запрос» ≥ 1 с; очередь outbox до вызова видна через `queueMs` в логе хоста. `ms` у `pty.send` в кольце включает паузу перед Enter (`enterDelayMs`), поэтому для приёмки берётся разбивка из лога хоста, а не кольцо. Кольцо живёт в памяти main и попадает только в архив.

Создание комнаты из диалога — это N последовательных `sessions.create` и один `rooms.create` (`NewSessionOrRoomDialog.tsx:575-689`); по кольцу RPC и логу создания сессий складывается полная картина без отдельного таймера. Если по данным окажется, что последовательность — сама причина минутных задержек, параллельный запуск уходит в часть B как отдельный пункт.

### A5. Профиль CPU по запросу

Методы `host.profile.start {seconds ≤ 60}` и `host.profile.status`. Хост через `node:inspector` (`Session`, `Profiler.enable/start/stop`, интервал выборки 1 мс) пишет `~/.parley/host/diagnostics/host-<ts>.cpuprofile`; хранит последние 5 файлов. Пока профиль идёт, второй старт отвергается. Накладные расходы только на время записи. Файл открывается в DevTools Chrome (Performance → Load profile).

### A6. Сборка архива в окне

Метод в main `app:save-diagnostics {profile?: boolean}`:

1. При `profile` — `host.profile.start 20`, ждать статуса `done` (окно показывает отсчёт).
2. `host.diagnostics` с таймаутом 5 с; при таймауте — `host-info.json` = `{responded:false, timeoutMs:5000}`.
3. `ps`, `uptime`, `sysctl` через `spawn`, таймаут 5 с каждый.
4. Zip: свой минимальный писатель (`desktop/src/main/diagnostics/zip.ts`, deflate через `zlib.deflateRawSync` по файлам, `zlib.crc32`), без новых зависимостей — упаковка electron-vite/electron-builder не меняется. Крупные файлы читаются потоково, сжатие по кускам ≤ 1 МиБ, чтобы не держать 10 МиБ логов в памяти разом.
5. Запись атомарно (`atomic-file.ts`) в `~/Downloads`, затем `shell.showItemInFolder`.

### A7. Приватность

Остаются: пути проектов, имена комнат и сессий, названия провайдеров, имена исполняемых файлов из `ps` (без аргументов — см. A2). Никогда: тексты писем и сообщений, вывод терминалов, `providers.json`, ключи, переменные окружения. Строгое правило для новых записей A4: только длины и идентификаторы.

### A8. Совместимость

Окно гейтит новые методы через `useHostSupports('host.diagnostics')`; без них кнопка собирает архив из файлов и `ps`, а поповер показывает `Host is outdated — restart it for full diagnostics`. Старые логи читаются как есть.

## Часть B. Разгрузка хоста

### B1. Дешёвые ограничения — без профиля, каждый пункт отдельно

1. **Scrollback экрана хоста 5000 → 1000** (`screen.ts:33`). Снимок при `attach` сериализует 1000 строк вместо 5000; память сетки на сессию падает в разы. Scrollback xterm в окне не трогать: живой вывод после attach остаётся полным.
2. **Батчер PTY с потолком** (`output-batcher.ts`): кап 256 КиБ на чанк. Сейчас 16-мс батч без предела: залп вывода даёт одну гигантскую строку, одно `JSON.stringify` и риск упереться в `MAX_LINE_BYTES` 8 МиБ кадрирования. Сброс медленного клиента с `pty.resync` (`methods/pty.ts:58-72`) остаётся как есть, но пишет `op:"pty.clientDropped"` `{ref, client, queuedBytes}`, чтобы в архиве было видно, когда он случается. Пауза `pty.pause()` по образцу Orca отвергнута: `onData` кормит не только клиентов, но и headless-экран, разбор `TerminalReady` у Codex и `hasDraft()/text()`, которыми пользуются `pty.send` и будильник, — пауза из-за одного медленного окна заморозила бы состояние сессии для всех.
3. **Seed ленты Claude с хвоста** (`feed-service.ts:251`): читать последние 16 МиБ транскрипта (как у Codex `ROLLOUT_SEED_MAX_BYTES`), выровняв на границу строки, а не весь файл.
4. **Опрос Codex адаптивный** (`feed-service.ts:774`): 2 с только для сессий с подписчиком ленты или в состоянии `working`; остальным 10 с.

Каждый пункт — измеряется архивом «до/после» на машине автора при тех же ~15 сессиях (строка `host: состояние`; для 3 — `лента: снимок` `seedMs`).

### B2. Структурные — только по профилю

Делается то, что в профиле A5 занимает ≥ 20 % времени главного потока. Кандидаты в порядке вероятности:

1. **Экраны PTY в worker_threads.** `pty/screen.ts` становится клиентом воркера: один воркер держит все headless-терминалы (или N воркеров по хешу ref); главный поток шлёт чанки `postMessage`, снимок — запрос с seq, воркер отвечает после записи всех чанков до этого seq. Разбор заголовка Codex остаётся в главном потоке (дешёвая regex) или переезжает вместе с экраном.
2. **Разбор ленты в воркере.** `feedFromTranscript` и разбор rollout Codex — чистые функции из `@parley/core`; seed и опрос выполняются в воркере, в главный поток возвращаются готовые items.
3. **Широковещание снимков works.** Если профиль показывает `JSON.stringify` больших снимков всем клиентам — слать дельты или реже.
4. **Сверки живости работ внахлёст** (вывод сессии по лагам, PR #49) — отдельная правка, если профиль подтвердит.

### B3. Приёмка

Из цели 5, проверяется архивом на машине автора и E2E на мок-сессиях:

- 15 живых бездействующих сессий: `cpuPct` в `host: состояние` < 10 (сейчас 77).
- `loop.p99Ms` < 50 за 10 минут с 15 сессиями.
- `op:"pty.send"` `queueMs + typeMs` < 300 для одиночного сообщения при пустом outbox.
- `создание сессии: время шагов` `totalMs` < 2000 без worktree.
- `op:"session.ready"` `readyMs` < 5000 для Claude.

## Порядок и бюджет

В этот план входят **A целиком и B1.1–B1.2**. B1.3–B1.4 и B2 — за порогом: они выбираются по первому архиву с машины автора и получают свою спеку-план.

1. **A** (A3 → A4 → A5 → A1/A2/A6), ветка `feat/host-diagnostics` от `origin/master`. Из dev-сборки с одним только A снимается **baseline-архив** на машине автора при ~15 сессиях и отдаётся разбору лагов.
2. **B1.1 и B1.2** — отдельные ветки и PR от той же базы, каждая сливается только после baseline; эффект каждой сверяется своим архивом «после».
3. **Профиль** из baseline → выбор пунктов B2 и B1.3–B1.4 → отдельная спека.

Релиз с A — минорная версия (новые методы протокола); B1.1–B1.2 могут войти в него же, если baseline снят до слияния.

## Мои выборы, не обсуждавшиеся явно

- Архив — zip в `~/Downloads`, а не папка и не диалог сохранения.
- Zip своими силами без зависимостей (из-за того, что runtime-зависимости desktop — только workspace-пакеты).
- Кольцо RPC в окне на 1000 записей — как сторона «запросил» вместо отдельных таймеров в диалогах.
- Профиль 20 с по умолчанию, предел 60 с, хранить 5 последних.
- `providers.json` и настройки в архив не входят вовсе.
- Строка состояния раз в 30 с (а не 10): точность динамики против ротации лога за сутки.
- Scrollback хоста 1000 (как у Orca), не 2000.
- Пороги приёмки в цели 5 — ориентир, а не контракт: уточняются по первому архиву.
- `processes.txt` без аргументов процессов (`comm`), чтобы бриф сессии и токены MCP не попадали в архив.
- Метка `requestedAt` в `pty.send`/`rooms.send` как сторона «запросил» — необязательное поле протокола, совместимое со старым хостом.
- Пауза PTY по образцу Orca отвергнута; вместо неё потолок батчера и лог сброса клиента.
- Объём плана: A + B1.1 + B1.2; остальное после baseline-архива.
