# План реализации: тема TUI — палитра, роли, заливка

Дата: 2026-09-22. Статус: черновик, ждёт запуска. Основание:
`2026-09-22-tui-theme-design.md` (дизайн, согласован по разделам).

> **Как гонять.** Семь кусков, каждый — 1–2 задачи плюс отдельная фаза
> проверки. Агентам `model: 'sonnet'`. Между кусками — стоп, показ итога
> пользователю, и только потом следующий. Внутри задачи: красный тест →
> минимальный код → зелёный → коммит.

**Правила проверки** (из опыта прогонов по рамкам):

- фаза проверки — две линзы с разными углами, каждой сказано исходить из того,
  что дефект есть;
- линзам задавать **разные имена временных файлов**: в одном рабочем дереве
  они видят файлы друг друга и принимают это за постороннее вмешательство;
- проверяющий сверяет код **с планом** и ошибку самого плана структурно не
  видит — диф всё равно читает человек;
- тесты на границы просить **инвариантом по диапазону**, а не одним числом;
- `tsc --noEmit` в `packages/tui` не смотрит тестовые файлы: «tsc чисто» не
  значит «типы в тестах целы».

**Команды на каждом куске:** `pnpm build`, `pnpm test`, `pnpm lint`.

**Сквозной инвариант кусков 1–3:** при `pinTheme(1)` кадр совпадает с
сегодняшним знак в знак. Если поехали чужие тесты — поехал план, а не тест.

## Кусок 1. Реестр тем и роли

Две задачи. Ничего не подключено: картинка не меняется, все существующие тесты
обязаны остаться зелёными без правок.

### A. Палитры, роли, контраст

**Файлы:** новые `packages/tui/src/theme/palettes.ts`, `theme/roles.ts`,
`theme/contrast.ts`, `theme/index.ts`; тесты `theme/roles.test.ts`,
`theme/contrast.test.ts`. В `packages/tui/package.json` — прямая зависимость
`chalk` (`^5`, та же версия, что тянет Ink).

**Что появляется:** `Palette` из 14 слотов плюс `kind` (дизайн 3.1), пять
палитр по таблице 3.3, `roles(palette, level)` с тремя ветками (4.1),
`theme()` / `applyThemeConfig(name, level?)` (3.4). Роли отдают **пропсы Ink**
(`{ color?, backgroundColor?, dimColor? }`), а не строки; отдельно флаг
`fills: boolean`.

**Приёмка:**

- уровни 3 и 2: у всех ролей hex из своей палитры, `fills === true`;
- уровень 1: ни одного `#` ни в одной роли ни в одной палитре — только имена
  ANSI и `dimColor`, `fills === false`;
- уровень 0: все роли — пустой объект, `fills === false`;
- `terminal` на любом уровне равен ветке уровня 1;
- неизвестное имя в `applyThemeConfig` — молча дефолт (`mocha`): валидация
  имени живёт в core, TUI от неё не падает;
- контраст — инвариант по всем пяти палитрам: `fg.default` и `fg.second` не
  ниже 4.5:1 против `bg.panel`, `bg.sidebar` и `bg.overlay` и не ниже 3:1
  против `bg.selection`; `fg.muted`, `fg.accent` и три `status.*` — не ниже
  3:1 против всех четырёх фонов (дизайн 7.2);
- иерархия ступеней: контраст между `text` и `subtext` и между `subtext` и
  `muted` не ниже 1.2:1 в каждой палитре — иначе палитра проходит контраст,
  слив три ступени текста в одну.

### B. Добивка и фиксация уровня в тестах

**Файлы:** новый `packages/tui/src/theme/fill.ts`, тест `theme/fill.test.ts`;
новый `packages/tui/test/theme-env.ts`; `packages/tui/vitest.config.ts`
(`setupFiles` получает `./test/theme-env.ts`).

**Что появляется:** `pad(used, width)` переезжает из `sidebar.tsx:212` в
`fill.ts` (в сайдбаре остаётся импорт, поведение то же); `fillLine(text, width)`
— строка ровно нужной ширины; `pinTheme(level)` по образцу
`pinUnicodeGlyphs()`, в общий setup ставится `pinTheme(1)`.

**Приёмка:** `pad` ведёт себя как прежде на вырожденных значениях
(`used > width`, `width = 0`); `fillLine` считает ширину по колонкам, а не по
длине строки (широкие символы и `…`); после правки setup весь `pnpm test`
зелёный **без единой правки существующих тестов**.

**Линзы:** (1) «контраст врёт» — формула яркости должна быть настоящей
sRGB-линеаризацией, а тест обязан падать на заведомо плохой паре, подсунутой
руками; (2) «hex протекает» — на уровнях ≤1 ни одна роль не отдаёт hex и ни
один компонент ещё не зовёт `theme()`.

## Кусок 2. Настройка темы

Две задачи. Значение ходит от файла до оверлея, но цвета ещё никто не читает.

### C. Ключ `theme` в core

**Файлы:** `packages/core/src/config.ts`, `packages/core/src/index.ts`
(экспорт), тест `packages/core/src/config.test.ts`.

**Что появляется:** `THEME_NAMES` (шесть строк), поле `theme: string` в
`HarnasConfig` с дефолтом `'mocha'`, `HARNAS_THEME` в `ENV_NAMES`, проверка
через тот же `take()`.

**Приёмка:** имя из файла и из окружения; неизвестное имя — дефолт плюс
`warning` вида «`theme: ожидается одно из …`», остальные поля при этом целы;
окружение перекрывает файл и попадает в `fromEnv`.

### D. Применение и строка в оверлее

**Файлы:** `packages/tui/src/use-config.ts`, `packages/tui/src/overlays.ts`
(`SETTINGS`, ширина колонки значения), `packages/tui/src/use-overlays.ts`
(`←`/`→` на строке темы); тесты `use-config.test.tsx`, `overlays.test.ts`,
`use-prefix-input.app.test.tsx` или `app.test.tsx` — один сквозной.

**Что появляется:** `applyThemeConfig(loaded.theme)` рядом с
`applyGlyphsConfig` при загрузке и в `update`; строка `theme` в оверлее
настроек; `←`/`→` листают значения по кругу и сразу пишут файл, `Enter` на этой
строке делает шаг вперёд (иначе строка выглядит мёртвой).

**Приёмка:** `SETTING_VALUE` расширяется с 7 до 12 — `tokyo-night` не должен
разъезжать колонку; строка не длиннее `PICKER_WIDTH`, хвост усекается штатно;
перекрытая `HARNAS_THEME` строка тусклая и не листается; смена темы применяется
без перезапуска.

**Линзы:** (1) «оверлей поехал» — проверить ширины строк оверлея на самом
длинном имени и самой длинной подсказке; (2) «состояние разошлось» — файл,
состояние и `theme()` после `update` говорят одно и то же, а ошибка записи не
меняет ни состояния, ни цвета.

## Кусок 3. Роли вместо имён ANSI

Одна задача, самая широкая по файлам и самая скучная по смыслу. Картинка не
меняется — это и есть приёмка.

**Файлы:** `glyphs.ts` (`statusColor`, `selectionProps`), `components/`:
`sidebar.tsx`, `panel.tsx`, `overlay.tsx`, `status-bar.tsx`, `thread.tsx`,
`activity-dot.tsx`, `root.tsx`; правится тест
`components/sidebar-selection.test.tsx`.

**Что появляется:** каждый литерал цвета заменяется ролью из `theme()`;
`borderColor` активной и неактивной зоны берёт `border.active` / `border.idle`;
`dimColor` остаётся только тем, что отдала роль.

**Приёмка:**

- при `pinTheme(1)` все кадры совпадают с прежними знак в знак — ни один тест,
  кроме `sidebar-selection`, не правится;
- `grep -rn "'cyan'\|'magenta'\|'green'\|'yellow'\|'red'\|blackBright"` по
  `packages/tui/src` не находит ничего вне `theme/`;
- `sidebar-selection` проверяет роли на двух уровнях: 1 — прежние коды, 3 —
  hex выбранного ряда и рамки.

**Линзы:** (1) «цвет потерялся» — сверить каждую строку таблицы 6.2 дизайна с
кодом: не пропала ли роль там, где цвет был; (2) «dim остался» — найти места,
где `dimColor` жёстко зашит мимо роли.

## Кусок 4. Заливка зон

Одна задача плюс тесты. Первый кусок, который видно глазами.

**Файлы:** `components/sidebar.tsx`, `components/overlay.tsx`,
`components/status-bar.tsx`, `components/panel.tsx` (карточка); тесты — новый
`components/theme-fill.test.tsx` с `FORCE_COLOR=3` и `pinTheme(3)`.

**Что появляется:** каждая строка блока — `<Text backgroundColor>` шириной в
блок, включая пустые; фон берётся ролью зоны; всё это только при
`theme().fills`.

**Приёмка:**

- при уровне 3 каждая строка блока сайдбара ровно ширины блока и несёт фон —
  инвариант по всем строкам кадра, а не по одной;
- пустые строки блока тоже залиты;
- плашка `new` несёт фон только под текстом и до ширины не добивается;
- при `pinTheme(1)` добивки нет вовсе: длина строк как сегодня;
- оверлей поверх сайдбара не оставляет непокрашенных дыр по краям.

**Линзы:** (1) «дыра в заливке» — искать строки, которые рисуются мимо общей
добивки (усечение, `…`, широкие символы, пустая ветка `map`); (2) «ширина
разъехалась» — при `sidebarWidth` на границах (минимум, очень большая) заливка
не должна переносить строку.

## Кусок 5. Зона агента

Одна задача плюс тесты. Самый рискованный кусок: чужой вывод.

**Файлы:** `components/terminal-view.tsx`; тесты
`components/terminal-view.test.tsx` (там уже стоит `FORCE_COLOR`).

**Что появляется:** в `styleProps` подстановка `fg.default` / `bg.agent` для
ячеек без своего цвета и фона; добивка хвоста строки до ширины панели и пустых
строк ниже `snapshot.rows`. `pty/terminal-buffer.ts` не трогается.

**Приёмка:**

- ячейка без фона получает `bg.agent`, ячейка с фоном гостя остаётся как есть;
- ячейка без цвета получает `fg.default`, окрашенная гостем — не трогается;
- хвост строки и строки ниже `snapshot.rows` залиты;
- `withCursor` жив: каретка на подставленных цветах инвертируется и на обычной,
  и на уже инверсной ячейке;
- при `pinTheme(1)` вывод панели совпадает с сегодняшним.

**Линзы:** (1) «гость перекрашен» — найти случай, где подстановка накрыла то,
что гость задал сам (в том числе `inverse` и `dim`); (2) «панель поехала» —
добивка не должна менять число строк и ширину при узкой панели и широких
символах.

## Кусок 6. Монохромный жёлоб

Одна задача плюс тесты.

**Файлы:** `glyphs.ts` (глиф `cursor`: `›`, в ASCII `>`), `theme/index.ts`
(выбор ряда одной функцией), `components/sidebar.tsx`,
`components/overlay.tsx`; тесты с `pinTheme(0)`.

**Что появляется:** при уровне 0 списки получают колонку слева в один знак:
маркер у выбранной строки, пробел у остальных; у двустрочного ряда маркер на
первой строке. Полезная ширина текста — `width - 1`.

**Приёмка:** при уровне 0 маркер стоит ровно у выбранного ряда и ровно на одной
его строке; в кадре нет ни одного ANSI-кода; при уровнях ≥1 жёлоба нет и ширина
прежняя; усечение считает уменьшенную ширину, а не прежнюю.

**Линзы:** (1) «жёлоб протёк» — уровень ≥1 не должен получать колонку ни в
одном списке; (2) «ширина не сошлась» — усечение и `…` на границе ширины при
включённом жёлобе.
