## 1. Зачем

Сессии одной работы уже знают друг о друге через карту и могут обмениваться
письмами, но письмо лежит в `map.json`, пока адресат сам не позовёт
`check_inbox`. Агент, который закончил ход и ждёт ввода у промпта, письма не
увидит никогда; агент-отправитель либо блокирует свой ход в `wait_for`, либо
теряет ответ. Разговора двух коллег над одной задачей из этого не выходит, и
человек видит переписку только по кусочкам: бейдж `▤N`, строка статуса, секция
ВХОДЯЩИЕ в деталях одной сессии.

Эта итерация делает три вещи:

1. письмо доходит до адресата само, штатным механизмом Claude Code (channels),
   и адресат отвечает без участия человека;
2. переписка поддерева одной родительской сессии видна человеку целиком в
   панели треда справа от панели агента, с отдельным списком решений;
3. сессии знакомятся с коллегами в брифе и могут запускаться как именованные
   агенты Claude Code проекта.

Юридическая рамка не меняется: стоковый `claude` из PATH, документированный
флаг, наш собственный MCP-сервер. `~/.claude` по-прежнему только читается
(`stat` файла агента), учётные данные не открываются.

## 3. Модель данных и инструменты

### 3.1 Письмо

```ts
export type MessageKind = 'note' | 'question' | 'decision';

export interface Message {
  id: string;
  from: string;
  to: string;               // одна сессия, как раньше
  at: string;
  text: string;
  kind: MessageKind;        // на диске может отсутствовать (карты до 2026-09-08):
                            // parseMap подставляет note, читатели дефолта не знают
  readAt: string | null;    // ставит только check_inbox или wait_for, как сегодня
  deleted?: boolean;
}
```

Нормализация живёт в `parseMap` рядом с `idle → active` и `pid ??= null`
(решение D10): один читатель карты подставляет дефолты, остальные видят
обязательные поля. Файл на диске получает новые поля при первой мутации, как
и с `idle`.

`question` — «жду ответа», `decision` — «мы договорились», `note` — всё
остальное. Единственное новое поле — `kind`: сторож канала (4.2) карту не
пишет, поэтому `readAt` по-прежнему значит «агент забрал письмо инструментом»,
а не «мы его отправили» (решение D16).

### 3.2 Сессия

```ts
export interface WorkSession {
  // ...как раньше
  /** Имя агента Claude Code проекта; null — обычная сессия. */
  agent: string | null;    // на диске может отсутствовать: parseMap подставляет null
}
```

Поле и всё, что с ним связано (5.1), — задача D (раздел 9), независимая от
разговора.

### 3.3 Инструменты

| Инструмент | Изменение |
|---|---|
| `send_message(to, text, kind?)` | `kind` из трёх значений, по умолчанию `note`; другое значение — ошибка с перечнем. Проверки отправителя и получателя как раньше. Потолок (4.7): сверх него — ошибка с текстом, что делать |
| `spawn_session(provider, label, task, contextFrom, agent?)` | `agent` — имя агента; проверка по 5.1. Провайдер, в шаблоне запуска которого нет подстановки `{agent}`, — ошибка «провайдер агентов не принимает» |
| `check_inbox()` | Поведение не меняется; в ответе у письма появляется `kind` |
| `wait_for("inbox")` | Поведение не меняется: писем не помечает, как сегодня. Сторож канала карту не пишет, и переписывать семантику незачем (решение D16) |
| `get_map`, `report`, `read_guide` | Сигнатуры не меняются; в карте видны `kind` и `agent` |

Инструментов удаления, правки или рассылки писем нет. Ответ `messageView`
дополняется полем `kind`.

### 3.4 Тред выводится, а не хранится

Тред сессии P — письма, у которых и отправитель, и получатель лежат в
поддереве P: сама P и её потомки по `parent`. Решения треда — его письма с
`kind: decision` по времени. Ни нового поля в карте, ни файла.

Группа, которую показывает панель и знает бриф, — «тред сессии S»:

- у S есть родитель — поддерево родителя (родитель, братья, S, потомки);
- S корень с детьми — её собственное поддерево;
- S одинокий корень (без родителя и детей) — вся работа: все сессии, все письма.

Чистая функция `threadOf(map, sessionId)` в `core/work/thread.ts` возвращает
владельца (`sessionId` или `null` для всей работы), участников и письма по
времени. Её используют бриф, панель и события строки статуса. Удалённая сессия
в письмах остаётся, участником не считается.

Там же живёт `participantLabel(map, id)` — единственное место, где id сессии
превращается в подпись: ярлык у известной, `<id> (удалена)` у той, чей id
в `deletedSessions` (ярлыка удалённой в карте не остаётся — только id), голый
id у чужого (решение D9). Её зовут бриф, события
строки статуса, детали (`overlays.ts`) и вид треда; локальные карты ярлыков в
`overlays.ts` и `work-events.ts` заменяются ею той же правкой.

## 4. Доставка через channel

### 4.1 Что это

Channels — механизм Claude Code (research preview): MCP-сервер, объявивший
`capabilities.experimental['claude/channel']`, шлёт клиенту уведомление
`notifications/claude/channel`, и оно попадает в контекст модели тегом
`<channel source="<имя сервера>" ...>`. События копятся, пока агент занят, и
приходят пачкой на границе хода; агент у промпта получает событие и начинает
ход сам. Диалог разрешения событие не задевает. Клиент уведомления не
подтверждает: если сервер не зарегистрирован как channel, событие молча
отбрасывается. Документация: `code.claude.com/docs/en/channels`,
`.../channels-reference`. Документация описывает поведение клиентов 2.1.211+
и 2.1.234+; локальный `claude` 2.1.263 подходит.

### 4.2 Кто пушит

Сервер `harnas-mcp` **получателя** — он и так один процесс на сессию и умеет
следить за `map.json`. При `HARNAS_CHANNEL=1` в окружении и непустом
`HARNAS_SESSION_ID` сервер объявляет `capabilities.experimental['claude/channel']
= {}` и `instructions` (4.5), а после `oninitialized` запускает сторож
входящих — цикл поверх существующего `waitForMap` (решение D8), без нового
примитива и без копии его логики `fs.watch` плюс опрос.

**Сторож звонит, а не приносит письмо** (решение D16). Уведомление говорит,
что пришло и от кого, но не несёт текста и **не трогает карту**: письмо
забирает сам агент своим `check_inbox`, как сегодня. Отсюда `readAt` остаётся
честным, `▤N` гаснет только когда агент действительно прочитал, потеря письма
при заблокированном channel невозможна, а гонки сторожа с `check_inbox` и
`wait_for` не существует.

```
сторож (один на процесс, модуль core/mcp/inbox-watch.ts) — только читает карту
┌──────────────────────────────────────────────────────────────────────────┐
│ while (!stopped)                                                          │
│   found = await waitForMap(map, probe, LONG, pollMs)                      │
│           probe: письма to === me && readAt === null && id ∉ rung         │
│                  (пусто → null: ждём дальше)                              │
│   for letter of found:                                                     │
│     rung.add(id)                      ← звоним про письмо один раз        │
│     await notification(channel)       ← сорвалось: rung.delete(id),       │
│                                          позвоним на следующем проходе    │
└──────────────────────────────────────────────────────────────────────────┘

состояния письма (карту меняет только агент своими инструментами)
  непрочитано ──notification (звонок)──▶ непрочитано, звонок сделан
       │                                        │
       └──────check_inbox / wait_for────────────┴──▶ прочитано (readAt)
```

Уведомление:

```
notifications/claude/channel
  content: «новое письмо от <ярлык> (<kind>): позови check_inbox»
  meta: { message_id, from, from_label, kind, unread }
```

`unread` — сколько непрочитанных у этой сессии на момент звонка: агент видит,
что один `check_inbox` заберёт всё. Ключи `meta` — только идентификаторы
(буквы, цифры, подчёркивание), иначе Claude Code их молча выбросит. Множество
`rung` живёт в памяти процесса и гасит повторные звонки; после перезапуска
процесса непрочитанное письмо позвонит ещё раз, и это правильно — агент его
так и не забрал. Та же схема идёт комментарием в шапку модуля сторожа
(решение D7).

### 4.3 Согласование с pull

Согласовывать почти нечего: сторож карту не пишет, а `check_inbox` и
`wait_for` работают как сегодня. Три следствия:

- пока висит `wait_for("inbox")`, сторож не останавливается — звонок агенту
  придёт вместе с результатом ожидания; лишнего письма это не создаёт, потому
  что письмо в карте одно;
- звонок про письмо, которое агент уже забрал `check_inbox` в том же ходу,
  даёт один пустой `check_inbox` — принятая цена простоты;
- `rung` не переживает перезапуск процесса: непрочитанное письмо позвонит
  снова, что и требуется.

### 4.4 Включение

- `config.json`: `channelPush: true` по умолчанию; переменная
  `HARNAS_CHANNEL_PUSH` (`0`/`1`). Там же `messageRate` (4.7) и `threadWidth`
  (6.1). Загрузчик в core, читают и TUI, и CLI.
- **Проба версии** (решение D19): при старте харнесс один раз зовёт
  `claude --version`; ниже минимума, установленного спайком (раздел 9), push
  выключается сам — ни флага, ни `HARNAS_CHANNEL` — и строка статуса один раз
  показывает `⚑ push выключен: claude <версия> младше <минимума>`. Иначе
  каждый запуск падал бы с «unknown option», а причина была бы видна только в
  панели. Проба не удалась (бинаря нет, таймаут) — push остаётся включённым,
  поведение как сегодня.
- `mcp/<id>.json`: при включённом push в `env` сервера добавляется
  `HARNAS_CHANNEL: "1"`. TUI пишет файл при каждом запуске и возобновлении
  (`planLaunch`/`planResume`), CLI — вместе с печатью команды.
- Реестр: у записи Claude в `args` и `resumeArgs` добавляется пара
  `'--dangerously-load-development-channels', '{channel}'`; подстановка
  `channel` = `server:harnas` (имя из `MCP_SERVER_NAME`) при включённом push,
  иначе `undefined`, и `substituteArgs` выбрасывает пару целиком, как сейчас
  делает с `--mcp-config`. Регулярное выражение `PLACEHOLDER` и тип
  `RunnerSubstitutions` в `providers.ts` закрыты списком — обе подстановки
  (`channel`, `agent`) добавляются туда же, иначе они молча не сработают.
  Флаг скрыт из `claude --help`, но принимается.
- `providers.json` заменяет `args` целиком: пользовательский оверрайд без
  `{channel}` выключает push для этого провайдера. Это законно, но молча,
  поэтому при включённом `channelPush` и отсутствии `{channel}` в оверрайде
  харнесс один раз пишет в строку статуса `⚑ providers.json без {channel}:
  push выключен`.
- Codex и GLM: ни `HARNAS_CHANNEL`, ни флага — pull, как сейчас.
- `harnas-core work session new` печатает команду с флагом и конфиг с
  переменной: сессия из терминала получает push наравне с сессией панели.

### 4.5 Что видит агент

Звонок тела письма не несёт (решение D16): агент сам начинает ход, а в
контексте появляется тег со звонком — `source` это имя сервера из конфига,
остальные атрибуты — ключи `meta`, внутри тега `content` уведомления. Текст
письма агент забирает `check_inbox` сам:

```
<channel source="harnas" message_id="m-03" from="s-01" from_label="план" kind="question" unread="1">
Новое письмо от план (question): позови check_inbox.
</channel>
```

`instructions` сервера (доставляются при подключении; в коде —
`CHANNEL_INSTRUCTIONS` в `core/mcp/tools.ts`):

> Письма коллег по этой работе объявляются тегом `<channel source="harnas">`:
> в нём `from` — id сессии-отправителя, `from_label` — её роль, `kind` — вид
> письма. **Текста письма в теге нет**: увидел тег — позови `check_inbox`, он
> отдаст все непрочитанные разом.
> Отвечай `send_message(to=<from>)` **только на `question`**; `note` и
> `decision` ответа не требуют, «спасибо» и «принято» не пишут. Договорённость
> фиксируй одним письмом с `kind: decision` тому, с кем договорился.
> Про письмо звонят один раз; `check_inbox` и `wait_for("inbox")` — страховка,
> если канал молчит.

### 4.6 Слабое место

Если политика организации блокирует channels, флаг перестанет приниматься или
сервер по любой причине не зарегистрирован как channel, Claude Code отбросит
звонок молча, и сервер об этом не узнает.

Со «звонком» (решение D16) это перестало быть слабым местом: письмо остаётся
непрочитанным в карте, `▤N` его показывает, `check_inbox` и `wait_for`
отдают его как раньше. Потерять письмо нельзя, теряется только автоматическая
побудка — то есть поведение откатывается ровно к сегодняшнему. Отдельный гейт
по `getClientCapabilities()` не нужен и не делается; сама функция логируется
в stderr сервера в спайке (раздел 9) как диагностика.

Что остаётся:

- стартовый баннер агента показывает регистрацию channel или причину отказа
  («blocked by org policy»), он виден в панели;
- признак неработающего push для человека — письма, которые висят
  непрочитанными, пока адресат жив и не занят;
- `channelPush: false` и проба версии (4.4) возвращают чистый pull;
- `wait_for` отправителя по таймауту вернёт `running`, и гид велит агенту
  обратиться к человеку.

Спайк канала — шаг 0, до всех задач (решение D17, раздел 9).

### 4.7 Потолок переписки

Хендофф проекта предупреждал: прямой чат агентов «разъезжается и деньги
горят». С push каждое письмо стоит хода адресата, и два вежливых агента могут
переписываться, пока не кончится лимит подписки (решение D4). Две защиты:

- **Этикет** во всех четырёх текстах (4.5, 5.2, 5.3): отвечать только на
  `question`; `note` и `decision` ответа не требуют; на вопрос — один ответ.
- **Скользящее окно `messageRate`** в `send_message` (решение D20): перед
  записью сервер считает письма с `from === me` за последний час по полю `at`
  всей карты, без привязки к треду; если их уже `messageRate` (по умолчанию 20
  в час, минимум 1, `config.json` и `HARNAS_MESSAGE_RATE`), письмо не
  создаётся, а ответ инструмента объясняет: «слишком часто: N писем за час;
  отчитайся `report` и обратись к человеку». Окно отличает петлю (десятки
  писем за минуты) от честной долгой работы (несколько заметок за часы) и
  восстанавливается само, в отличие от пожизненного счётчика. Состояния нет:
  всё выводится из карты. TUI считает то же условие и один раз показывает
  `⚑ слишком частые письма · <ярлык>` с источником в этой сессии.

## 5. Роли и бриф

Раздел целиком — задача D (раздел 9): она независима от разговора и
принимается отдельно (решение D3).

### 5.1 Агент Claude Code как роль

`agent` — имя файла `.claude/agents/<name>.md` в проекте или
`~/.claude/agents/<name>.md`. Проверка при создании сессии: `stat` обоих путей,
содержимое не читается; нет ни одного — ошибка с перечнем имён, найденных в
обоих каталогах (только имена файлов). Проверка живёт в core
(`work/agents.ts`), её зовут `spawn_session` и CLI `--agent`.

Запуск: подстановка `agent` и пара `'--agent', '{agent}'` в `args` и
`resumeArgs` записи Claude; без значения пара выпадает. По документации
`--agent` совместим с `--append-system-prompt`, `--mcp-config`, `--settings`,
`--resume`; живая проверка — раздел 9.

Оговорка в гиде и README: определение агента с ограниченным списком `tools`
обязано включать `mcp__harnas__*`, иначе роль не сможет ни писать коллегам, ни
отчитаться. Харнесс это не проверяет: файл агента он не читает.

В TUI пикера агентов нет: `prefix c` и `prefix C` стартуют мгновенно, диалога у
них нет, и заводить его ради одного поля не стоит. Имя агента видно в деталях
(`ctrl+q i`, поле АГЕНТ) и в карточке `pending` перед запуском.

### 5.2 Бриф: знакомство с коллегами

`buildBrief` получает два раздела между «Контекст» и «Правила»:

```
## Коллеги
- s-01 — план (родитель, агент planner): active
- s-03 — ревью: pending

## Решения треда
- 12:42 план: «миграции отдельным PR»
```

Коллеги — участники `threadOf(map, newSessionId)` без самой сессии, с ролью,
пометкой родителя, именем агента (если есть) и статусом. Решения — решения
того же треда. Пустые разделы не печатаются. Правило 2 брифа переписывается:

> Письма коллег приходят сами; на `question` отвечай тому, кто спросил, через
> `send_message`, и не заканчивай ход с неотвеченным вопросом; на `note` и
> `decision` не отвечай; договорённость помечай одним письмом `kind: decision`.

Это одинаково для сессий с агентом и без.

### 5.3 Системная вставка и гид

Вставка остаётся в бюджете двенадцати строк: строка `send_message` получает
виды письма, строка `check_inbox` становится «письма коллег приходят сами как
`<channel source="harnas">`; отвечай `send_message` только на `question`;
`check_inbox` — страховка». Число строк не растёт.

`read_guide` получает раздел «Как разговаривать»: что такое тред, три вида
писем, этикет (отвечать на вопрос в том же ходу, коротко, по делу; на заметку
и решение не отвечать; решение — одно письмо с `kind: decision` тому, с кем
договорился; не ждать `wait_for` того, кто и так ответит письмом), потолок
`messageRate` и что делать, упёршись в него, оговорка про `tools` агента, и
описание `agent` у `spawn_session`.

## 6. TUI: панель треда

### 6.1 Раскладка

`ctrl+q t` докует тред справа от панели агента; панель сжимается влево, PTY
получает новые колонки тем же путём, что при ресайзе терминала
(`usePtyResize`). Повторное `t` закрывает. Панель треда **не модальная**: ввод
остаётся у агента, как без неё. Модальные оверлеи ложатся поверх панели и
треда, тред возвращается после.

Ширина `threadWidth` — 30 колонок по умолчанию, минимум 24 (`config.json`,
переменная `HARNAS_THREAD_WIDTH`). Тред докуется, только если панели остаётся
**не меньше 80 колонок** (решение D21): 80 — минимум, на который рассчитан сам
Claude Code, и главный артефакт харнесса не должен ломаться ради ленты. Иначе
`t` показывает тот же вид модальным оверлеем, как сайдбар на узком терминале
по `b`. На терминале 138 колонок док открывается с сайдбаром, на 120 — после
`ctrl+q b`, ниже — всегда оверлей.

Макет 138×N (фрагмент), сайдбар 26, разделитель, панель 80, разделитель, тред 30:

```text
 1 Авторизация          ● │ (панель Claude, 80 колонок)                                                    │ тред · план               ▤1
   ~/dev/shop · main      │                                                              │ РЕШЕНИЯ
 сессии · Авторизация     │ > _                                                          │ ✓ 12:42 план: «миграции
 ● план           working │                                                              │   отдельным PR»
   ↑1.2к ↓845 · 12м       │                                                              │ ──────────────────────────────
 ● бэкенд            idle │ ← harnas · план: где лежит миграция users?                   │ 12:40 план → бэкенд ?
 ○ тесты           exited │                                                              │   где лежит миграция users?
                          │                                                              │ 12:41 бэкенд → план · канал
                          │                                                              │   db/migrations/0007_users.sql
                          │                                                              │ 12:42 план → бэкенд ✓
                          │                                                              │   миграции отдельным PR
                          │                                                              │ ▤ 12:43 план → тесты ?
                          │                                                              │   прогони e2e после мержа
 ⚑ ✓ план: решение «миграции отдельным PR»                                                                       ctrl+q ?
```

### 6.2 Какой тред

Группа выбранной сессии по 3.4. Заголовок `тред · <ярлык владельца>` или
`тред · работа`; справа `▤N` — непрочитанные во всём треде. Смена выбора в
сайдбаре меняет тред; закрытие и открытие не сбрасывают положение прокрутки
той же группы.

### 6.3 Содержимое

- Блок РЕШЕНИЯ: до пяти последних, одна строка на решение с переносом; старше
  сворачиваются в строку `+N раньше`. Нет решений — блока нет.
- Лента по времени: строка заголовка `12:40 план → бэкенд ?` и текст с
  переносом по ширине, без обрезки. Знаки видов: `?` вопрос, `✓` решение,
  у заметки ничего. Непрочитанное помечено `▤` и ярче, как в деталях.
- Удалённая сессия подписана `(удалена)`; неизвестный id печатается как есть.
- Лента держится на хвосте. Колесо мыши над тредом листает её; пока
  пользователь ушёл вверх, новое письмо позицию не сбивает, а в заголовке
  появляется `↓N`. Клик по треду ничего не делает. Клавиш прокрутки нет.
- Для этого `routeMouse` (`use-prefix-input.ts`) получает правую границу
  панели рядом с левой (решение D18): сегодня он отдаёт гостю всё правее
  `panelLeft`, а живой Claude Code включает отслеживание мыши — колесо над
  доком уходило бы агенту с координатой за пределами его колонок, и лента
  стояла бы на месте. События правее панели идут треду, гость видит только
  свои колонки.
- Перерисовка по событиям watcher карты, таймеров нет. Строки треда
  считаются `useMemo` по объекту карты и ширине, как `sessionOrders` в
  `app.tsx`; рисуется срез по прокрутке и высоте, как в оверлеях (решение
  D15). Чужое событие карты без новой карты строк не пересчитывает.

### 6.4 Остальное

- Строка статуса: событие решения `✓ план: решение «…»` (источник — сессия
  получателя, гаснет при подключении к ней, как у писем) и событие
  `⚑ тред перегрет · <ярлык>` (4.7). События писем не меняются.
- Сайдбар: бейдж `▤N` без изменений; с push он гаснет быстро, и это правда.
- Детали (`ctrl+q i`): поле АГЕНТ после ЗАДАЧА, только если агент задан;
  в ВХОДЯЩИЕ у прочитанного письма — тот же суффикс `· канал` / `· inbox`.
- Карточка `pending`: строка `агент: reviewer` под ярлыком, если задан.
- Справка `ctrl+q ?`, таблица клавиш README, настройки README: строка `t`,
  `channelPush`, `threadWidth`.
- Мышь: колесо над тредом — тред; всё остальное как раньше.

## 7. Ошибки и граничные случаи

- Неизвестный `kind` — ошибка с перечнем; письмо не создаётся.
- `agent` без файла — ошибка с перечнем найденных; провайдер без подстановки
  `{agent}` в шаблоне — ошибка; запись не создаётся.
- Push выключен, Codex, сессия из CLI без `HARNAS_CHANNEL` — поведение
  ровно сегодняшнее.
- Письмо `pending`-сессии лежит в карте; звонок придёт при первом старте, на
  втором ходу после брифа. Письмо вышедшей сессии ждёт `--resume`. Переписка
  переживает падение процесса: письмо непрочитано, `▤N` его показывает, звонок
  повторится.
- Уведомление не записалось в транспорт (сервер закрывается) — письмо
  осталось непрочитанным, звонок повторится при следующем старте. Карту
  сторож не пишет, поэтому «доставлено, но потеряно» невозможно (4.2).
- Звонок про письмо, забранное `check_inbox` в том же ходу, — один пустой
  `check_inbox` у агента (4.3).
- `claude` без поддержки флага channel — до запуска ловится пробой версии
  (4.4): push выключается, строка статуса объясняет. Если проба не сработала,
  процесс выходит с «unknown option», текст виден в панели, лечится
  `channelPush: false`.
- Оверрайд `providers.json` без `{channel}` при включённом push — разовое
  предупреждение в строке статуса, письма живут по pull (4.4).
- Ход, начатый событием channel, возможно, не даёт `UserPromptSubmit`: тогда
  `working` поднимает страховка по логу (`activity.ts`, первая запись
  транскрипта новее последнего хука) с задержкой в секунды, а `Stop` закрывает
  ход как обычно (решение D6, проверка в разделе 9).
- Событие channel приходит, когда человек печатает в той же панели: что
  станет с набранной строкой, проверяет спайк (решение D17, раздел 9); если
  строка теряется, ответ уходит в README как известное ограничение.
- Окно `messageRate` исчерпано — `send_message` отказывает с объяснением,
  строка статуса показывает событие (4.7).
- Отправитель или получатель удалён — как сейчас: пометка `deleted`, в
  треде «(удалена)». Сервер удалённой сессии писать не может.
- Старые карты: нет `kind` — заметка, нет `agent` — `null`. Миграции нет.
- Терминал уже порога — оверлей вместо дока; тред закрыт, если панель
  скрыта сайдбаром-оверлеем.
- Второй TUI на проекте не поддерживается, как раньше.

## 9. Порядок реализации и живая проверка

**Шаг 0. Спайк канала — до всех задач** (решение D17). Тридцать строк во
временном каталоге, не в репозитории: stdio-сервер с
`capabilities.experimental['claude/channel']`, шлющий одно уведомление через
десять секунд после `oninitialized` и печатающий в stderr
`getClientCapabilities()` и `getClientVersion()`. Запускается стоковым
`claude` вручную, с `--mcp-config` и
`--dangerously-load-development-channels server:<имя>`. Проверяется:

1. флаг принимается, стартовый баннер показывает регистрацию channel;
2. агент, сидящий у промпта, начинает ход сам, без нажатий;
3. **что происходит с набранной, но не отправленной строкой**, когда событие
   начинает ход (находка внешнего голоса 9);
4. даёт ли такой ход `UserPromptSubmit` в журнале хуков (решение D6);
5. то же под `--resume` и с `--agent`;
6. что видно в `getClientCapabilities()` — только как диагностика;
7. минимальная версия `claude`, принимающая флаг, — она идёт в пробу версии
   (4.4) и в README.

Результат записывается в TODOS и в этот раздел.

**Результат спайка 2026-09-18** (`claude` 2.1.276, Opus 5, подписка Max, сервер
из `--mcp-config` под именем `spike`):

1. флаг принят; баннер: «Channels (experimental) messages from server:spike inject
   directly in this session». Рядом жёлтая строка «server:spike · no MCP server
   configured with that name» — косметика: проверка идёт до загрузки серверов из
   `--mcp-config`, регистрация всё равно состоялась, события дошли. Для харнесса
   строка будет про `server:harnas`; README называет её ожидаемой;
2. событие будит агента у промпта: через 10 с после `initialize` пришло событие
   1, агент сам начал ход и ответил за 2 с; событие 2 через 60 с — так же;
3. набранная, но не отправленная строка при приходе события **остаётся в поле
   ввода**: событие обрабатывается, текст можно допечатать и отправить;
4. ход от события **даёт `UserPromptSubmit`**: в журнале хуков промпт
   `<channel source="spike" n="1" kind="question" unread="1"> …`, затем `Stop`.
   Значит, `activity` поднимает `working` штатно, страховка по логу не нужна
   (решение D6 закрыто), а `source` в теге — имя сервера из конфига без префиксов;
5. `--resume` с channel работает: сессия поднялась с историей, сервер
   подключился заново, событие 1 пришло и агент ответил. `--agent` не
   проверялся: у каталога спайка нет `.claude/agents`, роли — задача D;
6. `getClientCapabilities()` = `{"elicitation":{"form":{}},"roots":{"listChanged":true}}`:
   регистрацию channel клиент не объявляет, гейт по capability невозможен (после
   D16 он и не нужен);
7. версия 2.1.276 проверена; нижняя граница по документации 2.1.211 остаётся
   значением `CHANNEL_MIN_VERSION` в плане.
