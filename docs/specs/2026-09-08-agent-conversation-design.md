# Разговор агентов внутри работы: тред родителя и доставка через channel — дизайн

Дата: 2026-09-08. Статус: согласовано в диалоге по разделам, ждёт ревью
пользователя, затем план реализации для Workflow (агенты на Opus, ревью с
`effort: high`). Основание: `2026-09-02-coordination-design.md` (v3, письма и
`wait_for`), `2026-09-05-tui-v2-design.md` (сайдбар, панель, оверлеи, `activity`),
`2026-09-06-agent-guidance-plan.md` (гид и системная вставка), README.

---

## 1. Зачем

Сессии одной работы уже знают друг о друге через карту и могут обмениваться
письмами, но письмо лежит в `map.json`, пока адресат сам не позовёт
`check_inbox`. Агент, который закончил ход и ждёт ввода у промпта, письма не
увидит никогда; агент-отправитель либо блокирует свой ход в `wait_for`, либо
теряет ответ. Разговора двух коллег над одной задачей из этого не выходит, и
человек видит переписку только по кусочкам: бейдж `▤N`, строка статуса, секция
ВХОДЯЩИЕ в деталях одной сессии.

Эта итерация делает три вещи:

1. письмо доходит до адресата само, штатным механизмом Claude Code (channels),
   и адресат отвечает без участия человека;
2. переписка поддерева одной родительской сессии видна человеку целиком в
   панели треда справа от панели агента, с отдельным списком решений;
3. сессии знакомятся с коллегами в брифе и могут запускаться как именованные
   агенты Claude Code проекта.

Юридическая рамка не меняется: стоковый `claude` из PATH, документированный
флаг, наш собственный MCP-сервер. `~/.claude` по-прежнему только читается
(`stat` файла агента), учётные данные не открываются.

## 2. Решения диалога

| Вопрос | Решение |
|---|---|
| Кто с кем говорит | Тред родителя, адресные письма: у каждой родительской сессии одна переписка её поддерева; письмо адресовано одной сессии, а человек читает тред целиком |
| Как доставляется | Push через channel в `harnas-mcp` получателя; pull (`check_inbox`, `wait_for("inbox")`) остаётся страховкой. PTY-впечатывание не делается |
| Откуда роль | Необязательное поле `agent` — имя агента Claude Code проекта (`claude --agent`). Разговор от роли не зависит: этикет одинаков для сессий с агентом и без |
| Как фиксируются решения | Вид письма `kind: decision`; отдельного инструмента нет |
| Где читать | Панель треда справа, `ctrl+q t`, не модальная, ввод остаётся у агента; ширина 30 колонок; на узком терминале — тот же вид оверлеем |
| Письма от человека | Не в этой итерации, запись в TODOS |
| Имя агента в сайдбаре | Не показывается: 26 колонок. Видно в деталях и карточке `pending` |

## 3. Модель данных и инструменты

### 3.1 Письмо

```ts
export type MessageKind = 'note' | 'question' | 'decision';
export type DeliveredVia = 'channel' | 'inbox';

export interface Message {
  id: string;
  from: string;
  to: string;               // одна сессия, как раньше
  at: string;
  text: string;
  kind?: MessageKind;       // нет поля — note (карты до 2026-09-08)
  readAt: string | null;
  deliveredVia?: DeliveredVia; // ставится вместе с readAt
  deleted?: boolean;
}
```

`question` — «жду ответа», `decision` — «мы договорились», `note` — всё
остальное. `deliveredVia` говорит, дошло письмо само (`channel`) или его
забрали инструментом (`inbox`: и `check_inbox`, и `wait_for`). Это диагностика
слабого места из 4.6: если все письма `inbox`, push не работает.

### 3.2 Сессия

```ts
export interface WorkSession {
  // ...как раньше
  /** Имя агента Claude Code проекта; null — обычная сессия. */
  agent: string | null;    // нет поля — null
}
```

### 3.3 Инструменты

| Инструмент | Изменение |
|---|---|
| `send_message(to, text, kind?)` | `kind` из трёх значений, по умолчанию `note`; другое значение — ошибка с перечнем. Проверки отправителя и получателя как раньше |
| `spawn_session(provider, label, task, contextFrom, agent?)` | `agent` — имя агента; проверка по 5.1. Провайдер, в шаблоне запуска которого нет подстановки `{agent}`, — ошибка «провайдер агентов не принимает» |
| `check_inbox()` | Помечает `readAt` и `deliveredVia: 'inbox'`; в ответе у письма есть `kind` |
| `wait_for("inbox")` | Возвращая письма, помечает их так же, как `check_inbox` (раньше не помечал). Иначе после его возврата сторож канала пушил бы их второй раз |
| `get_map`, `report`, `read_guide` | Сигнатуры не меняются; в карте видны `kind`, `deliveredVia`, `agent` |

Инструментов удаления, правки или рассылки писем нет. Ответ `messageView`
дополняется полем `kind`.

### 3.4 Тред выводится, а не хранится

Тред сессии P — письма, у которых и отправитель, и получатель лежат в
поддереве P: сама P и её потомки по `parent`. Решения треда — его письма с
`kind: decision` по времени. Ни нового поля в карте, ни файла.

Группа, которую показывает панель и знает бриф, — «тред сессии S»:

- у S есть родитель — поддерево родителя (родитель, братья, S, потомки);
- S корень с детьми — её собственное поддерево;
- S одинокий корень (без родителя и детей) — вся работа: все сессии, все письма.

Чистая функция `threadOf(map, sessionId)` в `core/work/thread.ts` возвращает
владельца (`sessionId` или `null` для всей работы), участников и письма по
времени. Её используют бриф, панель и события строки статуса. Удалённая сессия
в письмах остаётся, участником не считается.

## 4. Доставка через channel

### 4.1 Что это

Channels — механизм Claude Code (research preview): MCP-сервер, объявивший
`capabilities.experimental['claude/channel']`, шлёт клиенту уведомление
`notifications/claude/channel`, и оно попадает в контекст модели тегом
`<channel source="<имя сервера>" ...>`. События копятся, пока агент занят, и
приходят пачкой на границе хода; агент у промпта получает событие и начинает
ход сам. Диалог разрешения событие не задевает. Клиент уведомления не
подтверждает: если сервер не зарегистрирован как channel, событие молча
отбрасывается. Документация: `code.claude.com/docs/en/channels`,
`.../channels-reference`. Документация описывает поведение клиентов 2.1.211+
и 2.1.234+; локальный `claude` 2.1.263 подходит.

### 4.2 Кто пушит

Сервер `harnas-mcp` **получателя** — он и так один процесс на сессию и умеет
следить за `map.json` (`fs.watch` каталога плюс редкий опрос, как в
`waitForMap`). При `HARNAS_CHANNEL=1` в окружении и непустом
`HARNAS_SESSION_ID` сервер:

1. объявляет `capabilities.experimental['claude/channel'] = {}` и `instructions`
   (4.5);
2. после `oninitialized` запускает сторож входящих: при старте и на каждое
   изменение карты берёт письма `to === me && readAt === null` по порядку `at`
   и для каждого шлёт

```
notifications/claude/channel
  content: <текст письма>
  meta: { message_id, from, from_label, kind }
```

3. после того как `notification()` разрешился (запись в транспорт), под
   блокировкой карты ставит `readAt` и `deliveredVia: 'channel'`.

Ключи `meta` — только идентификаторы (буквы, цифры, подчёркивание), иначе
Claude Code их молча выбросит. Защита от двойного пуша — множество id «в
доставке» в памяти процесса: `fs.watch` и опрос могут сработать вместе.

### 4.3 Согласование с pull

Пока в этом же процессе висит `wait_for("inbox")`, сторож стоит: письмо
придёт агенту результатом инструмента, и `wait_for` пометит его сам
(`deliveredVia: 'inbox'`). Счётчик ожидающих `wait_for` — поле состояния
сервера; по возврату сторож проверяет карту заново. `check_inbox` берёт
непрочитанные под блокировкой, гонки со сторожем нет: кто первый пометил, тот
и доставил.

### 4.4 Включение

- `config.json`: `channelPush: true` по умолчанию; переменная
  `HARNAS_CHANNEL_PUSH` (`0`/`1`). Загрузчик в core, читают и TUI, и CLI.
- `mcp/<id>.json`: при включённом `channelPush` в `env` сервера добавляется
  `HARNAS_CHANNEL: "1"`. TUI пишет файл при каждом запуске и возобновлении
  (`planLaunch`/`planResume`), CLI — вместе с печатью команды; переменная и
  флаг ниже всегда считаются из одной и той же настройки в один момент.
- Реестр: у записи Claude в `args` и `resumeArgs` добавляется пара
  `'--dangerously-load-development-channels', '{channel}'`; подстановка
  `channel` = `server:harnas` (имя из `MCP_SERVER_NAME`) при включённом push,
  иначе `undefined`, и `substituteArgs` выбрасывает пару целиком, как сейчас
  делает с `--mcp-config`. Флаг скрыт из `claude --help`, но принимается.
- Codex и GLM: ни `HARNAS_CHANNEL`, ни флага — pull, как сейчас.
- `harnas-core work session new` печатает команду с флагом и конфиг с
  переменной: сессия из терминала получает push наравне с сессией панели.

### 4.5 Что видит агент

В терминале агента — строка вида `← harnas · план: где лежит миграция users?`.
В контексте:

```
<channel source="harnas" from="s-01" from_label="план" kind="question" message_id="m-03">
где лежит миграция users?
</channel>
```

`instructions` сервера (доставляются при подключении):

> Письма коллег по этой работе приходят тегом `<channel source="harnas">`:
> `from` — id сессии-отправителя, `from_label` — её роль, `kind` — вид
> (`question` ждёт ответа, `decision` — договорённость, `note` — заметка).
> Отвечай `send_message(to=<from>)`. Договорённость фиксируй своим письмом с
> `kind: decision`. Письма не повторяются; `check_inbox` — страховка, если канал
> молчит.

### 4.6 Слабое место

Если политика организации блокирует channels, флаг перестанет приниматься или
сервер по любой причине не зарегистрирован как channel, Claude Code отбросит
событие молча, а письмо уже помечено `channel`. Сервер об этом не узнаёт.
Компенсации:

- стартовый баннер агента показывает регистрацию channel или причину отказа
  («blocked by org policy»), он виден в панели;
- `deliveredVia` в треде: если письма всегда `inbox` или переписка
  «зависает», push не работает;
- `channelPush: false` возвращает чистый pull без других изменений;
- `wait_for` отправителя по таймауту вернёт `running`, и гид велит агенту
  обратиться к человеку.

Живой прогон до TUI-части — раздел 9.

## 5. Роли и бриф

### 5.1 Агент Claude Code как роль

`agent` — имя файла `.claude/agents/<name>.md` в проекте или
`~/.claude/agents/<name>.md`. Проверка при создании сессии: `stat` обоих путей,
содержимое не читается; нет ни одного — ошибка с перечнем имён, найденных в
обоих каталогах (только имена файлов). Проверка живёт в core
(`work/agents.ts`), её зовут `spawn_session` и CLI `--agent`.

Запуск: подстановка `agent` и пара `'--agent', '{agent}'` в `args` и
`resumeArgs` записи Claude; без значения пара выпадает. По документации
`--agent` совместим с `--append-system-prompt`, `--mcp-config`, `--settings`,
`--resume`; живая проверка — раздел 9.

Оговорка в гиде и README: определение агента с ограниченным списком `tools`
обязано включать `mcp__harnas__*`, иначе роль не сможет ни писать коллегам, ни
отчитаться. Харнесс это не проверяет: файл агента он не читает.

В TUI пикера агентов нет: `prefix c` и `prefix C` стартуют мгновенно, диалога у
них нет, и заводить его ради одного поля не стоит. Имя агента видно в деталях
(`ctrl+q i`, поле АГЕНТ) и в карточке `pending` перед запуском.

### 5.2 Бриф: знакомство с коллегами

`buildBrief` получает два раздела между «Контекст» и «Правила»:

```
## Коллеги
- s-01 — план (родитель, агент planner): active
- s-03 — ревью: pending

## Решения треда
- 12:42 план: «миграции отдельным PR»
```

Коллеги — участники `threadOf(map, newSessionId)` без самой сессии, с ролью,
пометкой родителя, именем агента (если есть) и статусом. Решения — решения
того же треда. Пустые разделы не печатаются. Правило 2 брифа переписывается:

> Письма коллег приходят сами; отвечай тому, кто спросил, через
> `send_message`; договорённость помечай `kind: decision`; не заканчивай ход с
> неотвеченным вопросом.

Это одинаково для сессий с агентом и без.

### 5.3 Системная вставка и гид

Вставка остаётся в бюджете двенадцати строк: строка `send_message` получает
виды письма, строка `check_inbox` становится «письма коллег приходят сами как
`<channel source="harnas">`; отвечай `send_message` тому, кто в `from`;
`check_inbox` — страховка». Число строк не растёт.

`read_guide` получает раздел «Как разговаривать»: что такое тред, три вида
писем, этикет (отвечать на вопрос в том же ходу, коротко, по делу; решение —
одно письмо с `kind: decision` тому, с кем договорился; не ждать `wait_for`
того, кто и так ответит письмом), оговорка про `tools` агента, и описание
`agent` у `spawn_session`.

## 6. TUI: панель треда

### 6.1 Раскладка

`ctrl+q t` докует тред справа от панели агента; панель сжимается влево, PTY
получает новые колонки тем же путём, что при ресайзе терминала
(`usePtyResize`). Повторное `t` закрывает. Панель треда **не модальная**: ввод
остаётся у агента, как без неё. Модальные оверлеи ложатся поверх панели и
треда, тред возвращается после.

Ширина `threadWidth` — 30 колонок по умолчанию, минимум 24 (`config.json`,
переменная `HARNAS_THREAD_WIDTH`). Тред докуется, только если панели остаётся
не меньше 50 колонок; иначе `t` показывает тот же вид модальным оверлеем, как
сайдбар на узком терминале по `b`.

Макет 120×N (фрагмент), сайдбар 26, разделитель, панель 62, разделитель, тред 30:

```text
 1 Авторизация          ● │ (панель Claude, 62 колонки)                                  │ тред · план               ▤1
   ~/dev/shop · main      │                                                              │ РЕШЕНИЯ
 сессии · Авторизация     │ > _                                                          │ ✓ 12:42 план: «миграции
 ● план           working │                                                              │   отдельным PR»
   ↑1.2к ↓845 · 12м       │                                                              │ ──────────────────────────────
 ● бэкенд            idle │ ← harnas · план: где лежит миграция users?                   │ 12:40 план → бэкенд ?
 ○ тесты           exited │                                                              │   где лежит миграция users?
                          │                                                              │ 12:41 бэкенд → план · канал
                          │                                                              │   db/migrations/0007_users.sql
                          │                                                              │ 12:42 план → бэкенд ✓
                          │                                                              │   миграции отдельным PR
                          │                                                              │ ▤ 12:43 план → тесты ?
                          │                                                              │   прогони e2e после мержа
 ⚑ ✓ план: решение «миграции отдельным PR»                                                                       ctrl+q ?
```

### 6.2 Какой тред

Группа выбранной сессии по 3.4. Заголовок `тред · <ярлык владельца>` или
`тред · работа`; справа `▤N` — непрочитанные во всём треде. Смена выбора в
сайдбаре меняет тред; закрытие и открытие не сбрасывают положение прокрутки
той же группы.

### 6.3 Содержимое

- Блок РЕШЕНИЯ: до пяти последних, одна строка на решение с переносом; старше
  сворачиваются в строку `+N раньше`. Нет решений — блока нет.
- Лента по времени: строка заголовка `12:40 план → бэкенд ?` и текст с
  переносом по ширине, без обрезки. Знаки видов: `?` вопрос, `✓` решение,
  у заметки ничего. У прочитанного письма после заголовка тусклое `· канал`
  или `· inbox`. Непрочитанное помечено `▤` и ярче, как в деталях.
- Удалённая сессия подписана `(удалена)`; неизвестный id печатается как есть.
- Лента держится на хвосте. Колесо мыши над тредом листает её; пока
  пользователь ушёл вверх, новое письмо позицию не сбивает, а в заголовке
  появляется `↓N`. Клик по треду ничего не делает. Клавиш прокрутки нет.
- Перерисовка по событиям watcher карты, таймеров нет.

### 6.4 Остальное

- Строка статуса: событие решения `✓ план: решение «…»` (источник — сессия
  получателя, гаснет при подключении к ней, как у писем). События писем не
  меняются.
- Сайдбар: бейдж `▤N` без изменений; с push он гаснет быстро, и это правда.
- Детали (`ctrl+q i`): поле АГЕНТ после ЗАДАЧА, только если агент задан;
  в ВХОДЯЩИЕ у прочитанного письма — тот же суффикс `· канал` / `· inbox`.
- Карточка `pending`: строка `агент: reviewer` под ярлыком, если задан.
- Справка `ctrl+q ?`, таблица клавиш README, настройки README: строка `t`,
  `channelPush`, `threadWidth`.
- Мышь: колесо над тредом — тред; всё остальное как раньше.

## 7. Ошибки и граничные случаи

- Неизвестный `kind` — ошибка с перечнем; письмо не создаётся.
- `agent` без файла — ошибка с перечнем найденных; провайдер без подстановки
  `{agent}` в шаблоне — ошибка; запись не создаётся.
- Push выключен, Codex, сессия из CLI без `HARNAS_CHANNEL` — поведение
  ровно сегодняшнее.
- Письмо `pending`-сессии лежит в карте и пушится при первом старте; придёт
  на втором ходу, после брифа. Письмо вышедшей сессии ждёт `--resume`, и её
  сервер пушит его тогда же. Так переписка переживает падение процесса:
  непрочитанное не теряется, `▤N` его показывает.
- Уведомление не записалось в транспорт (сервер закрывается) — письмо не
  помечается; доставится при следующем старте.
- Отправитель или получатель удалён — как сейчас: пометка `deleted`, в
  треде «(удалена)». Сервер удалённой сессии писать не может.
- Старые карты: нет `kind` — заметка, нет `deliveredVia` — не показывается,
  нет `agent` — `null`. Миграции нет.
- Терминал уже порога — оверлей вместо дока; тред закрыт, если панель
  скрыта сайдбаром-оверлеем.
- Второй TUI на проекте не поддерживается, как раньше.

## 8. Тесты

Настоящий `claude` в автотестах не запускается никогда; E2E идут против
stub-бинаря.

core:
1. `send_message`: три вида принимаются, четвёртый — ошибка; без `kind` — `note`.
2. `check_inbox` ставит `deliveredVia: 'inbox'`; `wait_for("inbox")` — тоже,
   и второй `check_inbox` пуст.
3. `threadOf`: поддерево родителя; корень с детьми; одинокий корень — вся
   работа; письма между чужими поддеревьями в тред не попадают; удалённая
   сессия не участник, но её письма остаются.
4. Решения треда по времени.
5. Бриф: разделы Коллеги и Решения; пустые не печатаются; пометки родителя
   и агента; правило 2 новым текстом.
6. Системная вставка: не больше двенадцати строк с целью работы; в ней есть
   `channel` и виды письма.
7. `work/agents.ts`: каталог `~/.claude` передаётся параметром (в тестах —
   временный); файл в проекте, файл в пользовательском каталоге, ни там ни
   там — ошибка с перечнем имён из обоих.
8. Реестр: `startCommand`/`resumeCommand` Claude с `agent` и `channel`
   содержат обе пары; без значений пары выпадают целиком.
9. `mcpConfig` с push пишет `HARNAS_CHANNEL: "1"`, без push — нет.
10. Конфиг: `channelPush`, `threadWidth` из файла и окружения, минимум 24,
    битые значения — жалоба и дефолт.
11. CLI `work session new --agent`, печать команды с флагом channel.

MCP-сервер (клиент и сервер SDK в памяти, у клиента обработчик
`notifications/claude/channel`):
12. Письмо, положенное в карту, приходит уведомлением с `content` и `meta`
    (`message_id`, `from`, `from_label`, `kind`).
13. После уведомления письмо помечено `channel`; второй раз не приходит.
14. Письмо, лежавшее в карте до старта, приходит после инициализации.
15. Пока висит `wait_for("inbox")`, уведомления нет; `wait_for` возвращает
    письмо и помечает `inbox`; после возврата сторож не пушит его.
16. Без `HARNAS_CHANNEL` — ни capability, ни `instructions`, ни уведомлений.
17. Без `HARNAS_SESSION_ID` — сторожа нет и при `HARNAS_CHANNEL`.

TUI:
18. Вид треда с фикстуры: порядок, знаки видов, блок решений и `+N`,
    непрочитанное `▤`, суффикс доставки, «(удалена)», перенос по ширине.
19. Правило дока: панель ≥ 50 — док, иначе оверлей; `threadWidth` из конфига.
20. `prefix t` открывает и закрывает; при доке PTY получает `cols` меньше на
    ширину треда и разделитель, при закрытии — обратно.
21. Ввод при открытом треде уходит гостю.
22. Колесо над тредом листает его и не уходит гостю; `↓N` при новых письмах
    вне хвоста.
23. Смена выбранной сессии меняет тред и заголовок.
24. Событие решения в строке статуса; гаснет при подключении к получателю.
25. Детали: поле АГЕНТ и суффикс доставки; карточка `pending` с агентом.
26. Справка содержит строку `t`.
27. E2E со stub-бинарём: аргументы запуска содержат
    `--dangerously-load-development-channels server:harnas` и `--agent <name>`;
    с `channelPush: false` флага нет.
