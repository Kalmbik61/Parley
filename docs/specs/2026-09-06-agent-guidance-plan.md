## A. Гид для агентов: как и зачем пользоваться харнессом

### Проблема

Агент в сессии харнесса знает о нём только из брифа (если сессия порождена) и из
описаний шести MCP-инструментов. Сессия, открытая через `new`, брифа не получает
вовсе. Агент не знает, что для длинных или параллельных подзадач внутри темы
предпочтительна подсессия в этой же работе, и не знает, где взять подробности,
не грузя их заранее.

### Решение — два слоя, от дешёвого к подробному

1. **Короткая системная вставка** при каждом запуске из харнесса и из
   `harnas-core work session new`: флаг `--append-system-prompt` с текстом до
   12 строк (≈ 120 токенов). Содержание фиксировано в `core/work/guidance.ts`:
   - ты в работе `<id> — <заголовок>` харнесса my-harnas, твоя сессия `<id>`;
     цель работы одной строкой, если она не пуста;
   - инструменты MCP `harnas`: `get_map`, `report`, `spawn_session`, `wait_for`,
     `send_message`, `check_inbox`, `read_guide` — одной строкой на каждый;
   - правило предпочтения: подзадача внутри этой темы, которая живёт дольше
     одного хода или должна идти параллельно, — `spawn_session` в этой работе;
     собственные субагенты Claude — для коротких разведок и правок;
   - перед завершением обязательно `report`; подробности — `read_guide`.
   Подстановка `{systemPrompt}` в реестре провайдеров (`providers.ts`): у claude
   `args` и `resumeArgs` получают `--append-system-prompt {systemPrompt}`; у
   провайдера без такой возможности подстановка отбрасывается, как `{settingsFile}`.
   При `--resume` вставка передаётся заново: системный промпт не хранится в
   транскрипте, а собирается при каждом запуске. Ветка `resuming` в `plan()`
   (`work-launch.ts`) сегодня не собирает ничего, кроме id сессии, — она получает
   `subs.systemPrompt` наравне с `new` и `launch`.
2. **Подробный гид по запросу**: `core/work/guide.ts` (шаблонная строка ≈ 60 строк:
   сущности, жизненный цикл, что кладут в артефакты, как устроен бриф, как
   ждать подчинённую сессию, что значит `state: deleted`, чего не делать).
   MCP-сервер отдаёт его **седьмым инструментом `read_guide`** без аргументов.
   MCP-ресурс не подходит: Claude Code не даёт модели инструмента чтения
   ресурсов, а сервер их не объявляет (`capabilities: { tools: {} }`); ресурс был
   бы мёртвым слоем с зелёным тестом. Описание инструмента `get_map`
   заканчивается строкой «подробный гид — инструмент read_guide».

Skill-файл в `.claude/skills/` проекта не пишется: Claude Code читает skills
только из каталогов проекта и `~/.claude`, а сессии, запущенные мимо харнесса,
всё равно не имеют MCP и ничего не могут сделать с картой. См. `TODOS.md`,
раздел «Skill-файл харнесса для агента».

### Файлы

- `packages/core/src/work/guidance.ts` — `systemGuidance(map, sessionId)`.
- `packages/core/src/work/guide.ts` — `GUIDE`.
- `packages/core/src/providers.ts` — подстановка `{systemPrompt}` у claude.
- `packages/core/src/mcp/tools.ts` — инструмент `read_guide`, строка в описании
  `get_map`.
- `packages/core/src/cli.ts` — `work session new` печатает команду с
  `--append-system-prompt`.
- `packages/tui/src/work-launch.ts` — `subs.systemPrompt` во всех трёх режимах
  (`new`, `launch`, `resume`).
- README: раздел «Что видит агент» — два слоя.

## B. Тихий старт: бриф как контекст, а не как первое сообщение

### Проблема

`prefix C` создаёт дочернюю сессию и отдаёт бриф первым сообщением — агент сразу
идёт отвечать, хотя задачи у него нет и пользователь хотел сначала написать сам.

### Решение

Правило: **есть задача — бриф идёт первым сообщением; задачи нет — бриф уходит в
`--append-system-prompt` вместе с системной вставкой из A, а агент ждёт ввода.**

- `spawn_session` (задача обязательна, `stringArg` пустую строку не принимает) —
  без изменений: старт по брифу, агент работает. Пустая `task` — сорт записи,
  доступный только TUI и CLI; это фиксируется комментарием у `WorkSession.task`
  в `types.ts`, а не устной договорённостью.
- `prefix C` и `harnas-core work session new` без `--task` — `task` пустая строка
  вместо заглушки «Продолжить работу сессии …»; бриф собирается без строки
  «Задача:», но с разделом «Контекст» родителя и правилами; режим запуска `new`
  с `systemPrompt = вставка A + бриф`. Задачу пользователь пишет первым
  сообщением агенту.
- **`resume` тихой сессии**: системный промпт живёт в процессе, а не в
  транскрипте, и у тихой сессии транскрипт начинается с сообщения пользователя —
  контекста родителя там нет. Поэтому при `resume` сессии с пустой задачей
  `systemPrompt = вставка A + бриф`, как и при первом старте. Иначе `prefix r`
  поднимал бы агента без родительского контекста, и внешне это неотличимо от
  нормального возобновления.
- Пустая задача во всех читателях `task`: `summary.ts` (промпт суммаризатору
  опускает «Её задача: …», как уже сделано для цели работы), `cli.ts`
  (`--task` необязателен; без него печатается тихая команда — бриф в
  `--append-system-prompt`, без аргумента-промпта). Сайдбар рисует `label`, а не
  `task`; детали уже показывают `—` при пустой задаче — правок не требуют.
- Карточка `pending` и оверлей запуска показывают, каким будет старт: «по брифу»
  или «ждёт ваш запрос».
- **projectPath работы вместо projectPath харнесса**: `use-panel.ts` в `create` и
  `createChild` берёт путь харнесса, тогда как `workId` может принадлежать
  закреплённой чужой работе — сегодня это «карты нет» на `prefix c`/`prefix C`
  (хвост из `TODOS.md`). Раз `createChild` переписывается, оба вызова начинают
  брать `projectPath` записи работы, как `start` и оверлеи. Это закрывает хвост
  и обязательное условие для C: удаление по чужому `workId` и своему пути — это
  `rm` не в том проекте.

**Перед началом B** — ручная проверка на живом `claude` (один раз, руками
пользователя, не в тестах): `--append-system-prompt` действует вместе с
`--resume`. Stub-E2E проверяет только argv; если флаг при `--resume`
игнорируется, план B меняется (бриф первым сообщением с пометкой «жди
задачу»), и это отдельное решение.

### Файлы

- `packages/tui/src/work-launch.ts` — `createChildSession` без заглушки задачи;
  `plan()` выбирает режим по наличию `task`: пустая → `new` с системным промптом,
  иначе `launch`; `resume` при пустой задаче добавляет бриф в системный промпт.
- `packages/tui/src/use-panel.ts` — `create`/`createChild` по projectPath работы.
- `packages/core/src/work/brief.ts` — `buildBrief` пропускает «Задача:» при пустой
  задаче.
- `packages/core/src/work/summary.ts` — промпт без «Её задача» при пустой.
- `packages/core/src/work/types.ts` — комментарий: пустая `task` = тихий старт.
- `packages/core/src/cli.ts` — `--task` необязателен, тихая команда.
- Спецификация TUI v2, разделы 5.1–5.2, и мокапы 4.5: дописать правило.

## C. Удаление сессии

### Проблема

`prefix x` шлёт SIGHUP и оставляет запись `exited`; убрать зависшую или ненужную
сессию из работы нельзя, дерево засоряется.

### Решение

`prefix d` — удалить выбранную сессию с подтверждением (оверлей 48 колонок):

```
┌ удалить ○ бэкенд ────────────────────────────┐
│ запись, бриф и журнал событий будут удалены  │
│ транскрипт в ~/.claude останется             │
│ дочерние: ревью, тесты → поднимутся на уровень│
│ Enter — удалить · Esc                        │
└──────────────────────────────────────────────┘
```

- Живой процесс, чей PTY у харнесса, сначала закрывается: SIGHUP, ожидание выхода
  до 3 с, затем SIGKILL; запись удаляется только после выхода, чтобы обработчик
  выхода и хук `SessionEnd` не писали в уже удалённую сессию. **Сессия, живая по
  проверке живости** (`checkSession`: pid, а у CLI-сессий с `pid: null` — свежий
  журнал) и не держащаяся PTY харнесса, не удаляется: оверлей объясняет и
  предлагает закрыть её там, где она запущена. Проверка по одному `pid` била
  мимо: у CLI-сессий он всегда `null`, а срабатывала она на сессиях, переживших
  перезапуск харнесса.
- В карте: запись удаляется; у дочерних `parent` становится `parent` удалённой
  (или `null`), из `contextFrom` других сессий id вычищается; сообщения `from`/`to`
  удалённой остаются с пометкой `deleted: true`. След удаления — **только id** в
  `work.deletedSessions`; данных сессии (ярлык, задача, резюме) нигде не остаётся.
- **Id не переиспользуются**: в `work` добавляется `sessionSeq`;
  `nextSessionId` = max(`sessionSeq`, существующие) + 1 и сразу пишет счётчик.
  Карты без поля читаются как сейчас (максимум по списку), миграции нет.
- На диске: `briefs/<id>.md`, `events/<id>.jsonl`, `mcp/<id>.json` удаляются;
  отсутствие любого из них — не ошибка. `artifacts/` не трогаются.
  `deleteSessionFiles` получает `projectPath` записи работы (см. B).
- **`wait_for`**: id в `deletedSessions` → `{ state: "deleted", sessionId }`
  сразу; исчез во время ожидания → то же; id, которого не было никогда, →
  ошибка сразу, как сейчас (ловит опечатку агента). Гид и описание инструмента
  упоминают это состояние.
- **MCP-сервер удалённой сессии** ещё может быть жив (`SessionEnd` срабатывает
  до выхода процесса, CLI-сессия закрывается позже). Все инструменты, кроме
  `get_map` и `read_guide`, проверяют **свою** сессию через `requireSession`:
  `report`, `spawn_session`, `check_inbox` уже делают это, `send_message`
  проверяет только получателя — добавить проверку отправителя, иначе в карту
  ляжет письмо от несуществующего адресата, ответить на которое нельзя.
- Читатели карты (`use-map-sync`, живость, свёртка событий) не воскрешают
  удалённую запись: переходы адресуются только существующим сессиям; журнал
  `events/<id>.jsonl`, дописанный хуком после удаления (settings один на работу,
  хук пишет по `HARNAS_SESSION_ID`), игнорируется и записи не создаёт.
- MCP: инструмента удаления агентам не даём. `works-index` не меняется;
  `updatedAt` работы обновляется.

### Файлы

- `packages/core/src/work/types.ts`, `map.ts` — `sessionSeq`, `deletedSessions`,
  `removeSession(map, id)`; `store.ts` — `deleteSessionFiles(projectPath, workId, id)`.
- `packages/core/src/mcp/tools.ts` — `wait_for` со `state: deleted`;
  `send_message` проверяет отправителя.
- `packages/tui/src/use-overlays.ts`, `overlays.ts` — оверлей `delete`;
  `use-actions.ts` — `d`; `use-panel.ts` — закрыть, дождаться выхода, удалить по
  projectPath работы; строка статуса — `⚑ сессия удалена`; `use-map-sync.ts` —
  не трогать отсутствующие сессии.
- README, спецификация 3.2 (таблица клавиш), мокапы 4.x — новый оверлей.

## Тесты: чек-лист приёмки

   правило предпочтения подсессий.
2. Работа без цели → строка цели опущена.
3. Заголовок работы с кавычками и переносами не ломает текст вставки.
4. `GUIDE` упоминает предпочтение `spawn_session` и `state: deleted`.

   инструментов; описание `get_map` ссылается на `read_guide`.

9. `work-launch.test`: stub получает `--append-system-prompt` в `new`, `launch`,
