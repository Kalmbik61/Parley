# План реализации: гид для агентов, тихий старт дочерней сессии, удаление сессии

Дата: 2026-09-06. Статус: план, ждёт инженерного ревью. Основание: замечания
пользователя после первого живого прогона TUI v2 (пункты 2–4), спецификации
`2026-09-05-tui-v2-design.md` и `2026-09-02-coordination-design.md`.

Три независимых изменения. Каждое — отдельная задача Workflow со своим ревью;
порядок: A → B → C (B опирается на подстановку из A).

## A. Гид для агентов: как и зачем пользоваться харнессом

### Проблема

Агент в сессии харнесса знает о нём только из брифа (если сессия порождена) и из
описаний шести MCP-инструментов. Сессия, открытая через `new`, брифа не получает
вовсе. Агент не знает, что для длинных или параллельных подзадач внутри темы
предпочтительна подсессия в этой же работе, и не знает, где взять подробности,
не грузя их заранее. herdr решает это «agent skill»: короткий SKILL.md, который
ставится агентам и говорит, когда и как звать CLI.

### Решение — три слоя, от дешёвого к подробному

1. **Короткая системная вставка** при каждом запуске из харнесса и из
   `harnas-core work session new`: флаг `--append-system-prompt` с текстом до
   12 строк (≈ 120 токенов). Содержание фиксировано в `core/work/guidance.ts`:
   - ты в работе `<id> — <заголовок>` харнесса my-harnas, твоя сессия `<id>`;
   - инструменты MCP `harnas`: `get_map`, `report`, `spawn_session`, `wait_for`,
     `send_message`, `check_inbox` — одной строкой на каждый;
   - правило предпочтения: подзадача внутри этой темы, которая живёт дольше
     одного хода или должна идти параллельно, — `spawn_session` в этой работе;
     собственные субагенты Claude — для коротких разведок и правок;
   - перед завершением обязательно `report`; подробный гид — в `get_map`
     (поле `guide`) и в ресурсе MCP `harnas://guide`.
   Подстановка `{systemPrompt}` в реестре провайдеров (`providers.ts`): у claude
   `args` и `resumeArgs` получают `--append-system-prompt {systemPrompt}`; у
   провайдера без такой возможности подстановка отбрасывается, как `{settingsFile}`.
2. **Подробный гид по запросу**: `core/work/guide.md` (текст в пакете, ≈ 60 строк:
   сущности, жизненный цикл, что кладут в артефакты, как устроен бриф, как
   ждать подчинённую сессию, чего не делать). MCP-сервер отдаёт его ресурсом
   `harnas://guide`, а `get_map` возвращает поле `guide` **только при первом вызове
   в сессии** (флаг в контексте процесса сервера), дальше — `guideRef: "harnas://guide"`.
3. **Skill-файл по явной команде**: `harnas-core skill install [--dir <проект>]`
   пишет `<проект>/.claude/skills/harnas/SKILL.md` (frontmatter `name`,
   `description` с триггерами; тело — тот же `guide.md` плюс раздел «когда
   применять»). Это запись в репозиторий пользователя, поэтому только по команде
   и с печатью пути; `harnas-core skill remove` удаляет. В `~/.claude` не пишем.

### Файлы

- `packages/core/src/work/guidance.ts` — `systemGuidance(map, sessionId)` (слой 1),
  `GUIDE` (слой 2, импорт текста), `skillMarkdown()` (слой 3).
- `packages/core/src/work/guide.md` — текст гида (копируется в `dist` сборкой:
  добавить в `tsconfig`/скрипт `build` копирование `*.md`).
- `packages/core/src/providers.ts` — подстановка `{systemPrompt}` у claude.
- `packages/core/src/mcp/tools.ts`, `mcp/server.ts` — ресурс `harnas://guide`,
  поле `guide`/`guideRef` в `get_map`.
- `packages/core/src/cli.ts` — `skill install|remove`, `work session new` печатает
  команду с `--append-system-prompt`.
- `packages/tui/src/work-launch.ts` — `subs.systemPrompt` во всех трёх режимах
  (`new`, `launch`, `resume`).
- README: раздел «Что видит агент» — три слоя и команда `skill install`.

### Тесты

- `guidance.test.ts`: вставка ≤ 12 строк, содержит id работы и сессии, все шесть
  инструментов, правило предпочтения; `skillMarkdown` валидный frontmatter.
- `providers.test.ts`: у claude `--append-system-prompt` в `args` и `resumeArgs`;
  без подстановки флаг не остаётся висячим.
- `tools.test.ts`: первый `get_map` в сессии отдаёт `guide`, второй — `guideRef`;
  ресурс `harnas://guide` читается через SDK-клиент.
- `cli.test.ts`: `skill install` создаёт файл по пути проекта и печатает его;
  повторный запуск не дублирует; `remove` удаляет; `work session new` печатает
  команду с системной вставкой.
- `work-launch.test.ts`: stub получает `--append-system-prompt` в `new`, `launch`
  и `resume`; текст содержит id сессии.

### Вне объёма

Автоматическая установка skill в проект; гид для Codex/GLM (у них свои механизмы
системных промптов, провайдеры вне текущего объёма).

## B. Тихий старт: бриф как контекст, а не как первое сообщение

### Проблема

`prefix C` создаёт дочернюю сессию и отдаёт бриф первым сообщением — агент сразу
идёт отвечать, хотя задачи у него нет и пользователь хотел сначала написать сам.

### Решение

Правило: **есть задача — бриф идёт первым сообщением; задачи нет — бриф уходит в
`--append-system-prompt` вместе с системной вставкой из A, а агент ждёт ввода.**

- `spawn_session` (задача есть) — без изменений: старт по брифу, агент работает.
- `prefix C` и `harnas-core work session new` без `--task` — `task` пустая строка
  вместо заглушки «Продолжить работу сессии …»; бриф собирается без строки
  «Задача:», но с разделом «Контекст» родителя и правилами; режим запуска `new`
  с `systemPrompt = вставка A + бриф`.
- Пользователь может задать задачу дочерней сессии при создании: `prefix C`
  открывает однострочное поле «задача (Enter — без задачи)»; пустое — тихий старт,
  непустое — старт по брифу как у `spawn_session`. Оверлей на базе `overlay.tsx`,
  48 колонок, как подтверждения.
- Карточка `pending` и оверлей запуска показывают, каким будет старт: «по брифу»
  или «ждёт ваш запрос».

### Файлы

- `packages/tui/src/work-launch.ts` — `createChildSession(projectPath, workId,
  parentId, task)`; `plan()` выбирает режим по наличию `task`: пустая → `new` с
  системным промптом, иначе `launch`.
- `packages/core/src/work/brief.ts` — `buildBrief` пропускает «Задача:» при пустой
  задаче.
- `packages/tui/src/use-actions.ts`, `use-overlays.ts`, `overlays.ts` — оверлей
  ввода задачи для `C`.
- `packages/core/src/cli.ts` — `--task` необязателен.
- Спецификация TUI v2, раздел 5.1–5.2, и мокапы 4.5: дописать правило.

### Тесты

- `brief.test.ts`: пустая задача → нет строки «Задача:», контекст родителя есть.
- `work-launch.test.ts`: ребёнок без задачи → stub получает `--append-system-prompt`
  с брифом и **не** получает бриф аргументом-промптом; ребёнок с задачей → наоборот.
- `app.test.tsx`: `prefix C`, `Enter` на пустом поле → stub стартовал, первого
  сообщения нет (в кадре нет «# Работа»), панель ждёт ввода; `prefix C` с текстом →
  старт по брифу.

## C. Удаление сессии

### Проблема

`prefix x` шлёт SIGHUP и оставляет запись `exited`; убрать зависшую или ненужную
сессию из работы нельзя, дерево засоряется.

### Решение

`prefix d` — удалить выбранную сессию с подтверждением (оверлей 48 колонок):

```
┌ удалить ○ бэкенд ────────────────────────────┐
│ запись, бриф и журнал событий будут удалены  │
│ транскрипт в ~/.claude останется             │
│ дочерние: ревью, тесты → поднимутся на уровень│
│ Enter — удалить · Esc                        │
└──────────────────────────────────────────────┘
```

- Живой процесс, чей PTY у харнесса, сначала закрывается (SIGHUP, ожидание выхода
  до 3 с, затем SIGKILL). Сессию, запущенную вне харнесса и живую по pid,
  удалять нельзя: оверлей объясняет и предлагает `prefix x` там, где она запущена.
- В карте: запись удаляется; у дочерних `parent` становится `parent` удалённой
  (или `null`), из `contextFrom` других сессий id вычищается; сообщения `from`/`to`
  удалённой остаются с пометкой `deleted: true` (история переписки не теряется).
  Отдельной записи об удалении нигде не ведётся: это действие пользователя, а не
  агента, и в карте о сессии не остаётся ничего, кроме пометок в сообщениях.
- На диске: `briefs/<id>.md`, `events/<id>.jsonl`, `mcp/<id>.json` удаляются;
  `artifacts/` не трогаются (это файлы проекта).
- Id не переиспользуется: `nextSessionId` считает по максимальному id в истории
  карты, а не по длине списка — иначе новая сессия получит id удалённой, и старые
  ссылки в артефактах и переписке станут врать.
- MCP: инструмента удаления агентам не даём (это действие человека).
- `work-index` не меняется; `updatedAt` работы обновляется.

### Файлы

- `packages/core/src/work/map.ts` — `removeSession(map, id)`, `nextSessionId` по
  максимуму; `store.ts` — `deleteSessionFiles(projectPath, workId, id)`.
- `packages/tui/src/use-overlays.ts`, `overlays.ts` — оверлей `delete`;
  `use-actions.ts` — `d`; `use-panel.ts` — закрыть и дождаться выхода перед
  удалением; строка статуса — `⚑ сессия удалена`.
- README, спецификация 3.2 (таблица клавиш), мокапы 4.x — новый оверлей.

### Тесты

- `map.test.ts`: удаление поднимает детей, чистит `contextFrom`, помечает
  сообщения; `nextSessionId` после удаления не возвращает старый id.
- `store.test.ts`: файлы сессии удалены, артефакты целы.
- `app.test.tsx`: `prefix d` на живом stub → подтверждение → процесс вышел →
  записи нет в карте, в сайдбаре нет; `prefix d` на сессии «вне харнесса» →
  отказ с объяснением.
