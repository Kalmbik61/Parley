## 1. Зачем

1. **Принятые решения теряются в ленте.** Что и почему решили, команде не видно; окно
   показывает только текущее решение комнаты.
2. **Обсуждения комнат читаются только в окне.** Файла, который можно открыть, поискать и
   показать, нет.
3. **Уроки и факты проекта исчезают с сессией.** Родная память есть у каждого CLI своя:
   Claude не видит память Codex и наоборот, обе лежат в домашней папке и команде не
   видны.
4. **Поиска по прошлому нет.** Ни агент, ни человек не находят, что решали месяц назад и
   на какие грабли уже наступали.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Журнал решений | `.parley/decisions/`, файл на решение, в git; пишет хост, когда человек принимает решение или итог |
| История комнат | `.parley/history/` — локально; «Share history» кладёт снимок в `.parley/history-shared/`, в git |
| Память проекта | `.parley/memory.md`, в git, общая для команды; разделы Facts, Lessons, Agreements |
| Кто пишет память | Агенты предлагают (`remember`), человек принимает; по прямой просьбе человека — сразу, с Undo |
| Как память доходит до агента | Все факты-фразы — блоком в слое Parley (до 12 КБ); подробности — `memory_read` и поиск |
| Поиск | `search_history` по журналу, памяти, планам, бэклогу, историям комнат и итогам сессий; текстовый, без индекса |
| Родная память CLI | Не трогаем: личное остаётся там |

## 3. Журнал решений

### 3.1 Файл

`.parley/decisions/<дата>-<работа>-<комната>-<решение>-rev-<rev>.md`, например
`2026-10-05-w-0043-r-01-p-03-rev-02.md`. В имени есть принятый `rev`: повторная
обработка той же версии идемпотентна, новая принятая версия не затирает прежнюю. Отдельные файлы не дают конфликтов слияния, когда
решения принимают в разных ветках.

### 3.2 Когда пишется

Хост пишет файл, когда человек принимает решение (`rooms.resolveProposal` с Accept) или
итог плана «с проверкой» (итог — тоже решение). Возвращённые решения в журнал не идут:
они остаются в истории комнаты.

### 3.3 Содержимое

- заголовок (первая строка текста решения, иначе — «Decision p-03 in <комната>»), дата и
  время;
- комната и работа, ведущий, участники с ролями;
- текст решения в принятой версии (`rev`), замечание человека, если было;
- для решения с планом — режим и пункты с владельцами; подробности — ссылкой на снимок
  в `.parley/plans/` на неизменяемый снимок этого `rev` и события;
- для итога — сводка ведущего;
- связанные пункты бэклога.

### 3.4 Окно

Вкладка Decisions панели проекта: новые сверху, фильтр по тексту, открытие файла.

## 4. История комнат

### 4.1 Файл

`.parley/history/<работа>-<комната>.md`, локально. Читаемая лента:
- шапка — комната, работа, участники с ролями, рецепт, режим;
- письма — время, автор (ярлык и роль), вид (`question`, `decision`, `note`), текст;
- системные строки — события плана, смена режима, принятые и возвращённые решения.

### 4.2 Сборка

Источник правды — карта; файл производный. Хост переписывает его целиком через
несколько секунд после последнего изменения в комнате.

### 4.3 Share history

- Пункт меню комнаты кладёт снимок в `.parley/history-shared/<работа>-<комната>.md`.
- Перед записью окно предупреждает: текст уйдёт в git, проверь, нет ли в нём секретов.
- Повторный Share обновляет снимок; комната помечается «shared at <время>».
- Unshare удаляет снимок из рабочей копии; в истории git он остаётся.

### 4.4 Удаление и одиночные сессии

Удаление работы удаляет её локальные истории; выложенные снимки остаются — они в git и
принадлежат человеку. Истории одиночных сессий нет: их переписки — в журналах
провайдеров, итоги сессий находит поиск (раздел 6).

## 5. Память проекта

### 5.1 Файл

`.parley/memory.md`, в git:

```markdown
# Project memory

## Facts
- Build with `pnpm build`, test with `pnpm test` (vitest). <!-- m-004 · by: s-02 · 2026-10-04 -->
- Window texts are English; specs and TODOS are Russian. <!-- m-007 · human -->
  The README is English too; code comments stay Russian.

## Lessons
- PTY tests flake in worktrees with long paths — compare with a baseline run. <!-- m-009 · by: s-05 -->

## Agreements
- Sessions close only with the human's consent. <!-- m-010 · by: s-01 · on request -->
```

- Запись — пункт списка: одна фраза-факт. Строки с отступом под ней — подробности,
  необязательны. Служебный комментарий: id `m-NNN`, автор (`by: <сессия>` или `human`),
  дата, пометка `on request`.
- Разделы: **Facts** — как устроен проект; **Lessons** — грабли и уроки ошибок;
  **Agreements** — мелкие договорённости с человеком. Крупные правила совместной работы —
  в PARLEY.md.
- Человек правит в окне или в файле. Разбор и запись — как у бэклога: незнакомый текст
  сохраняется байт в байт, запись без id получает id. Используется принятый общий shared-domain
  lock (`backlog.lock`) и version/hash-bound запись с ограниченным повтором; отдельный замок
  памяти не создаётся. Маркеры конфликта — файл не трогается.

### 5.2 Как пишут агенты

`remember(kind, fact, details?, why, onHumanRequest?)`, `kind` — `fact`, `lesson`,
`agreement`:
- **По умолчанию** запись ждёт человека: она в локальном списке
  `.parley/memory-suggestions.json`, во вкладке Memory панели проекта — раздел
  `Suggested (N)` с Add, Edit & add, Dismiss; в ленте —
  `S03 suggests remembering: …`. Инструмент отвечает `suggested: ms-05`.
- **`onHumanRequest: true`** — человек сам попросил запомнить: запись сразу в
  `memory.md` с пометкой `on request`; в ленте —
  `S03 remembered on your request: … [Undo]`. Инструмент отвечает `remembered: m-012`.
- **Повтор** — тот же факт без учёта регистра у записи или ждущего предложения — не
  принимается: `already remembered: m-012`.
- **Undo** удаляет только строку, вставленную этой сохранённой операцией: id и hash строки должны совпасть. После человеческой правки возвращается memory-conflict, запись сохраняется; уже отсутствующая строка даёт идемпотентный missing. Остальные изменения файла не отменяются.

### 5.3 Чтобы агент делал это сам

Системная вставка: запоминай устойчивые факты о проекте, уроки ошибок и договорённости с
человеком через `remember`; не храни то, что и так есть в коде, git, PARLEY.md или
CLAUDE.md; один факт на вызов, коротко. Вставка укладывается в прежний потолок в 14
строк.

### 5.4 Доставка

- Блок в слое Parley — последним. Полный порядок: встроенные правила → строка моста
  (Codex) → роль → рецепт (ведущему) → бриф тихой сессии → PARLEY.md → **память**.
- Блок начинается строкой `Project memory (.parley/memory.md):`, дальше — все факты-фразы
  по разделам, с id; подробностей нет.
- Предел блока — 12 288 байт UTF-8, включая заголовки, id, provenance labels и
  строку-метку. Включаются только целые факты-фразы; переполнение даёт одно
  уведомление «почисти память» (memory-truncated).
- Происхождение agent/unknown сохраняется при человеческой правке. Принятие,
  изменение details/state и изменение самой фразы отмечаются отдельно; правка
  подробностей не повышает доверие к прежнему выводу агента. Текущие человеческие
  инструкции и условия задачи имеют приоритет над утверждениями памяти.
- Подробности — `memory_read(ids)` или поиск.
- Новая сессия видит текущую память с первого хода; идущая — после перезапуска и сжатия
  контекста, как PARLEY.md.

### 5.5 Граница со скиллами

`memory.md` хранит факты и уроки проекта, а не список скиллов машины. `remember`
не копирует `SKILL.md`, результат `find_skill`, пути установки и включённость плагинов
в память или PARLEY.md. Каталог скиллов зависит от CLI и рабочей папки сессии и
живёт в процессе MCP; память читается из основного проекта при сборке слоя.

Урок об использовании инструмента можно сохранить коротким фактом с контекстом,
но это не постоянное назначение скилла: в следующей задаче агент заново проверяет
доступность через навигатор. `search_history` не ищет в нативных каталогах скиллов;
`find_skill` не читает приватную историю или память проекта.

## 6. Поиск

### 6.1 Инструмент

`search_history(query, scope?, limit?)`:

| `scope` | Где ищет |
|---|---|
| `decisions` | Журнал решений |
| `memory` | Память проекта |
| `plans` | Снимки планов |
| `backlog` | Бэклог |
| `history` | Локальные истории комнат и выложенные снимки |
| `sessions` | Итоги и отчёты сессий из карт всех работ проекта |
| `all` (по умолчанию) | Всё сразу |

### 6.2 Как ищет

- Без учёта регистра; все слова запроса должны встретиться в одной записи. Запись —
  файл решения, факт памяти, пункт бэклога, пункт снимка плана, письмо истории, итог
  сессии.
- Порядок: выше записи с совпадением в заголовке или первой строке, при равенстве —
  новые.
- Ответ: откуда (файл и строка или id сессии), заголовок, отрывок около совпадения,
  дата. По умолчанию 10 результатов, не больше 30.
- Индекса нет: файлы читаются при каждом запросе.

### 6.3 Окно и гид

Поле поиска наверху панели проекта; результаты сгруппированы по источнику; клик
открывает файл на нужной строке, комнату или сессию. Гид: прежде чем решать что-то
крупное, поищи прошлые решения и уроки.

## 7. `.parley/`: дополнения к белому списку

К белому списку из спеки планов (и `recipes/` из спеки рецептов) добавляются:

```
!decisions/
!decisions/**
!memory.md
!history-shared/
!history-shared/**
```

`history/`, `memory-suggestions.json` и общий shared-domain lock остаются локальными.

## 8. Окно

- Панель проекта: вкладки Decisions и Memory (с `Suggested`), поле поиска.
- Меню комнаты: Share history и Unshare.
- Лента: строки о предложениях памяти и записях по просьбе (с Undo).
- Уведомления: память больше 12 КБ, ошибка чтения `memory.md`, ошибка записи журнала.

## 9. Инструменты агентов

| Инструмент | Кто | Что делает |
|---|---|---|
| `remember(kind, fact, details?, why, onHumanRequest?)` | любой | Предложить запись памяти или записать сразу по просьбе человека |
| `memory_read(ids?)` | любой | Записи памяти с подробностями; без `ids` — все |
| `search_history(query, scope?, limit?)` | любой | Поиск по прошлому (раздел 6) |

## 10. Граничные случаи

| Случай | Поведение |
|---|---|
| Корневой `.gitignore` скрывает `.parley/` | Журнал, память и выложенные истории остаются локальными; уведомление то же, что у бэклога |
| Маркеры конфликта или ошибка чтения `memory.md` | Блока памяти в слое нет; инструменты отвечают ошибкой; уведомление один раз |
| Память больше 12 КБ | Обрезка со строкой-меткой; уведомление «почисти память» |
| Журнал не записался при принятии | Решение всё равно принято; `host.log` и уведомление |
| Undo после того, как запись уже правили | memory-conflict; человеческая правка сохраняется, удаление возможно отдельным ручным действием |
| Share history | Сначала подтверждение про секреты |
| История не пересобралась | `host.log`; источник правды — карта |
| Работа удалена | Локальные истории удаляются, выложенные снимки остаются |
| Предложение памяти от закрытой сессии | Остаётся в `Suggested`, автор показан как был |

## 11. Тесты

**core (vitest):**
- журнал: имя файла и содержимое для решения и для итога; две принятые версии
  не затираются, повтор события идемпотентен, ссылка открывает snapshot своего rev;
- история: сборка ленты с шапкой и системными строками; Share и Unshare;
- память: разбор и запись без потерь, присвоение id, маркеры конфликта; маршрут
  `remember` (ждёт или сразу по просьбе); повтор; Undo;
- блок памяти в слое: только факты, последним, предел 12 КБ;
- `memory_read`;
- поиск: области, совпадение всех слов, порядок, отрывки, предел;
- белый список дополняется строками раздела 7;
- потолок 14 строк у системной вставки и английские тексты остаются зелёными.

**host:** журнал при принятии решения и итога; пересборка истории с задержкой;
уведомления; строки ленты.

**окно:** вкладки Decisions и Memory с `Suggested`; поиск; Share и Unshare с
подтверждением.

**Живые проверки:**
- принял решение — файл журнала появился (в проекте без корневого запрета — виден в
  git);
- агент предложил урок → Add → новая сессия Codex называет этот факт;
- «запомни X» → запись сразу, Undo работает;
- поиск находит прошлое решение и урок.

## 12. Порядок и зависимости
