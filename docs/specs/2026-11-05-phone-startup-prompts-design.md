# Стартовые вопросы CLI при запуске с телефона — дизайн sg-23

Статус: решения Q1–Q3 приняты человеком 2026-11-05 (переданы s-02 в r-03, m-26). В этом раунде поставляются только эта спецификация и
`docs/plans/2026-11-05-phone-startup-prompts-plan.md`; код приложения не меняется. Автор / лид r-03: s-06,
владелец: s-02. Само наличие документа не разрешает реализацию или новые правила выдачи доверия.

## 1. Цель и границы

Человек запускает сессию из iOS в новом проекте, отвечает на необходимые карточки на телефоне и получает
первый ход агента, не открывая Mac. Телефон отправляет только типизированные решения; терминалу отвечает
хост. Запрет `pty.input` и `pty.resize` из решения 5 мобильной спецификации остаётся абсолютным.

«Новый проект» — известный хосту проект без накопленных CLI-согласий; провайдер установлен, подключён,
имеет рабочие учётные данные, доступную модель и сеть. Чистая папка профиля своего endpoint с уже заданным
ключом входит в проверку. Первичная регистрация, ввод секретов, OAuth, системные окна Keychain и установка
CLI не превращаются в кнопки «Allow»: вход исключён из объёма принятого Q1 (§9); причина — «Provider needs sign-in». При отказе пользователя или
недоступном провайдере успехом считается явный отказ/блокировка, а не первый ход.

Общий путь запуска обслуживает также desktop, resume и wake; источник `phone` не даёт дополнительных прав.
Обычные tool permissions после первого хода остаются у `feed.decide` / провайдера. Обновление CLI уже имеет
отдельный дизайн от 2 ноября; sg-23 не запускает установщики и не заменяет этот дизайн.

## 4. Выбранная архитектура

### 4.1 Сначала подготовка, затем ограниченный ответ CLI

1. Проверить готовность провайдера, совместимость runner/version, определить профиль и плановый cwd.
2. Проверить доверие Parley для Codex **и семейства Claude**. Нет записи — прежняя `folder-trust`, до
   бюджета/worktree/settings/spawn. Телефонный `trustFolder` уже выражает согласие и не требует второй карточки.
   Это расширение текущего host-gate, а не утверждение, что он уже общий. Изменение для desktop и wake принято в Q3.
3. Выполнить имеющийся preflight MCP. Доверие папке не разрешает новые серверы MCP автоматически.
4. В существующих точках подготовки применить A29, custom onboarding/API-key seed и session-local Codex flags.
   Не переписывать чужой config целиком и не добавлять глобальные blanket-approvals. Сбой безопасной записи
   не означает успешное подавление: fallback возможен только для распознанного экрана.
5. Spawn получает внутренний `launchId`, уникальный в эпохе хоста. Начинается короткая фаза startup.
   Начальный task, уже переданный argv, второй раз не отправляется. Wake/mail и `pty.send` не должны попасть
   в меню startup; они ждут готовности по существующей очереди, не помечаются доставленными раньше неё.
6. После подтверждённого первого хода или готового composer без startup modal фаза закрывается. Последующие
   сообщения агента, tool prompts и цитаты CLI не распознаются этим механизмом.

### 4.2 Удержанный запуск и живой процесс — разные действия

`HeldLaunch` сегодня означает **процесс ещё не создан**. Его `continueLaunch` запускает процесс или вызывает
`WakeService.retry`; `refuseLaunch` закрывает только новую pending-сессию, сохраняя семантику resume/switch.
Нельзя класть живой startup-процесс в этот список: prune удалит live hold, а continue создаст второй процесс.

Новый coordinator `host/src/sessions/startup-prompts.ts` хранит live binding отдельно от `state.holds`:
`{ ref, hostEpoch, launchId, promptId, revision, screenFingerprint, decisionState }`.
Фаза: `observing → waiting → applying → observing → ready`; также `stopped` и `blocked`.
Карточка живого вопроса относится ровно к одному процессу. Одновременные C03 у двух сессий требуют двух решений.

Для C02, обнаруженного уже в терминале, нет универсального «да всем»: coordinator завершает только процесс,
который ещё не начал первый ход, и передаёт обычному preflight повторный запуск через `project-mcp`.
Оригинальный initial task сохраняется; повтор допустим только при доказанном отсутствии первого хода.
Если доказательства нет — blocked, без автоматического повторного исполнения задачи.

### 4.3 Распознавание и граница записи

`startup-prompt-registry.ts` — закрытый набор адаптеров по семейству, версии и promptId. Каждый имеет fixture,
полную форму видимого меню, ожидаемый выбранный пункт и точную последовательность клавиш. Тема C05 —
единственный заранее разрешённый нейтральный автоматический выбор. Остальные разрешающие действия требуют
имеющегося согласия конфигурации или нового решения человека. Regex по слову «trust»/«continue» недостаточен.

Хост использует **текущий видимый экран** `pty/screen.ts` (`@xterm/headless`), не историю и не сырые куски
stdout. Нужен callback после обработки write в xterm: существующий `screen.write` асинхронно парсит буфер,
немедленный `screenText()` ещё может читать предыдущий кадр. Split chunks, ANSI, очистка и resize входят в тест.
Динамические счётчики не должны менять смысловой fingerprint; смена пункта/пути/провайдера меняет revision.

Непосредственно перед **каждой** записью хост проверяет ref, эпоху/launchId, фазу, текущую форму экрана,
семантический fingerprint, выбранный пункт и состояние pending. Между проверкой и записью не допускается
`await`, позволяющий другому обработчику переключить процесс/меню. Многошаговый выбор проверяет новый кадр
между клавишами; никаких отложенных blind Enter. Ручной ввод с Mac инвалидирует старую карточку до записи.
Разрешение не выводится из текста проекта/вывода агента: оно связано с host-owned provider/profile/cwd.

При неизвестном экране или несовместимой версии хост **не отвечает**. По истечении 30 секунд startup без
готовности/известной карточки показывает сессии «Startup needs attention», безопасный reason code и доступные
Stop / Resume; это watchdog, не доказательство появления prompt. Для длинной загрузки готовность позже
снимает предупреждение. Общий raw screen, секреты, key suffix, env, заголовки MCP в карточку/аудит не попадают.
Timeout не нажимает Enter, не убивает рабочий агент и не повторяет его задачу автоматически.

## 5. Контракт согласий и b-021

### 5.1 Привязка существующих карточек

Добавить `holds: SessionRef[]` к `FolderTrustCard` и `ProjectMcpCard`, вычисляемые из настоящих удержаний
`state.holds`, с дедупликацией полного ref. Это b-021; отдельный исполнитель не должен повторно реализовать его.
`requestedBy.sessionId` — автор запроса, не удержанная сессия. При добавлении/удалении hold публикуется upsert,
даже если серверы/текст прежние; один MCP consent может охватывать несколько work и worktree.
Изменение только holds не меняет MCP revision выбора серверов. После восстановления/prune публикуется
актуальный список. Клиенты сопоставляют projectPath + workId + sessionId, а не work-level fallback.
При старом хосте без holds карточка остаётся в Inbox с явной неизвестной привязкой; её не приписывают всем
сессиям работы. Это additive поле для старых readers; MCP `version: 1` сохраняется, пока форма выбора прежняя.

### 5.2 Новая карточка живого вопроса

Предлагаемое дополнение к `ConsentCard` (не реализовано):

```ts
type CliStartupPrompt = 'claude-folder-trust' | 'claude-bypass-warning'
  | 'claude-api-key' | 'claude-security-notes' | 'codex-model-migration'
  | 'codex-welcome' | 'codex-full-access-warning';
interface CliStartupCard {
  id: string;
  kind: 'cli-startup';
  version: 1;
  revision: number;
  projectPath: string;
  at: string;
  state: 'pending' | 'allowed' | 'denied';
  ref: SessionRef;
  provider: string;
  providerLabel: string;
  cliVersion: string;
  prompt: CliStartupPrompt;
  // Только безопасные данные для шаблонов UI; без свободного терминального текста.
  context: { folder?: string; model?: string; authMode?: 'api-key' };
}
// Ровно существующий RPC, без input/keys/command/action строк от клиента:
consents.decide({ id, revision, decision: 'allow' | 'deny' });
```

Полный discriminated union должен ограничить context для каждого prompt. `version` определяет отображение,
`revision` — состояние конкретного вопроса; внутренние launchId/экран клиенту не нужны. `enabled` разрешён
только для project-mcp. Неверная revision/лишние поля отклоняются до side effects (`bad_request`).
Закрытая/утраченная карточка и повтор решения дают `applied:false`; первое принятое решение — `applied:true`.
`applied` значит «решение принято», а не «агент уже начал работу»; готовность показывается статусом сессии.

Allow соответствует конкретной подписи из §3: доверить именно показанную папку, подтвердить уже выбранный
bypass, использовать настроенный ключ, подтвердить Security notes, сохранить текущую модель, продолжить welcome.
Deny всегда останавливает этот live startup-процесс, без выбора неожиданного login/другой модели. Поведение
**project-mcp deny не меняется**: он продолжает с выключенными серверами. Остаточный C01 allow требует
действующей записи trust Parley; если её отозвали, карточка недействительна и возвращается preflight trust.

Ответ резервируется синхронно до I/O. Запись intent должна успешно сохраниться до PTY write; существующий
best-effort `consents.save` для новой ветки недостаточен. При сбое записи — ноль ввода. Если запись клавиш
неоднозначно завершилась/процесс сменился, карточку нельзя автоматически проигрывать снова: статус blocked,
повторное наблюдение. Crash между intent и write не позволяет обещать exactly-once; контракт — **at-most-once
для конкретного решения**, с возможной новой карточкой после сверки. После рестарта хоста все live bindings
считаются утраченными, старые карточки удаляются; заново запущенный процесс получает новый launchId и consent.
Предстартовые folder/MCP holds по-прежнему восстанавливаются существующим механизмом.

## 6. Телефон, окно и совместимость

Новый вид отображается существующим потоком `consents.list` / `consents.changed` в Inbox → Needs you и на
странице точной сессии. Нужны явные renderer branches для `cli-startup`: существующая phone-карточка MCP
не означает автоматическую поддержку нового вида. Заголовок называет провайдера/сессию; текст и кнопки —
из проверенных UI-шаблонов, показывают последствия allow. Вопрос о bypass не называется просто «Continue».

Remote сохраняет app lock, переключатель запуска/сообщений, аудит `call`, лимиты и `by: phone`; нового RPC и
доступа к `pty.input` не появляется. Для актуального клиента `revision` передаётся при обоих ответах.
Потеря ответа сети вызывает перечитывание карточек, а не повтор решения. Unknown kind/version виден как
неподдержанный запрос с предложением обновить приложение, без активной кнопки разрешения. Совместимый
phone client — предусловие positive E2E; старые клиенты не входят в обещание «всё решается с телефона».

Desktop/island получают ту же новую ветку; старый Telegram/другие consumers должны безопасно пропускать
неизвестный вид, не трактуя его как folder trust. Смена app background/foreground восстанавливает карточку
через снимок; это не зависит от push-уведомления. Сырой terminal-view не нужен для приёмки.

## 7. Проверка результата

Матрица §3 задаёт **15 отдельных ID** (C01–C08, X01–X07); test manifest обязан иметь строку на каждый ID.
Для известных блокирующих вопросов — отдельный positive case до first turn и отказ; для Н — fixture/probe
в T1/T2 либо документированное N/A на поддерживаемой версии. Нельзя зачесть общий timeout-тест вместо
воспроизведения известного вопроса. Неблокирующим строкам соответствует тест отсутствия ложной карточки.

Сквозной обязательный маршрут: iOS → New session → свежий известный проект → folder consent → MCP consent
(если нужен) → известные startup cards → первый ответ на безопасную задачу. По одному прогону для Claude,
Codex, GLM, custom bearer, custom api-key и дополнительного Claude account; минимум один новый worktree,
Codex resume с другим cwd и пустым prompt. Для вариантов, которым нужны реальные доступы, отсутствие
credentials означает «не проверено», а не pass. Без-Mac измерение: 0 действий в desktop после phone launch;
PTY write audit подтверждает, что ответы пришли из coordinator, а remote вызовов `pty.input` — 0.

Дополнительные критерии:

- На каждый разрешённый экран не более одной последовательности ответа; нет повторной отправки initial task.
- Два телефона / телефон и Mac, двойное нажатие, смена меню, close/switch/restart, потеря ответа сети — ноль
  ввода в чужой процесс или следующий экран. Карточка сессии A не видна как карточка B.
- Profile seed сохраняет посторонние настройки и права файла; ключи и их хвосты не встречаются в wire/audit/fixtures.
- Старт после MCP deny достигает первого хода без запрещённых серверов; смена fingerprint требует нового решения.
- Unknown prompt не становится auto-allow; blocked отражён на телефоне, startup watchdog детерминированно проверен.

Измерять время от принятого последнего решения до first turn отдельно от ожидания человека/сети/очереди.
Фиксированного SLA первого ответа пока нет: **not measured**. 30 секунд — порог диагностического watchdog,
не обещание скорости модели. Живые пробы CLI и UI в этом документальном раунде не выполнялись.

## 8. Риски и ограничение реализации

Главные риски — изменяемый TUI, чужие launch overrides, общий профиль GLM/Claude, одновременные записи
профиля CLI, TOCTOU между кадром и PTY write и аварийное восстановление. Из-за них live-write coordinator
и изменения trust/write boundary выделены senior-only в плане; остальные задачи выполняет junior.
Свободный терминальный текст не становится программой действий хоста. Не подтверждённые key names и
внутренние поля CLI не добавляются «на всякий случай»; каждый adapter имеет проверенный диапазон версий.

## 9. Решения человека — приняты 2026-11-05

Источник: решения человека, переданные владельцем s-02 в r-03, сообщение m-26.

1. **Q1 — граница входа: принято.** Без-Mac обещание относится только к уже подключённому провайдеру.
   Первичный и повторный вход исключены из объёма; при необходимости входа показывается «Provider needs sign-in».
   OAuth, ввод секретов и системные окна входа этим планом не реализуются.
2. **Q2 — опасные режимы: принято.** Уже запрошенный bypass/full-access подтверждается на телефоне
   карточкой с явным описанием риска: allow разрешает только этот запуск, deny останавливает запуск.
   Parley не включает опасный режим самостоятельно и не подавляет предупреждение молча.
3. **Q3 — единое доверие: принято.** Host `folder-trust` gate распространяется на все Claude-family launches,
   включая desktop и wake, с использованием существующего согласия Parley. Одного старого нативного trust
   без записи Parley недостаточно; человек один раз подтвердит карточку.

Открытых продуктовых развилок Q1–Q3 больше нет. Разрешение этого раунда остаётся документальным:
зафиксировать решения и закоммитить спецификацию с планом; реализация приложения не разрешена.
