# Parley обновляет себя сам — дизайн

Дата: 2026-11-15. Редакция 6. Автор: s-370 (Fable). Ревью критика s-392 (Codex Astra): редакции 1–4 — «вернуть»
(10, 9, 4 и 3 замечания), редакция 5 — «принять с правками» (1 замечание), редакция 6 — «принять». Что сделано по
каждому замечанию — в §12. Уточнения, принятые при реализации, — в §13.

Меняет прежние решения:

- План релиза 0.1.0, V6 (`docs/specs/2026-10-01-release-0.1.0-plan.md`) и шапка `main/update-check.ts`: «окно только
  сообщает о новой версии, ничего не скачивается и не ставится». Теперь по клику человека Parley скачивает релиз и
  заменяет себя.
- `README.md`, раздел «Updates» («it does not update itself») и перечень собственных запросов Parley.

## 1. Зачем

Сейчас Parley раз в сутки спрашивает GitHub о последнем релизе и показывает тост со ссылкой на страницу релиза.
Дальше человек делает всё руками: выходит, качает `.dmg`, заменяет приложение, снимает карантин. У автора для этого
есть скрипт `~/.local/bin/parley-update` (103 строки, bash): он качает zip релиза через `gh`, сверяет SHA-256 с
`SHA256SUMS.txt`, проверяет версию приложения внутри, ждёт выхода из Parley, заменяет `/Applications/Parley.app`
переименованием и снимает карантин.

Цель: то же самое делает сам Parley, по кнопке в окне, без терминала и без `gh`.

## 2. Что остаётся как есть

- Проверка новой версии (`main/update-check.ts`): запрос `releases/latest` при старте и раз в сутки, переключатель
  «Check for updates», `PARLEY_UPDATE_CHECK=off`. Разбор ответа и сравнение версий не меняются.
- Выход из приложения целиком: вопрос о несохранённых файлах (`guardWindowClose`), вопрос о живых сессиях и
  остановка хоста (`quit-guard`). Установка идёт через этот же выход и ничего в нём не повторяет и не обходит.
- Сборка и релиз: имена файлов `parley-macos-<arch>.zip` и `SHA256SUMS.txt`, подпись ad-hoc.
- Хост, протокол, остров, телефон не трогаются. Всё изменение — в `packages/desktop`.
- Скрипт `parley-update` остаётся у автора: он умеет то, чего в окне не будет (`--force`, установка названной версии).

## 3. Решения

1. **Только по клику.** Parley ничего не скачивает сам: загрузка начинается с кнопки «Update». Около 200 МБ без
   спроса — не то, что обещает README о собственных запросах.
2. **Установка — отдельным кликом «Restart now».** Готовое обновление не ставится при обычном выходе и при
   выключении системы.
3. **«Restart now» — это обычный выход с намерением.** Клик запоминает намерение и вызывает `app.quit()`. Вопросы
   задаёт сам выход, хост гасит он же. Намерение переживает только собственные повторы этого выхода (§5.4): любой
   другой выход, начатый позже, его сбрасывает. Перечислять пути отмены выхода для этого не нужно.
4. **Источник — только найденный релиз.** Окно не передаёт main ни версию, ни адрес, ни путь. Main ставит релиз,
   который сам нашёл проверкой: стабильный `X.Y.Z` строго новее запущенной версии. Понижения и переустановки нет.
5. **Адреса — из констант:** `https://github.com/Kalmbik61/Parley/releases/download/v<версия>/<файл>`, где файл —
   `parley-macos-<arch>.zip` или `SHA256SUMS.txt`, `<arch>` — архитектура запущенной сборки (`process.arch`: `arm64`
   или `x64`). Из ответа GitHub адреса не берутся.
6. **Перенаправления не проверяются.** GitHub отдаёт файлы релиза через перенаправление на свой CDN. Первый запрос
   идёт на `github.com` по TLS, перенаправление выдаёт он же, а целостность архива даёт SHA-256. (`Response.url` у
   `net.fetch` Electron к тому же не заполняется.) Критик принял это в рамках объявленного корня доверия.
7. **Проверка та же, что в скрипте:** SHA-256 архива равен строке `SHA256SUMS.txt` того же релиза; внутри архива
   есть `Parley.app` той же версии с идентификатором `dev.parley.desktop`.
8. **Долгая работа — до выхода, после выхода — два переименования.** Архив распаковывается и проверяется рядом с
   приложением, пока Parley работает. Сценарий `/bin/sh`, запущенный на выходе, только переименовывает прежнее
   приложение в сторону, новое — на его место, и открывает его. Запуску Parley замена не мешает; единственный замок —
   между двумя сценариями замены одного приложения (§5.5).
9. **Прежнее приложение хранится, пока новое не запустилось.** Его удаляет новая сборка, когда прочла итог замены и
   узнала в нём свою версию.
10. **Где нельзя — как раньше.** Если Parley не может заменить себя (§5.2), кнопка остаётся прежней «Download» со
    страницей релиза.
11. **Корень доверия не меняется:** релиз репозитория на GitHub по TLS, как при ручной загрузке и в скрипте.
    `SHA256SUMS.txt` лежит там же, где архив: он ловит порчу и обрыв загрузки, а не подмену релиза.

## 4. Поведение для человека

### 4.1. Тост

| Состояние | Текст | Кнопки |
|---|---|---|
| Найдена версия, заменить себя можно | `Parley X.Y.Z is available` | «Update», «Later» |
| Найдена версия, заменить себя нельзя | то же | «Download» (страница релиза), «Later» — как сейчас |
| Идёт загрузка | `Downloading Parley X.Y.Z… N%` (без процента, если размер неизвестен) | «Cancel» |
| Проверка и распаковка | `Checking Parley X.Y.Z…` | «Cancel» |
| Готово | `Parley X.Y.Z is ready` и строка `Restarting stops running agents` | «Restart now», «Later» |
| Не удалось | `Couldn't update to X.Y.Z: <причина>` | «Download» (страница релиза), «Later» |

Тост один, тот же `UPDATE_TOAST_ID`: состояния сменяют друг друга на месте. Правила `dismissedUpdate` прежние с одной
поправкой: «Update» версию закрытой не записывает. Смахнутый тост о версии больше не появляется, но загрузка, если
шла, продолжается, а состояние видно в настройках.

«Restart now» тост не закрывает: если выход отменён вопросом, тост остаётся на месте.

### 4.2. Настройки

Settings → Notifications, под переключателем «Check for updates», — строка состояния с одной кнопкой:

| Состояние | Строка | Кнопка |
|---|---|---|
| Нет новой версии или проверка выключена | строки нет | — |
| Найдена, можно заменить | `Parley X.Y.Z is available` | «Update» |
| Найдена, нельзя заменить | `Parley X.Y.Z is available` | «Download» |
| Загрузка | `Downloading X.Y.Z — N%` | «Cancel» |
| Проверка | `Checking X.Y.Z…` | «Cancel» |
| Готово | `X.Y.Z is ready to install` | «Restart to update» |
| Не удалось | `Couldn't update: <причина>` | «Try again» |

Строка нужна, потому что тост можно смахнуть, а другого входа к обновлению тогда не остаётся.

### 4.3. После перезапуска

Окно при старте читает итог замены (§5.6) и показывает его один раз:

- запущенная версия равна версии из итога — тост `Parley updated to X.Y.Z`;
- итог — отказ и запущена прежняя версия — тост `Couldn't update to X.Y.Z: <причина>. The previous version is
  still installed.`

Доступы macOS (папки, микрофон) новая сборка спросит заново, как и после ручной замены: у каждой сборки своя
подпись ad-hoc. Это не меняется.

## 5. Устройство

Всё в `packages/desktop/src/main`, кроме тоста и строки настроек.

### 5.1. Состояние

```ts
type UpdateFailure =
  | 'network'        // нет ответа, не 2xx, обрыв, вышло время ожидания
  | 'too_large'      // файл больше предела
  | 'checksum'       // архива нет в SHA256SUMS.txt или хэш не совпал
  | 'bad_archive'    // не распаковался, нет Parley.app, чужая версия или идентификатор, не снялся карантин
  | 'disk'           // ошибка записи: каталог загрузки, каталог рядом с приложением, файл сценария
  | 'cannot_replace'; // к моменту установки заменить себя уже нельзя

type UpdateState =
  | { phase: 'idle' }
  | { phase: 'available'; version: string; url: string; canInstall: boolean }
  | { phase: 'downloading'; version: string; url: string; received: number; total: number | null }
  | { phase: 'verifying'; version: string; url: string }
  | { phase: 'ready'; version: string; url: string }
  | { phase: 'failed'; version: string; url: string; reason: UpdateFailure };
```

`url` — страница релиза из проверки (для «Download»). Состояние живёт в main; окно получает его событием
`app:update-state` и по запросу `app:get-update-state`. Прежние `app:update-available` и `app:get-update`
заменяются ими: окно и main едут в одной сборке, пары версий здесь нет.

Мост окна (`bridge.app`): `getUpdateState()`, `onUpdateState(listener)`, `downloadUpdate()`,
`cancelUpdateDownload()`, `installUpdate()`, `takeUpdateResult()`. Ни один вызов не принимает версию, адрес или
путь.

Переходы:

- **Проверка нашла релиз.** Из `idle`, `available` и `failed` → `available` с найденной версией. В `downloading`,
  `verifying` и `ready` находка состояния не меняет: релиз, выбранный кликом, остаётся выбранным, пока он не
  установлен, не отменён или не отказал. Повторное сообщение о той же версии (проверка шлёт его при каждом удачном
  ответе) ничего не меняет в любом состоянии, кроме `idle`.
- `downloadUpdate()` из `available` (с `canInstall`) или `failed` → `downloading` → `verifying` → `ready` либо
  `failed`. Из прочих состояний — ничего.
- `cancelUpdateDownload()` из `downloading` и `verifying` → `available` с последней найденной версией.
- `installUpdate()` из `ready` — §5.4; состояние остаётся `ready`. Из прочих — ничего.
- Переключатель «Check for updates» выключили → `idle`; идущая попытка отменяется, готовая удаляется.

**Попытка.** У каждой загрузки свой номер и свои каталоги (§5.3). Отмена обрывает запрос, завершает дочерний
процесс попытки (`ditto`, `defaults`, `xattr`) и ждёт его конца; каталоги попытки удаляются только после этого.
Итог отменённой попытки состояния не меняет. Новая попытка чужих каталогов не трогает и не переиспользует.

События о ходе загрузки — не чаще четырёх в секунду.

### 5.2. Можно ли заменить себя

`canInstall` считается при каждом переходе в `available` и ещё раз в `installUpdate()`. Все условия сразу:

- `process.platform === 'darwin'` и `app.isPackaged`;
- путь исполняемого файла имеет вид `<каталог>/<имя>.app/Contents/MacOS/<файл>`; `<каталог>/<имя>.app` — «путь
  приложения» (после `realpath`);
- путь приложения не лежит в `/Volumes/` и не содержит `/AppTranslocation/`;
- у процесса есть право записи в `<каталог>` и в сам каталог приложения;
- `/usr/bin/lockf` умеет брать замок на открытый дескриптор оболочки (форма `lockf -s -t 0 <fd>`; на ней стоит
  замок замены, §5.5). Проверяется один раз за запуск пробным вызовом на файле в каталоге загрузок.

### 5.3. Загрузка и проверка

Каталоги попытки номер `n`:

- загрузки — `<parleyHome>/desktop/updates/<n>/` (права `0700`): сюда пишется архив;
- подготовки — `<каталог>/.<имя>.app.update-<pid>-<n>/`, рядом с приложением, на том же томе: сюда распаковывается
  `Parley.app` и пишется сценарий замены. `<pid>` — pid процесса main. Каталогом владеет этот main, а после
  запуска сценария — сценарий; передача отмечается файлом `handoff` внутри каталога (§5.4).

Шаги:

1. `SHA256SUMS.txt` — `net.fetch`, без куки и токенов (`credentials: 'omit'`), заголовки как у проверки версии.
   Предел размера 64 КиБ, предел времени на весь запрос 30 с. Из него берётся строка, чьё второе поле в точности
   равно имени архива; хэш — 64 шестнадцатеричных знака. Нет строки или форма другая → `checksum`.
2. Архив — потоком в файл, SHA-256 считается по ходу. Предел размера 1 ГиБ (`too_large`). Ожидание без единого
   байта дольше 60 с → `network`; отсчёт идёт от начала запроса, то есть покрывает и ожидание заголовков, и
   перенаправления, и сбрасывается только полученными байтами. Общего предела времени нет.
3. Хэш файла не равен ожидаемому → `checksum`.
4. Распаковка: `/usr/bin/ditto -xk <архив> <каталог подготовки>`. Ненулевой код → `bad_archive`.
5. Проверка приложения: есть `Parley.app/Contents/MacOS/Parley`; `CFBundleShortVersionString` равен версии;
   `CFBundleIdentifier` равен `dev.parley.desktop` (чтение — `/usr/bin/defaults read <app>/Contents/Info <ключ>`).
   Иначе → `bad_archive`.
6. Карантин: `/usr/bin/xattr -dr com.apple.quarantine <app>`. Команда возвращает 0 и тогда, когда атрибута нет
   (проверено на macOS 27). Ненулевой код → `bad_archive`.
7. Каталог загрузки удаляется: архив больше не нужен.

Любой отказ и отмена удаляют оба каталога попытки (после конца дочернего процесса). Одновременно идёт одна попытка.

### 5.4. Установка: «Restart now»

**Клик.** `installUpdate()` из `ready`:

1. Повторная проверка §5.2 и того, что подготовленное приложение на месте; отказ → `failed: cannot_replace`.
2. Сценарий замены пишется в каталог подготовки (`helper.sh`, права `0700`); отказ → `failed: disk`.
3. Запоминается намерение: `{ версия, путь приложения, путь подготовленного приложения, путь сценария, путь итога }`.
4. `app.quit()` — «своим» вызовом (см. ниже).

Parley при этом не меняется: вопросы о несохранённых файлах и о живых сессиях задаёт обычный выход, хост гасит он же.
Отказались в любом из вопросов — приложение работает дальше, как после отменённого ⌘Q.

**Намерение переживает только свои повторы выхода.** Модуль `main/quit-intent.ts`:

- «свой» вызов — `app.quit()`, обёрнутый так, что на время самого вызова стоит отметка; `before-quit` Electron
  порождает синхронно внутри `app.quit()`;
- слушатель `before-quit`: отметки нет → намерение сбрасывается; отметка есть → намерение остаётся;
- «своими» вызовами делаются ровно четыре места: клик из этого раздела и три существующих повтора выхода —
  `quit-guard.ts` (после вопроса о сессиях и остановки хоста), `window.ts` в ответе «закрыть» на вопрос о файлах
  (`if (quit) app.quit()`) и `window.ts` в «Quit anyway» зависшей страницы, если вопрос был задан из-за выхода
  (`quitting`). Сторожа получают для этого по одному необязательному параметру — функцию «повторить выход».

Следствия, без перечисления путей отмены:

- выход отменён или брошен любым способом (ответ «Cancel», неудачное сохранение, перезагрузка или падение
  страницы, отменённая выгрузка) — намерение остаётся в памяти, но следующий выход, начатый не повтором (⌘Q, меню,
  Dock), сбрасывает его первым же `before-quit`;
- человек нажал ⌘Q, пока стоит вопрос, заданный «Restart now», — намерение сброшено, выход пройдёт без установки;
- повтор выхода, принадлежащий чужой попытке, намерения не найдёт: оно сброшено её первым `before-quit`.

**Вызов, слившийся с идущим выходом.** `app.quit()` во время уже идущего выхода (Electron ждёт выгрузки страниц)
возвращается сразу и `before-quit` не порождает (`Browser::Quit`, Electron 44.4.5). Поэтому:

- выключение системы сбрасывает намерение явно: обработчик `powerMonitor 'shutdown'` (`index.ts:300–303`) делает
  это до своего `app.quit()`. Иначе выключение, пришедшее посреди выхода «Restart now», запустило бы сценарий;
- ⌘Q посреди выхода «Restart now» ничего не меняет: это тот же выход, начатый кликом.

**Событие `quit`.** Слушатель синхронный и срабатывает один раз. Намерения нет → ничего. Намерение есть — по
порядку:

1. До запуска в каталоге подготовки синхронно создаётся пустой файл `handoff`: с этого мига каталог считается
   переданным сценарию. Не создался → сценарий не запускается, в файл итога пишется отказ `helper` (не затирая
   существующий файл, флаг `wx`).
2. `spawn('/bin/sh', [сценарий, pid, путь приложения, путь подготовленного, версия, путь итога], { detached: true,
   stdio: 'ignore' })`, сразу — слушатель `error`, затем `unref()`. Запуск не удался, и это видно сразу (исключение
   или `child.pid === undefined`) → отказ `helper` в файл итога тем же способом.

Отказ, который виден только позже (событие `error` после возврата, `/bin/sh` не прочёл файл сценария), main записать
не обещает: процесс уже завершается. Тогда Parley просто вышел, обновление не поставлено, тоста при следующем
запуске нет.

Переданный каталог убирает только сценарий. Старт окна каталог с файлом `handoff` не удаляет никогда (§5.6): по
мёртвому pid нельзя понять, что закончился и дочерний `mv` или `rm` убитого сценария.

### 5.5. Сценарий замены

Текст сценария собирает функция в коде из констант: пути и версия в текст не подставляются, только передаются
аргументами. Параметры сборки текста — время ожидания и пути утилит (`mv`, `rm`, `lockf`, `open`, `ps`); в
приложении это константы (60 с и `/bin/mv`, `/bin/rm`, `/usr/bin/lockf`, `/usr/bin/open`, `/bin/ps`), тесты
подставляют свои. Тело сценария обёрнуто в функцию, вызываемую последней строкой: оболочка разбирает файл целиком
до исполнения.

Имена рядом с приложением `<каталог>/<имя>.app`: прежнее приложение — `<каталог>/.<имя>.app.old`, итог —
`<каталог>/.<имя>.app.result`, замок замены — `<каталог>/.<имя>.app.swap`. Итог лежит рядом с приложением, а не в
доме Parley: он относится к этому приложению, какой бы дом ни был у запущенного экземпляра.

**Один пишущий на приложение.** Два экземпляра с разными домами Parley могут оба запустить сценарий. Замок замены —
замок ядра на файле `<каталог>/.<имя>.app.swap`: сценарий открывает файл на своём дескрипторе (`exec 9>файл`) и
берёт замок без ожидания (`lockf -s -t 0 9`). Замок держится, пока жив сценарий или его дочерний процесс, и
снимается ядром с их концом: мёртвых замков, записи владельца и их уборки нет. Занято (код 75) или замок взять не
удалось → сценарий отступает (`busy`). Сам файл замка не удаляется никогда и ничего не содержит. `open` запускается
с закрытым дескриптором замка. Запуску Parley замок не мешает и стартом окна не читается. (Проверено на macOS
27.2: второй претендент получает 75; после `kill -9` держателя и его дочерних процессов замок свободен.)

Всё, что сценарий меняет рядом с приложением, включая файл итога, он делает, держа замок. Отказы до замка
(`quit_timeout`, `busy`) итога не пишут.

Перед каждым `mv` сценарий проверяет, что места назначения нет: `mv` на существующий каталог положил бы источник
внутрь него.

| № | Шаг | Отказ → исход | Что на диске после отказа |
|---|---|---|---|
| 1 | Ждёт конца процесса окна (`kill -0`), не дольше предела | `quit_timeout`, итог не пишется | ничего не тронуто |
| 1а | Берёт замок замены | `busy`, итог не пишется | ничего не тронуто |
| 2 | Ждёт, пока не останется процессов, чей исполняемый файл лежит в `<приложение>/Contents/MacOS/` (другой экземпляр того же приложения), не дольше предела. Сравнение — точное начало строки `ps -axo comm=`, без регулярных выражений | `still_running` | ничего не тронуто |
| 3 | Проверяет: приложение на месте, подготовленное приложение на месте | `no_app` | ничего не тронуто |
| 4 | Убирает остаток прежней замены `.old` (приложение на месте, значит, это не единственная копия) | `swap_failed` | прежнее на месте |
| 5 | Переименовывает приложение в `.old` | `swap_failed` | прежнее на месте |
| 6 | Переименовывает подготовленное приложение на место | возвращает `.old` на место → `swap_failed`; возврат не удался → `restore_failed` | `swap_failed`: прежнее на месте. `restore_failed`: приложения нет, прежнее — в `.old`, новое — в каталоге подготовки |
| 7 | Пишет итог `swapped`, открывает приложение (`open`) | `open` вернул не ноль → итог `launch_failed` | новое на месте, прежнее в `.old` |
| 8 | Удаляет каталог подготовки | — | новое на месте, прежнее в `.old` до подтверждения |

После отказов шагов 2–6, при которых приложение на месте, сценарий пишет итог, удаляет каталог подготовки и открывает
прежнее приложение (`open`). После `busy` он удаляет свой каталог подготовки и открывает приложение. После
`restore_failed` он пишет итог, ничего не удаляет и ничего не открывает. Замок снимается с концом сценария. После
шага 6 сценарий приложение больше не трогает: отката после `open` нет.

Итог — одна строка: `swapped X.Y.Z` либо `failed X.Y.Z <код>`. Версию main проверяет до запуска
(`^\d+\.\d+\.\d+$`), коды — `still_running`, `no_app`, `swap_failed`, `restore_failed`, `launch_failed` и `helper`
(его пишет main, §5.4).

Если сценарий убит:

| Где убит | Что на диске | Что дальше |
|---|---|---|
| Шаги 1–4 | прежнее на месте | Parley открывается как обычно. Каталог подготовки остаётся лежать: он передан сценарию, и старт окна его не трогает (риск 7). Замок освобождается, когда кончится последний процесс, державший его дескриптор |
| Между шагами 5 и 6 | приложения нет; прежнее в `.old`, новое в каталоге подготовки | вручную: `mv <каталог>/.<имя>.app.old <каталог>/<имя>.app` — эта строка есть в README |
| После шага 6 | новое на месте; прежнее в `.old` | Parley открывается новой версией. Без итога `.old` остаётся до следующего обновления (шаг 4) |

Процессы прежней сборки вне `Contents/MacOS/` заменой не проверяются, как и в скрипте: мост Remote access
переживает выход намеренно, и новое окно само заменяет мост другой версии; хост, который не погас, новое окно
покажет прежним тостом «Host is outdated — restart».

### 5.6. Старт окна

Только там, где заменить себя можно (§5.2); до создания окон:

1. **Итог.** Файл итога рядом с приложением читается и удаляется. Чужая форма — как отсутствие.
   - Версия итога равна запущенной (`swapped` или отказ `launch_failed`: приложение всё-таки запустилось) → тост
     «обновлено», `.old` удаляется в фоне.
   - Отказ и запущена другая версия → тост отказа.
   - `swapped` с другой версией или итога нет → ничего; `.old`, если он есть, не трогается.
2. **Каталоги подготовки** рядом с приложением (`.<имя>.app.update-<pid>-<n>`). Каталог удаляется, только если
   `<pid>` из имени не жив (или равен своему) и файла `handoff` в каталоге нет, то есть сценарию его не передавали.
   Переданный каталог и каталог живого чужого экземпляра не трогаются. Переданный каталог, который сценарий не
   убрал сам (сценарий убит, запуск не удался), остаётся лежать (риск 7).
3. **Каталог загрузок** в доме Parley очищается целиком.

Готовое, но не установленное обновление после перезапуска окна качается заново (§11).

## 6. Приёмка

«Тест» — юнит- или интеграционный тест в `packages/desktop`; «вживую» — лист для человека.

Тесты сценария замены запускают настоящий `/bin/sh` во временном каталоге с поддельным приложением (каталог
`X.app` с `Contents/MacOS/X`). Текст сценария собирается с коротким временем ожидания и с подставными утилитами:
`open` — файл, записывающий свои аргументы и возвращающий заданный код; `ps` — файл, печатающий заданный список;
`mv` и `rm` — обёртки над настоящими, отказывающие на заданном по счёту вызове. Сеть в тестах загрузки —
подставной `fetch`; дочерние процессы проверки — настоящие (`ditto`, `defaults`, `xattr` есть на macOS и в CI).

## 7. Риски

1. **Parley ставит скачанный код.** Корень доверия — релиз репозитория на GitHub; тот, кто может выпустить релиз в
   репозитории, может доставить код на машину одним кликом человека. При ручной загрузке и в скрипте — то же самое.
2. **Запуск Parley в момент замены.** Между концом процесса окна и концом замены Parley ничем не заперт. Длина
   этого промежутка не измерена: в него входят опрос сценария (шаг 0,1 с), проверка `ps`, удаление остатка `.old`
   от прошлой замены, если он есть, и два переименования. Parley, открытый человеком в этот промежуток, запустится
   из прежнего каталога, который затем будет переименован в `.old`. Он останется прежней версией до следующего
   запуска, и его исправная работа после смены каталога на диске не гарантируется. Если до этого новую версию
   откроет экземпляр с другим домом Parley, она удалит `.old` под работающим процессом. Запрета запуска на время
   замены нет намеренно: у скрипта тот же промежуток, а запирающий старт протокол оказался сложнее самой замены
   (ревью редакции 2); критик этот размен принял. Каталог подготовки работающего сценария старт окна не трогает, а
   два сценария друг другу не мешают (замок замены).
3. **Окно между двумя переименованиями.** Сценарий, убитый между шагами 5 и 6, оставляет машину без приложения по
   привычному пути; обе копии целы, восстановление — одной командой из README.
4. **Остатки старой сборки.** Хост, который не погас, и мост Remote access живут после замены из переименованного,
   а после подтверждения — удалённого каталога. Так же ведёт себя скрипт. Окно заменяет мост при старте и
   предлагает перезапустить хост.
5. **Каталог подготовки доступен на запись пользователю.** Процесс с правами пользователя может подменить
   подготовленное приложение между проверкой и установкой. Такой процесс может заменить и само приложение; новой
   возможности это ему не даёт.
6. **Синхронность `before-quit`.** Намерение опирается на то, что Electron порождает `before-quit` внутри вызова
   `app.quit()`. Если это изменится, свой вызов перестанет отличаться от чужого и намерение будет сбрасываться —
   обновление перестанет ставиться, но не поставится без клика. Тест SU-10 на настоящем `app` в e2e не идёт;
   проверяется вживую (SU-26).
7. **Каталог подготовки, который никто не уберёт.** Переданный сценарию каталог убирает только сценарий. Если
   сценарий убит или не запустился, каталог рядом с приложением (сотни мегабайт, имя начинается с точки) остаётся
   лежать, пока его не удалит человек. То же, если pid из имени непереданного каталога достался постороннему
   процессу — до старта, когда этот pid освободится.

## 9. Совместимость

Окно и main — одна сборка, поэтому замена каналов `app:update-available` / `app:get-update` на
`app:update-state` / `app:get-update-state` не требует пары версий. Хост и протокол не меняются. `ui.json` новых
полей не получает.

Релиз без этой работы итог не читает и `.old` не убирает: после SU-26 рядом с тестовым приложением остаются `.old`
и файл итога, пока их не уберёт человек.

## 10. Проверка вживую

Установленная сейчас сборка обновлять себя не умеет, поэтому до первого релиза с этой работой проверяется только
половина пути (SU-26, SU-27): приложение из ветки с версией ниже последнего релиза, в отдельном каталоге (не
`/Applications`) и с отдельным домом Parley, чтобы не делить данные и блокировку с рабочим Parley. Оно заменяет
только себя: путь приложения берётся из пути исполняемого файла. После замены в каталоге лежит выпущенный релиз,
который итога не читает, поэтому тоста «updated to» в этой проверке нет.

Полный путь (SU-28) проверяется на первом обновлении с выпущенной версии с этой работой на следующую.

## 11. Чего в этой работе нет

- Автоматической загрузки и установки без клика; установки при обычном выходе.
- Подписи релиза отдельным ключом, зашитым в приложение (защита от подмены релиза).
- Проверки хоста перенаправлений (решение 6).
- Запрета запуска Parley на время замены (риск 2); замок есть только между сценариями замены.
- Отката после неудачного `open`: новое приложение остаётся на месте, прежнее — в `.old`.
- Сохранения скачанного архива между запусками окна и докачки.
- Замены более новым релизом, найденным во время загрузки или готовности: он предлагается после.
- Выбора версии, понижения и переустановки (`--force`, тег) — это остаётся в скрипте.
- Кнопки «Check now», заметок релиза в окне, разностных обновлений по `.blockmap`.
- Атомарного обмена каталогов и собственного бинарного помощника.
- Windows и Linux: сборок под них нет.

## 13. Уточнения при реализации

Там, где спека молчала, исполнители приняли решения; ревьюер кода s-395 (Codex Astra) оценил каждое 2026-11-15.
Они действуют наравне с остальным текстом.

1. **Манифест больше 64 КиБ** → `too_large` (§5.3, шаг 1).
2. **Заголовки запросов файлов релиза** (исключение из «как у проверки версии», §5.3, шаг 1): `Accept: */*`,
   `Accept-Language: en`, `User-Agent: Parley`; `X-GitHub-Api-Version` не шлётся — это загрузка файла, а не API.
3. **Отменённая попытка** кончается внутренним исходом `cancelled`. В `UpdateState` он не попадает: состояние после
   отмены задаёт переход из §5.1.
4. **`no_app`, когда приложения нет на месте** (§5.5, шаг 3): итог пишется, каталог подготовки не удаляется, `open`
   не зовётся.
5. **Место приложения занято после шага 5** (§5.5, шаг 6) → `restore_failed`: обе копии целы, ничего не удаляется.
6. **Итог-отказ, кроме `launch_failed`, с версией, равной запущенной** (§5.6, п. 1): тоста нет, `.old` не трогается.
7. **Каталог загрузок** при старте очищается по содержимому, сам каталог остаётся (§5.6, п. 3).
8. **Переход `downloading` → `verifying`** происходит в момент запуска первого дочернего процесса попытки (`ditto`):
   к этому мигу архив скачан и его хэш сверен.
9. **«Try again»** в строке настроек зовёт `downloadUpdate()` при любой причине отказа; при `cannot_replace` попытка
   снова кончится тем же отказом.
10. **Предел ожидания сценария** (§5.5, шаги 1 и 2) — по прошедшему времени, включая сами проверки; зависшая
    проверка процессов обрывается и считается ответом «процесс есть». Часы — `/bin/date +%s`, точность — секунда:
    ожидание не кончается раньше предела и кончается не позже чем через секунду и одну проверку после него. Список
    процессов пишется во временный файл `.ps-list` внутри каталога подготовки и удаляется вместе с ним.
11. **Окружение при перезапуске.** Сценарий открывает приложение через `open`, а тот окружение сценария не
    передаёт: Parley, запущенный с переменной `PARLEY_HOME`, после обновления откроется с домом по умолчанию.
    Обычного запуска из Dock это не касается; для живой проверки в отдельном доме лист приёмки задаёт переменную
    через `launchctl setenv`.
12. **Старт окна и `lockf`** (исключение из §5.6: «только там, где заменить себя можно»). Для чтения итога и уборки
    умение `lockf` не проверяется: достаточно остальных условий §5.2. Старт только читает и удаляет, замка не
    берёт; на системе без нужной формы `lockf` сценарий замены не запускался, и убирать после него нечего.
13. **Выключенная проверка.** Пока переключатель «Check for updates» выключен, установщик не принимает находок
    проверки и не начинает загрузку, даже если ответ GitHub на запрос, начатый до выключения, пришёл позже.
    Ответ такого запроса, пришедший уже после повторного включения, принимается: проверка включена, и находка
    настоящая.
14. **Выход во время подготовки.** Если Parley выходит, пока идёт загрузка или распаковка, попытка отменяется до
    конца выхода: дочерний процесс завершается, его конца дожидаются, каталоги попытки удаляются. Это делается в
    том же шаге, где выход гасит хост, и ждёт не дольше 5 с. Выход в обход этого шага (тестовый режим) обрывает
    запрос и завершает дочерний процесс без ожидания; каталог тогда убирает следующий старт окна.
15. **Обрыв запроса.** Запрос файла обрывается при любом отказе попытки, а не только при отмене и по времени. Хэш
    архива считается по байтам, уже записанным в файл.
