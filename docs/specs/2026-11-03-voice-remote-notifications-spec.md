# Parley — Спецификация №1
# Голосовой интерфейс мобильного Parley, использование OpenAI API-кредитов и единая маршрутизация уведомлений

**Версия:** 1.0 (proposal / ready for decomposition)  
**Дата:** 2026-11-03  
**Приоритет:** ближайший продуктовый релиз после стабилизации текущего мобильного MVP  
**Аудитория:** архитектор, ведущий агент, исполнители, независимый verifier  
**Продукт:** Parley Remote / Bring Your Own Parley — пользователь подключает собственный хост Parley; облачного хостинга пользователей нет.

> **Решение:** GPT-Live — исключительно разговорный голосовой слой. Существующий Parley Assistant на подключённом CLI-провайдере (Claude Code / Codex / совместимый провайдер) остаётся интеллектом и точкой управления работами, комнатами и агентами. Уведомления рождаются один раз в хосте и доставляются в выбранный канал: мобильное приложение или Telegram, без неуправляемых дублей.

## 0. Статус и границы документа

Этот документ — новая функциональная спецификация. Он не утверждает, что все её функции уже реализованы. Перед декомпозицией сверить ветку `master` и сохранить принятые ранее ограничения безопасности.

**Существующее основание в репозитории `Kalmbik61/Parley`:**

- `packages/mobile` — Expo SDK 58 / React Native, iOS-first, экранные маршруты Inbox / Works / Settings; дизайн `docs/specs/2026-10-29-mobile-app-design.md`, план `docs/plans/2026-10-29-mobile-app-plan.md`.
- `packages/remote-client` — транспортонезависимый мобильный клиент; `packages/remote` — bridge; `packages/protocol/src/remote/*` — контракты.
- Сопряжение через QR, Noise, собственный relay пользователя, недоверенный relay, вторичная проверка allowlist на хосте, push-шлюз без пользовательского содержимого — **сохраняются**.
- `packages/host/src/assistant/assistant-service.ts` — существующий CLI Assistant; `packages/host/src/assistant/assistant-endpoint.ts` — инструменты помощника; `packages/protocol/src/assistant.ts` — существующий протокол.
- `packages/host/src/telegram/notify.ts` и Telegram-модуль — существующие триггеры/уведомления. `docs/specs/2026-10-19-assistant-control-telegram-design.md` — предыдущий дизайн Telegram.
- На Desktop уже есть Whisper (speech-to-text) и локальный Qwen3-TTS. Не подменять это GPT-Live: в новой схеме мобильный разговор — отдельный транспортный адаптер к **тому же** Assistant Service.

**Инварианты:** нельзя открывать CLI в интернет; нельзя раздавать ключи провайдеров телефону или relay; нельзя обходить существующее подтверждение через `propose_*`; нельзя превращать голосовое «да» в подтверждение особо опасного действия без отдельной авторизации.

## 1. Цель

После подключения к своему Parley пользователь открывает приложение и видит **готовый экран ассистента** (его дизайн уже существует, переиспользовать), начинает живой двусторонний голосовой разговор, спрашивает о работах, отдаёт поручения и получает результаты. Backend-оркестратор запускается **по необходимости**, используя выбранную пользователем подключённую подписку CLI-провайдера. Изменения в работах не создают одновременно одинаковые уведомления в Parley App и Telegram.

### Персоны и основные сценарии

1. Разработчик с 10–50 параллельными сессиями: «Парли, что зависло?», «Проверь, почему второй завод не закончил задачу», «Попроси ведущего уточнить критерии».
2. Пользователь вне дома: Mac-хост работает, приложение подключается через уже согласованный remote-bridge.
3. Пользователь общается с Live и одновременно работает оркестратор: можно задавать другие вопросы; длительный job продолжает выполняться независимо от аудиосессии.
4. Пользователь не хочет дублей: app — основной канал; Telegram — только явно настроенный резерв/альтернатива.

### Цели первого выпуска

- Voice-first интерфейс после pairing, с доступом к Inbox/Works/Settings.
- Реальный двусторонний голос с прерыванием (barge-in), текстовым транскриптом и текстовым fallback.
- Одна и та же реализация Assistant Service для Desktop, Mobile и Telegram.
- Стабильные длительные делегации к Assistant; корреляция, отмена и честные статусы.
- Прозрачный бюджет GPT-Live и отдельные лимиты CLI-провайдера.
- Одно событие → одна каноническая запись → маршрутизированная доставка; эскалация только когда нужна.
- Без регрессии Noise/relay, паринга, подтверждений, текущих мобильных возможностей.

### Не цели

- Parley Cloud, продажа общего доступа к API-ключам, мультиарендность.
- Голосовая идентификация владельца, паспортное хранилище, автоматические покупки.
- Перенос **безлимита Voice в ChatGPT** в стороннее приложение.
- Полноценная автономность ассистента и ночная консолидация памяти — см. спецификацию №2.

## 2. Продуктовые ограничения и оплата OpenAI

**Критическое различие:**

1. **Лимит голосового режима ChatGPT Pro внутри ChatGPT** — это не универсальный API-лимит. Его нельзя просто использовать для GPT-Live в Parley.
2. **API credits for ChatGPT subscribers:** владелец подходящего платного Pro подключает подписку к **своей API-организации**, активирует льготу в ChatGPT/API Platform; затем использует проектный API-ключ и API-кредиты. На дату этой спецификации: Pro $100 → до $100/месяц, Pro $200 → до $200, Pro $500 → до $500; первая выдача пропорциональна остатку цикла, остаток сгорает, провайдер может изменить программу. Проверять фактический баланс, права организации и модельные лимиты. GPT-Live покрывается этими API-кредитами; использование CLI Codex через API-ключи этой льготой не покрывается.
3. **Sign in with ChatGPT (SIWC)** — отдельная интеграция с особыми условиями и допустимыми сценариями; не считать, что она автоматически даёт GPT-Live или разрешает платное перепродавание включённых лимитов. В v1 **не реализуется** без подтверждения доступных endpoint-ов и условий.
4. GPT-Live (`gpt-live-1`) на дату спецификации: **$0.05/минуту** активной сессии, расчёт посекундный; время молчания и ожидания backend тоже оплачивается. Отдельно оплачиваются модели/инструменты backend, если там есть платные API-вызовы. Цена — конфигурируемая справочная величина, не хардкод тарифов навсегда.

**Решение первой версии:** режим `voiceProvider=openai_api`, **пользовательский API project key в настройках Mac-хоста**, зашифрованное хранение средствами ОС, никогда не отправлять его в клиент, relay или Telegram. Пользователь самостоятельно активирует и проверяет льготу на сайте OpenAI. Показать `Grant active` только после реальной проверки доступности/баланса, не выводить статус из наличия Pro.

**Бюджетные политики:**

- `sessionMaxMinutes` = 30 по умолчанию; предупреждение за 2 минуты.
- `dailyMaxVoiceMinutes` и `monthlyVoiceBudgetUsd` — настраиваемые пользователем, выключить автопродолжение при превышении.
- `maxConcurrentVoiceSessionsPerHost` = 1 для v1.
- Нет автоматического включения платной дозаправки API-баланса; если доступные кредиты исчерпаны, завершить аудиосессию и предложить текстовый режим, без скрытой смены платёжного способа.
- Финальные расходы считать по usage API; локальный таймер — только предварительная оценка. Не обещать точный остаток там, где API-провайдер не предоставляет его непосредственно.
- CLI Assistant расходует **свою** авторизованную подписку/лимиты по правилам официальных CLI; голос и CLI — независимые лимиты.

## 3. Архитектура

```text
  Parley Mobile (Expo RN)
    ├─ Assistant first screen: microphone, transcript, cards, task state
    ├─ WebRTC ───────────────► OpenAI GPT-Live API (voice only)
    │                            │ delegation.created / output events
    └─ encrypted Parley Remote ─► user relay ─► user's Mac remote bridge
                                                     │
                                                 Parley Host
                                                     │
                          ┌──────────────────────────┴────────────────────┐
                          │                                               │
                    VoiceGateway                                     Notification Router
                          │                                               │
                    Assistant Adapter                             Canonical Event / Outbox
                          │                                               ├─ App/APNs
                    Assistant Service                                     └─ Telegram
                          │
                 CLI subscription provider (Claude/Codex/...)
                          │
                   Parley works / rooms / agents
```

В режиме `client delegation` событие Live на **первичном WebRTC data channel** приходит приложению и пересылается по существующему E2EE remote-каналу в хост с `delegationId`. Хост собирает контекст, запускает существующий Assistant и возвращает **проверенные** краткие обновления. Мобильный `VoiceGateway` отправляет их в GPT-Live через `session.thinking.append` или `session.commentary.append` с исходным `delegation_id`. При дальнейшей зрелости допустим альтернативный sideband backend, но не вводить второй сетевой путь в MVP без обоснования. Это не прямой доступ GPT-Live к MCP или к CLI.

**Важное свойство:** runtime job хранится на хосте, а не в жизненном цикле телефонного экрана. При закрытии Live-сессии задача не прерывается, если пользователь отдельно не нажал «Остановить задачу».

### Модули (предлагаемые контракты, не утверждение об их наличии)

- `packages/host/src/voice/` — `VoiceSessionService`, delegation adapter, policy and usage.
- `packages/protocol/src/remote/voice.ts` — методы `voice.*` и события (Zod, строгие размеры, версия capabilities).
- `packages/mobile/src/voice/` — WebRTC controller, audio/session UI binding, transcript stream, reconnect policy.
- `packages/host/src/notifications/` — `NotificationEventService`, `NotificationRouter`, delivery workers, receipt/ack.
- `packages/protocol/src/notifications.ts` — единый envelope и маршрутные настройки; повторно использовать существующие механизмы событий.

**Запрет:** не создавать второй самостоятельный «мобильный ассистент» с собственной бизнес-логикой. Весь смысл действий и подтверждений остаётся в Assistant Service и host services.

## 4. Voice UX и поведение

### 4.1 Первый экран

- После успешного pairing: Voice screen — первая вкладка и главный landing. Нынешние Inbox, Works, Settings доступны отдельными вкладками/переходами; существующий дизайн голосового экрана является источником визуального решения.
- Состояния: `idle`, `connecting`, `listening`, `speaking`, `delegating`, `paused`, `offline`, `limit_reached`, `error`.
- Кнопки: «Начать / закончить», «Выключить микрофон», «Открыть текстовый чат», «Текущие задачи», «Прервать ответ».
- Транскрипт пользователя и ответов с пометками частичных фрагментов; ответы backend как отдельные карточки прогресса, не притворяться финальным ответом.
- В состоянии `Mac offline` не отправлять фиктивную делегацию; голос без доступа к хосту может сообщить причину отключения, но не обещать исполнение.
- Запрещено запускать микрофон или платную сессию без явного жеста/согласия пользователя; при блокировке iOS/уходе в background корректно остановить или приостановить согласно реальным ограничениям платформы. Не обещать постоянное фоновое прослушивание.

### 4.2 Маршрутизация запросов

| Пример | Путь | Почему |
|---|---|---|
| «Сколько агентов сейчас активно?» | `host.get_runtime_status()` | Детерминированное чтение состояния без CLI-модели. |
| «Какая комната ждёт меня?» | `host.get_attention_summary()` | Данные из host без рассуждения. |
| «Почему Auth не закончил задачу? Проверь зависимости» | `assistant.submit_job()` | Нужен CLI Assistant + инструменты/контекст. |
| «Скажи ведущему пересмотреть план» | `assistant.propose_message()` | Действие через существующую карточку подтверждения. |
| «Создай комнату из двух агентов» | `assistant.propose_room()` | Нельзя создавать без прежней host-проверки прав и согласия. |

Routing **детерминированен в приложении** по разрешённым tool names/политикам. Нельзя позволять LLM самостоятельно обходить обязательное подтверждение. Список быстрых операций ограничен (`read-only allowlist`); всё неизвестное → делегация к Assistant.

### 4.3 Жизненный цикл одного разговора

1. Пользователь включает микрофон; мобильное приложение проверяет pairing/разрешения, бюджет и доступность хоста.
2. Хост с API-ключом запрашивает GPT-Live сессию / защищённый handshake для WebRTC; мобильный клиент получает только короткоживущие параметры соединения, а не постоянный API-ключ.
3. При `session.started` включить передачу аудио, transcript and status.
4. Когда Live делегирует, приложение формирует `voice.delegation.submit` с оригинальным `delegationId`, `turnId`, нормализованным текстом и актуальным UI context. **Не строить задачу из одного обрывка аудиотранскрипта.**
5. Хост создаёт или продолжает job в Assistant Service; сессия оркестратора определяется конфигурацией пользователя, не моделью GPT-Live.
6. Хост пишет прогресс/результат в своё долговременное хранилище, проверяет права, исключает секреты и возвращает краткий результат для озвучивания.
7. Mobile отправляет verified text через Live `session.commentary.append` (до 500 токенов на append), нефинальные немые обновления — `session.thinking.append`; не отправлять туда логи и скрытое рассуждение.
8. При закрытии voice-сессии host job остаётся жить; его итог появится в истории Assistant и через выбранный notification route.

**Concurrency:** каждое поручение получает `jobId`, `delegationId`, `turnId`, `revision`; один GPT-Live разговор может содержать несколько jobs. Если пользователь исправил команду, более старый результат не выдавать за новую истину. Для write-actions — идемпотентность и повторная проверка фактического состояния после потери соединения.

## 5. Контракты на границе mobile ↔ host

Предлагаемые семантические структуры; имена/поля уточнить под существующие протоколы и zod-схемы.

```ts
type VoiceStartRequest = {
  provider: 'openai_api';
  model: 'gpt-live-1';
  clientSessionId: string;
  scope: { hostId: string; workspaceId?: string };
};

type VoiceDelegationSubmit = {
  voiceSessionId: string;
  delegationId: string;
  turnId: string;
  utterance: string;                  // завершённая/согласованная реплика
  uiContext?: { screen: string; selectedRef?: string };
  idempotencyKey: string;
};

type AssistantJob = {
  jobId: string;
  voiceSessionId?: string;
  delegationId?: string;
  state: 'queued'|'running'|'needs_confirmation'|'completed'|'failed'|'cancelled';
  revision: number;
  requestText: string;
  resultSummary?: string;             // без логов и секретов
  createdAt: string;
  updatedAt: string;
};

type VoiceUsage = {
  voiceSessionId: string;
  durationSec?: number;
  estimatedCostUsd: number;
  finalCostUsd?: number;
  source: 'estimate'|'api_usage';
};
```

**Реальные RPC names (кандидаты):** `voice.session.prepare`, `voice.delegation.submit`, `voice.job.get`, `voice.job.cancel`, `voice.usage.get`, `notifications.get`, `notifications.preferences.get/set`, `notifications.acknowledge`. Все методы должны пройти role `remote` allowlist **на bridge и на host** с тестами на запрет всего остального. Клиент не вызывает существующие внутренние `/assistant/*` HTTP endpoints напрямую: они остаются локальной границей CLI инструментов.

**Поток событий:** `voice.job.changed`, `notification.created`, `notification.acknowledged`, `voice.session.closed`. На reconnect — snapshot + monotonic sequence/revision, не «доверять, что всё дошло по стриму».

## 6. Уведомления: единая модель вместо двух рассылок

### 6.1 Источник и маршрутизация

`Work / Agent / Room changes → Attention Aggregator → Canonical Notification Store + Outbox → Router → [App push / Telegram]`

- **Единственный источник истины** — host. Не создавать уведомление отдельно в Telegram-модуле и отдельно в push-модуле.
- События имеют `eventId`, `dedupeKey`, `hostId`, `workspaceId`, `entityRef`, `type`, `severity`, `createdAt`, `revision`, `requiresAction`, `payloadRef`.
- В уведомлении **не хранить необходимость дважды выполнять действие**. Кнопка/карточка отсылает к одному host action, который проверяет ревизию и использует `idempotencyKey`.
- Для миграции обернуть текущие `NotifyMemory`, `worksTriggers`, `activityTransition`, а не дублировать их алгоритмы.

### 6.2 Режимы доставки

1. `APP_ONLY` — все внешние сообщения только push в приложение; Telegram как канал запросов может быть включён, но не присылает уведомления.
2. `TELEGRAM_ONLY` — все внешние сообщения только в Telegram; приложение сохраняет внутреннюю историю, не шлёт push.
3. `SMART` (рекомендованный default после pairing и отдельного согласия) — **App основной, Telegram резерв только для критических неподтверждённых событий**; не отправлять два одинаковых обычных уведомления.
4. `BOTH` — доступен только как явно включаемый diagnostic/legacy режим с предупреждением о дублях, не default.

**Важное различие:** доставлено в APNs ≠ прочитано человеком; отсутствие подтверждения получения push нельзя однозначно трактовать как недоставку. В `SMART` не переносить все непрочитанные события в Telegram. Для `severity=critical` и `requiresAction=true` через настраиваемый интервал (пилот: 10 минут) допускается эскалация, только если **нет подтверждённого действия** и Telegram разрешён. Эскалация может создать второе оповещение, но относится к *тому же* `notificationId`, без повторения операции.

### 6.3 Матрица событий

| Событие | Внутренний Inbox | Push App | Telegram в SMART |
|---|---:|---:|---|
| Агент начал работу / выполнил micro-step | Activity feed | Нет | Нет |
| Сессия завершила работу | Да | Свернутое информирование / digest | Нет |
| Комната ждёт решения | Да | Да | Эскалация при просрочке, если критично |
| Разрешение на опасное действие | Да | Да | Эскалация при просрочке, если критично |
| Провайдер исчерпал лимит / требуется login | Да | Да (с группировкой) | Только по правилам эскалации |
| Ассистент завершил фоновую задачу | Да | Да, если приложение не активно | Обычно нет |
| Ошибка проверки результата / проверка не пройдена | Да | Да | Только критичное |

### 6.4 Подавление, подтверждение, отказоустойчивость

- Если соответствующий экран активен и host получает **достоверный presence heartbeat** для этого устройства, не отправлять push по тому же событию; в Inbox оно остаётся.
- `seen` (открыл карточку) и `acknowledged` (выполнил действие/закрыл уведомление) — разные статусы; подтверждение действия не имитировать прочтением.
- Для push соблюдать старое правило **без содержимого**: `kind`, `count`, неприватный `route`, opaque ID; названия проектов, тексты агентов, команды и секреты — **не** в APNs.
- В Telegram содержимое показывается согласно явной настройке пользователя и с предупреждением, что облачные чаты Telegram не E2EE.
- `eventId`/`dedupeKey` сохранять до перезапуска host (SQLite/outbox), durable retries с ограничением попыток и jitter; дубликаты из провайдера или после restart не создают два сообщения в Inbox.
- На `ack` из любого канала обновляется каноническое событие и, если возможно, Telegram message / badge; старые кнопки должны возвращать `already_handled`, а не выполнять действие повторно.
- Из нескольких хостов на одном телефоне не смешивать источники; ключи включают `hostId`.

## 7. Безопасность и границы доступа

- Мобильная сторона: Keychain и текущая криптография Noise; transport-level server identity и revocation; никакой возможности обхода existing remote allowlist через Voice.
- OpenAI API key хранится только на пользовательском Mac; передача по WebRTC не должна его раскрывать; секреты не пишутся в диагностике.
- Live — недоверенный интерфейс намерений, а не авторизатор: команда в transcript может быть ошибочной или подделанной; действие исполняет только Parley Host после проверок.
- `read` и `propose` доступны согласно remote-policy; `execute` только при подтверждённой карточке с известной версией.
- Prompt injection из чужих писем/логов/сайтов не может добавить неразрешённые инструменты.
- Не копировать целые transcripts в память без явной политики пользователя; хранить журнал заданий и минимальную необходимую историю.
- Устройство можно отозвать с Mac: voice-сессии этого устройства завершаются, pending approvals перестают приниматься.

## 8. Телеметрия и качество (local-first)

Собирать локально, без отправки третьим лицам по умолчанию:

- `first_audio_latency_ms`, `first_useful_reply_ms`, `delegation_to_job_ms`, `job_completed_ms`, `voice_interrupt_success`, `stream_reconnect_count`;
- `voice_session_duration_sec`, `voice_estimated_cost_usd`, `voice_final_cost_usd`, `assistant_provider`, `limit_reached`;
- `notifications_generated`, `delivered_by_channel`, `escalated`, `duplicate_suppressed`, `unacknowledged_action_count`.

Успех UX: пользователь голосом узнаёт реальные статусы и возвращается к актуальной карточке без повторной отправки поручения. Запрещено метриками записывать аудио, токены, приватные тексты, конфиденциальные имена проектов.

## 9. Этапы реализации

**V1-A — фундамент (до Voice):** схема уведомлений, canonical store/outbox, маршрутизация и тесты dedupe; адаптер существующих Telegram triggers; capability protocol с закрытой удалённой поверхностью.

**V1-B — voice spike:** токен-безопасная `gpt-live-1` WebRTC-сессия iPhone, надежное завершение по таймеру, транскрипт, barge-in, измерение цены, ошибка по исчерпанию баланса.

**V1-C — Assistant bridge:** `client delegation` по Noise с `delegationId`, один job на запрос, reuse существующего CLI Assistant, раздельные быстрые readonly инструменты, проверка результатов, продолжение jobs после закрытия голоса.

**V1-D — единый UX:** существующий дизайн voice-first, inbox/progress/cards, контекст от selected work, настройка уведомлений и отображение budget, переключение в текст.

**V1-E — hardening:** E2E на реальном iPhone и мобильной сети, replay/reconnect, host reboot, лимиты API, падение CLI, отзыв устройства, Telegram fallback, автотесты, security review и сохранение старых мобильных сценариев.

Не принимать этап при отсутствии verifier; критические границы `remote ↔ host` и `billing/auth` проверить отдельным senior review.

## 10. Приёмочные критерии / тестовые сценарии

| ID | Given / When / Then |
|---|---|
| VO-01 | Пользователь спарил iPhone; приложение открывается на голосовом экране, Inbox/Works/Settings доступны, старые сценарии работают. |
| VO-02 | Mac в сети, API grant активирован; старт аудио успешен, поток двусторонний, перебивание прекращает текущий ответ без остановки job. |
| VO-03 | «Сколько агентов?» возвращает данные host без запуска CLI процесса. |
| VO-04 | «Почему задача зависла?» запускает выбранного пользователя CLI Assistant, а не reasoning внутри GPT-Live. |
| VO-05 | Закрытие voice-сессии не убивает фоновый job; после возвращения виден статус и финал ровно один раз. |
| VO-06 | Для предложения отправить письмо появляется карточка; до нажатия запись в комнату не создаётся. |
| VO-07 | Лимит/отсутствие API баланса дают понятный fallback в текстовый режим; нет неожиданных расходов или скрытой оплаты. |
| VO-08 | Обычная Done-нотификация при `SMART` уходит в приложение и **не** в Telegram. |
| VO-09 | Критическая просьба не подтверждена 10 минут, резерв разрешён — появляется одна Telegram-эскалация с исходным `notificationId`. |
| VO-10 | Одна карточка подтверждена в Telegram; повторное нажатие в App не исполняет действие повторно. |
| VO-11 | Повтор host events, reconnect и restart не создают новых Inbox records с тем же `dedupeKey`. |
| VO-12 | APNs payload не содержит пользовательских текстов; Telegram выключен — бот не уведомляет. |
| VO-13 | Отозванный iPhone не получает события и не может вызывать новые remote методы Voice. |
| VO-14 | Попытка вызвать запрещённый метод через `voice.*` отвергнута и bridge, и host. |
| VO-15 | Устаревшее delegated result после исправления запроса пользователя не произносится как актуальный результат. |
| VO-16 | Финальный отчёт тестов содержит затратный профиль: минуты аудио, CLI usage, стоимость, первую задержку ответа. |

## 11. Открытые решения к фазе планирования

- Есть ли уже окончательно согласованный экран voice-first в приложении или только дизайн-прототип: исполнитель сверяет со свежим кодом и не переизобретает UX.
- Какой способ защищённого создания GPT-Live WebRTC-сессии удобнее с текущим remote-bridge: host-mediated SDP/ephemeral setup или дополнительный sideband. Выбрать после рабочего spike на реальном iPhone.
- Какие события у пользователя считаются `critical` и сколько минут ждать эскалации: пилотные 10 минут подтвердить UX-тестом.
- Где хранить outbox в действующем host SQLite без дублирования уже существующих баз/структур.
- Включать ли в будущем SIWC и какие его endpoint-ы/условия подходят к Voice — отдельное исследование, не блокирует первую версию.
