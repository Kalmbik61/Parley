## 1. Зачем

Ради готовых сценариев OMC и ставят: «интервью → консенсус-план → исполнение →
проверка» запускается одной командой. В Parley комнату собирают руками: кого позвать,
каких провайдеров, кому worktree, кто ведёт, как вести этапы. Механика под сценарии уже
спроектирована — роли, режимы и планы, решения человека, будильник, — не хватает
заготовки, которая собирает всё это одним выбором и подсказывает ведущему, как вести
работу.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Что такое рецепт | Пресет комнаты: состав по ролям, провайдеры, режим, worktree, плейбук ведущего. Дальше комната работает на уже спроектированной механике; своей машины стадий нет |
| Откуда рецепты | Встроенные Parley и рецепты проекта — файлы в `.parley/recipes/`, в git |
| Встроенные в v1 | Plan & build, Review, Debug |
| Где выбирается | Наверху диалога «New session or room»; после выбора строки правятся свободно |
| Плейбук | Только ведущему, блоком в слое Parley; снимком в комнате |
| Агенты | Видят рецепт комнаты в `get_map`; запускать рецепты в v1 не умеют |
| Тексты | Плейбуки встроенных рецептов — свои, по-английски; из OMC и oh-my-codex ничего не переносится дословно и не пересказывается близко к тексту |

## 3. Рецепт

| Поле | Что это |
|---|---|
| `id` | `builtin:plan-build`, `project:<имя файла без .md>` |
| `name`, `description` | Подпись и одна строка по-английски |
| `mode` | Режим комнаты: `free`, `checklist`, `verified` |
| `agents` | Строки состава (ниже) |
| `playbook` | Плейбук ведущего: этапы, когда звать человека, что класть в бэклог |

Строка состава:

| Поле | Что это |
|---|---|
| `role` | Любая роль: `builtin:<id>`, `claude:<имя>`, `codex:<имя>` |
| `provider`, `model`, `effort` | Необязательно: поверх умолчаний роли |
| `worktree` | Своя рабочая копия: да или нет (по умолчанию нет) |
| `lead` | Ведущий; ровно у одной строки |
| `count` | Сколько таких агентов, от 1 до 3 (по умолчанию 1) |

Правила: не меньше двух агентов (рецепт — заготовка комнаты; одиночную сессию с ролью
делает выбор роли), ровно один ведущий, `count` у ведущего — 1.

## 4. Встроенные рецепты v1

### 4.1 Plan & build — `builtin:plan-build`

- **Режим:** `verified`.
- **Состав:** ведущий — `builtin:planner`; `builtin:critic`; `builtin:executor` (по
  умолчанию 1, в диалоге до трёх, `worktree: true`); `builtin:reviewer`. Провайдеры —
  умолчания ролей: критик и ревьюер на Codex.
- **Плейбук ведущего:**
  1. Выясни у человека цель и критерии приёмки — одним письмом с вопросами; жди ответа.
  2. Набросай план; спроси критика (`question`), где в нём дыры; поправь.
  3. Принеси решение с планом «с проверкой»: пункты исполнителям с областью и критериями;
     у пунктов реализации проверяющий — ревьюер. При доступном `find_skill` найди
     подходящий скилл владельца через `for` и назови его в `scope`; если не нужен,
     не назначай. Проверяющему скилл ищется отдельно в его CLI.
  4. Веди план: снимай блокировки, отвечай на вопросы.
  5. Всё проверено — принеси итог (`propose_completion`) и предложи хвосты в бэклог.
- **Как ревьюер видит код исполнителя:** `git diff` ветки исполнителя из основной копии —
  ветки worktree видны в общем репозитории. Это пишется в плейбуке.

### 4.2 Review — `builtin:review`

- **Режим:** `free`. Все роли — только для чтения.
- **Состав:** ведущий — `builtin:reviewer` (Codex); `builtin:architect` (Claude). Без
  worktree.
- **Что ревьюить** — ветку, PR или диапазон коммитов — человек пишет задачей в комнату.
- **Плейбук ведущего:**
  1. Уточни объём ревью, если из задачи он не ясен.
  2. Раздели: ревьюер — корректность, регрессии, тесты; архитектор — границы и дизайн.
     Каждая находка — с файлом и строкой. При доступном навигаторе подбери скиллы
     участникам через `find_skill` с `for`, только если они подходят.
  3. Сведи находки в одно решение: по важности, с предложенными действиями.
  4. После принятия разложи хвосты через `backlog_suggest`. Код не правится.

### 4.3 Debug — `builtin:debug`

- **Режим:** `checklist`.
- **Состав:** ведущий — `builtin:debugger` (`worktree: true`: исправление делается там);
  `builtin:researcher` — логи, история, документация, без worktree.
- **Плейбук ведущего:**
  1. Воспроизведи сбой — по возможности падающим тестом.
  2. Гипотезы; исследователь проверяет логи, историю изменений, документацию.
     При доступном навигаторе назови подходящий скилл каждому участнику через `for`.
  3. Список: воспроизвести, найти причину, минимально исправить, доказать тестом.
  4. Сдай доказательства; хвосты — в бэклог.

### 4.4 Тексты плейбуков

По-английски, свои; не длиннее 30 строк каждый; не повторяют встроенные правила Parley,
гид и тексты ролей. Перед релизом человек просматривает все три.

## 5. Рецепты проекта

### 5.1 Файл

`.parley/recipes/<id>.md`, в git: белый список `.parley/.gitignore` из спеки планов
дополняется строками `!recipes/` и `!recipes/**`.

```markdown
---
name: Payments change
description: Plan & build with a security review for payments code
mode: verified
agents:
  - role: builtin:planner
    lead: true
  - role: builtin:executor
    worktree: true
    count: 2
  - role: builtin:reviewer
  - role: codex:security-reviewer
---
Lead playbook: stages, when to ask the human, what goes to the backlog.
```

Frontmatter — YAML, тело файла — плейбук. Разбор YAML — зависимостью core, общей со
спекой ролей (там frontmatter агентов Claude); выбор и лицензия — в плане.

### 5.2 Save as recipe

Кнопка в диалоге «New session or room»: имя и описание, режим и строки берутся из
диалога, плейбук — шаблоном этапов. Файл пишет главный процесс окна и открывает его во
вкладке редактора. Имя занято — предложение переименовать или заменить.

### 5.3 Битый рецепт

Ошибка YAML, неизвестное поле, роль с неверной записью, нет ведущего или их два, меньше
двух агентов, `count` вне 1–3 или не 1 у ведущего, неизвестный режим — рецепт виден в списке с причиной, но
выбрать его нельзя.

## 6. Запуск комнаты

### 6.1 Диалог

- Наверху — выбор рецепта: `No recipe` (по умолчанию), затем встроенные, затем рецепты
  проекта; под ним — описание.
- Рецепт заполняет строки: роль, провайдер, модель и усилие (умолчания роли или заданные
  рецептом), worktree, метка ведущего; `count` разворачивается в строки. В диалоге
  появляется переключатель режима — рецепт подставляет свой.
- Дальше всё правится: строки добавляются и убираются, роли и провайдеры меняются,
  ведущий переназначается, режим переключается. Модель и усилие уходят в сессию по
  правилу спеки ролей — только изменённые человеком.
- Задачу человек, как и сейчас, пишет в комнату один раз для всех после создания.

### 6.2 Что запоминает комната

`Room.recipe: { id, name, playbook } | null` — снимок на момент создания: правка файла
рецепта действует только на новые комнаты. Режим — из диалога (`Room.mode`).

### 6.3 Плейбук в слое ведущего

Порядок слоя Parley у ведущего: встроенные правила → строка моста (Codex) → роль →
**рецепт** → бриф тихой сессии → PARLEY.md → память проекта. Блок начинается строкой
`Recipe: <name> — you lead this room.`, дальше плейбук. У участников блока нет: им
хватает ролей. Обработанный плейбук ≤32 768 байт UTF-8 **включая конечную marker строку**: длинный текст обрезается по последней строке с явной меткой и безопасным warning. Native role permissions/model/effort остаются нетронутыми. Итоговый сериализованный слой после preprocessing/escaping не обрезается; overflow даёт ошибку до spawn по спеке PARLEY.md, 3.3, с final host env/runtime guard.

У рецепта и строки состава нет поля `skill`: роли и плейбук стабильны, а ведущий
ищет скиллы на машине участника при раздаче конкретной задачи. Снимок рецепта
не содержит индекс, список доступных скиллов или глобальные настройки CLI.
Навигатор выключен или скилла нет — этапы рецепта работают как раньше. Shared `yaml@2.9.1` parseDocument (ISC) разбирает рецепт/плейбук полноценно, включая multiline и mapping/schema validation, duplicate keys и bounded aliases; ошибки дают только safe code/position. Snapshot рецепта и accepted rev не меняются из-за native catalog/CLI gates.

### 6.4 Смена ведущего

Прежний ведущий закрыт, и его место занял первый живой участник — Parley отдаёт новому
ведущему плейбук письмом от `parley`. В слой новый ведущий получит его при следующем
запуске.

### 6.5 Где рецепт виден

В шапке комнаты, рядом с переключателем режима, — чип `Plan & build`; по клику —
плейбук только для чтения.

## 7. Агенты

`get_map` показывает у комнаты `recipe` (id и имя). Запуск рецептов агентами
(`create_room(recipe)`, `list_recipes`) — вне v1.

## 8. Граничные случаи

| Случай | Поведение |
|---|---|
| Провайдер строки недоступен | Строка показывает это; у встроенной роли выбирается другой провайдер; строку с нативной ролью правят или убирают |
| Нативной роли из рецепта проекта нет на этой машине | Рецепт выбирается, строка помечена «роль не найдена» и не запустится, пока её не поправят |
| Роль «только чтение» не обеспечить (подмена провайдера) | По правилу спеки ролей строка не создаётся; частичный сбой диалога — Retry повторяет только упавших |
| Корневой `.gitignore` скрывает `.parley/` | Рецепты проекта локальные; уведомление то же, что у бэклога |
| Имя при Save as recipe занято | Переименовать или заменить |
| `count` больше трёх | Не принимается |
| Человек поменял режим в диалоге | Действует выбор человека |
| Файл рецепта изменили после создания комнаты | Комната живёт со своим снимком |

## 9. Тесты

**core (vitest):**
- правила рецепта: агентов не меньше двух, ровно один ведущий, `count` 1–3 и у ведущего 1,
  запись ролей, режим;
- встроенные рецепты сходятся со встроенными ролями, плейбуки — английские и не длиннее
  30 строк;
- разбор рецепта проекта: frontmatter, тело как плейбук, каждая ошибка из 5.3;
- блок рецепта в слое ведущего на своём месте и его нет у участников;
- снимок рецепта в комнате; письмо новому ведущему;
- работа без навигатора и без подходящих скиллов; скилл не входит в рецепт или role.

**окно:** выбор рецепта заполняет строки, режим и ведущего; строки после этого правятся;
Save as recipe пишет файл, занятое имя; битые рецепты нельзя выбрать; чип и плейбук в
шапке.

**Живые проверки:**
- Plan & build на учебном проекте от начала до конца: вопросы человеку → критик → план
  «с проверкой» → исполнитель в worktree → проверка ревьюера через `git diff` → итог;
- Review на ветке: находки с файлом и строкой, хвосты в бэклог;
- Debug с падающим тестом.

## 10. Зависимости и порядок

- Нужны роли, режимы и планы, слой Parley из спеки PARLEY.md: рецепты реализуются после
  них.
- YAML-разборщик — общий с frontmatter ролей и скиллов (этап 1 единого плана).
- Навигатор — необязательная подсказка ведущему, не обязательная зависимость запуска.
- Белый список `.parley/.gitignore` — из спеки планов, плюс `recipes/`.

## 11. Вне объёма

- Рецепты Compare approaches и «исследование на двух моделях».
- Запуск рецептов агентами.
- Смена рецепта у существующей комнаты.
- Стадии с автопереходами — решено не делать: комнату ведут режим, план и ведущий.
- Личные рецепты в `~/.parley/`.
- Обмен рецептами между проектами.
- Переменные рецепта, кроме `count`.


## Фактическая реализация и отступления (2026-10-06)

Сверено с кодом и сообщениями коммитов ветки `feat/parley-upgrade`. Живые проверки раздела 9
(Plan & build, Review и Debug на учебном проекте от начала до конца) не проводились: они остаются
за P32.

**Сделано.**

- Ядро и хост (P25, fbdcf95 — каталог и разбор; 80b30a3 — доставка и каталог для окна): три
  встроенных рецепта, рецепты проекта общим разборщиком YAML, строгая проверка схемы, ролей,
  числа агентов, ведущего и режима. Снимок рецепта `Room.recipe = { id, name, playbook }` делается
  при создании комнаты, старые карты читаются как комната без рецепта. Метод `recipes.list`
  отдаёт встроенные рецепты и рецепты проекта; битый файл виден с диагностикой, остальной каталог
  работает. `rooms.create` получил необязательные `mode` и `recipe`.
- Плейбук получает только ведущий: слоем при запуске (по карте, а не по параметрам вызова), а если
  ведущий уже запущен или сменился, — письмом от `parley` ровно один раз. Отметка
  `recipeLeadNotified` пишется в той же мутации карты, что и письмо, поэтому перезапуск хоста
  повтора не даёт. `get_map` показывает агентам только id и имя рецепта, текст плейбука не утекает
  участникам.
- В `.parley/.gitignore` белый список получил `!recipes/` и `!recipes/**`.
- Окно (P26, 2c42dc6): выбор рецепта в диалоге «New session or room» заполняет состав по ролям,
  режим и ведущего; поля остаются редактируемыми, явный выбор человека не перетирается умолчаниями
  роли. Комната создаётся с режимом и снимком рецепта из свежего `recipes.list`; строки, которые
  не удались, остаются видны, Retry повторяет только их. Чип рецепта в шапке комнаты показывает
  плейбук только для чтения. Сценарий e2e `room-recipes`.

**Отступления от текста выше.**

- **Save as recipe открывает файл в системном редакторе**, а не во вкладке встроенного
  редактора окна: встроенный редактор в `.parley` намеренно не пускает (раздел 5.2). Запись только
  в `.parley/recipes/<имя>.md` через главный процесс; имя файла проверяется строго, содержимое —
  тем же разборщиком, что читает каталог, поэтому файл, который каталог счёл бы битым, не
  пишется; занятое имя без явного Replace не перезаписывается; симлинки отвергаются.
- **Рецепт требует двух агентов.** При одной строке в диалоге рецепт и режим не применяются:
  запускается обычная сессия, и об этом говорит заметка в диалоге. Пустой `provider` в Save as
  recipe не уходит.
- Плейбуки встроенных рецептов короче лимита: 8, 6 и 6 строк при пределе 30.
- Навигатор остаётся необязательным: плейбуки говорят «если доступен `find_skill`».

Запуск рецептов агентами и смена рецепта у готовой комнаты остаются вне версии 1, как записано
в разделе 11.
