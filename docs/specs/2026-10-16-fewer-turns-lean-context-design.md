# Меньше ходов и легче контекст у агентов комнаты — дизайн (часть C)

Дата: 2026-10-16. Статус: черновик на утверждение. Продолжение `2026-10-16-mail-economy-and-map-journal-design.md` (части A и B исполняются параллельно); основание — спайк `2026-10-16-mail-economy-spike-0.md`, прогоны A и B.

## Зачем

Спайк показал: письма — 0,08 % входных токенов комнаты. Расход = число ходов × контекст хода. Ведущий комнаты из трёх агентов за пятиминутную задачу сделал 37 вызовов модели по ≈ 90 тыс. токенов каждый (3,3 млн), стартовый контекст — 56 тыс. до первого действия. Задача части C — сократить и ходы, и контекст, не потеряв смысла комнаты: каждый участник по-прежнему видит каждое письмо, ведущий ведёт, человек видит всё.

## Что есть сейчас (факты по коду `master` b16ef1c7 и по транскриптам прогона B)

**Откуда ходы.** Ведущий прогона B, 37 вызовов модели: `wait_for` 11, текст без инструмента 12 («жду s-03», «план принят, раздаю»), `check_inbox` 3, `Read` 2, `Bash` 2, `Monitor` 2 (ждал встроенным Monitor Claude Code), по одному `get_map`, `send_message`, `Write`, `report`, `ToolSearch`. Ожидание и комментарии к ожиданию — около 25 из 37.

- `wait_for("inbox")` (`core/src/mcp/tools.ts:945-956`) возвращает непрочитанные письма (`state: "message"`), **но прочитанными их не помечает**: следующий `wait_for` возвращается сразу с теми же письмами, пока агент не позовёт `check_inbox` (`:1117-1121`, `readBy`). Отсюда пары и тройки `wait_for` подряд в транскрипте и лишний `check_inbox` после каждого ожидания.
- Будит агента всё: любое письмо в комнату, включая «принял, начинаю» соседа (в обоих прогонах такие были: 204, 156, 300 символов), указатель хоста после каждого письма в простое (`wake-service.ts`, `delivery.ts:67-91`: «New messages (N) in r-01 … Call check_inbox.»), возврат `wait_for`.
- Гид советует ждать `wait_for("inbox")` (`guide.ts:183-189`) и не говорит ни про молчание вместо подтверждений, ни про один долгий `wait_for` вместо цикла; `DEFAULT_TIMEOUT_SEC` 600, `MAX_TIMEOUT_SEC` 1800 (`tools.ts:94-97`), у Codex `tool_timeout_sec` 1860 (`mcp-config.ts:126`).
- Каждый вызов модели — это чтение всего контекста заново (у Claude — `cache_read`): 5,16 млн из 5,30 млн входных в прогоне A.

**Из чего контекст.** Стартовые 56 тыс. токенов сессии в my_harnas у автора (o200k, оценка по файлам):

## Цели

1. Входные токены комнаты на той же задаче и том же составе — **минус 30 %** (мерить драйвером спайка, тремя прогонами, сравнивать медиану).
2. Ходов ожидания у ведущего — не больше одного на событие, которое его касается.
3. Смысл комнаты сохранён: каждое письмо доходит каждому участнику (в `check_inbox`/`wait_for` и в окне), порядок писем прежний, человек будит всех сразу, вопрос будит адресата сразу.
4. Контекст, который добавляет сам Parley, — минус 40 % (схемы инструментов, гид); чужой контекст режется по явному выбору человека, не молча.

## Не-цели

- Скрывать письма от части участников или вводить отдельный машинный канал.
- Менять формат карты (часть B) или тело письма (часть A).
- `--bare` для подписочных сессий Claude: он ломает вход.
- Трогать `~/.claude`, `~/.codex`, глобальные CLAUDE.md и настройки пользователя: всё — флагами запуска своей сессии.

## Часть C1. Меньше ходов

### C1.1 `wait_for` помечает доставленное прочитанным

`wait_for("inbox")` отдаёт письма и ставит `readBy` (в части B — курсор) так же, как `check_inbox`. Один вызов на событие вместо `wait_for` + `check_inbox` + повторного `wait_for`. Указатель хоста меняет хвост на «Call check_inbox or wait_for("inbox")». `check_inbox` остаётся для тех, кто не ждёт. Старые сессии ничего не теряют: у них `wait_for` просто вернёт то же, что и раньше, но помеченное.

Ожидаемо: −2…−3 вызова на каждое событие у ждущего; в прогоне B — около 8 из 37 вызовов ведущего.

### C1.2 Пробуждение по значимости и пачкой

Письмо приходит всем и видно всем — меняется только **когда будят простаивающего агента**:

| Письмо | Будит сразу |
|---|---|
| от человека | всех адресатов (как сейчас) |
| с `to` или `@sNN` на меня, `kind: question` | да |
| `decision` ведущего, `roomTask`, системные строки о принятии плана | да |
| `note` соседа всем без упоминания | **нет**: ждёт следующего события или окна тишины `SETTLE_MS` (30 с), затем один указатель на все накопившиеся |

Реализация — в будильнике (`wake-service.ts`, `deliveryAction` в `core/work/delivery.ts`): для писем без адресата и упоминания откладывать указатель до `SETTLE_MS` тишины в комнате; при любом «срочном» письме сбрасывать всю пачку одним указателем «New messages (N)». Занятого агента, как и сейчас, не трогают: письма ждут конца хода. Для `wait_for("inbox")` — то же правило: срочное возвращается сразу, несрочное после `SETTLE_MS` или вместе со срочным.

Ожидаемо: при 3 участниках подтверждения и промежуточные заметки перестают стоить по ходу каждому.

### C1.3 Гид: тишина вместо подтверждений, одно долгое ожидание

В тему переписки гида и в бриф участника комнаты:

- не подтверждать получение и не объявлять начало работы: молчание — «получил»; писать только результат, вопрос или решение;
- ждать одним вызовом: `wait_for("inbox", 1800)`, без текста до и после, без `Monitor`/`sleep`/повторов; на `state: "running"` — повторить один раз, затем закончить ход: Parley разбудит указателем;
- ведущему: ждать ответов на раздачу одним `wait_for("inbox")`, а не по id каждого исполнителя.

Правило про тишину окно отражает: системная строка «план принят» (уже есть при `rooms.resolveProposal`) заменяет письмо ведущего «план принят, раздаю».

### C1.4 Меньше повторных чтений

- `get_map` без справочника `providers` по умолчанию. В ответе две части: `map` — сессии с их `provider`, `model`, `effort`, ролью, результатом и сводкой, комнаты, планы, непрочитанное (в прогоне B — 705 токенов) — остаётся как есть; `providers` — одинаковый для всех каталог «какие модели и уровни усилия принимает провайдер» для `spawn_session` (1616 токенов, 70 % ответа) — по `field: "providers"`, а при неверной модели в `spawn_session` приходит в тексте ошибки. Сведения о том, кто что делал и на какой модели, не трогаются.
- `check_inbox`/`wait_for` не повторяют письма, уже отданные в этом же ходу (сейчас это и есть C1.1).

### C1.5 Приёмка C1

На задаче спайка (ревью документа, 3 агента) тремя прогонами: ходов ведущего ≤ 20 (было 37), `wait_for` подряд без нового письма — 0, письма-подтверждения — 0, итоговый файл не хуже по разбору человеком. E2E на мок-сессиях: `wait_for` помечает прочитанным; несрочное письмо не рождает указатель до `SETTLE_MS`; `question` рождает сразу; человеческое — сразу всем.

Lean-режим без `disableAllHooks` (автопамять, плагины, чужие MCP) даёт ≈ −19 тыс. на каждый вызов модели сверх того, что уже делает навигатор. Базовые ≈ 24 тыс. — системный промпт Claude Code, встроенные инструменты, CLAUDE.md и гид Parley — остаются.

**Скиллы и MCP пользователя в lean-режиме.**
- Скиллы из `~/.claude/skills` и скиллы проекта (в том числе встроенные `parley` и `minimal-development`) остаются: навигатор отдаёт их имена, `find_skill` — описания с диска (`skills/claude-listing.ts`). Пропадают только скиллы отключённых плагинов (superpowers, OMC…): Claude Code их не перечисляет, и `find_skill` их не видит, потому что берёт доступность из вложения `skill_listing` транскрипта. Если они нужны агентам комнат — отдельная задача: `find_skill` читает `SKILL.md` отключённых плагинов с диска и отдаёт путь; текст скилла агент прочитает, а хуки, команды и MCP плагина работать не будут.
- Чужие MCP-серверы в lean-сессию не подключаются вовсе, и подключить сервер к уже идущей сессии Claude Code нельзя — «навигации» для MCP нет. Взамен — список на работу: в панели Capabilities человек отмечает, какие из своих серверов получают агенты этой работы; Parley переносит их определения (чтение `~/.claude.json`, без записи) в свой `--mcp-config` рядом с `parley`, у Codex — `-c mcp_servers.<id>.enabled=true`. По умолчанию — ни одного; гид: «нужен инструмент чужого MCP — назови человеку сервер, он включается на работу в Capabilities».

## Мои выборы, не обсуждавшиеся явно

- Несрочные письма откладываются, но не позже окна тишины: комната не теряет темп, когда больше никто не пишет.
- Lean-режим по умолчанию только для сессий, созданных Parley в комнаты и через `spawn_session`: это рабочие, а не окно человека.
- `--bare` только для GLM; для подписки Claude честно признаётся предел.
- Критерий −30 % — на той же задаче спайка, тремя прогонами и по медиане: один прогон, как показал спайк, шумит на ±10 % из-за простоев.
