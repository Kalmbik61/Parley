## 1. Зачем

1. **Плана нет — есть текст.** У комнаты один слот решения: свободный текст до 10 000
   знаков, версия, «принять» или «вернуть». После принятия ведущий раздаёт части
   упоминаниями. Кто что делает, что от чего зависит, что сделано и проверено — нигде не
   записано, следить за этим некому, кроме ведущего и человека.
2. **«Готово» ничем не подтверждено.** `report(done)` сдаёт сессия сама; критериев
   приёмки и проверки другой сессией нет. То, что OMC и oh-my-codex дают упорством
   (ralph, журнал целей ultragoal), в Parley держится на внимании человека.
3. **Задачам «на потом» негде жить.** Хвосты работы, найденные ошибки, идеи теряются в
   переписке или уходят в файлы, о которых Parley не знает.
4. **`.parley/` целиком скрыт от git.** Делиться с командой нечем: бэклог и планы должны
   попадать в git, а карты, журналы и учёты — нет.
5. **Не каждой задаче нужна церемония.** Мелкой хватает текста, связанной — списка,
   рискованной — проверки. Тяжёлый путь не должен навязываться.

## 2. Решения

| Вопрос | Решение |
|---|---|
| Уровни | Бэклог проекта и план комнаты; списков у отдельных сессий нет |
| Где бэклог | `.parley/backlog.md`, в git; по выбору — `TODOS.md` проекта (спека `2026-10-07-backlog-todos-file-design.md`) |
| `.parley/` | Наполовину общий: новый каталог прячет себя целиком (`*`), а при первой общей записи свой `.gitignore` становится белым списком и пропускает в git только общие файлы (бэклог, снимки планов и т. д.) |
| Где план | В карте работы (`map.plans`); Markdown-снимки — в `.parley/plans/`, в git |
| Режим комнаты | Переключатель `Free · Checklist · Verified`, по умолчанию Free. Человек — в любую сторону, ведущий — только вверх (`set_room_mode`) |
| Проверка | В Verified: владелец сдаёт, проверяющий (сессия или ведущий) проверяет, итог принимает человек. В Checklist проверки нет |
| Очередь | Parley сам будит владельцев, чья очередь пришла, и тех, кому вернули; в пределах лимитов будильника |
| Предложения агентов | `backlog_suggest` с видом находки; правило проекта решает, что записывать сразу, а что предлагать человеку |
| Хранение предложений и правила | Локально, в `.parley/`, не в git |

## 3. `.parley/`: общее и локальное

### 3.1 Состав

```
.parley/
  .gitignore                  свой, Parley: сначала `*`, с первой общей записи — белый список
  backlog.md                  общее — в git
  plans/                      общее — в git: снимки планов комнат
  works/                      локальное: карты, журналы, брифы, MCP, лимиты
  backlog-suggestions.json    локальное: ждущие предложения агентов
  preferences.json            локальное: правило предложений
  backlog.lock                локальное
  *-receipt.json              локальное: учёты навыка и PARLEY.md
```

### 3.2 `.gitignore`: сначала `*`, затем белый список

Новый каталог получает `.gitignore` из одной строки `*`: в git не попадает ничего, в том числе сам
`.gitignore`. Белым списком он становится при первой общей записи (раздел 3.3):

```
*
!.gitignore
!backlog.md
!plans/
!plans/**
```

Всё, что Parley заведёт в `.parley/` позже, по умолчанию останется локальным.

### 3.3 Переход и чужие правила

- `writeSelfIgnore` для нового каталога пишет `*\n` (в том числе при переносе `.harnas` → `.parley`).
- Белым списком файл становится при первой общей записи: бэклог, снимок плана, память
  проекта, журнал решений, общая история комнаты или рецепт. Parley переписывает
  `.gitignore` под общим замком проекта, только если в нём ровно его `*\n` или прежний
  сгенерированный белый список. Правленный человеком файл не трогается; окно один раз показывает уведомление
  `parley-gitignore-custom`.
- Если корневой `.gitignore` проекта скрывает сам `.parley/` (так в этом репозитории),
  git не пустит внутрь никакие исключения: бэклог и планы остаются локальными. Корневой
  `.gitignore` — файл человека, Parley его не правит; окно один раз показывает
  уведомление `parley-dir-ignored`: убрать строку `.parley/`, если нужно делиться.
  Проверка — `git check-ignore` на `.parley/backlog.md`.
- Проект со старым `.harnas/`: общие файлы лежат в каталоге состояния, который выбирает
  `stateDir`, — переносом данных они переедут вместе с ним.

## 4. Бэклог

Shared project context использует verified canonical main checkout и сохраняет явно выбранную вложенную папку проекта относительно checkout root. Missing/unverified corresponding folder не заменяется repo root или participant cwd. Для non-Git допустим verified canonical project directory; ошибка Git в неоднозначном контексте не доказывает non-Git. Local workPaths сохраняются. Версионированные sequence/terminal suggestion records лежат локально и не меняют форматы b-NNN/sg-NN или dedup только open/pending. Lock + compare/retry защищает от обнаруженных внешних изменений; portable compare→rename не обещает filesystem CAS, Markdown и JSON не одна atomic transaction, partial retry идемпотентен по reserved operation/ID.

### 4.1 Формат `backlog.md`

```markdown
# Backlog

## Ideas
- [ ] Auto-resume after the subscription limit resets <!-- b-007 -->
  Park sessions on the limit and resume them after the reset.
- [ ] Bridge for .claude/CLAUDE.md <!-- b-008 · taken: w-0043/r-01 -->
- [x] PARLEY.md template <!-- b-003 · done: 2026-10-05 -->
- [ ] Flaky resume test on CI <!-- b-012 · by: s-03 -->
```

- Пункт — строка `- [ ]` или `- [x]` в начале строки. Заголовок — текст до служебного
  комментария. Подробности — следующие строки с отступом от двух пробелов.
- Служебный комментарий в конце строки пункта: `b-NNN` (id) и пометки через `·`:
  `taken: <работа>/<комната или сессия>`, `done: <дата>`, `by: <сессия>` (записал агент).
- Пункт относится к ближайшему заголовку выше — это его раздел.
- Пункт без id (написан руками) получает следующий `b-NNN` при ближайшей записи Parley.
- Всё, что Parley не понимает (абзацы, таблицы, другие списки), сохраняется байт в байт:
  Parley переписывает только строки пунктов, которые трогает, и дописывает новые в конец
  раздела или файла.

### 4.2 Запись

- Под замком `.parley/backlog.lock` с проверкой времени изменения: файл поменялся между
  чтением и записью — перечитать и повторить.
- Маркеры конфликта слияния (`<<<<<<<`) в файле — Parley его не трогает: вкладка
  показывает ошибку, инструменты отвечают ошибкой.
- Файл создаётся при первой записи с заголовком `# Backlog`.

### 4.3 Что с пунктом происходит

- **Человек** добавляет, правит, отмечает сделанным и удаляет пункты во вкладке Backlog
  или в самом файле.
- **«Take into room…»** открывает диалог «New session or room» с текстом пункта задачей;
  после создания пункт получает `taken`.
- **Закрытие:** план, который закрывает пункт (раздел 7), при завершении ставит `[x]` и
  `done`. Взятый в комнату Free пункт закрывает человек.
- **Агенты** пунктов не закрывают и не правят. Добавляют только через `backlog_suggest`:
  записать сразу или предложить человеку — решает правило проекта (раздел 5). Читают —
  `backlog_list`.

### 4.4 Окно

Вкладка Backlog панели проекта (той, что вводит спека Capabilities; если её ещё нет, этот
подпроект заводит панель сам): разделы файла, фильтры «открытые», «взятые», «сделанные»,
добавление и правка, «Take into room…», «Open file» — открыть `backlog.md` в редакторе.

## 5. Предложения агентов

### 5.1 Инструмент

`backlog_suggest(kind, title, details?, why)` — для любой сессии:

| `kind` | Что это |
|---|---|
| `bug` | Найденная ошибка |
| `debt` | Долг: чистка, недостающий тест, хрупкое место |
| `idea` | Новая возможность или расширение задачи |

### 5.2 Правило проекта

Переключатель на вкладке Backlog, хранится в `.parley/preferences.json` (локально):

| Значение | Что записывается сразу | Что приходит предложением |
|---|---|---|
| `ask` | ничего | всё |
| `problems` (по умолчанию) | `bug`, `debt` | `idea` |
| `everything` | всё | ничего |

- Записанное сразу попадает в `backlog.md` с пометкой `by: <сессия>`; инструмент
  отвечает `added: b-012`.
- Предложение лежит в `.parley/backlog-suggestions.json` (`sg-NN`, вид, заголовок,
  подробности, «зачем», автор — работа и сессия, время) и в `backlog.md` не пишется, пока
  человек его не примет; инструмент отвечает `suggested: sg-05`.
- Повтор — тот же заголовок без учёта регистра у открытого пункта или ждущего
  предложения — не принимается: `already in backlog: b-012`.

### 5.3 Окно

- Наверху вкладки Backlog — раздел `Suggested (N)`: заголовок, подробности, «зачем»,
  автор с чипом роли; кнопки Add, Edit & add, Dismiss.
- Строка в ленте комнаты автора: `S03 suggested for the backlog: …` или
  `S03 added to the backlog: …`.
- Счётчик ждущих предложений у панели проекта.

### 5.4 Чтобы агент делал это сам

- Системная вставка: заметил стоящую работу вне своей задачи — предложи её через
  `backlog_suggest`, одна находка — один пункт, с причиной; задачу ради неё не расширяй;
  сначала проверь `backlog_list`.
- Гид ведущего: перед `propose_completion` собрать хвосты работы в предложения.
- Проект, который ведёт свой `TODOS.md`, указывает в PARLEY.md, куда класть хвосты.

## 6. Режим комнаты

### 6.1 Три режима

| Режим | Когда | Как работает |
|---|---|---|
| `free` (по умолчанию) | Мелкие задачи | Как сейчас: решение текстом, части раздаются упоминаниями |
| `checklist` | Несколько связанных частей | Каждое решение — со списком: пункты, владельцы, зависимости; Parley будит по очереди и закрывает план, когда всё сделано |
| `verified` | Важное, рискованное, или когда просит человек | Плюс критерии и проверяющий у каждого пункта, итог принимает человек |

В карте у комнаты поле `mode`; у существующих комнат при чтении — `free`.

### 6.2 Кто переключает

- **Человек** — переключателем `Free · Checklist · Verified` в шапке комнаты, в любую
  сторону.
- **Ведущий** — инструментом `set_room_mode(mode, reason)`, только вверх
  (`free` → `checklist` → `verified`), например когда человек просит проработать решение
  детально. Причина обязательна, одной строкой. В ленте —
  `S01 switched the room to Checklist: the human asked for a detailed plan`. Понижает
  только человек: понижение снимает проверки, которые он мог включить сам.
- `propose_decision` проверяет соответствие режиму: в `free` план не принимается; в
  `checklist` и `verified` решение без плана нужного вида не принимается.

### 6.3 Переключение посреди работы

| Переход | Что происходит |
|---|---|
| `verified` → `checklist` (человек) | Сразу: критерии и проверяющие не используются, пункты `done` в ожидании проверки считаются сделанными, `returned` — снова `in_progress`; письма проверяющим отменяются; план закроется сам, когда всё сделано |
| `checklist` → `verified` | План идёт списком, пока человек не примет версию плана с критериями и проверяющими; если переключил человек — письмо ведущему «добавь критерии и проверяющих». После принятия проверка действует для несделанных пунктов |
| `free` → `checklist` или `verified` | Если переключил человек — письмо ведущему «принеси план для текущей задачи» |
| любой → `free` (человек) | С подтверждением: активный план отменяется |

## 7. План комнаты

### 7.1 Модель

План — в карте работы, список `plans`; у плана `roomId`. Активный план в комнате — не
больше одного; закрытые и отменённые остаются историей. Счётчик — `work.planSeq`.

| Поле плана | Что это |
|---|---|
| `id` | `pl-01` |
| `roomId` | Комната |
| `mode` | `checklist` или `verified` |
| `status` | `proposed` → `active` → (`completing`, только `verified`) → `completed`; или `cancelled` |
| `rev` | Номер переделки |
| `goal` | Абзац: что значит «готово» целиком |
| `items` | Пункты |
| `backlog` | Id пунктов бэклога, которые закрывает план |
| `acceptedAt`, `completedAt` | Время принятия и закрытия |

| Поле пункта | Что это |
|---|---|
| `id`, `title` | `1`, `2`, … и заголовок |
| `owner` | Сессия-владелец — живой участник комнаты |
| `scope` | Область: файлы или часть системы, свободным текстом; здесь ведущий может назвать скилл участника и способ его загрузки |
| `after` | Id пунктов, от которых зависит этот |
| `criteria` | Только `verified`: критерии приёмки, от одного до десяти |
| `verifier` | Только `verified`: сессия-проверяющий; не указана — ведущий; не может быть владельцем |
| `status` | `waiting`, `ready`, `in_progress`, `done`, `blocked`; в `verified` ещё `verified`, `returned` |
| `evidence` | Что сдал владелец: текст и пути артефактов |
| `note` | Замечание проверяющего или причина блокировки |
| `log` | Короткий журнал: время, кто, статус, заметка |

### 7.2 Проверка плана при предложении

- владельцы и проверяющие — живые участники комнаты;
- в зависимостях нет циклов и ссылок на несуществующие пункты;
- в `verified`: у каждого пункта есть критерии, проверяющий не совпадает с владельцем;
- до 30 пунктов и 30 связанных ID бэклога; общий текст решения, цели, названий, scope и критериев — до 10 000 единиц UTF-16, как у прежнего решения Free. Текст evidence вместе с путями артефактов ограничен отдельно теми же 10 000 единицами; длина артефакта — до 1024. UTF-8 байты ограничивают общий MCP envelope (64 КиБ), а не заменяют лимит текстовых полей.

Нарушение — `propose_decision` отклоняется с понятной ошибкой.

### 7.3 Путь

Уточнение к переходу §6.3: уже выполненный Checklist-пункт сохраняет `done` при принятом человеком переходе в Verified, если его title/owner/scope/after не изменились. Добавление критериев/проверяющего только для этого перехода не заставляет повторять выполненную работу. В плане и immutable snapshot явно сохраняется основание «выполнено в Checklist, принято в ревизии N»; такой пункт не называется `verified`. Он может удовлетворять зависимость и итоговое закрытие принятого плана. Основание выводится из прежнего выполненного пункта и принятого перехода, не задаётся агентом в draft. Для несделанных пунктов действует обычная независимая проверка. Обычная последующая семантическая правка, изменение основных полей или инвалидированная зависимость удаляет это основание/результат и включает обычные правила §7.3.7.

1. **Предложение.** Ведущий — `propose_decision(text, plan)`. Карточка решения
   показывает план целиком; человек — Accept или Return for rework, повтор — `rev + 1`.
2. **Принятие.** План `active`. Пункты без зависимостей — `ready`, остальные —
   `waiting`. Части раздаёт Parley письмами владельцам `ready`-пунктов (раздел 8).
3. **Работа.** Владелец — `plan_update(planId, rev, item, in_progress | blocked, note)`, сдаёт —
   `plan_submit(planId, rev, item, evidence)`: пункт `done`.
4. **Очередь.** Пункт становится `ready`, когда все его `after` — `done` (в `checklist`)
   или `verified` (в `verified`).
5. **Проверка** (только `verified`). Проверяющий — `plan_verify(planId, rev, item, verified | returned, note)`. `returned` — владелец переделывает и сдаёт снова.
6. **Закрытие.**
   - `checklist`: все пункты `done` — план `completed` сам, строка в ленте.
   - `verified`: все пункты `verified` — план `completing`, ведущий приносит итог
     `propose_completion(planId, rev, summary)`; человек принимает — `completed`, возвращает с
     замечанием — снова `active`.
   - При закрытии связанные пункты бэклога получают `[x]` и `done`.
7. **Переделка на ходу.** Ведущий приносит новую версию тем же `propose_decision`. После
   принятия пункты с прежним `id` сохраняют статус только при неизменных заголовке,
   владельце, области, зависимостях, критериях и проверяющем. Изменённые пункты и
   зависимые от них результаты теряют прежнюю сдачу/проверку; очередь пересчитывается,
   удалённые пункты уходят в журнал.

### 7.4 Последнее слово за человеком

В панели плана человек может отметить пункт сделанным (`checklist`) или проверенным и
вернуть (`verified`), отменить план. Если проверить пункт, кроме владельца, некому (в
комнате только ведущий, и пункт его), проверяет человек.

### 7.5 Решение и итог в карте

`Proposal` получает `kind: 'decision' | 'completion'`; у решения — необязательный
`plan` (черновик плана), у итога — `planId`. Принятие решения с планом переносит
черновик в `map.plans` со статусом `active`.

### 7.6 Снимки в `.parley/plans/`

Файл `<работа>-<комната>-<план>-rev-<rev>-<событие>.md`, где событие —
`accepted`, `completed` или `cancelled`: цель, режим, статус, даты, пункты с владельцами
(ярлык и роль), областью, зависимостями, итоговыми статусами, кратко — доказательства и
замечания проверяющих.

| Режим | Когда пишется |
|---|---|
| `checklist` | При принятии, принятой переделке, закрытии и отмене |
| `verified` | При принятии, принятой переделке, закрытии и отмене |

Checklist тоже сохраняет принятую версию: иначе журнал решения не сможет
сослаться на её состав после переделки. Это экспорт без дополнительного действия
человека. Снимки разных принятых версий и событий не перезаписывают друг друга. Повторная
обработка того же события идемпотентна. Решение в журнале ссылается на снимок именно
своего `rev` и события; статус в живой карте может меняться дальше.

## 8. Будильник

### 8.1 Кому и когда

| Событие | Кому письмо | Что в нём |
|---|---|---|
| План принят | Владельцам `ready`-пунктов | `planId`, `rev`, пункт, область (включая подсказку скилла), критерии (в `verified`), подсказка про `plan_submit` |
| `plan_submit` в `verified` | Проверяющему | Пункт, критерии, доказательства, подсказка про `plan_verify` |
| Пункт стал `ready` по очереди | Его владельцу | То же, что при принятии |
| `returned` | Владельцу | Замечание проверяющего |
| `blocked` | Ведущему | Пункт и причина |
| Всё проверено (`verified`) | Ведущему | «принеси итог через `propose_completion`» |
| Человек вернул итог | Ведущему | Замечание человека |
| Человек поднял режим | Ведущему | Что принести (6.3) |
| Владелец закрыт или удалён | Ведущему | Пункт стал `blocked` |

### 8.2 Как

- Отправитель — новый системный `parley`, в ленте «Parley». Письма несут план, который
  принял человек: агент выполняет свой пункт, а не обсуждает его. Это пишется в гиде.
- Доставка — существующая: указатель после хода, подъём спящей сессии. Владелец ещё не
  запущен — Parley запускает его сессию при включённом autoLaunch; при выключенном окно
  показывает «готов к запуску».
- Лимиты прежние (`messageRate` 20 в час, `resumeRate` 6 в час); сверх лимита письма
  ждут очереди, окно это показывает.
- Drain очереди и автоматическое пробуждение — обязанность существующего host.
  Standalone MCP сразу резервирует письма и выполняет доступный flush; без host
  rate-held intents остаются pending до следующего вызова координации плана или
  старта host. Отдельный таймер в каждом MCP-процессе не добавляется.
- События плана — системными строками в ленте комнаты: `#2 verified by S04`,
  `#3 returned: …`, `Plan pl-01 completed`.

## 9. Окно

- **Шапка комнаты:** переключатель `Free · Checklist · Verified` с подсказками;
  понижение с активным планом — с подтверждением.
- **Панель плана** в комнате: шапка — цель, режим, статус, прогресс (`3/5 verified` или
  `3/5 done`); пункты — заголовок, чип владельца (с ролью, если есть), статус,
  зависимости, раскрываются критерии, доказательства, замечания; действия человека из 7.4.
- **Карточка решения** показывает предложенный план; кнопки прежние.
- **Карточка итога** (`verified`): сводка ведущего и состояние плана; Accept и Return с
  замечанием.
- **Сайдбар:** у строки комнаты значок прогресса `3/5`.
- **Панель проекта:** вкладка Backlog с разделом `Suggested (N)` и переключателем
  правила предложений.
- **Уведомления:** `parley-gitignore-custom`, `parley-dir-ignored`, ошибка записи
  снимка, маркеры конфликта в `backlog.md`.

## 10. Инструменты агентов

| Инструмент | Кто | Что делает |
|---|---|---|
| `propose_decision(text, plan?)` | ведущий | Решение; в `checklist` и `verified` — с планом нужного вида |
| `propose_completion(planId, rev, summary)` | ведущий | Итог плана `verified` в статусе `completing` |
| `set_room_mode(mode, reason)` | ведущий | Поднять режим комнаты |
| `plan_update(planId, rev, item, status, note?)` | владелец | `in_progress` или `blocked` |
| `plan_submit(planId, rev, item, evidence)` | владелец | Сдать пункт |
| `plan_verify(planId, rev, item, verdict, note)` | проверяющий, без него — ведущий | `verified` или `returned` |
| `backlog_list(filter?, text?)` | любой | Пункты бэклога с id, разделом, статусом, пометками |
| `backlog_suggest(kind, title, details?, why)` | любой | Записать или предложить по правилу проекта |

- Изменяющие вызовы плана несут `planId` и текущий `rev`; старое письмо или результат
  проверки после принятия переделки получает «конфликт» без изменения карты.
- Повторный или поздний вызов проверяется по статусу: сдать можно только из `ready`,
  `in_progress` или `returned`, проверить — только из `done`; иначе ответ «конфликт».
- `get_map`: у комнаты — `mode`; планы кратко: статус, прогресс, пункты с владельцами и
  статусами.
- Гид: новая тема `plans` — режимы, план, инструменты, письма Parley, бэклог и
  предложения.
- Системная вставка: строки о режимах и планах и о `backlog_suggest` укладываются в
  прежний потолок в 14 строк — соседние строки сжимаются; проверка потолка остаётся.

Free сохраняет прежний ответ `propose_decision`: `{proposalId, rev}`. Сведения об effects добавляются только к инструментам планов; новый режим не меняет прежние Free-клиенты. Гид при выключенном навигаторе не обещает `find_skill`, а описывает нативную загрузку доступного скилла.

### 10.1 Скиллы в назначениях

При доступном навигаторе ведущий ищет подходящий скилл через `find_skill(query, for)`
для владельца пункта, а при необходимости — отдельно для проверяющего. Результат
записывается в `scope` или текст решения обычным текстом; нового поля `skill` нет.
Поиск не является критерием готовности: допустим ответ «скилл не нужен». Если после
назначения файл исчез, участник сообщает об этом ведущему и продолжает в рамках роли
или просит изменить назначение. Parley не загружает скилл за него.

Содержание принятого назначения приходит в системном письме владельцу и остаётся
в снимке плана. В `evidence` участник может назвать использованный скилл; чтение
`SKILL.md` само по себе не означает, что пункт выполнен или проверен.

## 11. Граничные случаи

| Случай | Поведение |
|---|---|
| Корневой `.gitignore` скрывает `.parley/` | Бэклог и планы остаются локальными; уведомление один раз |
| `.parley/.gitignore` правил человек | Не переписываем; уведомление один раз |
| Строки `backlog.md`, которые Parley не понимает | Сохраняются байт в байт |
| `backlog.md` правят одновременно Parley и человек | Замок и проверка времени изменения; редактор окна показывает конфликт, как для любого файла |
| Маркеры конфликта в `backlog.md` | Файл не трогается; вкладка и инструменты — ошибка |
| Нарушение правил плана (7.2) | `propose_decision` отклоняется с понятной ошибкой |
| Владелец закрыт или удалён | Пункт `blocked`, письмо ведущему |
| Ведущий закрыт | Его место занимает первый живой участник, как сейчас; план идёт дальше |
| Комната закрыта с активным планом | План отменяется |
| Сессия в worktree | `backlog.md` и `plans/` — в каталоге состояния основного проекта, не в worktree |
| Снимок не пишется | `host.log` и уведомление; план идёт дальше |
| Лимиты будильника | Письма ждут очереди, окно это показывает |
| Нет `preferences.json` | Правило `problems` |
| Предложение от закрытой сессии | Остаётся в `Suggested`, автор показан как был |

## 12. Тесты

**core (vitest):**
- бэклог: разбор и запись без потерь чужого текста, разделов и id; пометки `taken`,
  `done`, `by`; присвоение id пунктам без него; маркеры конфликта;
- `.gitignore`: новый каталог получает `*`, первая общая запись переключает его на белый список;
  переписывается только прежнее `*` или сгенерированный белый список; обнаружение корневого запрета;
- предложения: маршрут по правилу и виду, повтор, локальное хранение;
- режимы: соответствие решения режиму; переключение — человек в любую сторону, ведущий
  только вверх; переходы из 6.3;
- план: проверки 7.2; статусы пунктов в обоих режимах; очередь по `after`; слияние
  переделки; закрытие и закрытие пунктов бэклога;
- версии: изменение title/owner/scope/after/criteria/verifier сбрасывает результат
  и зависимые проверки; старый planId/rev отклоняется без мутации;
- письма: кому уходит письмо на каждое событие из 8.1, planId/rev и scope со скиллом;
- снимки: когда пишутся по режимам, содержимое;
- права инструментов: ведущий, владелец, проверяющий; конфликты по статусу;
- потолок 14 строк у системной вставки и английские тексты остаются зелёными.

**host:** письма, будильник и запуск ждущих сессий; лимиты; уведомления; строки ленты о
режиме и событиях плана.

**окно:** переключатель режима, панель плана, карточка решения с планом, карточка итога,
вкладка Backlog с `Suggested` и правилом, «Take into room…», значок прогресса.

**Живые проверки:**
- комната в Checklist из двух-трёх сессий с зависимостями: Parley сам будит следующих;
- комната в Verified с проверяющим на Codex: возврат → повторная сдача → проверено →
  итог принят;
- ведущий сам поднимает режим, когда человек просит проработать решение детально;
- агент по ходу работы предлагает хвосты: `bug` записывается сразу, `idea` ждёт в
  `Suggested`;
- пункт бэклога взят в комнату и закрыт планом;
- в проекте без корневого запрета git видит `backlog.md` и снимок плана.

## 13. Порядок и зависимости

- **Две группы задач единого плана:** этап 6 — `.parley/`, бэклог и предложения;
  этап 7 — режимы, планы, инструменты, будильник, панель и снимки. Отдельных
  конкурирующих очередей реализации нет.
- **Панель проекта** — из спеки Capabilities; если её ещё нет, план (а) заводит её сам.
- **Роли** (`2026-10-02-agent-roles-design.md`) подсвечиваются у владельцев,
  проверяющих и авторов предложений; планы от ролей не зависят.
- **PARLEY.md** (`2026-10-02-parley-md-design.md`) даёт ведущему правила проекта, по
  которым он решает, поднимать ли режим, и куда класть хвосты; правки системной вставки
  делаются вместе.
- Навигатор необязателен: план работает при `skillNavigator: false`. Порядок
  реализации и общая панель проекта закреплены в едином плане.

## 14. Вне объёма

- Собственные списки задач Claude и цели Codex (`/goal`).
- Импорт существующего `TODOS.md`.
- Планы у одиночной сессии без комнаты; несколько активных планов в комнате; планы через
  несколько работ.
- Оценки и сроки.
- Синхронизация с GitHub Issues.
- Шаблоны планов — это рецепты комнат, следующий подпроект.
- Закрытие пунктов бэклога агентами.
- Режим по умолчанию для новых комнат из настроек или PARLEY.md.

## Граница API бэклога

MCP предоставляет только backlog_list и backlog_suggest, с project/work/session identity из доверенного launch context. Эти tools не редактируют, не удаляют и не закрывают существующие пункты. Ручные host methods доступны аутентифицированному клиенту по существующему общему host token; caller-chosen hello.client не служит подтверждением человека. Это разделение интерфейсов, а не sandbox для владельца полного токена или файлового доступа того же пользователя. Новая архитектура аутентификации в P21 не вводится.

Для handwritten строки Take сначала выполняет version-bound prepareTake: назначает stable ID в существующей shared transaction, сохраняя её текст. Dialog затем создаёт room/session; taken ставится только после успешного создания. При ошибке marker сохраняются созданный target и stable ID; Retry повторяет marker, не создание комнаты.

  написанной руками.
- Режимы, версии планов, будильник и письма (P22, cec588d; P23, 6a3635f и b511fda); панель плана,

**Отступления от текста выше.**

- Белый список `.parley/.gitignore` (раздел 3.2) шире, чем там записано (с 2026-10-06 он включается
  при первой общей записи, а не при создании каталога): к `backlog.md` и
  `plans/` добавились `memory.md`, `decisions/`, `history-shared/` и `recipes/`. Переписывается
  только точная прежняя версия файла; правленный человеком не трогается, окно один раз
  говорит об этом уведомлением `parley-gitignore-custom`.
- `get_map` (раздел 10) у агента теперь компактный: у комнаты — `mode`, `recipe` (id и имя),
  решение, счётчики писем и непрочитанного; планы — только живые (`proposed`, `active`,
  `completing`), с точной ревизией, нужной для `plan_*`, и урезанными длинными текстами. Закрытые
  и отменённые планы в карту агента не входят: их читают как снимки в `.parley/plans/` через
  `search_history` (область `plans`). Письма и длинные тексты читаются страницами `get_map`.
- Бюджет работы (P37, e87d125). Письма от агентов (приглашения комнаты — тоже письма), запуски,
  возобновления и новые сессии считаются на работу и на более узкую комнату; пороги — в Settings →
  Agents («Work limits»). Письма самого Parley (в том числе будильник планов), человека и хоста
  в счёт не идут, Stop, close, `report` и чтение не блокируются. Прежние `messageRate`
  (20 в час на сессию) и `resumeRate` (6 в час на сессию) остаются. Это счёт сессий и писем,
  а не токенов и денег.
- Подагенты и форки внутри CLI бюджетом не ограничиваются и предотвращёнными не называются.
