# План агента в комнате и на вкладке Agents — дизайн

**Дата:** 2026-10-18. **Статус:** место показа выбрано пользователем (A + D), текст написан по его поручению «пиши
спеку». Решения — раздел 8. После ревью 2026-10-18 уточнены достоверность восстановления, сводка до обрезки,
настоящие ID субагентов, сброс явной сессии и открытие подробностей в узком окне. Источник — проход индекса лога.
**База:** `master` 9582ec91.
**База реализации:** `5dbe95b6`; к началу реализации индексы уже поддерживают дочитывание хвоста. План подключается к существующим накопителям, сохраняя эту оптимизацию.

---

## 1. Зачем

Пользователь, 2026-10-18:
- «Сейчас когда агенты работают, не совсем видно, над чем они работают. Хотелось бы видеть, над какими задачами
  работает каждый агент. Какие задачи он сделал и какие задачи ему предстоят.»
- «Не рисовать какую-то канбан-доску, а просто видеть и понимать, что за задача.»
- «При наведении мышки на неё видеть её description. Либо кликать и видеть подробное описание задачи, что он должен
  сделать, с чем это связано.»

Выбор места (из обсуждения вариантов «комната / сайдбар / шапка Chat / вкладка Agents»): **обзор — в карточке
участника комнаты, подробности — на вкладке Agents правого сайдбара.** В сайдбар работ и шапку Chat план не добавляем.
При открытии подробностей в узком окне левый сайдбар закрывается, чтобы освободить место для Agents.

## 2. Что есть сейчас (проверено 2026-10-18)

**Что пишет Claude Code.** Текущий CLI (логи 2.1.227 и 2.1.229, бинарник 2.1.302) ведёт план инструментами
`TaskCreate` / `TaskUpdate`. `TodoWrite` в 400 последних логах не вызван ни разу.

| Инструмент | Вход | Ответ (`toolUseResult` в логе) |
|---|---|---|
| `TaskCreate` | `subject`, `description`, `activeForm`, `metadata?` | `{ task: { id: "1", subject } }`; текст ответа — `Task #1 created successfully: …` |
| `TaskUpdate` | `taskId`, необязательно `status` (`pending` · `in_progress` · `completed` · `deleted`), `subject`, `description`, `activeForm`, `owner`, `addBlocks`, `addBlockedBy`, `metadata` | `{ success, taskId, updatedFields, statusChange?: { from, to } }` |
| `TodoWrite` (старый, в CLI ещё есть переменная `CLAUDE_CODE_ENABLE_TODO_TOOLS`) | `todos: [{ content, status, activeForm }]` — весь список целиком | — |
| `update_plan` (Codex) | `plan: [{ step, status }]` — весь список целиком, `explanation?` | — |

Номер задачи в `TaskCreate` не передаётся: его назначает CLI и возвращает в ответе. В живых логах номера идут
`1, 2, 3…` в порядке создания. Задачи на диске CLI не хранит: каталоги `~/.claude/tasks/session-*` пусты. Значит,
единственный источник — вызовы в логе и в хуках.

**Что уже умеет Parley.**
- Этапы субагента на экране агента вкладки Agents: `agentSteps` берёт последний `TodoWrite` или `update_plan`
  из `children` карточки (`packages/desktop/src/renderer/agents/agents-model.ts:82`). `TaskCreate` он не знает,
  поэтому у текущего Claude Code этапов нет. Это уже дефект.
- Вторая строка карточки участника комнаты (`components/rooms/ParticipantStrip.tsx`): `doing ?? task`.
  - `doing` — ожидание `wait_for` или живые субагенты; хост считает их в `LiveMetrics.tasks` / `waitingFor`
    (`core/src/work/activity.ts`, `host/src/activity/activity-service.ts`).
  - `task` — задача сессии из карты.
- Справа во второй строке стоит чип роли. Клик по строке открывает терминал участника, а строка субагентов —
  поповер `AgentsBadge`.
- План комнаты (`RoomPlan`, `PlanPanel.tsx`): пункты с `owner` (id сессии), `title`, `scope`, `criteria`, `status`.
  Это уровень «что поручено». План агента — уровень ниже, «как он это делает».
- Вкладка Agents показывает сессию `focusedSessionOf`: активную вкладку-сессию, а если активна комната — последнюю
  посещённую сессию по MRU. Выбрать участника комнаты она сейчас не умеет.
- Лента Chat не годится источником плана. Это кольцо последних элементов, засеянное хвостом лога, и ранние
  `TaskCreate` долгой сессии из неё выпадают. У субагента в ленте не больше 100 последних вызовов
  (`FEED_AGENT_CHILDREN`). У завершённого вложенного вызова есть `response.text`: `finishTool` сохраняет
  сокращённый результат (`FEED_CHILD_RESULT_LIMIT`). Он может содержать настоящий ID созданной задачи.

## 3. Цели, не-цели, анти-цели

**Цели**
1. По комнате сразу видно, над каким пунктом сейчас работает каждый агент и сколько пунктов сделано.
2. Наведение показывает пункты плана: что сделано, что идёт, что впереди. У текущего пункта видно описание.
   Для длинного плана число скрытых пунктов указано явно; сводка учитывает все пункты.
3. Клик открывает подробности на вкладке Agents: список с тем же лимитом, описания и с чем связана работа (пункт
   плана комнаты, поручённый этому агенту).
4. Этапы субагентов снова видны у текущего Claude Code.
5. План считается в одном месте (`@parley/core`) — правило «статусы из одного места».

**Не-цели**
- Канбан, колонки, перетаскивание.
- Правка плана человеком: план принадлежит агенту, окно его только показывает.
- План в сайдбаре работ и в шапке Chat.
- Связь отдельных пунктов плана агента с пунктами плана комнаты: связываем только сессию с её пунктом комнаты.
- `owner`, `addBlocks`, `addBlockedBy`, `metadata` из `TaskUpdate` — читаем, но не показываем.
- Генерация плана за агента или извлечение его из произвольного текста/code mode. Нет поддерживаемых вызовов —
  нет плана, в том числе у Codex; поддержка формата не означает наличие плана у каждой сессии.

**Анти-цели** (сделано, но провал)
- Описание, придуманное моделью: показываем только то, что агент написал сам.
- План вытесняет более важное: ожидание `wait_for` и живые субагенты по-прежнему видны первыми.
- Хост снова перечитывает большие логи по таймеру. Корень лагов 0.15.0 (2026-10-17) — `rooms.usage`, перечитывавший
  ≈370 МБ логов каждые 10 с. Повторять это нельзя.
- Устаревший план выглядит живым. Когда все пункты закрыты, карточка возвращается к задаче сессии.
- Ошибка или незавершённый вызов инструмента выглядят как выполненное изменение плана; угаданный ID меняет чужой пункт.

## 4. Модель плана — `@parley/core`

Новый модуль (имя — на усмотрение строителя, например `core/src/agent-plan.ts`, экспорт `@parley/core/agent-plan`).
Чистые функции, без диска.

```ts
type AgentPlanStatus = 'pending' | 'in_progress' | 'completed';

interface AgentPlanItem {
  id: string | null;          // подтверждённый ID TaskCreate; неизвестный ID и снимки списка — null
  subject: string;            // subject | content | step
  description: string | null; // только TaskCreate/TaskUpdate
  activeForm: string | null;
  status: AgentPlanStatus;
}

/** Полное состояние только на время свёртки; обрезанный снимок обратно в свёртку не подаётся. */
interface AgentPlanState {
  items: AgentPlanItem[];
  explanation: string | null; // update_plan.explanation (Codex)
  updatedAt: string;
  partial: boolean;           // есть пропущенные данные/неустановленные ID
}

interface AgentPlanSummary {
  current: AgentPlanItem | null;
  next: AgentPlanItem | null;
  done: number;
  total: number;
}

/** Ограниченный снимок для SessionIndex, LiveMetrics и окна. */
interface AgentPlan extends AgentPlanState {
  omitted: number;            // число пунктов, скрытых только лимитом отображения
  summary: AgentPlanSummary;  // вычислена по полному состоянию до обрезки
}

interface PlanCall {
  name: string;
  input: Record<string, unknown>;
  result?: unknown;           // объект результата, JSON-строка или текст ответа
  status: 'running' | 'done' | 'failed' | 'rejected';
  at: string;
}

function applyPlanCall(plan: AgentPlanState | null, call: PlanCall): AgentPlanState | null;
function capPlan(plan: AgentPlanState): AgentPlan;
/** Возвращает готовую summary; окно не пересчитывает её по обрезанным items. */
function planSummary(plan: AgentPlan): AgentPlanSummary;
```

Правила свёртки:
- Применяются только вызовы со статусом `done`, без явной ошибки результата (`success: false`, `is_error: true`).
  `running`, `failed` и `rejected` ничего не меняют. Отсутствие ответа не считается успехом.
- `TaskCreate` добавляет пункт в конец со статусом `pending`. ID берётся из `result.task.id` (в том числе из
  JSON-строки `response.text`) или из текста успешного ответа `Task #N created successfully: …`.
  У успешного вызова без распознаваемого ID пункт получает `id: null`, план — `partial: true`.
  Порядковые ID не придумываются; `TaskUpdate` никогда не сопоставляется с таким пунктом по позиции или заголовку.
- `TaskUpdate` находит пункт по `taskId` и меняет пришедшие поля. `status: deleted` убирает пункт. Неизвестный
  `taskId` — пункты не меняются; существующий план помечается `partial`, выдуманный пункт не добавляется.
- Успешные `TodoWrite` и `update_plan` заменяют список целиком и снимают `partial`, если сам снимок полный.
- **Граница плана** (Р10). Новый план начинается, когда:
  - успешный `TaskCreate` приходит, а все пункты полного, не `partial`, текущего плана закрыты;
  - новый уникальный `TaskCreate` возвращает ID уже имеющегося пункта — трактуем как новый список.
    Повтор того же вызова сначала отсекается по ID вызова; меньший, но ещё не встречавшийся ID сам по себе
    не сбрасывает план (ответы параллельных вызовов могут приходить в ином порядке).
  Сжатие контекста план не трогает: лог продолжается, номера тоже.
- Неизвестные статусы читаются как `pending`. Пустые `subject` пропускаются.
- `current` — первый пункт `in_progress`. `next` — первый `pending`, когда `in_progress` нет. `done` — число
  `completed`, `total` — число пунктов. Эти значения вычисляются до ограничения списка.
- `capPlan` сохраняет не больше 50 пунктов и исходный порядок: сначала первые 50; если `current` (или, при его
  отсутствии, `next`) вне этого набора, он заменяет последний пункт набора. `omitted = total - items.length`.
  `description` выбранных пунктов и пунктов в `summary` ограничивается 4096 символами с `…` в конце.
  Полностью завершённый план из 60 пунктов даёт `60/60`, текущий пункт №51 остаётся в обзоре и списке.
- `partial` означает неполноту источника, а `omitted` — только ограничение отображения. При `partial` точный общий
  счётчик `n/m` не показывается; рядом со списком — `Plan may be incomplete`. Числа `summary` описывают лишь
  восстановленную часть. Ограничение до 50 само по себе `partial` не выставляет.

Эти же функции зовут хост (план сессии) и окно (этапы субагента из `children`), вместо отдельного расчёта `agentSteps`.

## 5. Хост: план сессии в живых метриках

*Переписано 2026-10-18 при составлении плана: разведка кода показала путь проще, чем хуки и засев.*

- **Источник — уже идущий проход индекса лога.**
  - `indexSessionFile` у Claude и `indexCodexSession` у Codex читают файл целиком; живое обновление на базе
    реализации использует `extendClaudeSessionIndex` / `extendCodexSessionIndex` и существующее дочитывание хвоста.
  - Пересчёт идёт через `log-index.ts`: отложенно, не чаще раза в 2 с (`LIVE_REINDEX_MIN_INTERVAL_MS`). У Codex
    дополнительно опрос раз в 2 с.
  - Коллектор плановых вызовов принадлежит накопителю индекса, получает записи через `feed`, независимо копируется
    через `clone` и отдаёт снимок через немутирующий `finish` в `build`. Поздние ответы сохраняют исходный порядок
    вызовов между хвостами. Полное чтение и дочитывание дают одинаковый `SessionIndex.plan`; новых чтений диска нет.
- **Хуки не нужны.** `PostToolUse` в журнал хуков на диск не попадает, он идёт только в ленту по HTTP. А индекс лога
  есть у любой сессии, с хуками и без, живой и спящей. Поэтому нет ни засева, ни нового метода протокола.
  Повторы внутри самого журнала отсекаются в пределах одного прохода по ID вызова.
- **Claude.**
  - Вызовы — блоки `tool_use` в `message.content` записей ассистента.
  - Ответы — записи пользователя с блоком `tool_result` (`tool_use_id`) и полем `toolUseResult`.
  - Коллектор сохраняет только плановые вызовы в порядке первого появления, связывает ответы по `tool_use_id`
    и в `finish()` проигрывает их в исходном порядке вызовов, затем вызывает `capPlan`.
    Повтор вызова/ответа с тем же ID не создаёт второй операции и не меняет её место.
  - Ответ с `tool_result.is_error: true` или `toolUseResult.success: false` означает ошибку; отклонённый вызов
    тоже не применяется. Вызов без ответа пропускается, включая `TaskCreate`; при следующей переиндексации
    появившийся успешный ответ позволяет применить его на исходной позиции, перед последующими обновлениями.
  - Успешный ответ нормализуется из объекта `toolUseResult` или текста/текстовых блоков `tool_result.content`.
  - Записи `isSidechain: true` пропускаются: это вызовы субагентов в старом формате лога. В новом формате они лежат
    в отдельных файлах `subagents/*.jsonl` и в лог сессии не попадают.
- **Codex.** Запись `response_item` с `payload.type: function_call`, `name: update_plan`, а в `arguments` — JSON
  `{ plan, explanation? }`; результат `function_call_output` связывается по `call_id`.
  Применяется успешный завершённый вызов; отсутствие результата и явная ошибка не меняют план. Битый JSON
  пропускается. Порядок и отсечение повторов те же, что у Claude. В настоящих журналах пользователя за 20 дней
  таких вызовов нет: Codex работает в code mode. План Codex будет виден только при поддерживаемых вызовах;
  отсутствие вызовов — нормальный сценарий, поддержка парсера проверяется фикстурой с ответом инструмента.
- **Протокол:** в `LiveMetrics` новое поле `plan?: AgentPlan | null`. `metricsFor`
  (`host/src/activity/activity-service.ts`) берёт его из `indexed?.plan`.
  - Поля нет — хост старой версии, окно план не показывает.
  - `null` — плана нет.
  - `activity.changed` и так рассылается только при изменении значения: сравнение `sameLive`.
- **Потолки** (разделы 4 и 8): в индексе хранится до 50 пунктов с сохранением текущего/следующего и сводкой по
  полному плану; `description` до 4096 символов, хвост обрезан с пометкой. Полное состояние
  свёртки живёт только во время сборки снимка; таблица вызовов/ответов хранится в накопителе для следующего хвоста.
  Публикуемый индекс всех сессий хранит ограниченные снимки.
- План показывается у любой сессии в карте работы — живой, спящей, закрытой: `recompute` считает метрики для
  всех. План берётся из лога и не «протухает» вместе с процессом.

## 6. Карточка участника комнаты (A — обзор)

Вторая строка карточки:

1. **Текст:** `doing ?? пункт плана ?? task`. Ожидание и субагенты важнее плана. Без них:
   - `▸ {subject}` для пункта `in_progress`;
   - `Next: {subject}` для `next`, если в работе ничего нет;
   - задача сессии, если все пункты закрыты или плана нет.
2. **Счётчик `3/7`** — маленький чип справа во второй строке, перед чипом роли. Он есть, пока в плане есть открытые
   пункты, и в том числе когда текст строки занят ожиданием или субагентами. Так план не теряется, даже если строку
   занял `doing`. В тесной строке первым сжимается текст, счётчик — целиком. При `partial` вместо числа — `Plan`,
   чип сохраняется для доступа к предупреждению и подробностям; завершённость неизвестной части не утверждается.
3. **Наведение на счётчик или на текст пункта** — поповер в манере `AgentsBadge`:
   - сохранённые пункты: значок статуса и `subject` (сделано, в работе, впереди), `+{omitted} more` при обрезке;
   - `Plan may be incomplete`, если источник неполный;
   - у пункта `in_progress` — первые 6 строк `description`;
   - у Codex над списком — `explanation`;
   - внизу «Open in Agents».
   Длинный план прокручивается внутри поповера.
4. **Клик по счётчику, по тексту пункта или по «Open in Agents»** открывает правый сайдбар на вкладке Agents с
   планом этого участника (раздел 7). Клик по первой строке карточки по-прежнему открывает терминал.
   Когда строка показывает задачу (`task`), клик по ней ведёт себя как сейчас.

Тексты окна — по-английски (окно только на английском с 2026-09-27).

## 7. Вкладка Agents (D — подробности)

- **Чья сессия.**
  - Клик из карточки участника задаёт вкладке явную сессию. В шапке вкладки — имя участника (`S02 бэкенд`).
  - Когда человек активирует другую вкладку-сессию, вкладка снова следует за `focusedSessionOf`.
    Сброс привязан к фактической активации вкладки `terminal`/`diff`, а не к изменению результата
    `focusedSessionOf`: у комнаты MRU уже может указывать на ту же сессию. Сброс действует и при закрытой панели.
    Существующие входы `openAgentsPanel` и `openAgentInPanel` явно снимают пин перед открытием своей сессии.
  - Без явного выбора всё как сейчас.
- **Узкое окно.** Если правый сайдбар не помещается, `openPlanInPanel` закрывает левый через существующий
  `setSidebar('left', { open: false })`, затем открывает Agents и закрепляет участника. Фокус комнаты сохраняется.
  Минимальная ширина окна приложения — 800 px: без левого сайдбара места для центра и Agents достаточно.
  Размеры сайдбаров не переписываются; автоматического восстановления левого сайдбара не вводим.
- **Раздел «Plan» сверху**, над списком субагентов:
  - **Связь с комнатой.** Пункты активных планов комнат, где `owner` — эта сессия и статус `ready`, `in_progress`,
    `blocked` или `returned`. Формат строки: `pl-01 · item 6: {title}`. Клик открывает комнату, `scope` — в
    подсказке. Нет таких пунктов — строки нет.
  - `explanation` (Codex).
  - **Список пунктов:** значок статуса, `subject`, счётчик в заголовке раздела. Клик по пункту раскрывает
    `description` в Markdown (`RoomMarkdown`). Пункт `in_progress` раскрыт сразу. Пункт без описания не
    раскрывается. При `omitted > 0` — `+{omitted} more`; при `partial` заголовок `Plan` без `n/m` и предупреждение.
  - Плана нет — раздела нет.
- **Экран субагента** (`AgentDetail`): те же `applyPlanCall` и `capPlan` по `children` в порядке вызовов;
  передаются `child.status`, `child.response?.text`, `child.at`. ID восстанавливаются из JSON/текста результата,
  не из позиции в кольце. `failed`, `rejected` и `running` пропускаются.
  Если `toolCount > children.length` или усечён `input`/`response` планового вызова, неполнота известна до
  свёртки: `partial` накладывается на состояние после каждого шага, до обработки следующего вызова,
  и сохраняется в снимке. Иначе правило «все пункты закрыты» могло бы сбросить уже восстановленные пункты.
  В разделе — `Plan may be incomplete`, в том числе если пункты
  восстановить не удалось. Статусы чужих или неизвестных ID не переносятся на оставшиеся пункты.

## 8. Решения

| # | Решение | Почему |
|---|---|---|
| Р1 | Источник — проход индекса лога (`SessionIndex.plan`), не хуки и не лента Chat | Лента — кольцо с хвостом, теряет ранние пункты; индекс уже читает весь лог и есть у всех сессий |
| Р2 | В строке карточки `subject`, а не `activeForm` | Совпадает с текстом в списке, не меняется со статусом |
| Р3 | Счётчик — отдельный чип и живёт рядом с `doing` | Иначе ожидание или субагенты прячут план целиком |
| Р4 | Все пункты закрыты — строка возвращается к задаче сессии | Анти-цель «устаревший план выглядит живым» |
| Р5 | Потолки: 50 пунктов, описание до 4096 символов; сводка до обрезки, текущий/следующий пункт сохранён | Ограничить снимок, сохранив верный прогресс и текущую работу |
| Р6 | План виден и у спящих и закрытых сессий | Он из лога; «что осталось» полезно и после остановки |
| Р7 | Связь с комнатой — по `owner` пункта плана комнаты, без сопоставления пунктов | Сопоставлять тексты — гадание |
| Р8 | `owner`, `addBlocks`, `addBlockedBy` не показываем | Не просили; можно добавить потом |
| Р9 | `TodoWrite` поддерживаем дальше | В CLI есть переключатель на старые инструменты, у Codex свой |
| Р10 | Новый успешный `TaskCreate` после закрытия полного плана или повтор ID пункта новым уникальным вызовом начинают новый план | Повтор записи не должен сбрасывать план; меньший новый ID сам по себе не доказывает сброс |
| Р11 | Засева и ленивого чтения нет: план есть у всех сессий из индекса | Индекс строится при старте хоста для всех логов |
| Р12 | Задержка плана — до ~2 с (интервал переиндексации) | Для обзора хватает; хуки ради мгновенности не нужны |
| Р13 | Участник комнаты — одна сессия: карточка показывает план этой сессии, связь с комнатой — по её id | Участники комнаты и есть сессии; перезапуск сохраняет id |
| Р14 | Только успешные вызовы, свёртка в порядке вызовов, повторы по ID отсечены | Ошибка или задержанный ответ не создают ложный прогресс |
| Р15 | ID задачи из результата; неизвестный ID остаётся `null`, неполнота отмечается явно | Порядковый номер из обрезанного хвоста может изменить чужую задачу |
| Р16 | Пин снимается по фактической активации сессии и существующим входам в Agents | MRU комнаты может совпадать с выбранной сессией до перехода |
| Р17 | При нехватке места открытие плана закрывает левый сайдбар | Подробности доступны в 800×500 с сохранением фокуса комнаты |

## 9. Проверки (состояние на 2026-10-18)

1. ~~Тело хука `PostToolUse`~~ — снято: хуки не используются (раздел 5).
2. Субагенты: в логах субагентов за 30 дней вызовов `TaskCreate`/`TaskUpdate`/`TodoWrite` нет. Их записи лежат в
   отдельных файлах `subagents/*.jsonl` и в план сессии не попадают. Старый формат (`isSidechain` в логе сессии)
   отсекается. Экран субагента сворачивает свои `children`, используя настоящие ID из результатов;
   корректность на неполном хвосте проверяется фикстурой, наличие живых вызовов не предполагается.
3. Codex: `update_plan` — `function_call` с JSON в `arguments` (так в тесте `core/src/codex/codex.test.ts`). В
   настоящих журналах за 20 дней вызовов нет — успешную пару вызов/ответ проверить фикстурой, живой путь —
   если такие вызовы появятся. Отсутствие плана без вызовов проверяется отдельно.
4. Время прохода индекса на самом большом логе пользователя до и после правки: свёртка плана добавляет не больше
   10 %. Замер — шагом плана.

## 10. Оставлено строителю

- Имя и место модуля в core, имена функций и полей протокола.
- Внешний вид значков статуса — те же, что сейчас в `AgentDetail` (`CheckCircle2`, `LoaderCircle`, `Circle`).

- Тексты английских строк.

## 11. Приёмка

- **Core.** Обезличенные реальные записи (2.1.227/2.1.229) и синтетические граничные фикстуры: создание,
  обновление, `deleted`, неизвестный `taskId`, `TodoWrite`, `update_plan`, успешный ответ без ID, ошибка и
  отсутствие ответа. Повтор старого вызова не сбрасывает план; задержанный ответ не меняет порядок свёртки.
  План из 60 завершённых пунктов даёт `60/60`; текущий №51 остаётся видимым; `partial` не выдаётся за полный план.
- **Хост.**
  - Индекс лога (Claude и Codex) несёт `plan`; свёртка в проходе индекса, без новых чтений.
  - `activity.changed` несёт `plan` и уходит только при изменении.
  - Хост без поля — окно не падает.
- **Окно.**
  - Порядок текста во второй строке (`doing` → пункт → `task`).
  - Счётчик рядом с `doing`.
  - Поповер с описанием текущего пункта.
  - Клик открывает вкладку Agents на нужном участнике.
  - Комната с MRU B → открыть план A → активировать B: пин снят, видна B; то же после закрытия/открытия панели.
  - В 800×500 левый сайдбар закрывается, видны Agents и описание плана, комната остаётся активной.
  - Раздел «Plan» со связью с комнатой.
  - В хвосте субагента сохранился Create №2, Update №1 не изменяет его; доступный `response` даёт настоящий ID.
  - Без плановых вызовов у Codex план не появляется; фикстура с успешным `update_plan` показывает его.
- **Живая проверка:** комната с двумя агентами Claude и одним Codex, длинные названия пунктов и проекта, окно
  800×500. Замер прохода индекса — в пределах порога из 9.4.
