## 1. Зачем

Человек, 2026-10-21: срочный MVP, одновременно много сессий (бэк, фронт, модель, проработка решений, в соседних
окнах — улучшения Parley). За два дня подписка за 200 $ улетела целиком, и «пришлось переключать глобальный
Claude с одной подписки на другую, то есть перелогинившись». Хочется, «чтобы всё это замыкалось в рамках работы с
Parley»: внизу видны обе подписки, у каждой своё имя; когда одна кончилась, новые сессии идут на другую; «ведущий
или другие сессии поняли, что у кого-то в комнате кончился лимит, и нужно запустить нового агента с новой
подпиской» — а «при запуске новых сессий Parley прочитает карту и поймёт, кто что делал».

Сейчас второй аккаунт того же CLI в Parley завести нельзя: свои провайдеры (PR #86) требуют адрес и ключ, то
есть это «Claude Code на чужом адресе за токены», а не «ещё один аккаунт Claude». У Codex нет даже отдельной
папки на провайдера.

## 2. Цели, не-цели, анти-цели

**Цели**
- Из окна Parley добавить ещё один аккаунт Claude Code или Codex: имя, своя папка, вход из Parley в браузере.
- Такой аккаунт — полноценный провайдер: сессии, комнаты, Chat, MCP Parley, роли, навыки, помощник,
  `create_session` у агентов, лимиты в строке статуса.
- Лимиты каждого аккаунта видны человеку (строка статуса) и агентам (`get_map`).
- Когда участник комнаты упёрся в лимит: человек узнаёт сразу, ведущий получает письмо с перечнем свободных
  аккаунтов того же CLI, спрашивает человека и после ответа заводит замену через `create_session`. После сброса
  лимита Parley возвращает старую сессию (как в спеке застрявших).
- Глобальные Claude Code и Codex (в `~/.claude` и `~/.codex`) ничего не замечают; это проверяется тестами.

**Не-цели**
- Перенос истории сессии с одного аккаунта на другой. Замена — новая сессия, которая читает карту.
- Автоматическое распределение нагрузки или переключение сессий хостом по лимиту.
- Чужие аккаунты: Parley не принимает вставленные токены, не предлагает «поделиться входом» и не подсказывает,
  как это сделать. Только `claude auth login` / `codex login` в браузере. (Решение человека: «если человеку
  нужен будет логин на чужой аккаунт, они как-нибудь сами договорятся… мы в этом не участвуем».)
- Аккаунты Anthropic Console (`claude auth login --console`, оплата за токены) и второй ключ GLM — это свои
  провайдеры, не подписки.
- Проверка изоляции на Linux и Windows (как у своих провайдеров: проверено только на macOS).

**Анти-цели** (провал, даже если всё остальное работает)
- Вход в аккаунт в Parley разлогинил, перенастроил или сменил модель глобальному Claude или Codex.
- Parley прочитал или скопировал учётные данные: связку ключей, `auth.json`, токены. Состояние входа Parley
  узнаёт только у самого CLI (`claude auth status`, `codex login status`).
- Ведущий отдал часть застрявшего кому-то, не спросив человека.

## 3. Решения (приняты человеком в диалоге 2026-10-21)

1. **Только свои аккаунты.** Никакой помощи с чужими.
2. **Claude Code и Codex в одной работе.** Codex «так и надо» — несмотря на то, что его половина вдвое больше
   (раздел 9).
3. **Имя необязательное.** Без имени — стандартное: «Claude Code 2», «Codex 2» и дальше по порядку. Глобальный
   остаётся «Claude Code» / «Codex» без номера (моё решение К1, человек не возражал).
4. **Внизу видны все аккаунты**, у каждого свой сегмент с лимитами.
5. **Истории не переносить.** Кончился лимит — новая сессия на другом аккаунте, карта расскажет ей, кто что делал.
6. **Ведущий спрашивает обязательно.** При лимите участника и свободном аккаунте ведущий пишет `@human` с
   вариантами, среди них «завести замену на <аккаунт>», и заводит только после ответа.
7. **Одним куском** вместе с доводкой `feat/stuck-sessions`, а не двумя этапами.

## 5. Устройство

### 5.1 Запись
Файл тот же — `~/.parley/custom-providers.json` (`core/src/custom-providers.ts:41`). У записи появляется поле
`kind`: `'endpoint'` (нынешние свои провайдеры; отсутствие поля читается как `endpoint`, миграции нет) |
`'claude-account'` | `'codex-account'`. У аккаунта поля: `id`, `kind`, `label` (пустая строка = стандартное
имя), `link` (bool; у `endpoint` это по-прежнему `linkClaude`). Полей `baseUrl`, `auth`, `models`,
`contextWindow` у аккаунта нет; `asRecord` (`:110`) проверяет по `kind`.

**Id и папка.** Аккаунт Claude — `custom-<slug>` (как свои провайдеры: так бесплатно работают
`isClaudeCode(id)`, `claudeRootFor`, `customProviderProjectRoots`, индекс журналов). Аккаунт Codex —
`codex-<slug>`. Префикс `codex-` сейчас нигде не принимается: шаблон `CUSTOM_ID_PATTERN`
(`custom-providers.ts:52`) и его копия в протоколе (`customId`, `protocol/src/custom-providers.ts:34`) знают
только `custom-`, и на них стоят `isValidCustomProviderId`, `customProviderDir`, `removeCustomProviderDir`,
`claudeRootFor`, `customProviderProjectRoots`, скан занятых папок (`methods/custom-providers.ts:52`) и
`providers.deleteCustom`. Решение (К8): шаблон становится `^(custom|codex)-[a-z0-9]+(?:-[a-z0-9]+)*$` в
обоих местах; `customProviderProjectRoots` отдаёт **только** папки `custom-*` (корни Claude), новая
`codexAccountRoots` — только `codex-*`; `claudeRootFor` на `codex-*` не зовётся (`isClaudeCode` false), но
защищается исключением; `applyOverride` (`providers.ts:1072`) резервирует оба префикса.
Папка у обоих — `~/.parley/providers/<id>/`. Стандартный slug — `claude-2`, `codex-2`, … (slug — первый свободный
номер, занятые — дальше; имя по умолчанию следует за slug: `custom-claude-3` ↔ «Claude Code 3»).

**Протокол.** `CustomProviderInfo` (`protocol/src/custom-providers.ts:21`) получает `kind` и `signedIn:
boolean | null` (null — не проверялось); поля адреса/ключа/моделей — только у `endpoint`.
`providers.saveCustom` принимает либо нынешнюю форму (`kind: 'endpoint'`), либо `{id|null, kind: 'claude-account'
| 'codex-account', label, link}`. Новые методы: `providers.signIn(id)`, `providers.cancelSignIn(id)`,
`providers.signOut(id)`, `providers.authStatus(id)` (5.5). У `providers.list` в `needs` появляется третье
значение `'sign-in'`.

### 5.2 Семейство Codex и запись реестра
- `ProviderFamily` (`providers.ts:30`) становится `'claude' | 'codex'`; встроенный `codex` получает
  `family: 'codex'`. Новый помощник `isCodex(entry | id)` по образцу `isClaudeCode` (`:423`): для строки —
  `id === 'codex'` или префикс `codex-`; для записи — семейство. **Все** проверки `=== 'codex'` из карты кода
  (ядро: `work/launch.ts`, `work/agents.ts`, `work/metrics.ts`, `work/summary.ts`, `work/room-usage.ts`,
  `work/native-context.ts`, `mcp/tools.ts`; хост: `activity/*`, `feed/feed-service.ts`, `hooks/hook-server.ts`,
  `pty/*`, `sessions/sessions-service.ts`, `wake/wake-service.ts`, `compaction/*`, `context/*`,
  `capabilities/*`, `limits/limits-service.ts`; окно: `ChatView`, `feed-view`, `ProviderCard`, `island/requests`,
  `attention/notify`, `RoomContextChip`, `CompactForm`) переводятся на `isCodex`. Это сквозная правка, и она
  входит в объём; где проверка означает именно «глобальный Codex» (каталог моделей, карточка установки), она
  остаётся по id — таких мест мало, исполнитель помечает каждое комментарием.
- `isClaudeCode('codex-…')` — false (строковая ветка проверяет префикс `custom-`, не трогаем).
- **Аккаунт Claude** → `ProviderEntry` семейства `claude`, раннер — копия записи реестра `claude` **после**
  `providers.json` (К11; не константы `PROVIDERS.claude` и не GLM): те же

- **Аккаунт Codex** → запись семейства `codex`, раннер — копия реестровой записи `codex` **после** применения

- Строитель записей аккаунтов — отдельная `accountProviderEntry(record, registry)`, а не `customProviderEntry`

- `loadProviders` (`:1135`) добавляет аккаунты так же, как свои провайдеры — после `providers.json`, только на

### 5.3 Окружение запуска (`host/src/sessions/provider-env.ts`)
`providerLaunchEnv` (`:23`) сейчас выходит сразу, если нет `secret` (`:26`). Новое правило: **ветка изоляции
включается, если есть `secret` или `configDir`**. Для аккаунта:
- срезать те же селекторы, что у ключевых провайдеров (`GLM_SELECTORS`, `:4-17`): `CLAUDE_CODE_OAUTH_TOKEN*`,
  `*_FILE_DESCRIPTOR`, `CLAUDE_CONFIG_DIR`, `CLAUDE_SECURESTORAGE_CONFIG_DIR`, селекторы моделей, `CLAUDE_CODE_REMOTE*`,
  а также `ANTHROPIC_*` и `CLAUDE_CODE_USE_*` (унаследованный ключ не должен перебить вход по подписке);
- семейство `claude`: `CLAUDE_CONFIG_DIR=<папка>`; семейство `codex`: `CODEX_HOME=<папка>`; у Codex срезать
  унаследованные `CODEX_HOME` и `OPENAI_API_KEY` (ключ из окружения перебил бы вход; список доуточняет задача 0);
- `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` у аккаунтов **не ставить** (К12). В бинаре 2.1.306 флаг включает режим
  «провайдер под управлением хоста»: настройки входа из `settings.json` не применяются, часть предикатов способа
  входа возвращает `false`, проверка принудительного способа входа коротится. Свои провайдеры живут под ним
  только с ключом; с OAuth-подпиской он не проверялся. Маркер изоляции в тестах — сам `CLAUDE_CONFIG_DIR`;
- **ключ не ставится** — ни `ANTHROPIC_*`, ни плейсхолдер.
Признак «сессия со своим токеном хуков» сейчас считается тремя разными предикатами: `entry.custom`
(`work/launch.ts:385-388`, там же имя `settings-<id>.json`), `provider === 'glm'` (`work/settings-file.ts:194`),
`secret` (`sessions-service.ts:669`). У аккаунта есть `custom` и `configDir`, но нет `secret`, и хуки бы
отвалились. Все три выравниваются на `entry.custom !== undefined` (К13); GLM получает `custom`-подобный признак
или остаётся явным исключением — исполнитель выбирает по коду и фиксирует тестом, что у GLM ничего не меняется.

**Codex: папка из записи, а не из `process.env`.** Все места, где `codexHome` берётся из `process.env.CODEX_HOME`
(`work/launch.ts:273/313/358`, `work/agents.ts:119`, `capabilities/snapshot.ts`, `native-targets.ts`,
`share-skill.ts`, `role-catalog-cache.ts`), получают его из записи провайдера: `codexHomeFor(entry, env)` по
образцу `claudeConfigDirFor` (`providers.ts:436`) = `runner.configDir ?? env.CODEX_HOME`. Дескриптор
нативного контекста (`work/native-context.ts:20`, `roots.codexHome`) — оттуда же.

### 5.5 Вход и состояние входа
- **Проверка:** `providers.authStatus(id)` запускает в папке аккаунта (с окружением 5.3)
  `claude auth status --json` (поле `loggedIn`; проверено 2026-10-21 на 2.1.306: в пустой папке —
  `{"loggedIn": false, "authMethod": "none", …}`) или `codex login status` (текст `Not logged in` и код
  возврата; формат «вошёл» — задача 0). Результат живёт в памяти хоста и кладётся в `signedIn` записи
  `providers.list` (вместе с `signingIn` — идёт ли сейчас вход, чтобы окно после повторного открытия Settings показало
  терминал входа) и в `providerReadiness` (новая опция `signedIn`): аккаунт без входа — `needs: 'sign-in'`,
  `available: false`. Текст отказа запуска: «<name> is not signed in: open Settings → Providers and press Sign
  in». Ранняя проверка готовности в `createTimed` (`sessions-service.ts:869-871`) расширяется с «есть `secret`»
  на «есть `secret` или `configDir`», иначе отказ по входу придёт уже после записи сессии в карту. Процесс MCP
  (ядро) это состояние получает от хоста вместе с лимитами (5.8, К7), а не вычисляет сам.
- **Когда проверять** (К5): при старте хоста, после Save, после выхода процесса входа, после Sign out, по
  ручному обновлению лимитов, и когда у сессии этого аккаунта наступил эпизод `sign-in` (спека застрявших 3.2).
  Не чаще раза в 30 с на аккаунт; результат кэшируется в памяти хоста. Проверка не трогает ни связку ключей,
  ни `auth.json`: это команда самого CLI.
- **Вход:** `providers.signIn(id)` поднимает PTY с командой `claude auth login` (`--claudeai` по умолчанию)
  или `codex login` в окружении 5.3. Это **отдельный маленький путь PTY** (К14), не `pty-manager` сессий: тот
  работает по `SessionRef {projectPath, workId, sessionId}` (`pty-manager.ts:43`, `methods.ts:185-316`,
  `events.ts:22-24`), и слушатели активности, ленты и будильника ищут по нему сессию. У входа свои методы
  `providers.signIn(id)`, `providers.signInInput(id, data)` (вставить код из браузера), `providers.signInResize
  (id, cols, rows)`, `providers.cancelSignIn(id)` и события `providers.signInOutput {id, data}`,
  `providers.signInExit {id, code}`; окно рисует их тем же xterm (панель 4.1). Выход процесса → `authStatus` →
  `providers.changed`. Параллельно один вход на весь хост (у `codex login` локальный порт обратного вызова;
  второй параллельный вход упадёт) — **свой замок** «идёт вход», не очередь `serialized` из
  `methods/custom-providers.ts:29`: та держит и подготовку папки при каждом запуске своих провайдеров, и десять
  минут входа остановили бы все запуски. `cancelSignIn` убивает процесс. Таймаут 10 минут — то же, что
  Cancel. `codex login --device-auth` не предлагается (К15): обычный вход открывает браузер сам; если проба
  задачи 0 покажет, что обратный вызов из PTY не срабатывает, план переключит Codex на `--device-auth` — это
  всё ещё вход в браузере в свой аккаунт.
- **Выход:** `claude auth logout` / `codex logout` в том же окружении; затем `authStatus`.
- **Изоляция входа.** Claude: имя записи связки ключей получает хвост `-<sha256(папки)[:8]>` при
  `CLAUDE_CONFIG_DIR` и без `CLAUDE_SECURESTORAGE_CONFIG_DIR` (спека своих провайдеров 6.1, проверено по коду
  2.1.302). Codex: `auth.json` лежит в `CODEX_HOME` (задача 0 проверяет вживую, что `~/.codex/auth.json` не
  меняется). Повторная проба при подъёме `minVersion` — правило К9 той спеки.

### 5.8 Карта для агентов, письмо ведущему, гид
- **`get_map` → `providers[]`** (`mcp/tools.ts:589`) дополняется полями `family` и `limits` (только когда
  известны): `ProviderLimits` ядра — `{ fiveHour: { usedPercent, resetsAt } | null, week: { … } | null, at }`. Источник (К7) — **хост**:
  сервер MCP живёт в своём процессе, не видит ни кэша входа (5.5), ни других работ (служба лимитов,
  `limits-service.ts:191-200`, обходит все работы, а ядро перечислять работы не умеет), поэтому ядро
  спрашивает хост по тому же каналу, что `create_session` (`host/src/agent/session-endpoint.ts`, токен
  `PARLEY_*`): новая точка `POST /agent/providers` отдаёт те же строки, что `providers.list` (`id`, `label`,
  `family`, `available`, `needs`, `models`, `effort`, `limits`). Хост недоступен — прежние строки без `limits`
  и с `available` по локальной готовности, плюс `note: "host unreachable: sign-in state and limits unknown"`.
  GLM — без лимитов, как сейчас в окне без `zai`. Запрос — POST с пустым телом (сервер хуков принимает на путях агента
  только POST), ответ `{ ok: true, result: { providers } }`; без `keyHint`, `check` и `custom`.
- **`create_session`** принимает id аккаунта как любой провайдер; описание инструмента говорит: «An account of
  the same CLI (for example `custom-claude-2`) is a separate subscription with its own limits — see
  `providers[].limits` in `get_map`».
- **Письмо ведущему про `limit`** (спека застрявших 5.2) получает абзац, когда есть хотя бы один другой
  вошедший провайдер того же семейства:
  `Other Claude Code accounts in Parley right now: Claude Code (weekly 31 % used, resets Mon 10:00 local time);
  Claude Code 2 — out of limit until 19:27. A replacement can be started on a free one with create_session
  (provider: "claude").` Варианты для `@human` дополняются: «start a replacement on <name> and hand it @s03's
  part». Без свободных аккаунтов письмо прежнее.
- **Гид, тема `stuck`** (спека застрявших 5.4): при `limit` ведущий пишет одно сообщение `@human` с вариантами,
  включая замену на названном аккаунте, **и ждёт ответа**; после «да» — `create_session` на этом провайдере, в
  комнату, задача и указатель на карту новой сессии, письмо застрявшему о передаче. Самостоятельно замену не
  заводит (решение 6). Строка в роли ведущего (`LEAD_ROLE`) — та же ссылка на тему.
- Строка ленты, уведомление человеку и `SessionNeed.account` называют аккаунт именем провайдера
  (`providerName`), а не «Claude Code» вообще.

- `claude auth status --json` после входа: `loggedIn: true`, `authMethod: "claude.ai"`, `apiProvider: "firstParty"`,
  `email`, `orgId`, `orgName`, `subscriptionType` (`"max"`), `projectsDirectory`, `configDirectory`. Для карточки
  аккаунта: «Signed in as <email> · <subscriptionType>».
- Глобальный `claude auth status --json` до и после входа/выхода в папке — байт в байт тот же; в двух папках —
  разные аккаунты.
- Запись связки ключей аккаунта: `Claude Code-credentials-26ecb921`, где `26ecb921` = первые 8 hex `sha256` пути
  папки **без** завершающей косой черты (совпадает со спекой своих провайдеров 6.1). После `claude auth logout` в
  папке запись исчезла, глобальная `Claude Code-credentials` осталась.
- Сессия в папке **без** `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST` (`claude -p … --model haiku`) отвечает на
  подписке аккаунта (К12 подтверждено). Проба `/login`/`/logout` внутри интерактивной сессии не делалась —
  эквивалентно проверены `auth login`/`auth logout` в той же папке; обновление токена дольше часа не проверялось.
- Унаследованные переменные: `CLAUDE_CODE_OAUTH_TOKEN=x` **перебивает** вход (`authMethod: "oauth_token"`) —
  срезать обязательно. `ANTHROPIC_API_KEY=x` и `ANTHROPIC_AUTH_TOKEN=x` при входе по claude.ai в `-p` ответ не
  перебили (ключ из окружения без одобрения не применяется) — всё равно срезаются по 5.3, это защита, а не
  исправление.
- Версии: `claude auth login/status/logout` есть в 2.1.304 (самая старая установленная; 2.1.302–303 на машине
  нет). `ACCOUNT_MIN_VERSION_CLAUDE = '2.1.304'` — самая старая проверенная; изоляция папки проверена по коду
  2.1.302 раньше (спека своих провайдеров 6.1).

**Тесты** (без «веры»):
- изоляция Claude: сессия аккаунта получает `CLAUDE_CONFIG_DIR=<папка>`, без `CLAUDE_SECURESTORAGE_CONFIG_DIR`,
  без `ANTHROPIC_*` и `CLAUDE_CODE_OAUTH_TOKEN*`; соседняя сессия глобального Claude ничего из этого не получает;
  `~/.claude` не меняется (расширение `host/src/methods/custom-providers.isolation.test.ts`);
- изоляция Codex: `CODEX_HOME=<папка>`, `~/.codex` не меняется; роли, навыки, MCP-флаги и rollout — из папки;
  лимиты относятся к id аккаунта;
- готовность: без входа — `needs: 'sign-in'`, запуск отказан с текстом 5.5; после входа — доступен;
- `get_map`: строки `providers` приходят от хоста (`POST /agent/providers`) и совпадают с `providers.list`;
  при недоступном хосте — прежние строки с пометкой;
- письмо ведущему с абзацем о свободных аккаунтах и без него; гид и роль ведущего — английские тексты под
  `english-text.test.ts`;
- E2E (`desktop/e2e/`, заглушки как `stub-custom-agent.mjs`, плюс заглушка `auth status`/`login status`):
  добавить аккаунт Claude → сегмент и пилюля; Sign in → заглушка «входит» → доступен; новая сессия на нём с
  маркерами окружения; шкала лимитов; комната с участником на лимите → письмо ведущему называет свободный
  аккаунт; то же для аккаунта Codex; 800×500 без горизонтальной прокрутки, светлая и тёмная темы;
- `core/test/frame-scan.ts`: новые строки под правила — явные исключения с причиной «спека подписок N.M».

### 9.2 Отличия от плана, этап 2
Решения с номерами — решения контролёра по ходу исполнения плана 2 (`docs/specs/2026-10-21-subscriptions-plan-2-claude-accounts.md`;
журнал исполнения лежит в `.superpowers/` и в репозиторий не попадает); в 5.1 и 5.2 выше остались прежние формулировки.
- **Запись реестра.** `ProviderEntry.account` — отдельное постоянное поле рядом с `custom` (союз на `custom` сломал бы
  `host/src/methods/providers.ts` и `custom-check.ts`); все проверки вида «провайдером владеет окно и у него своя
  папка» идут через `managedRecord(entry)` и `isManagedEntry(entry)` (решение 5).
- **Минимальная версия.** `ACCOUNT_MIN_VERSION_CLAUDE = '2.1.304'`, вместо ориентира «не ниже 2.1.302» из 5.2: `claude auth
  login/status/logout` проверены на 2.1.304, самой старой установленной (решение 3, итоги задачи 0 в 9.1).
- **Стандартное имя.** Хост записывает вычисленное стандартное имя («Claude Code 2», …) в `label` при сохранении, если
  человек оставил поле пустым, — имена не меняются после удаления соседнего аккаунта (решение 6). Номер имени — номер
  выданного slug (`custom-claude-N` ↔ «Claude Code N», итоговая волна, решение 7), а не «число аккаунтов + 2»: иначе
  после удалений получались одинаковые стандартные имена. Пустое имя при правке возвращает имя по id; поле нового
  аккаунта в окне подсказывает первый свободный номер среди известных окну id `custom-claude-N` (оставшуюся папку или
  забытый ключ видит только хост и сдвигает номер сам).
- **Удаление аккаунта.** Перед удалением записи хост выполняет `claude auth logout` в окружении аккаунта (решение 12): вход
  лежит в связке ключей под именем папки, и новый аккаунт на освободившемся id унаследовал бы его. Сбой выхода
  журналируется и удалению не мешает. Удаление с «Also delete its folder» при живой сессии провайдера отказано
  (`conflict`, раздел 10); без галочки запись уходит, как прежде.
- **Неизвестное состояние входа.** Пока кэш входа пуст (старт хоста, первая проверка идёт), запуск сессии и помощник
  ждут её исход, а не отказывают как невошедшему; проверка, которая не смогла выполниться при пустом кэше, пишет
  «не вошёл», а не оставляет «не знаем» навсегда. Эпизод `sign-in` просит проверку мимо 30-секундного кэша.
- **Старое окно после понижения.** Окно, собранное до этого этапа, после понижения версии падает на пилюле аккаунта
  (аккаунты уже сохранены, а окно их вида не знает); падение держит `ErrorBoundary`. Зафиксировано, не исправляется.
- **Канал агента.** Строки провайдеров для `get_map` отдаёт `POST /agent/providers` (решение 9): сервер хуков
  разбирает маршруты только по `POST`, как у `create_session`; 5.8, К7 и раздел 9 уже говорят `POST`.
- **Альтернативы при лимите.** В письмо ведущему попадают только провайдеры того же семейства без ключа
  (`runner.secret`): глобальный Claude Code и аккаунты подписки (решения 8 и 10). GLM и свои провайдеры с адресом —
  чужие модели, а не «другие аккаунты Claude Code».
- **Проверка входа (К5).** Не чаще одного раза в 30 с на аккаунт, но после входа и выхода — принудительно (кэш в этот
  момент заведомо устарел); идущую проверку обычный вызов делит.
- **Окно, 800×500.** E2E нашёл в карточке аккаунта строку состояния с e-mail без точек переноса: адрес из букв и точек
  растягивал панель Providers до горизонтальной прокрутки; исправлено классами `min-w-0 break-all` (коммит
  `f966c06b`).
- **Не вошло в E2E.** Сценарий «комната с участником на лимите → письмо ведущему называет свободный аккаунт» (раздел 9,
  «Тесты») для Claude не сделан: текст письма покрыт `host/src/stuck/stuck-service.test.ts`; сценарий комнаты — вместе
  с аккаунтами Codex на этапе 3.

## 10. Граничные случаи
- CLI ниже `minVersion` — сегмент приглушён, карточка: «<name> requires Claude Code 2.1.3xx or newer».
- Вход запущен, человек закрыл Settings — процесс живёт, панель при возврате показывает его; Cancel и таймаут
  — 5.5.
- Удалён аккаунт с живыми сессиями — как у своих провайдеров (`deleteCustom` в `serialized`, сессии дорабатывают
  ход, повторный запуск отказан). Папку с живыми сессиями не удалять: отказ с текстом.
- У человека `CLAUDE_CONFIG_DIR` задан глобально — глобальная запись `claude` живёт там (`userClaudeConfigDir`),
  аккаунты — в своих папках; ссылки «Bring from» берут оригиналы из `userClaudeConfigDir()`.
- Глобальный Claude разлогинен — аккаунты работают; и наоборот.
- Эпизод `sign-in` у сессии аккаунта (слетел вход) — проверка входа, `needs: 'sign-in'`, уведомление человеку
  с кнопкой Sign in (спека застрявших 6.5: автопродолжения нет).
- Два аккаунта с одинаковым именем — допускается (id разные), в списке рядом с именем подсказка папки.
