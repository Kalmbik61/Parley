## 1. Цель и когда рой не нужен

**Рой** — группа сессий под одной сессией-королевой для **больших исследовательских задач, которые не помещаются в один контекст**: аудит всего репозитория, большой корпус документов, поиск в интернете. Королева режет задачу, добавляет трутней (читают срезы) и проверяющих (перепроверяют утверждения), сводит результат и сдаёт его тому, кто рой запустил. Только чтение: код рой не пишет.

**На узкой задаче рой не рекомендуется — берите одного агента.** Пилот 1 (`docs/audits/2026-10-28/swarm-pilot-result.md` в основном репозитории) задал рою вопрос об одном модуле на ~15 файлов: рой проиграл по покрытию (7/8 против 8/8) и времени (9,5 против 6,0 мин при перезапуске читателей, 20,7 мин от старта), расход не выиграл ($3.19 против $2.91); все четыре читателя Haiku сдали `partial`, пробелы закрывала королева на Opus. Нарезка и волна проверки добавили последовательные шаги, но ничего не ускорили. Это обязано стоять в описаниях `create_swarm` / `swarm_add` и в брифе королевы: «если задача помещается в один контекст — не запускай рой». Скилл `research-swarm` (когда рой нужен, нарезка, формат сдачи, проверка, сводка) — следующий этап поверх этих инструментов; здесь только указатель на него.

Порядок работ: **сначала видимая часть** (карта, сайдбар, шапка чата, карточка работы, остров — раздел 7), затем инструменты и лимиты. Пока инструментов нет, рой можно завести тестовой записью в карте и увидеть в окне.

## 2. Сущность и карта

Сущность называется `WorkSwarm` (правило имён — 2.3). Лежит в `WorkMap.swarms?: WorkSwarm[]` рядом с `rooms` и `plans` (`packages/core/src/work/types.ts:634`).

```ts
type SwarmStatus = 'running' | 'collecting' | 'done' | 'failed' | 'cancelled';
type SwarmRole = 'queen' | 'drone' | 'verifier';
type SwarmCreator =
  | { kind: 'session'; sessionId: string }
  | { kind: 'room'; roomId: string }
  | { kind: 'human' };

interface WorkSwarmMember {
  sessionId: string;
  role: SwarmRole;
  n: number;                 // номер среди своей роли: «Трутень 2»; у королевы 1
  addedAt: string;
  handedAt: string | null;   // сдал (done-report принят хостом); трутни и проверяющие
}

interface WorkSwarm {
  id: string;                // 'sw-01'; счётчик Work.swarmSeq, id не переиспользуется (как roomSeq, types.ts:613)
  tag: string;               // 'Research' | 'Аудит' | 'Отладка' | свой текст, 1–24 знака, без переводов строки; задаёт создатель
  creator: SwarmCreator;
  objective: string;         // ≤ 4096
  queen: string;             // sessionId королевы; она же первый элемент members
  members: WorkSwarmMember[];
  status: SwarmStatus;
  createdAt: string;
  endedAt: string | null;    // таймер в окне считает createdAt → endedAt ?? now
  expiredAt: string | null;  // истёк срок жизни swarmMinutes (3.0); итог ждёт сдачи королевы
  result: { summary: string; at: string; deliveredAt: string | null } | null;  // summary ≤ 4096
  failure: string | null;    // причина failed / cancelled
  seenAt: string | null;     // человек увидел итог (карточка в окне)
}
```

Дополнительно: `Work.swarmSeq?: number` и счётчики лимитов `WorkResources.swarmSpawned?`, `swarmsCreated?` (раздел 5). Показ состояния участника — чистая функция `memberState(swarm, member, session)` в core: `handed` (есть `handedAt`), `closed` (рой в `failed`/`cancelled`, участник не сдал — его закрыл хост, 3), `failed` (`session.result === 'failed'`, сессия закрыта без сдачи или её нет в карте), `waiting` (`lifecycle === 'pending'`: добавлен, процесс не стартовал, например Codex ждёт согласия на папку, sessions-service.ts:1141–1147), иначе `working`.

### 2.1 Чтение старых карт

`normalizeMap` (`packages/core/src/work/map.ts:548`) ставит `map.swarms ??= []` рядом с `map.plans ??= []` (:576) и вызывает `migrateSwarm` после `migrateRoom`; `schemaVersion` остаётся 2 (поле необязательное, как `resources`, types.ts:646). `migrateSwarm` следует подходу `memberLog` (map.ts:687): запись неверной формы (нет `id`, статус вне списка, нет королевы среди `members`) **убирается**, карта остаётся читаемой; неизвестную роль участника — отбросить; создатель, которого нет в карте, становится `{ kind: 'human' }`. Валидацию счётчиков добавить в `validateResources` (resource-policy.ts:509): необязательные неотрицательные целые. Тест: карта без `swarms` читается, а пустой массив `swarms` в файл не пишется (запись добавляет ключ, только когда есть хотя бы один рой).

### 2.2 Удаление

`removeSession` (map.ts:173) — чистая функция карты, процессов не трогает: (а) создатель-сессия удалена → `creator = { kind: 'human' }` (как `createdBy = null`, :181, и `ownerId = null`, :186); (б) участник удалён → запись остаётся (счётчик `3/5` не прыгает), состояние: `handed`, если был `handedAt`, иначе `failed`; (в) королева удалена и рой не терминален → `status = 'cancelled'`, `failure = 'queen deleted'`. `deleteRoom` (rooms.ts:399) переводит `creator: room` в `human`. Живые участники терминального роя закрывает хост (3.3), поэтому отдельный код в `del` (sessions-service.ts:1273) не нужен. Номер `sw-NN` не освобождается.

### 2.3 Правило имён (столкновение с островом)

`packages/desktop/src/renderer/island/swarm/` (`Swarm.tsx`, `engine.ts`: `createSwarm`, `SwarmEngine`, `SwarmOptions`; `spec.ts`: `SwarmSpec`) — анимация «роя душ» в капсуле и острове; она остаётся как есть, и голые `Swarm` / `createSwarm` / `SwarmSpec` принадлежат ей. Рабочая сущность везде называется с префиксом: типы `WorkSwarm`, `WorkSwarmMember`, `SwarmStatus`, `SwarmRole`, `SwarmCreator` (в `@parley/core`, файл `packages/core/src/work/swarms.ts`); поле карты `swarms`; id `sw-NN`; хост — `packages/host/src/swarms/swarms-service.ts`, метод `createWorkSwarm`; MCP — `packages/core/src/mcp/swarm-tools.ts` (в нём только константы инструментов и вызов канала); окно — `sidebar/SwarmRow.tsx`, `CardSwarmRow`, `lib/swarm-view.ts`, строки `S.workSwarm.*`, ряд острова `kind: 'work-swarm'`. Агентский инструмент `create_swarm` — имя для модели, не имя TypeScript-символа. Импорт `Swarm` из `island/swarm/` рядом с `WorkSwarm` в одном файле допустим, потому что имена разные.

## 3. Жизненный цикл

| Переход | Кто и по какому событию |
|---|---|
| создание → `running` | `create_swarm` (агент) или `swarms.create` (человек): под замком карты создаётся `WorkSwarm` и сессия королевы |
| `running` → `collecting` | хост: у роя есть хотя бы один трутень/проверяющий и все они терминальны (`handed` или `failed`/закрыты). Письмо королеве от `parley`: «все сдали, пиши сводку» |
| `collecting` → `running` | `swarm_add` королевы (вторая волна, например проверяющие после читателей) |
| `running`/`collecting` → `done` | королева сдала `report` со статусом `done` (3.2): `result.summary = session.summary` |
| → `failed` | королева сдала `report` со статусом `failed`, либо её сессия закрыта без сдачи (не человеком), либо запуск королевы отказан бюджетом, либо истёк срок жизни `swarmMinutes` (3.0) |
| → `cancelled` | человек (`swarms.cancel`: пункт меню строки роя), закрытие королевы человеком, удаление королевы (2.2) |

В терминальном состоянии `endedAt` ставится один раз, таймер встаёт, а хост закрывает всех ещё живых трутней и проверяющих (причина «рой завершён»). Королеву хост не закрывает: она остаётся обычной сессией, с ней можно продолжить разговор.

### 3.0 Срок жизни роя

Решение человека (вопрос 3): у роя есть срок жизни `swarmMinutes` (раздел 5, по умолчанию 90 минут, 0 — без срока). Срок считается от `createdAt`. Хост сверяет сроки на каждом снимке карты и по своему таймеру (раз в 30 с), потому что у зависшего роя снимков может не быть. Когда нетерминальный рой просрочен:
1. одна запись карты: `status = 'failed'`, `failure = 'time limit: 90 min'`, `endedAt = expiredAt = now`;
2. хост закрывает живых трутней и проверяющих, как в любом терминальном состоянии;
3. королеве письмо от `parley`: «Время роя sw-NN вышло (90 мин). Участники закрыты. Сдай что есть: report со сводкой собранного и пометкой, что покрыто не всё».

Итог создателю у просроченного роя уходит **с частичной сводкой**: доставка (3.3) ждёт `report` королевы (`done` или `failed`), и `result.summary` берётся из него, а статус роя остаётся `failed`. Если королева не сдала за 10 минут после `expiredAt` (`SWARM_EXPIRY_GRACE_MS`), итог уходит без сводки: «время вышло, королева не сдала».

### 3.1 Кто выполняет

Один сервис хоста `swarms-service.ts` подписан на `works.onChange` и сверяет рои на каждом снимке — по образцу `stopRetired` (sessions-service.ts:1303, подписка :1325), поэтому переходы переживают перезапуск хоста и не зависят от того, дошёл ли ответ модели. Все записи идут через `updateMap` (core) и идемпотентны: повторная сверка ничего не меняет.

### 3.2 Сдача трутня и автозакрытие

Сдача трутня или проверяющего — его вызов `report` со статусом `done`. Инструмент ставит `session.result = 'done'`, `resultAt`, `summary`, но сессию не закрывает (описание `report`: tools.ts:409–412, запись: :751–778). Триггер хоста: участник роя, у которого `session.result === 'done'` и `handedAt === null`. Тогда: (1) в одной записи карты `handedAt = session.resultAt`; (2) `sessions.close(ref)` (sessions-service.ts:1254: остановка процесса, затем `closed`) без согласия человека — как закрывает свои сессии движок (host.ts:398). Порядок «сначала запись, потом закрытие» нужен, чтобы после падения хоста сверка дозакрыла участника, у которого `handedAt` уже есть, а сессия ещё жива. `progress` не сдаёт; `failed` — состояние `failed` без `handedAt`, сессия тоже закрывается. Повторный `report` закрытой сессии хост-инструмент уже отвергает (tools.ts:766), поэтому трутень не может переписать сданное; королева читает результат так же, как у любых сессий: `wait_for` по id возвращает итог закрытой сессии сразу (tools.ts:113–118), полный текст — `get_map {session, field: "summary"}`.

### 3.3 Результат создателю

По переходу в `done`/`failed`/`cancelled` хост шлёт итог: текст «Рой sw-NN [тег] готов, 3/5, 4:12» + `result.summary` (обрезка как у `shrinkSummary`, tools.ts:745) + путь к полному отчёту королевы.
- Создатель `session`: письмо `letters.add({ from: PARLEY, to: [sessionId], roomId: null, kind: 'note' })` — как письма хоста сессиям (rooms.ts:431, 499; запись вне разбора карты — `writeLetters`, letter-store.ts:345); письмо будит спящую сессию обычным будильником.
- Создатель `room`: письмо в комнату живому ведущему — `liveLead(map, room)` (rooms.ts:123) тем же способом, что `parleyNote` (rooms.ts:319), с `roomId`. Нет живого ведущего или комната в архиве/удалена → путь человека.
- Создатель `human` (или путь человека): `host.broadcast('host.notice', { kind: 'swarm-done' | 'swarm-failed', ref: королева, text, at })` (образец sessions-service.ts:397; виды уведомлений — protocol/types.ts, `NoticeKind`; текст/звук — attention/notify.ts:115) и **карточка в окне**: строка роя остаётся видимой, пока `seenAt === null`; раскрытие показывает `result.summary`, `swarms.seen` ставит `seenAt`.
Доставка «как минимум один раз»: `result.deliveredAt` пишется после письма; при перезапуске хоста недоставленный итог отправляется снова (в тексте есть `sw-NN`, дубль безвреден).

## 4. Инструменты агента

Оба — по образцу `create_session`: определение инструмента в `core/mcp` (session-tools.ts:4), вызов `POST` на канал хоста с токеном сессии (session-tools.ts:33–63; хост выводит работу и вызывающего из токена, модель не может выбрать чужую область), новый маршрут `/agent/swarms` рядом с `AGENT_SESSIONS_PATH` (session-endpoint.ts:7, подключение host.ts:445), проверка ключей аргументов как session-endpoint.ts:39–46, ошибки в виде `code: message` (session-tools.ts:59). Список инструментов — рядом с `CREATE_SESSION_TOOL` (tools.ts:1795), вызов — рядом с ним же (:1805). Создание сессий идёт через `sessionsService.create` / `createTimed` (sessions-service.ts:1049) с новым внутренним полем `swarm: { swarmId, role }`, которое агентский эндпоинт не принимает — ровно как `deferLaunch` и `workspace` разрешены только движку (:1055–1056).

**`create_swarm({ tag, objective, provider, model?, effort?, role? })` → `{ swarmId, queenSessionId }`.** `tag` — один из `Research`, `Аудит`, `Отладка` или свой текст ≤ 24 знаков. Хост в одной записи карты: проверяет лимиты (раздел 5), создаёт `WorkSwarm` и сессию королевы (`label` = «Королева sw-NN», бриф = шаблон хоста + `objective`: что такое рой, когда он не нужен, как добавлять трутней, как сдавать итог `report done`), `createdBy` не ставится. Создатель определяется хостом, не аргументом: вызывающий — живой ведущий комнаты (`liveLead`) → `{ kind: 'room', roomId }`; иначе `{ kind: 'session', sessionId }`; `swarms.create` от человека → `{ kind: 'human' }` (вопрос 1). Роль королевы по умолчанию — выбор вызывающего (`role` как у `create_session`, список `list_roles`).

**`swarm_add({ role: 'drone' | 'verifier', task, provider, label?, model?, effort?, agentRole? })` → `{ sessionId, member: 'Трутень 3' }`.** Рой определяется по токену вызывающего, аргумента `swarmId` нет: добавить в чужой рой нельзя. `agentRole` — id роли; по умолчанию `builtin:researcher` для трутня (`readOnly: true`, roles/builtin.ts:155–162; для Codex это `read-only` песочница, roles/catalog.ts:141–152) и `builtin:verifier` для проверяющего (его роль `readOnly: false`, builtin.ts:123–130: запрет записи держит только бриф). `task` — бриф среза; хост дописывает правила трутня (читать, не писать, не создавать сессий, сдать `report done` с фактами и источниками `path:line`/url, при неполном покрытии сказать об этом).

Отказы (в виде `code: message`, `data.reason` в `HOST_ERROR_REASONS`, protocol/types.ts:285):

| Код | Когда |
|---|---|
| `not-queen` | `swarm_add` вызвала не королева какого-либо роя |
| `swarm-closed` | рой в терминальном состоянии |
| `swarm-member` | рой-сессия вызвала `create_session` / `create_swarm` или попыталась войти в комнату (`add_to_room` проверяет закрытость участника: tools.ts:1136) |
| `swarms`, `swarm-sessions`, `swarm-concurrent`, `swarm-total` | новые лимиты (раздел 5), в виде `ResourceDeniedError` |
| `resource-budget` | общие лимиты запуска (`workConcurrent`, `workLaunches`), как `refuseLaunch` (sessions-service.ts:388–418) |

Проверка принадлежности — **на хосте**, по карте: вызывающий ищется в `swarms[].members`; для `create_session` — новая ветка рядом с проверкой «вызывающая сессия ещё жива» (sessions-service.ts:1130–1131), для `create_swarm` — то же. Текст роли это не заменяет.

`swarm_status` и `swarm_cancel` в v1 нет: королева смотрит `wait_for` и `get_map`, отменяет только человек (вопрос 5).

## 5. Лимиты

Сегодня `create_session` агента упирается в `resources.spawned` / `spawnedByRoom` против `workNewSessions` (50) и `roomNewSessions` (12) (sessions-service.ts:1137–1149; умолчания resource-policy.ts:51–61), и счётчик не уменьшается (types.ts:585–594). Рой не должен ни тратить его, ни упираться в него. Поэтому у сессий роя **своя ветка** в той же мутации `createPendingSession` (sessions-service.ts:1128–1150), с отдельными счётчиками и порогами.

**Новые пороги** (`ResourceLimits`, resource-policy.ts:26–49; попадают в `RESOURCE_LIMIT_KEYS`/`BOUNDS` (:63–77), настройки (config.ts:150 — добавить имена окружения) и окно настроек (strings.ts:1179 — подписи); агент их менять не может, как и нынешние):

| Поле | Что ограничивает | Умолчание | Границы |
|---|---|---|---|
| `swarmSessions` | участников одного роя, считая королеву (`swarm.members.length`) | 16 | 2…64 |
| `swarmConcurrent` | одновременно живых и заказанных участников одного роя | 8 | 2…64 |
| `workSwarmSessions` | сессий роя, созданных агентами, за всё время работы (не уменьшается) | 64 | 0…1000 |
| `workSwarms` | роёв, созданных агентами, за всё время работы | 6 | 0…100 |
| `swarmMinutes` | срок жизни одного роя от `createdAt`, минут (3.0); 0 — без срока | 90 | 0…1440 |

0 в `workSwarmSessions` / `workSwarms` — «агентам рои запрещены», как ноль у `workNewSessions` (resource-policy.ts:67). Умолчания: пилот 1 — 4 + 2 + королева = 7; большой аудит — десяток трутней и волна проверки; `workConcurrent` = 24 общий, поэтому один рой не должен занимать больше трети.

**Новые счётчики** `WorkResources.swarmSpawned` (все сессии роя, созданные по агентскому вызову, включая королеву агента) и `swarmsCreated` — необязательные, `?? 0` для старых карт; `ensureResources` (resource-policy.ts:165) и инициализация в sessions-service.ts:1146 учитывают их. Размер роя считается по `members`, отдельного счётчика на рой нет. Человек: `swarms.create` королеву не считает ни в `swarmSpawned`, ни в `workSwarms` (человек и сегодня лимитов `spawned` не тратит — проверка идёт только при `requestedBy`, :1058, :1128); но её `swarm_add` — действие агента и считается.

**Порядок проверок** в одной записи карты, при отказе ничего не пишется (как сегодня): рой жив → `swarmSessions` → `workSwarmSessions` (для `create_swarm` ещё `workSwarms`) → `swarmConcurrent` → `reserveAttempt` (resource-policy.ts:259: окно запусков и слоты одновременных). `ResourceDeniedCode` (:108) расширяется кодами `swarms`, `swarm-sessions`, `swarm-concurrent`, `swarm-total`, область `swarm`, тексты в `DENIED_TEXT` (:136), строка для окна — strings.ts:2654; `resourceStatus` (:427) получает счётчики роя.

**Какие общие лимиты сессии роя обходят, а какие соблюдают:**

| Лимит | Сессия роя |
|---|---|
| `workNewSessions`, `roomNewSessions` (`spawned`, `spawnedByRoom`) | **обходит**: ветка роя их не читает и не увеличивает |
| `roomConcurrent`, `roomLaunches` | не применяются: участники не в комнатах, `roomOfSession` даёт `null` (resource-policy.ts:160, 274), комнатные проверки пропускаются |
| `workConcurrent` (24) | **соблюдает**: это живые процессы; рой делит слоты работы с остальными (`occupied`, :206) |
| `workLaunches` (60/час) | **соблюдает**: запуск участника — `launch` в `reserveAttempt`; возобновления и повторы тоже |
| `resumeRate`, `workMessages`, `roomMessages`, `fanout` | соблюдает без изменений (письма и возобновления не отличают роя) |

Следствие: исчерпанные 50/50 `create_session` не мешают рою, а рой не мешает создавать обычные сессии, пока в работе есть свободные слоты `workConcurrent` и запуски.
