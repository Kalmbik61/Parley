## 1. Зачем и что решено

### 1.1 Вопрос человека

Добавить в Parley доступ с телефона, как мобильное приложение Orca, и сделать это первым
шагом к AI_APP («Джарвис»): тот же телефон потом становится устройством и для Джарвиса.

**Ответ решения `p-01`:** первый шаг к AI_APP — это не экран, а **канал**:
- паринг устройства;
- узкий версионируемый протокол событий и решений;
- push «нужен ты».

Протокол не привязан к конкретному хосту: телефон — клиент нескольких хостов. Джарвис позже
подключится вторым клиентом (или вторым хостом) и ничего не сломает. Сливать с приложением
AI_APP сейчас не будем: у AI_APP облачный бэкенд, это потребительский продукт для РФ, а
Apple Developer аккаунта ещё нет.

### 1.2 Что взять у Orca и чего не брать

Orca: `mobile/` на Expo 55 / RN 0.83, ~185 тыс. строк TS. Около четверти коммитов репозитория
за сентябрь — по мобильным путям. Копировать код бессмысленно, берём идеи.

**Берём:**
- QR-оффер по версионированной схеме;
- токен на каждое устройство и отзыв;
- белый список методов для мобильных токенов;
- снимок экрана headless xterm плюс поток вывода;
- статусы по хукам, ответы на разрешения по структурированным данным, а не по экрану;
- push-регистрацию через десктоп: у телефона нет облачных учётных данных;
- E2E по их схеме — когда появится недоверенный relay (этап C).

**Не берём:**
- агенты по умолчанию YOLO (`DEFAULT_TUI_AGENT_ARGS = YOLO_TUI_AGENT_ARGS`);
- тихие записи доверия в `~/.claude.json`;
- `settings.update` с `agentDefaultArgs`/`agentDefaultEnv` с телефона;
- push с текстом ответа агента через свой сервер (`notification-options.ts`);
- вечный токен из QR без ротации;
- `0.0.0.0` после первого паринга;
- чтение OAuth из Keychain;
- 298 методов.

### 1.3 Что уже есть в Parley

- **Несколько клиентов хост держит.** Рассылка всем клиентам (`host/src/context.ts:76-78`),
  подписчики PTY на сессию (`host/src/methods/pty.ts`). Есть защита `rev` у
  `rooms.resolveProposal` (`protocol/src/methods.ts:107-120`): телефон не примет текст
  решения, которого человек не видел.
- **Сети нет.**
  - Unix-сокет `~/.parley/host/host.sock`, один общий токен на запуск хоста.
  - Токен сравнивается через `!==` (`host/src/server.ts:103`) — для локального сокета
    допустимо.
- **Деталей запроса разрешения хост не знает.** Файловый журнал хуков оставляет только имя
  события (`core/src/work/events.ts`). Ответ на разрешение сегодня — клавиши в PTY, и от гонки
  окна с телефоном он не защищён. Это закрывает план «Chat» (`feed.decide`, `applied: false`).
- **Логика «нужен ты» — чистые функции окна** (`renderer/attention/derive.ts`):
  `sessionAttention`, `roomAwaitsDecision`, `isHumanUnread`, `humanUnreadLetters`.

### 1.4 Провайдерский удалённый доступ — не замена

- **Claude Code Remote Control.** Одна сессия, только подписка и облако Anthropic.
  Транскрипт хранится у Anthropic.
- **Codex Remote.** Хост — десктоп-приложение ChatGPT. Codex CLI в документации как хост не
  упомянут (вывод, не проверено).

Ни тот, ни другой не видят комнат, решений, карты работы и других провайдеров — это и есть
ценность нашего клиента. Включать Remote Control в сессии, которой управляют с нашего
телефона, нельзя: два независимых ввода в один PTY. Это строка README, а не механизм — мост
Remote Control не видит.

## 2. Рамка удалённого доступа

Добавляется к рамке README («Legal frame») и к чек-листу 15.1 спеки Orca-UI.

1. **По умолчанию выключено.** Мост не запускается, порт не слушается, push не уходит, пока
   человек не включил «Remote access» в Settings.
2. **Только человек.** Нет ни одного пути, где мост или хост сами отвечают агенту:
   - решение на разрешение рождается только из `feed.decide` по нажатию на телефоне.
     Клавиш ответа (`pty.input`) у телефона нет: клавиша не привязана к запросу, и тап по
     устаревшему снимку одобрил бы то, чего человек не видел. Сессия без карточки (Codex,
     экран без события) на телефоне — «Answer at your Mac»;
   - правил «авто-allow» и политик на телефоне нет;
   - «Allow and don't ask again» — только то, что CLI сам предложил в
     `permission_suggestions` (на сессию).
3. **Нет скрытых запусков.** Сессия, запущенная или поднятая с телефона, видна в окне как
   любая другая: карта общая.
4. **Телефон не меняет агентов и Parley.** С телефона недоступны:
   - `settings.*`, `host.shutdown`;
   - `works.delete`, `sessions.delete`;
   - `worktrees.*`, `changes.commitProject`, `wake.*`;
   - `pty.resize`.

   Аргументов и окружения агентов в протоколе моста нет вовсе.
5. **Один человек.** Паринг — для своих устройств владельца Мака. Общего доступа, гостевых
   устройств и «поделиться сессией» нет: никто чужой не работает через подписку владельца.
6. **Учётные данные не трогаем.** Ни токенов провайдеров, ни Keychain, ни чужих API. Мост
   ходит в сеть только одним способом — Web Push в службу push браузера телефона
   (Apple/Google/Mozilla), и тело зашифровано по RFC 8291.
7. **Push без содержимого.** Только вид и счётчик («2 waiting»). Названий работ, текстов
   агентов, команд и путей в push нет; детали телефон берёт по каналу.
8. **Всё видно.**
   - Каждое изменяющее действие с телефона пишется в журнал на Маке (раздел 8).
   - Паринг подтверждается на Маке.
   - Отзыв устройства сразу рвёт его соединения.
9. **Слушаем только loopback.** Мост — `127.0.0.1:<порт>`, наружу его выводит выбранный
   человеком «фасад» (раздел 4). На других интерфейсах мост не слушает никогда.
10. **README честно говорит, что это значит.** Сопряжённое устройство может делать всё, что
    человек делает, печатая агенту. Его компрометация — это выполнение кода на Маке
    руками агента. Поэтому — отзыв, журнал, лимиты и выключатель.

Пограничный тест (`core/test/frame-check.test.ts` или свой в `packages/remote`) проверяет:
белый список не содержит запрещённых методов из п. 4 и `pty.input`, мост не слушает ничего,
кроме `127.0.0.1`. Главная гарантия — не тест по исходникам, а вторая граница на хосте
(раздел 3.2): хост сам отклоняет у клиента `remote` всё вне того же списка.

## 3. Архитектура

```
iPhone (PWA)  ──HTTPS/WSS──▶  фасад (Tailscale Serve | Headscale | relay)
                                   │
                                   ▼  127.0.0.1:<порт>
                       packages/remote — мост (Node)
                        │                     │
       unix-сокет хоста │                     │ unix-сокет управления
                        ▼                     ▼
               packages/host (+ проверка роли)  окно (Settings → Remote access)
```

### 3.1 Пакеты

| Пакет | Что | Среда |
|---|---|---|
| `packages/protocol` | новый вход `@parley/protocol/remote`: схемы zod кадров моста, паринга, push-пейлоада; списки методов по этапам | браузер, RN и Node — без `Buffer` и `node:*` |
| `packages/remote` | мост: клиент хоста, WebSocket-сервер, устройства, паринг, push, журнал, сокет управления, раздача PWA | Node 22 (встроенный в приложение) |
| `packages/remote-client` | ядро клиента без UI: подключение к нескольким хостам, переподключение, снимок плюс события, действия, хранилище токенов (интерфейс) | браузер и RN |
| `packages/remote-web` | PWA: UI поверх `remote-client`, manifest, service worker | браузер |

`remote-client` отделён от UI нарочно. Этот пакет без изменений возьмёт RN-приложение (и
Джарвис, раздел 12), заменив только хранилище токенов (Keychain вместо IndexedDB) и
push-регистрацию.

### 3.2 Мост

- **Клиент хоста.**
  - Подключается к `host.sock` с `hello { client: 'remote' }` и токеном из `host.token`.
    Токен читается заново при каждом переподключении: он меняется с каждым запуском хоста.
  - Рукопожатие и переподключение выносятся из `desktop/src/main/host-connection.ts` в
    `@parley/host/client` (там нет Electron). Окно и мост берут один код.
- **Поведение хоста не меняется, кроме одной проверки роли.**
  - Мост для хоста — ещё один клиент.
  - **Вторая граница** (ревью s-03, отступление от «хост не меняем» в `p-01` — сообщено
    человеку). Хост не различает клиентов, и без проверки баг в разборе кадров или белом
    списке моста давал бы полный контроль над хостом (`settings.set`, `host.shutdown`,
    `sessions.create`). Поэтому `server.ts` на `hello { client: 'remote' }` запоминает роль и
    отвечает `unknown_method` на всё вне `REMOTE_ALLOWED` из `@parley/protocol/remote` — того
    же списка, по которому фильтрует мост. Это несколько строк в `handleMessage`, без новой
    подсистемы. От злонамеренного локального процесса это не защищает (он читает
    `host.token`), от ошибок моста — защищает.
  - Пока мост подключён, хост не уходит по простою (`context.ts:65-67`). С включённым
    «Remote access» хост живёт, пока работает мост. Это осознанно: с телефона можно поднять
    спящую сессию.
- **Мост мультиплексирует телефоны в одного клиента хоста.** Подписки хоста привязаны к
  клиенту (`methods/pty.ts`: подписчики PTY на сессию, у плана «Chat» — `feed.subscribe`).
  Поэтому мост:
  - ведёт счётчик подписок на `ref`: `detach`/`unsubscribe` одного телефона не рвёт поток
    другому, а последний отписавшийся снимает подписку у хоста;
  - буферизует отдельно для каждого телефона. Медленный телефон получает свой
    `pty.resync`/снимок и не тормозит остальных. Хост сам отрубает медленного клиента
    (`pty.ts:57-63`), а мост для хоста быстрый.
- **Хост не запущен.**
  - Мост ждёт сокет и сообщает телефону `host: offline`.
  - Сам хост не запускает (этап A). Запуск хоста мостом — открытый вопрос этапа B (раздел 13).
- **Запуск моста.**
  - Мост запускает окно тем же способом, что хост (`desktop/src/main/host-launcher.ts`):
    отдельным процессом, переживает окно.
  - Останавливается при выключении «Remote access», через сокет управления.
  - PID и лог — в `~/.parley/remote/`.
- **Файлы** (`~/.parley/remote/`, каталог 0700, файлы 0600):
  - `remote.json` — включено, порт, фасад;
  - `devices.json` — устройства, хэши токенов, push-подписки;
  - `vapid.json` — ключи VAPID, создаются при первом включении;
  - `audit.jsonl` — журнал;
  - `control.sock` и `control.token`;
  - `bridge.pid` и `bridge.log`.
- **Сокет управления** (unix, токен как у хоста) — только для окна:
  - статус;
  - создать оффер паринга;
  - подтвердить или отклонить паринг;
  - список и отзыв устройств;
  - журнал;
  - тестовый push;
  - остановка.

  Окно не ходит в мост по WebSocket.

## 4. Сеть: сменный фасад

Мост слушает только `127.0.0.1:<порт>`. Порт фиксируется при первом включении — первый
свободный, начиная с 8791 (8787 на машине владельца занят), — и хранится в `remote.json`:
команда фасада ссылается на него.
Наружу его выводит фасад, который человек выбирает и настраивает сам. Parley фасад **не
настраивает**: в Settings — команда для копирования и проверка, что адрес отвечает.

**Варианты** (что работает у человека, решает спайк, раздел 11.2):

1. **Tailscale Serve** (по умолчанию в принятом решении).
   - HTTPS на `https://<мак>.<tailnet>.ts.net`, доступ только из tailnet, шифрование
     WireGuard. Команда вида `tailscale serve --bg --https=443 localhost:8791` — точный синтаксис сверить по
     документации Tailscale в спайке.
   - Funnel (публичный доступ) запрещён: README и проверка в Settings.
   - **Риск для РФ** (находка s-03): по публичным источникам 2023–2024 Tailscale отвечает 451 на
     вход и DERP из РФ. Проверка — первым пунктом спайка, до шагов на iPhone.
2. **Headscale на своём VPS** + клиенты Tailscale. На iOS приложение Tailscale умеет свой
   сервер координации. Та же модель, что в п. 1, без зависимости от серверов Tailscale; DERP
   свой.
3. **Свой relay** (этап C, раздел 11.5) — «тупой» склейщик кадров, обе стороны подключаются
   исходящими соединениями. Relay недоверенный, поэтому только вместе с E2E (раздел 6.6).

**Защиты не зависят от фасада.** Паринг, токены устройств, белый список, лимиты и журнал
работают одинаково при любом варианте. Фасад даёт только доставку и TLS.

**Дополнительная проверка для Tailscale Serve** (сверить в спайке). Serve добавляет
заголовки личности (`Tailscale-User-Login`). Если они приходят и на апгрейд WebSocket, мост в
режиме `facade: tailscale` требует заголовок и сверяет логин с записанным при паринге. Так
отсекаются Funnel и другие пользователи tailnet. Локальный процесс на Маке подделает
заголовок, но он и так читает `host.token`: новой поверхности это не открывает.

**Если ни п. 1, ни п. 2 у человека не работают**, E2E и relay переезжают из этапа C в v1.
Это отдельное решение человека по итогам спайка.

**Host и Origin.** Мост на `127.0.0.1` доступен любой странице браузера на самом Маке, в том
числе через DNS rebinding. Поэтому:
- на всех HTTP-запросах, включая `/pair` и апгрейд WebSocket, мост требует `Host` из
  допустимых: имя фасада из `remote.json` и `127.0.0.1:<порт>`;
- на апгрейде и `/pair` мост требует `Origin` = `https://<имя фасада>`;
- запросы с признаком Funnel (`Tailscale-Funnel-Request` — сверить в спайке) отбрасываются;
- в `ws` задаётся `maxPayload` 1 МиБ (по умолчанию ~100 МиБ).

**Публичность имени.** Имя `…ts.net` попадает в журналы Certificate Transparency: имя
tailnet и Мака видно всем. Это не секрет, но README об этом говорит. Для Serve — ACL tailnet
только на устройства владельца.

## 5. Устройства и паринг

### 5.1 Поток

1. **Оффер.** Settings → «Pair a device»: мост создаёт оффер — 128-битный секрет, срок
   10 минут, одноразовый; одновременно живёт один оффер. Окно показывает:
   - QR с `https://<фасад>/pair#o=<секрет>&h=<hostId>` (фрагмент не попадает в логи сервера
     и фасада);
   - короткий код из 8 знаков base32 для ручного ввода.
2. **Ввод на телефоне.**
   - **Основной путь — код.** На iOS хранилище PWA, добавленной на экран «Домой», отдельно
     от Safari (проверить на устройстве). Порядок: открыть адрес фасада в Safari → «Добавить
     на экран „Домой“» → открыть Parley с экрана «Домой» → ввести короткий код.
   - QR — второй путь: для Android и десктопного браузера, на iOS — если спайк покажет, что
     фрагмент переживает установку.
   - `start_url` манифеста и любые ссылки PWA секрета оффера не несут.
3. **Запрос.** Телефон шлёт `POST /pair { offer, deviceName, userAgent }`; имя устройства
   человек правит на телефоне.
4. **Подтверждение на Маке.** Окно показывает диалог: «Allow “<имя>” to control Parley?»,
   кнопки «Allow» / «Deny».
   - Имя и user agent задаёт сам телефон, поэтому они подписаны «unverified».
   - Проверенное поле одно — логин tailnet, если фасад его дал.
   - Без ответа за срок оффера — отказ.
   - Неподтверждённых запросов одновременно не больше трёх.

   Короткий код (8 знаков base32, 40 бит) безопасен благодаря этому шагу и лимиту попыток
   (раздел 5.2): подбор без нажатия на Маке ничего не даёт.
5. **Выдача токена.** После «Allow» телефон получает `{ deviceId, token, hostId, hostName }`:
   токен — 32 байта `randomBytes`. В `devices.json` пишется только `sha256(token)`, имя, время
   паринга, логин фасада и push-подписка.

### 5.2 Токены

- **Сравнение.** `timingSafeEqual` по хэшам.
- **Ротация — не на каждом `hello`** (ревью s-03). На iOS параллельно живут PWA, service
  worker и запуск по тапу на push, хранилище пишется асинхронно, а процесс убивается без
  предупреждения. Ротация на каждом подключении запирала бы законное устройство. Поэтому:
  - токен меняется раз в 7 дней — явным методом `token.refresh`, который клиент зовёт под Web
    Locks API (один писатель на источник);
  - мост держит окно из трёх последних токенов; старые действуют 10 минут после выдачи нового;
  - старый токен вне окна — отказ, запись в журнал и уведомление окна «device presented an
    old token». Автоматического отзыва нет: решение за человеком.
- **Отзыв.** Settings → Devices → «Revoke»: запись удаляется, все WebSocket устройства
  закрываются сразу кодом 4401, push-подписка стирается.
- **Лимиты — не по адресу.** За фасадом все запросы приходят с `127.0.0.1`, и лимит по адресу
  дал бы любому участнику tailnet запереть владельца. Лимиты такие:
  - на оффер: 10 неверных кодов — оффер аннулируется, нужен новый QR;
  - на устройство: неверный `hello` — 5 в минуту; изменяющие методы — 30 в минуту;
  - глобально: не больше 60 неудачных `hello` и `/pair` в минуту, сверх — пауза с записью в
    журнал.
- **Потолки.** Устройств не больше 5, имя устройства — 64 знака, текст `rooms.send` у моста
  — 16 КБ (у хоста предела нет: `methods.ts:126`).

## 6. Протокол моста `parley-remote` v1

### 6.1 Кадры

JSON по WebSocket, `permessage-deflate` включён. Формы — как у протокола хоста:
- `{ id, method, params }` → `{ id, result }` | `{ id, error: { code, message, data? } }`;
- событие — `{ event, data }`.

Схемы — `@parley/protocol/remote`.

### 6.2 Рукопожатие

Первый кадр — `hello` за 5 с:

```
hello { protocol: 1, deviceId, token, client: 'pwa/<версия>' }
→ { protocol: 1, hostId, hostName, bridgeVersion, hostVersion | null,
    stage: 'A' | 'B', methods: string[], events: string[], token: <новый> }
```

- `hostId` — постоянный id установки (UUID в `remote.json`). По нему `remote-client`
  различает хосты.
- `methods` и `events` — фактический белый список. Клиент прячет то, чего нет, так же как окно
  по `hello.methods` хоста.
- `protocol` растёт только при несовместимой смене. Новые методы — добавлением, как у хоста.

### 6.3 Белый список

Мост пропускает к хосту только перечисленное. Остальное получает `unknown_method` и ход в
журнал как попытка.

| Этап | Методы → хост | События ← хост | Правила моста |
|---|---|---|---|
| A | `works.list`, `providers.list`, `host.info` | `works.changed`, `activity.changed`, `host.notice`, `providers.limitsChanged` | только чтение |
| B | + `rooms.send`, `rooms.resolveProposal`, `mail.markRead`, `sessions.resume`, `sessions.stop`, `pty.send`, `feed.snapshot`, `feed.subscribe`, `feed.unsubscribe`, `feed.decide`, `pty.attach`, `pty.detach`; уведомление `activity.seen` | + `feed.changed`, `pty.output`, `pty.resync`, `pty.exit` | см. ниже |
| B (по решению) | `sessions.create` | — | см. раздел 13 |

Правила этапа B:
- **`rooms.resolveProposal`.** Без `rev` мост отвечает `bad_request`. Телефон обязан
  показать человеку ту ревизию, которую принимает.
- **`rooms.send`.** Только `kind: note | question`. `decision` пишет только хост от имени
  ведущего.
- **`pty.input` не пропускается вовсе** (рамка п. 2). Текст агенту — только через
  `pty.send` с его отказами `blocked`, `busy`, `draft`. Если когда-нибудь понадобятся клавиши
  для Codex, то только при `blocked`, со сверкой ревизии снимка экрана (`screenRev`) и без
  «always» — и отдельным решением человека.
- **`pty.attach`.** Только вид: размер не шлётся (`pty.resize` запрещён). Телефон рисует
  снимок в своём масштабе, Мак не переформатируется.
- **`feed.decide`.** Как в окне. `applied: false` — «answered elsewhere». Это и есть защита
  от гонки окна с телефоном.

### 6.4 Снимок

`works.changed` — полный снимок всех работ (`WorksSnapshot`).
- **Этап A.** Мост отдаёт его как есть, со сжатием. В спайке и на A меряем размер на
  настоящих работах.
- **Больше 256 КБ после сжатия.** Мост шлёт дельты (JSON Patch по `hostId` + ревизия), клиент
  при пропуске просит снимок (`works.list`). Это задача A, если замеры покажут нужду.

### 6.5 Несколько хостов

`remote-client` хранит список `{ hostId, hostName, url, deviceId, token }`. Каждый хост —
отдельное соединение со своим состоянием. UI показывает переключатель хостов, когда их
больше одного. Второй Мак, Linux-машина или будущий хост Джарвиса подключаются тем же
парингом.

### 6.6 E2E (этап C или раньше по разделу 4)

По схеме Orca:
- закреплённый X25519-ключ моста в QR и эфемерный ключ клиента;
- HKDF-SHA256 с хэшем рукопожатия;
- раздельные ключи на направление;
- XSalsa20-Poly1305 с nonce-счётчиком;
- привязка к пути.

В браузере — tweetnacl или libsodium-wasm: WebCrypto не везде даёт X25519. Добавляем в
отличие от Orca forward secrecy — эфемерный ключ и у моста. Пока фасад доверенный (WireGuard
своего tailnet), E2E не делаем: двойное шифрование и криптобиблиотека в PWA не окупаются.

## 7. Push

- **Механизм.** Web Push (RFC 8030/8291) с VAPID: мост шлёт прямо в службу push браузера,
  своего сервера нет. Подписка создаётся в PWA по нажатию человека (на iOS — только у
  установленной PWA, iOS 16.4+) и уходит мосту методом `push.subscribe`. Этот метод —
  локальный для моста, к хосту не идёт.
- **Когда шлём.** Только на переход «не ждёт → ждёт». Мост считает его по `works.changed` и
  `activity.changed` теми же чистыми функциями, что окно. Они выносятся из
  `renderer/attention/derive.ts` в `@parley/core/attention`, окно их реэкспортирует. Поводы:
  1. сессия перешла в `blocked` (`sessionAttention` → `needs-you`);
  2. у комнаты появилось решение или сменился `proposalId` (`roomAwaitsDecision`);
  3. новое непрочитанное прямое письмо человеку (`humanUnreadLetters`).
- **Что шлём.**
  - Пейлоад: `{ v: 1, kind: 'needs-you', count, hostId }`. Счётчик — сознательный выбор
    (в `p-01` было «агент ждёт»): число не раскрывает содержимого, а человеку важно «одно или
    пять».
  - Текст уведомления service worker собирает сам: «Parley — 2 waiting».
  - Один `tag` на хост: новое уведомление заменяет старое.
  - Пачка за 3 с — одно уведомление.
  - Уведомлений «закончил ход» нет на этапе A; на B — переключатель на телефоне, по умолчанию
    выключен.
- **Правила Web Push на iOS** (ревью s-03):
  - каждый push обязан показать уведомление, иначе Apple отзывает подписку. «Молчаливых»
    очисток нет, push на переход к нулю не шлём;
  - VAPID `sub` — валидный `mailto:` или `https:`. Невалидный даёт у Apple 403 `BadJwtToken`;
  - ответ службы push 404/410 — подписка удаляется из `devices.json`.
- **Ограничение** — пишется в README и в Settings: push приходит, только пока Мак не спит,
  хост и мост работают и фасад доступен. Будить Мак мы не умеем и не будем.
- **Подавление — по присутствию, а не по фокусу** (ревью s-03). Окно Parley часто остаётся на
  переднем плане, когда человек ушёл. Окно сообщает мосту по сокету управления присутствие из
  `powerMonitor` Electron: `getSystemIdleState(60)` — `active` / `idle` / `locked`.
  - `active` — push не шлём;
  - `idle` и `locked` — шлём.
  - Окно закрыто — шлём всегда.

## 8. Журнал действий

`~/.parley/remote/audit.jsonl`, строка на событие:

```
{ at, deviceId, deviceName, kind, method?, target?, outcome, detail? }
```

- `kind`: `pair-request`, `pair-allowed`, `pair-denied`, `hello`, `hello-failed`, `call`,
  `call-refused`, `revoked`, `token-reuse`.
- `call` — только изменяющие методы этапа B.
  - `target` — ref сессии или id комнаты.
  - `detail` — для `rooms.send`/`pty.send` длина и первые 8 знаков `sha256` текста (в тексте
    могут быть секреты; полный текст — только по флагу `auditFullText` в `remote.json`, по
    умолчанию выключен); решение `feed.decide` (`allow`/`deny`); действие `resolveProposal` с
    `rev`.
- Ротация по 5 МБ, хранится последний архив.
- Settings показывает последние 200 строк.

## 9. Клиент: PWA

- **Стек.** Vite, React 18, zustand, Tailwind 4 — как в окне. Токены облика Organic берутся из

     (текст решения строчным Markdown, без кнопок), письма человеку;
  4. Settings телефона: push вкл/выкл, отвязать устройство, версия.

  Плашка `host offline` / `reconnecting`.
- **Этап B — добавляется:**
  - лента комнаты с полем ввода и `@`-упоминаниями;
  - карточка решения «Accept» / «Return for rework» с заметкой;
  - вид сессии Claude — лента `feed.*` и карточки разрешений, вопросов, плана из плана
    «Chat»;
  - вид терминала только для чтения (для Codex и экранов без карточки) с плашкой «Answer at
    your Mac», без клавиш;
  - «Resume» / «Stop».
- **iOS.** В фоне WebSocket рвётся. Будит push, при открытии — переподключение и снимок.
  Держать соединение в фоне не пытаемся.

## 12. Джарвис и AI_APP

Связь — через `parley-remote`, а не слиянием кода.

- **Путь 1 (ближний): Джарвис на телефоне — клиент моста.**
  - RN-приложение AI_APP берёт `@parley/remote-client` и подключается к Маку тем же
    парингом.
  - Голос и лента Джарвиса превращают «поручи агентам…» в `rooms.send` / `sessions.create`.
  - Решения Parley показываются в ленте Джарвиса карточкой согласия (этап 2 плана AI_APP —
    «доверенные действия»).
  - Бэкенд AI_APP в этом не участвует: данные кода и агентов в облако AI_APP не уходят. Это
    важно для ФЗ-152 и для доверия.
- **Путь 2 (дальний): бэкенд AI_APP — relay.**
  - Нужен, если Джарвис сам, без телефона, ставит задачи агентам на Маке (тул агента
    AI_APP).
  - Только с E2E: облако видит шифротекст, а ключ устройства — у бэкенда как у ещё одного
    сопряжённого клиента с отзывом и журналом.
  - Требует отдельного решения: это меняет рамку AI_APP.

Ни один путь не требует решать это сейчас. Требует другого: чтобы `remote-client` был без UI,
протокол — версионируемым, а паринг поддерживал несколько хостов и несколько клиентов. Это
заложено в разделах 3.1 и 6.
