# Координация агентов внутри работы (v3) — дизайн

Дата: 2026-09-02. Статус: согласовано, реализация после v2.
Реализуется не через Ralph, а отдельным workflow. Этот документ — источник истины
для того workflow; v1 и v2 не должны делаться вразрез с ним.

---

## 1. Зачем

Внутри одного проекта несколько агентских сессий разных провайдеров (Claude, Codex,
GLM и любой добавленный) работают над одной задачей и **знают друг о друге**: кто что
делает сейчас, что уже сделано, где лежит результат. Сессии могут порождать новые
сессии с нужным провайдером и передавать им контекст, обмениваться сообщениями и
ждать результата подчинённой сессии, если он нужен.

Знание друг о друге строится **не на прямом чате агентов, а на общей карте** — одном
компактном JSON на работу. Это решение унаследовано из хендоффа (`docs/harness-handoff.md`,
раздел «Оркестратор») и здесь конкретизировано.

Принятые в обсуждении решения (каждое — выбор из 2–3 вариантов):

| Вопрос | Решение |
|---|---|
| Как запускаются сессии | Интерактивно в панели харнесса; новую сессию порождает **агент** из текущей, указывая провайдера из реестра |
| Что делает вызывающий агент | Асинхронно по умолчанию: `spawn_session` сразу возвращает id; ожидание только явным `wait_for` |
| Где живёт карта | Гибрид: карта и артефакты в проекте (`.harnas/`), реестр провайдеров и глобальный индекс работ в `~/.harnas/` |
| Как появляется резюме | Гибрид: статусы жизненного цикла ведёт харнесс по логам и PTY, резюме и артефакты пишет агент через `report`; для сессий без отчёта резюме можно дозаказать |
| Доставка сообщений | Pull через карту плюс бейдж непрочитанных в TUI; push в PTY — отложенный эксперимент |
| Порядок работ | После v2. Суммирование токенов в индексе сессий делается заранее, в v1 |
| Метрики | Обязательны: токены (4 счётчика), длительность, вызовы инструментов — как в Claude Code |

Юридические рамки не меняются: спавнится только немодифицированный `claude` из PATH
под логином пользователя, `~/.claude` строго read-only, `.credentials.json` не трогать.
Дозаказ резюме через `claude -p` — тот же разрешённый сценарий (стоковый бинарь).

## 2. Сущности

- **Проект** — папка на диске. Идентификатор — тот же slug, что использует Claude Code
  для `~/.claude/projects/<slug>`, чтобы связывать сессии с логами.
- **Работа** (work) — единица координации внутри проекта: заголовок, цель, статус
  `active | done | archived`. Содержимое целиком в `<проект>/.harnas/works/<work-id>/`.
- **Сессия** — один агентский процесс, привязанный к работе: провайдер, задача, родитель
  (кто породил, если агент), статус, метрики, резюме, артефакты. Сессии, открытые
  пользователем руками внутри работы, регистрируются так же, как порождённые агентом.
- **Провайдер** — запись в реестре `~/.harnas/providers.json`. Единственный источник
  допустимых значений для `spawn_session`.
- **Артефакт** — файл в проекте (обычно `.harnas/works/<id>/artifacts/`), на который
  карта ссылается путём относительно корня проекта: план, отчёт QA, спецификация, бриф.
- **Сообщение** — от сессии к сессии, хранится в карте, доставляется по pull.

Именование: сущность харнесса называется «работа», а не «проект», чтобы не путать с
проектом Claude Code (`~/.claude/projects/<slug>`).

### Раскладка на диске

```
<проект>/.harnas/
  works/<work-id>/
    map.json              карта работы (пишет только харнесс)
    map.json.bak          предыдущая версия, обновляется при каждой записи
    map.lock              файловая блокировка на время записи
    briefs/<session-id>.md   стартовый промпт сессии (артефакт, можно править до запуска)
    settings.json         хуки Claude Code для сессий работы (`--settings`), один на работу
    events/<session-id>.jsonl   журнал событий хуков сессии, дописывается самим хуком
    artifacts/            планы, отчёты и прочее, что кладут агенты

~/.harnas/
  providers.json          реестр провайдеров
  works-index.json        глобальный индекс работ: путь проекта, id, заголовок, статус, updatedAt
```

Коммитить `.harnas/` в репозиторий проекта или добавить в `.gitignore` — выбор
пользователя, харнесс это не решает.

## 3. Карта `map.json`

Один файл на работу. **Пишет только харнесс** (MCP-сервер и TUI), агенты напрямую не
редактируют — иначе параллельные агенты затирают друг друга. Читать напрямую можно.

```json
{
  "schemaVersion": 1,
  "work": {
    "id": "w-0042", "title": "Авторизация", "goal": "…",
    "status": "active", "createdAt": "…", "updatedAt": "…"
  },
  "sessions": [
    {
      "id": "s-01", "provider": "claude", "label": "план",
      "task": "Составить план реализации авторизации",
      "parent": null, "contextFrom": [],
      "status": "done",
      "history": [ { "status": "active", "at": "…" }, { "status": "done", "at": "…" } ],
      "startedAt": "…", "endedAt": "…",
      "providerSessionId": "bb2137cb-…",
      "metrics": {
        "durationMs": 81582,
        "tokens": { "input": 1200, "output": 800, "cacheRead": 50000, "cacheWrite": 3000 },
        "toolCalls": { "Bash": 13, "Edit": 4 }
      },
      "summary": "План готов: 5 шагов, миграции отдельно.",
      "artifacts": [ { "kind": "plan", "path": ".harnas/works/w-0042/artifacts/plan.md" } ]
    },
    {
      "id": "s-02", "provider": "codex", "label": "бэкенд",
      "task": "Реализовать шаги 1–3 плана",
      "parent": "s-01", "contextFrom": ["s-01"],
      "status": "active", "history": [ { "status": "pending", "at": "…" }, { "status": "active", "at": "…" } ],
      "startedAt": "…", "endedAt": null,
      "providerSessionId": null, "metrics": null,
      "summary": null, "artifacts": []
    }
  ],
  "messages": [
    { "id": "m-01", "from": "s-02", "to": "s-01", "at": "…", "text": "…", "readAt": null }
  ]
}
```

Поля сессии:

| Поле | Кто пишет | Смысл |
|---|---|---|
| `id`, `provider`, `label`, `task`, `parent`, `contextFrom` | харнесс при создании | неизменяемые |
| `status`, `history`, `startedAt`, `endedAt` | харнесс | жизненный цикл (раздел 6) |
| `pid`, `startedAtProcess`, `launchedBy` | харнесс при запуске | процесс сессии и кто её запустил (`tui` / `cli`); по ним проверяется живость после перезапуска (TUI v2, раздел 5.4) |
| `providerSessionId` | харнесс при запуске | id сессии у провайдера (для Claude — uuid jsonl-файла) |
| `metrics` | харнесс | из логов провайдера; `null`, пока сессия жива (считается на лету), фиксируется при завершении |
| `summary`, `artifacts` | агент через `report` | резюме результата и ссылки |

Статусы сессии: `pending` (создана, не запущена), `active`, `exited` (процесс вышел
без отчёта), `done`, `failed`. Первые три ставит харнесс по PTY, хукам и логам,
последние два приходят только из `report`. Статус `idle` **удалён 2026-09-05**
(ревью TUI v2): простой живого агента описывает не карта, а `activity`, выводимая
из журнала событий (`docs/specs/2026-09-05-tui-v2-design.md`, раздел 4); старые
карты с `idle` читаются как `active`.

Карта остаётся компактной: у завершённой сессии одна запись с резюме и ссылками,
транскрипт никуда не копируется — он лежит у провайдера и доступен по
`providerSessionId` тому, кому нужны детали. Это и есть «архив» работы.

## 4. MCP-сервер `harnas-mcp`

Живёт в `packages/core`, stdio-транспорт, **один процесс на сессию**. Харнесс генерирует
для каждой запускаемой сессии свой MCP-конфиг, в котором сервер получает через окружение:

- `HARNAS_WORK_DIR` — путь к `.harnas/works/<work-id>/`;
- `HARNAS_SESSION_ID` — id сессии в карте.

Поэтому агенту не нужно представляться: сервер знает, кто звонит.

### Инструменты

| Инструмент | Что делает |
|---|---|
| `get_map()` | Вся карта плюс список провайдеров из реестра (id, бейдж, доступен ли в PATH). Один вызов — полная картина |
| `report(status, summary, artifacts)` | `done` / `failed` — финальный отчёт; `progress` — обновляет `summary`, статус не меняет. Повторный `report` перезаписывает резюме. `artifacts`: массив `{kind, path}` с путями относительно корня проекта |
| `spawn_session(provider, label, task, contextFrom)` | Проверяет провайдера по реестру и наличие команды в PATH, собирает бриф (раздел 5), создаёт запись `pending`, возвращает `{sessionId}`. Неизвестный провайдер или отсутствующая команда — ошибка с перечнем допустимых, запись не создаётся |
| `wait_for(target, timeoutSec)` | `target` — id сессии или `"inbox"`. Возвращается, когда сессия дошла до `done` / `failed` / `exited` (с её резюме) или пришло новое сообщение. Таймаут ограничен сверху (по умолчанию 10 минут, максимум 30), потому что у MCP-клиентов есть свой предел на вызов. По таймауту возвращает `{state: "running"}`, агент решает, звать ли снова. Сессия, удалённая пользователем (id в `work.deletedSessions`), — `{state: "deleted", sessionId}` сразу, в том числе если исчезла во время ожидания. Id, которого не было никогда, — ошибка, не ожидание |
| `send_message(to, text)` | Кладёт сообщение в карту. `to` — id сессии; неизвестный id — ошибка. Отправитель тоже проверяется: сервер удалённой сессии писать в карту не может |
| `check_inbox()` | Отдаёт непрочитанные сообщения для текущей сессии и помечает их прочитанными (`readAt`) |
| `read_guide()` | Подробный гид по харнессу текстом (`core/work/guide.ts`); сессии не требует. Короткая вставка приходит через `--append-system-prompt` (план 2026-09-06, раздел A) |

### Запись в карту

Временный файл + атомарный `rename` под файловой блокировкой `map.lock`. Перед записью
текущая версия копируется в `map.json.bak`. Если карта не парсится, сервер отказывается
писать и возвращает ошибку. Блокировка, не снятая дольше нескольких секунд, — ошибка
вызова, без тихого ожидания. Никакого демона: TUI следит за `map.json` тем же
watcher-механизмом core, что уже есть.

### Работа без TUI

Слой работает и без панели. Команда core (`harnas-core work session new --work <id>
--provider <p> --task "…"`) создаёт запись `pending`, генерирует MCP-конфиг и печатает
готовую команду запуска. Стоковый `claude`, запущенный из обычного терминала этой
командой, видит карту, отчитывается и порождает `pending` сессии, которые пользователь
откроет из харнесса. Сессия, запущенная с нашим MCP-конфигом, но без `HARNAS_SESSION_ID`,
получает только `get_map`; остальные инструменты отвечают, что сессию надо создавать
через харнесс или указанную команду.

## 5. Реестр провайдеров и запуск сессии

Реестр **уже существует в коде**: `packages/core/src/providers.ts` (`PROVIDERS`,
`runnerCommand`), сделан в v2, со `command` и `resumeArgs` для Claude / Codex / GLM.
Этот слой его не заменяет, а расширяет: в `RunnerConfig` добавляются аргументы
запуска новой сессии с id, MCP-конфигом и стартовым промптом, а `~/.harnas/providers.json`
становится **необязательным файлом переопределений и дополнений** поверх встроенного
реестра (свои CLI, другой путь к бинарю). Итоговая форма записи:

```json
{
  "claude": {
    "badge": "Claude",
    "command": "claude",
    "args": ["--session-id", "{sessionUuid}", "--mcp-config", "{mcpConfig}", "{prompt}"],
    "resumeArgs": ["--resume", "{providerSessionId}", "--mcp-config", "{mcpConfig}"],
    "logs": { "adapter": "claude", "root": "~/.claude/projects" }
  },
  "codex": {
    "badge": "Codex",
    "command": "codex",
    "args": "…заполняется по итогам discovery v2…",
    "resumeArgs": "…",
    "logs": { "adapter": "codex", "root": "~/.codex/sessions" }
  }
}
```

Подстановки: `{sessionUuid}` — uuid, сгенерированный харнессом; `{mcpConfig}` — путь к
сгенерированному MCP-конфигу; `{prompt}` — путь или текст брифа (как принимает CLI);
`{providerSessionId}` — id для возобновления. У `claude` флаг `--session-id` позволяет
заранее знать имя jsonl-файла — без угадывания по времени создания. Как это устроено у
Codex, выясняет discovery v2; в реестре остаётся поле под это. Если провайдер не умеет
принимать id снаружи, адаптер логов сопоставляет новую сессию по cwd и времени запуска,
и это фиксируется в его записи реестра.

Бейдж модели для сессии берётся из логов провайдера через таблицу нормализации
`specs/runners.md`; бейдж провайдера — из реестра.

### Бриф

`spawn_session` собирает стартовый промпт из:

1. заголовка и цели работы;
2. id и роли (`label`) новой сессии;
3. текста задачи;
4. для каждой сессии из `contextFrom` — её резюме и пути к артефактам (не содержимое);
5. трёх правил: в начале вызвать `get_map`; вопросы задавать через `send_message`
   и проверять `check_inbox`; перед завершением обязательно вызвать `report`.

Бриф сохраняется в `briefs/<session-id>.md` — его можно прочитать и поправить до
запуска. Он нарочно короткий: агент сам прочитает план целиком, если он ему нужен.

### Последовательность запуска

1. Агент вызывает `spawn_session`. Сервер валидирует, пишет бриф, создаёт `pending`.
2. TUI видит новую `pending` сессию в карте и поднимает процесс в фоне, не переключая
   панель (настройка `autoLaunch`, по умолчанию включена; при выключенной — по
   `Enter` через диалог с брифом, дизайн TUI v2, 5.2): команда и аргументы из
   реестра, cwd проекта, сгенерированный MCP-конфиг, бриф стартовым промптом.
   Статус → `active`, `providerSessionId` записан. Если TUI не запущен, сессия ждёт;
   в списке видна команда для ручного запуска.
3. Дальше сессия живёт как любая интерактивная: разрешения и вопросы агента
   обрабатывает пользователь в панели.

Сессия, созданная пользователем руками (выбрал провайдера, написал задачу), проходит
тот же путь `pending → active`; разница в том, что роль и текст задачи вводит
пользователь и `parent` пустой. Бриф при этом **всё равно собирает харнесс** по тому же
шаблону (работа, роль, задача, три правила) — иначе агент не узнает про `get_map` и
`report`. `contextFrom` для ручной сессии пуст; контекст пользователь даёт текстом задачи.

## 6. Жизненный цикл и метрики

Переходы статусов (ставит харнесс, кроме `done` / `failed`):

| Переход | Условие |
|---|---|
| `pending → active` | панель открыта, процесс запущен; записываются `pid`, `startedAtProcess`, `launchedBy` |
| `active → exited` | процесс завершился (SessionEnd-хук, выход PTY или проверка живости по pid), `report` не было |
| `exited → active` | возобновление через `resumeArgs`; id сессии в карте тот же |
| `done`/`failed → active` | возобновление завершённой сессии тем же диалогом; прежнее резюме остаётся в карте до нового `report` |
| `* → done`/`failed` | только из `report` |
| `exited → done`/`failed` | сессию возобновили и агент отчитался |

Код выхода процесса пишется в последнюю запись `history` (`exitCode`), глиф
статуса от него не зависит.

Каждый переход добавляется в `history`.

Метрики считаются из логов провайдера общей функцией core по `providerSessionId`:
длительность (первая/последняя запись), токены (`input`, `output`, `cacheRead`,
`cacheWrite` — для Claude из `message.usage.*`, подтверждено schema-report),
вызовы инструментов по именам. Пока сессия жива, метрики пересчитываются при чтении
по событиям watcher и в карту не пишутся. При переходе в `done` / `failed` / `exited`
итоговые числа фиксируются в карте — архив хранит их, даже если логи провайдера
позже почистят.

**Задача для v1 (заранее):** добавить в `SessionIndex` суммирование токенов по
четырём счётчикам, чтобы список сессий показывал их сразу, до этого слоя.

Дозаказ резюме для `exited` сессии: один вызов `claude -p` (стоковый бинарь) с
транскриптом; результат записывается как `summary` с пометкой `summarySource: "auto"`,
в отличие от `"agent"` для отчёта самого агента.

## 7. Изменения в TUI

Раздел заменён документом `docs/specs/2026-09-05-tui-v2-design.md` (2026-09-05):
сайдбар и одна панель, префиксный ввод, `activity` из хуков. Ниже — исходный
состав, сохранён для истории:

- **Строка статуса** внизу терминала — единственный канал уведомлений в обоих
  режимах; предупреждение о параллельных агентах переезжает туда из правой панели.
- **Список слева сверху** получает второй режим: работы, сгруппированные по проектам,
  внутри работы — сессии со статусом, бейджем провайдера, токенами, длительностью и
  значком непрочитанных сообщений. Текущий режим «все сессии» остаётся.
- **Панель слева снизу** для выбранной сессии: задача, резюме, артефакты и уже
  существующие подсессии субагентов.
- **Действия**: новая работа; новая сессия в работе; открыть `pending`; возобновить
  `exited`; дозаказать резюме для `exited`.
- Предупреждение при второй параллельной сессии одного провайдера остаётся, как в
  `specs/pty.md`.

## 8. Ошибки и граничные случаи

- Команда провайдера не найдена в PATH — `spawn_session` возвращает ошибку сразу.
- Карта не парсится — сервер отказывается писать; `map.json.bak` содержит предыдущую
  версию.
- Блокировка не снята дольше нескольких секунд — ошибка вызова.
- `wait_for` / `send_message` на несуществующий id — ошибка; `wait_for` на удалённую
  пользователем сессию — `{state: "deleted"}` (план 2026-09-06, раздел C).
- Сессия без `HARNAS_SESSION_ID` — только `get_map`.
- Агент вызвал `report` дважды — последний побеждает.
- `report` с путём артефакта вне проекта — ошибка; относительный путь обязателен.
- Второй TUI на том же проекте — не поддерживается в этой версии; блокировка карты
  защищает файл, но `pending` сессию откроет тот TUI, который первым увидит событие.

## 9. Тесты

- **core**: хранилище карты (атомарная запись, блокировка, два параллельных писателя
  не теряют записи), сборка брифа, валидация провайдера по реестру, метрики из фикстур
  логов, выведение статусов по последовательности событий.
- **MCP-сервер**: клиент и сервер из SDK в одном процессе через транспорт в памяти;
  все инструменты, включая ошибочные вызовы.
- **Интеграция**: тот же stub-бинарь, что в v1, проверяет, что панель получает команду,
  cwd, MCP-конфиг и бриф из реестра. Настоящий `claude` в тестах не запускается никогда.

---

## 10. Вне объёма

- Push сообщений в PTY (печать в чужую панель) — отложенный эксперимент, формат
  сообщений в карте его допускает без переделки.
- Headless-конвейер (`claude -p`, `codex exec` по цепочке без человека) и роутер по
  капабилити/стоимости — не в этой версии; лимиты подписки для непрерывной работы не
  решены.
- Несколько TUI на одном проекте.
- Синхронизация карты между машинами.
- Сплит правой области на две живые панели (`O`/`X`): заготовка в дизайне,
  раздел 2.5; требует изменений в PTY-слое (две панели, фокус, ресайз) и
  делается отдельной фазой после v3.
- Правка брифа из TUI, файловый пикер для отправки файлов агенту, журнал
  уведомлений.

## 11. Решения по вопросам дизайна (2026-09-02)

Ответы на вопросы дизайнера, зафиксированные как часть спецификации:

- Бриф для ручной сессии собирает харнесс по общему шаблону (раздел 5).
- Правка брифа: файл правится внешним редактором, TUI перечитывает его при запуске.
- Сессии проекта, не привязанные к работе, в режиме «работы» не показываются.
- `archived` работы скрыты; `done` при старте свёрнуты.
- Фильтр провайдера в режиме «работы» действует на сессии, работы остаются видимы.
- Сессия, запущенная вне TUI (`harnas-core work session new`), в панель не
  подключается: у харнесса нет её PTY; TUI показывает пометку и детали.
- Время с последнего события показывается только в деталях (статус `idle` удалён 2026-09-05).
- Дозаказ резюме для Codex-сессий: транскрипт извлекает адаптер core, резюме
  делает тот же `claude -p`. Для GLM (runner-only, без истории) дозаказ недоступен.
- Работы всех проектов из глобального индекса видны; запуск сессии чужого
  проекта идёт с cwd того проекта; новая работа всегда создаётся в cwd харнесса.
- В деталях показываются непрочитанные и последние 5 прочитанных входящих;
  исходящие не показываются.
- Код выхода различается только текстом, не глифом.
