# A44c — после возврата из фона лента доезжает до конца на глазах: расследование

Сессия s-252 (Opus, исследователь), лид s-174. Ветка `parley/w-0054/s-252`, код = `feat/mobile-a40-a43` @ ac1433a2
(сборка, которая у человека на iPhone). Договор — D1 §9.2 «Прокрутка», ревизии A44 и A44b; план, разделы A44 и A44b.

Жалоба человека: после ухода Parley в фон и возврата открытый чат «висит секунд 30, пока сам докручивается до конца».
Ожидание: как при первом открытии после A44b — последнее сообщение сразу, без видимой прокрутки.

Коротко. Нашлись три механизма; первые два — у человека, третий — при переподключении моста на Маке.

1. **Всплеск строк при перечитывании идёт путём «живого роста».** В фоне подписка снята, и всё, что агент сделал за это
   время, приходит одним `feed.loaded` (в комнате — одним `room.loaded`). Список уже показан и не прижат, поэтому рисует
   новые строки пачками по 10, а контроллер на каждую пачку даёт **анимированную** прокрутку к концу. Анимация всё время
   отстаёт, лента едет на глазах, к концу прыгает только повтор через 80 мс после последней пачки. Время растёт с числом
   новых строк; у работающего агента идущий ход не сворачивается, и каждый вызов инструмента — своя строка.
2. **Погоня срывает сама себя.** iOS присылает `onMomentumScrollEnd` за каждую анимацию, которую перебила следующая, а
   `momentumEnded` при этом снимает защиту «своей прокрутки» уже у новой, ещё летящей анимации. Если между ростами прошло
   больше 150 мс (окно эха роста) — например, пока поток JS занят рендером `feed.loaded`, — первый же кадр анимации вдали
   от конца засчитывается как позиция человека: `atBottom = false`. Дальше лента никуда не ведётся и встаёт не у конца.
3. **Смена эпохи размонтирует список.** `bridge.status` с новой эпохой обнуляет снимок, экран сессии и экран комнаты
   уходят в скелетон, `FlatList` размонтируется. Новый список монтируется уже **видимым** (раскрытие — раз за открытие),
   со смещением 0: человек видит верх окна, потом ту же погоню (1), которая может сорваться (2). Наверху ещё и срабатывает
   `onStartReached` и расширяет окно на 30 строк.

Реальный путь «Мак + реле + телефон» не запускался: пара симулятора с Маком человека требует его согласия (решение лида,
m-3342). Всё ниже — повтор точных последовательностей стора на симуляторе (DEMO) и повтор `remote-client` с настоящими
таймингами повторов. Число «30 с» по величине не воспроизведено: в симуляторе погоня длится 0,5–2,2 с на 60–213 строк;
время пачки на iPhone не измерено.

## Как воспроизводил

- **Симулятор.** Свой iPhone 17 Pro, iOS 27.2, Metro на 8107, `PARLEY_MOBILE_DEV_DEMO=1`. Нативный dev-клиент взят из
  сборки s-251 (тот же Expo SDK 58; в нём лишние нативные модули A47, JS ac1433a2 их не трогает). После прогона
  устройство удалено.
- **Последовательности стора — как в коде, не придуманные.** Возврат из фона: `feed.reload` (так делает
  `live.ts:357` при уходе в фон), через 3 с `feed.loaded` со свежей JSON-копией элементов (как ответ `feed.snapshot`),
  с 0, 3 или 61 новой строкой. Смена эпохи: `bridge.status` с новой эпохой (`reducer.ts:247-254`), через 1,5 с `snapshot`,
  ещё через 1 с `feed.loaded`. Комната: `room.reload` → `room.loaded` с 60 новыми письмами.
- **Ленты.** `a44-session-big`: 80 ходов, 322 свёрнутые строки, окно 30. Перед «ростом окна» — 150 новых строк при
  открытом экране (якорь окна выбран при открытии, рост входит в окно). Комната `a44-room-big`: 300 писем.
- **Наблюдение.** Временные `console.log` с отметкой времени в мс на `onContentSizeChange`, `onScroll`,
  `onMomentumScrollBegin/End`, вызов `scrollToEnd` и смену `atBottom`; видео `simctl io recordVideo`, кадры через
  100–200 мс. Временный код не закоммичен.
- **`remote-client`.** Скрипт с настоящими `createLiveSync` и `createRemoteStore` из `dist`, виртуальное время, подставной
  `rpc` со сценариями сокета (жив, мёртв до пробы, снят таймером фона, таймаут снимка).

## Корень

### 1. Всплеск при перечитывании идёт путём «живого роста»

- При уходе в фон подписка снимается и запись ленты помечается к перечитыванию (`packages/remote-client/src/live.ts:352-358`).
  Мост больше не шлёт `feed.changed`; всё накопленное приходит одним `feed.loaded` (`reducer.ts:367-381`) после возврата.
  Для комнаты — одним `room.loaded` (`live.ts:363`, `reducer.ts:296-303`).
- Идущий ход не сворачивается: тело хода без `turn` выводится строкой на элемент (`packages/mobile/src/feed/fold.ts:152`).
  У ведущей сессии, которая минуту-две работала без человека, это десятки строк.
- Окно хвоста этот всплеск не режет: якорь выбран один раз при открытии (`use-tail-window.ts:12-14`), новое внизу входит
  в окно целиком.
- Список показан, поэтому рисует по 10 строк за пачку: `maxToRenderPerBatch={hiddenFeed ? WINDOW_ROWS : 10}`
  (`src/app/session/[ref].tsx:503`, `src/app/room.tsx:389`).
- Прижатие кончилось через 500 мс тишины после открытия (не позже 3 с), и рост у человека внизу даёт анимированную
  прокрутку: `issue(following, now, first || following.pinned ? 'instant' : 'animated')` (`follow-end.ts:115`). Каждая
  пачка перебивает предыдущую анимацию; к концу приводит только повтор `settle` через 80 мс после последней пачки
  (`follow-controller.ts:38-46`).
- Длительность ≈ (новых строк / 10) × время пачки. В симуляторе пачка 80–105 мс; на iPhone не измерено.

Первое открытие от этого защищено правилами A44b: список скрыт, прижат (прокрутки мгновенные) и рисует по 30 строк. На
перечитывание ни одно из этих правил не распространяется.

### 2. Погоня срывает сама себя: `momentumEnded` снимает защиту новой прокрутки

- iOS присылает `onMomentumScrollEnd` за программную анимацию и тогда, когда её перебила следующая: в прогоне 3 каждое
  новое `scrollToEnd` сопровождалось `momentumEnd` предыдущей анимации через 7–8 мс, с `toEnd` 1211…2999.
- `follow-end.ts:197`: `if (own(s, now) && !s.momentum) return { state: { ...s, ownUntil: 0 } … }` — защита своей прокрутки
  снимается целиком, хотя новая анимация ещё летит.
- Пока высота растёт чаще чем раз в 150 мс, кадры прикрывает эхо роста (`follow-end.ts:171`, `GROWTH_ECHO_MS = 150`).
  Когда пауза дольше (рендер `feed.loaded` занял 159 мс; на телефоне пачки медленнее), кадр анимации вдали от конца
  оценивается как позиция (`follow-end.ts:172`) — `atBottom = false`.
- После этого `keepEnd` у повтора ничего не делает (`follow-end.ts:213-215`), рост не ведётся (`follow-end.ts:111-117`),
  лента стоит не у конца. Вернуть «внизу» может только кадр, который случайно окажется в 80 pt от конца, или «Jump to
  latest». На телефоне, где пачки медленнее 150 мс, этот срыв вероятен и при обычном возврате (на устройстве не проверено).
- Поведение закреплено тестом `follow-end.test.ts:193` «the momentum end of our own scroll only clears the flag».

### 3. Смена эпохи размонтирует список

- Эпоха — `${bootId}:${n}` моста: меняется при перезапуске моста и при переподключении моста к хосту
  (`packages/remote/src/host-link.ts:254`), то есть при перезапуске или обновлении Parley на Маке. Тогда
  `reducer.ts:247-254` ставит `snapshot: null`, а элементы лент оставляет с комментарием «элементы прежние на экране до
  нового снимка».
- Экран этим не пользуется: на `state.snapshot === null` экран сессии возвращает скелетон (`[ref].tsx:295-297`), комната —
  `room.tsx:318`. `FlatList` размонтирован. Контроллер и окно живут в компоненте выше раннего `return` и переживают это:
  `revealed = true` (раскрытие раз за открытие, `follow-controller.ts:28`), `hadRows = true`, `pinned = false`.
- Новый `FlatList` монтируется видимым (`hiddenFeed = false`, `[ref].tsx:213`), смещение 0 — человек видит верх окна.
  Окно — все строки от якоря первого открытия, по 10 за пачку, погоня анимированная (п. 1) и может сорваться (п. 2).
  Наверху срабатывает `onStartReached` (`[ref].tsx:505`, `room.tsx:392`) и расширяет окно ещё на 30 строк (в логе `start`
  292 → 262).

### Был ли у человека путь 3 — нет

Журнал моста человека `~/.parley/remote/bridge.log`: последняя смена эпохи — `host.connected`, эпоха
`dfe530fc20d2de8f:2`, 2026-11-03T17:52:55Z; новых записей после 2026-11-03T18:16Z нет. Сборка ac1433a2 — 2026-11-03T23:41:59Z.
Телефон после неё подключался 2026-11-04T05:33:28Z и 06:21:47Z (`audit.jsonl`, `kind: connect`) и писал s-38 и s-231.
Значит, утренние возвраты шли без смены эпохи — путём 1, возможно с срывом 2. Путь 3 — это «переподключение моста» из
брифа, отдельный случай.

### Гипотезы лида

- **H1** (смена эпохи → скелетон → перемонтирование, раскрытие раз за открытие) — подтверждена как механизм (п. 3), но к
  обычному возврату из фона не относится: эпоха при нём не меняется (журнал моста выше).
- **H2** (снимок приходит поздно) — частично. Пока ждём, ничего не двигается: старый хвост, статус `loading`/`error`.
  Сама задержка не прокручивает, но удлиняет «висит». Повтор `remote-client`, время от возврата до `feed.loaded`
  (подписка 150 мс, снимок 400 мс, проба `ping` 3 с — `supervisor.ts:451`):

  | Сценарий | `feed.loaded` |
  | --- | --- |
  | S1. Сокет жив | 0,55 с |
  | S2. Сокет мёртв, проба 3 с, переподключение 0,6 с | 4,55 с (готовы в 3,6 с, но ждём повтор через 1 с: `live.ts:79`) |
  | S3. Сокет мёртв, переподключение 2,5 с | 6,05 с |
  | S4. Фон > 30 с, связь снята таймером, переподключение 1,5 с | 2,05 с |
  | S5. Сокет жив, `feed.snapshot` один раз упёрся в таймаут 15 с (`rpc.ts:6`) | ~16 с |
  | S6. То же дважды (паузы 1 с, 2 с) | ~33 с |

  Паузы 5/10/30 с нужны только при череде временных отказов. Реальный риск — таймаут снимка большой ленты: до 4 МиБ
  (`FEED_MAX_BYTES`, `packages/host/src/feed/feed-service.ts:88`), расшифровка и разбор в JS телефона. Не измерено.
- **H3** (что-то при возврате снимает «внизу») — подтверждена в другой форме: снимает не событие iOS при возврате, а сама
  погоня (п. 2). Событий раскладки, клавиатуры или safe area при возврате в повторе не было; обложку замка и Face ID
  симулятор в DEMO не показывает — не проверено.

## План исправления (для исполнителя)

### Поведение

- Возврат из фона, переподключение и переподписка — любое перечитывание ленты сессии или комнаты: человек, который был у
  конца, видит последнее сообщение сразу. Первый кадр после перечитывания — либо конец, либо скелетон ленты; показ не
  позже 600 мс (правило A44b), без видимой прокрутки.
- Перечитывание приносит не больше одной пачки (≤ 10 новых строк): список не прячется, конец догоняется мгновенной
  прокруткой.
- Человек был не у конца: позиция не трогается (её держит `maintainVisibleContentPosition`), новые строки считаются в
  «Jump to latest».
- Перемонтирование списка (смена эпохи и любое другое) у человека внизу — как первое открытие: скрыт, окно последних 30
  строк, прижатие, показ ≤ 600 мс.
- Живой рост по одной-две строки — как сейчас.

### Изменения

1. **`packages/mobile/src/feed/follow-end.ts`** — чистые функции:
   - `reread(s, now, keys)`. Если `!s.atBottom` или палец/инерция человека — состояние без прокрутки, `away` по
     `countAfter`. Иначе `fresh` — строк после `s.seenKey` (`null`, если якорь пропал, например ход свернулся). При
     `fresh !== null && fresh <= REREAD_INSTANT_ROWS` (10, одна пачка): снова прижать — `pinned: true`, `openedAt` и
     `lastGrowthAt` = `now`, `seenKey` — последний, `away: 0`. Рост тогда идёт мгновенной прокруткой
     (`follow-end.ts:115`), прижатие кончится по обычным 500 мс. Иначе — «переоткрыть»: `{ ...open(), layoutHeight:
     s.layoutHeight, seenKey: последний }` и признак `reopen: true`.
   - `remounted(s)`: у человека внизу — то же «переоткрыть»; не внизу — состояние как есть (позицию через
     перемонтирование не сохранить, сейчас она теряется так же).
   - `momentumEnded` (`follow-end.ts:197`): конец инерции во время своей прокрутки больше не обнуляет `ownUntil` — он истекает
     сам через `OWN_SCROLL_MS`. Уход вверх вдали от конца по-прежнему считается сразу (`follow-end.ts:170`, правило N6).
   - `scrolled`: движение **вниз** (смещение не уменьшилось) без пальца у человека внизу `atBottom` не снимает: человек
     уходит от конца только вверх. Это закрывает срыв п. 2 без опоры на тайминги.
2. **`follow-controller.ts`** — `reread()` и `remounted()`. При «переоткрыть»: сбросить таймеры прижатия, показа и
   повтора; `commit` должен уметь переход `revealed` true → false — новый вызов `io.onConceal()` (или `onReveal` с
   булевым аргументом).
3. **`use-follow-end.ts`** — отдать `reread`, `remounted`; `onConceal` → `setRevealed(false)`; сообщить экрану, что
   было «переоткрыть» (возврат функции или колбэк), чтобы экран сбросил окно.
4. **`use-tail-window.ts`** — `reset()`: якорь снова `TAIL`. На следующем рендере окно — последние 30 строк (с границей
   блока), эффект `use-tail-window.ts:12-14` закрепит новый якорь. Ранние строки вернутся через `onStartReached`, как
   при первом открытии.
5. **`src/app/session/[ref].tsx` и `src/app/room.tsx`:**
   - Перечитывание: помнить прошлый статус записи (`feed.status` / `roomChats[...].status`). Переход в `ready` из
     `loading`, `error` или `stale` при уже показанных строках → `follow.reread()` в `useLayoutEffect` до отрисовки; при
     «переоткрыть» там же `reset()` окна. Хуки ставить выше ранних `return` (порядок хуков).
   - Перемонтирование: `ref`-колбэк `FlatList` видит новый экземпляр после первого → `follow.remounted()` и при
     «переоткрыть» `reset()` окна.
6. **`packages/remote-client/src/live.ts:352-358`** — при уходе в фон или обрыве помечать открытые комнаты `room.reload`,
   как ленты помечаются `feed.reload`. Сейчас перечитанная комната остаётся `ready` (`live.ts:363`), и экран не отличит
   перечитывание от письма. `room.tsx` смотрит на `status` только для пустой ленты (`room.tsx:136`, `room.tsx:416`).

Отклонённый вариант для п. 3: не размонтировать список при `snapshot === null`, а рисовать экран по последнему найденному
снимку. Так сохраняется и позиция человека, который был не у конца. Цена — экран на время `starting` хоста рисуется по
устаревшему снимку (заголовок, команда, «⋯»). Выбрал «переоткрыть при перемонтировании»: меньше кода, одинаково для обоих
экранов, ведёт себя как первое открытие. Решение за лидом.
