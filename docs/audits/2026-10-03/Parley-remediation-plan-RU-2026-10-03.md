# Parley: план решений по результатам доказательного аудита

Дата: 3 октября 2026. Тип: проект технических решений, без реализации.

## 1. Что предлагается сделать

Сохранить нынешнюю архитектуру Parley: native CLI вендоров, локальный host, MCP, комнаты и Electron UI. Для исправления подтверждённых дефектов не нужны собственный model gateway, новый агентный фреймворк или перенос всего состояния в базу данных. Нужны более строгие контракты на границах существующих модулей: жизненный цикл процесса, привязка vendor session, адресация, доставка, полномочия и размер передаваемого контекста.

Первый выпуск исправлений должен обеспечить пять результатов: удаление не выходит за выбранную работу; черновик сохраняет адресатов; процесс не остаётся неучтённым после ошибки запуска; Stop имеет проверяемый результат; resume никогда автоматически не выбирает чужую беседу. Следом — разделение доверенных инструкций и агентных данных, восстановление после аварий, ограничения fanout и компактные ответы. Navigator и память развивать после измеримой телеметрии и точного определения доступных native skills.

План покрывает 55 исходных обозначений из основного отчёта и приложений. Это не 55 независимых дефектов: многие ID описывают один механизм. Они сгруппированы в 29 пакетов A01–A29. Будущие возможности отдельно описаны в F01–F05; их отсутствие не считается дефектом уже поставленного продукта. В конце дана полная матрица покрытия, включая вторичные UX/QA/документационные замечания.

Блокер для доказательства vendor-поведения остаётся прежним: живые агентные прогоны в этой задаче запрещены. Можно спроектировать и выполнить безопасные fixture/contract tests, но нельзя честно объявить подтверждёнными доставку инструкций реальной модели, эффективность prompt caching или итоговую экономию токенов только по argv и заглушкам. Отдельный live acceptance gate описан в A27; он потребует нового явного разрешения и бюджета. Для составления этого плана такой прогон не выполнялся.

### Приоритет и размер

P1 — исправить до длительной автономной работы или демонстрации затронутой гарантии. P2 — обязательное повышение надёжности и предсказуемости следующими небольшими выпусками. P3 — улучшение продукта или дополнительная защита по условиям использования. Приоритет относится к предлагаемому порядку реализации; исходная оценка сохранена в матрице. Например, fanout в основном отчёте R9 был P2, в приложении O3 — P1; здесь выбран P1 для автономного режима.

Размер относительный: S — локальная граница/небольшое число модулей; M — согласованное изменение core/host/UI или адаптера; L — изменение состояния, восстановления и совместимости нескольких подсистем. Это не оценка календарных сроков. Риск — вероятность регрессии от изменения, а не тяжесть исходной находки.

## 2. Общие правила реализации и миграций

1. Сначала записать инвариант и воспроизводящий дефект тест, затем минимально изменить соответствующую границу. Не переносить весь проект на новую архитектуру ради одного контракта.
2. Состояние работы версионировать. Новые поля сначала сделать читаемыми с безопасными значениями для старых карт. Если старый writer может потерять новые поля, host/MCP должны проверять минимальную write-версию и отказать с понятным сообщением о несовместимости. Нельзя рассчитывать, что старый процесс сохранит незнакомое состояние.
3. Миграция выполняется одним владельцем под блокировкой, атомарно, с локальной резервной копией и проверкой схемы до замены. Не мигрировать автоматически неизвестные/повреждённые данные. Отдельный recovery preview показывает, что будет восстановлено или удалено. Не закрывать чужие активные процессы ради миграции молча.
4. Для новых API добавить operationId, стабильные коды ошибок, work/session/room ID и revision там, где важен порядок. Повтор того же operationId с тем же содержимым возвращает прежний результат; с другим содержимым — conflict. Это предотвращает повтор операции, но не даёт «ровно один раз» для рассуждения модели.
5. Старые интерфейсы поддерживать только там, где это безопасно. Потенциально опасное неявное поведение — чужой resume, обход Stop, перемещение чужого ведущего — лучше отклонять с объяснением, чем сохранять ради совместимости.
6. Не смешивать три разных факта: процессу напечатали указатель; агент забрал сообщение; агент выполнил задачу. UI и метрики должны обозначать каждый факт отдельно.
7. Новые лимиты вводить на ресурс и действие, а не по числу строк. Начальные численные пороги в плане — кандидаты для нагрузочного теста, не доказанные оптимальные значения и не обещание экономии.
8. Сохранить полезные свойства текущего решения: запуск native CLI без shell-склейки, собственные login/trust вендора, защищённый host token, revision проверки proposal, dirty-buffer/merge guards и ручной terminal fallback.

## 3. Решения для существующего кода

### A01. Ограничить удаление реальной зарегистрированной работой

Покрытие: R1, S1. Приоритет P1; размер S–M; риск средний. Зависимости: нет.

**Инвариант.** Любой destructive core API способен удалить только зарегистрированный каталог конкретной работы внутри её state root. Ошибка чтения карты не является разрешением удаления.

**Минимальное решение.** Ввести общий валидатор WorkId/SessionId на protocol и core границах; принимать текущий реальный формат ID, запрещать разделители, абсолютные пути, пустые значения и traversal. В deleteWorkFiles независимо от входного валидатора проверить принадлежность записи известному проекту, вычисленный путь, canonical containment и отсутствие нежелательного symlink-перехода. Не считать startsWith достаточной проверкой границы пути. Отдельно обрабатывать «работа отсутствует», «карта повреждена», «работа занята». Удаление повреждённой записи — отдельный явный recovery action с preview.

**Модули/API.** packages/protocol/src/methods.ts:35; packages/host/src/methods/works.ts:30–37; packages/core/src/work/store.ts:58,202. Схема ошибки: INVALID_ID, UNKNOWN_WORK, CORRUPT_WORK, WORK_BUSY, PATH_OUTSIDE_STATE. Проверка обязательна и при прямом вызове core, не только IPC.

**Совместимость.** Корректные ID остаются прежними. Legacy запись, не проходящая новый формат, требует подтверждённого соответствия registry → canonical path; не переименовывать автоматически. Проверки lstat/realpath и повторная проверка перед удалением снижают риск подмены, но не являются полной защитой от враждебного same-UID процесса, меняющего файловую систему конкурентно.

**Приёмка.** Пропустить через реальную schema/handler допустимый ID, неизвестный ID, ../, абсолютный путь, пустую строку, повреждённую карту, symlink ancestor и похожий префикс каталога. В собственном временном sandbox sentinel-сосед остаётся целым во всех отказах; допустимая work удаляется; отказ чтения никогда не переходит к recursive rm. В тестах исключить любые пути за пределами fixture root.

### A02. Восстанавливаемые блокировки карты и индекса

Покрытие: R3, O1. Приоритет P1; размер M; риск высокий из-за конкурентности. Зависимости: общий формат состояния.

**Инвариант.** Авария писателя не блокирует будущие записи навсегда; живой владелец никогда не теряет свою блокировку из-за чужого recovery.

**Минимальное решение.** Сохранить файловую модель, но записывать уникальный owner token, PID, идентификатор старта процесса/boot и время приобретения. На EEXIST проверять владельца, а не только возраст файла. Восстановление должно иметь отдельную атомарно захватываемую recovery-блокировку; конкурентные acquirer обязаны учитывать её. После захвата повторно проверить идентичность старой блокировки и смерть владельца. Release удаляет только lock с собственным token. Точно выбранный алгоритм описать как небольшой протокол и проверить interleaving-тестами; недостаточно добавить unlink после timeout. Если в используемом runtime доступен надёжный OS advisory lock, сравнить его с этим протоколом, не вводя зависимость без необходимости.

**Модули/API.** packages/core/src/work/store.ts:110–139,237–247,389–405; ориентир существующего recovery владельца host: packages/host/src/host.ts:406–465. Один механизм для map.lock и works-index.lock, единый порядок захвата. Если map уже записана, а индекс не обновлён, индекс должен безопасно перестраиваться как производное состояние, а не превращать успешную запись в неизвестный результат.

**Совместимость.** Старый пустой lock не содержит доказательства смерти владельца. Его автоматическое удаление при работающих старых writers небезопасно: нужен режим восстановления после их остановки/проверки, с диагностикой. PID без времени старта недостаточен из-за повторного использования PID. Не применять TTL как доказательство смерти.

**Приёмка.** SIGKILL собственного тестового писателя отдельно на карте и индексе; следующий writer восстанавливает работу. Живой медленный writer не вытесняется. Два recovery одновременно не создают двух владельцев. Старый release не снимает новый lock. Crash между записью map и индексом устраняется rebuild без потери map. Все проверки только в disposable state.

### A03. Запуск процесса как восстанавливаемая операция

Покрытие: сопутствующий R3, O2, вторичное замечание о частичном создании команды. Приоритет P1; размер L; риск высокий. Зависимости: A02; согласование с A04, A11.

**Инвариант.** После завершения launch известно одно из двух: процесс зарегистрирован и управляем, либо созданный этой попыткой процесс остановлен и его ресурсы очищены. «Ошибка пользователю, живой неучтённый PTY» недопустима.

**Минимальное решение.** Перед pty.start сохранить launchAttempt с attemptId, sessionId, launch generation, effective cwd/profile и состоянием prepared. Затем запустить процесс, записать его identity и состояние committed. При неудаче фиксации остановить именно полученный handle/принадлежащую попытке process group, дождаться выхода и снять hook/PTY registrations. Cleanup должен быть awaitable и идемпотентным. Возвращать operation result с идентификаторами уже созданных объектов даже при частичном отказе команды. Не удалять успешно работающих участников молча.

**Модули/API.** packages/host/src/sessions/sessions-service.ts:303–330,168–185; packages/core/src/work/launch.ts:478–499; auto-launch.ts:16–29; соответствующие session-create/room-create ответы protocol. Можно оставить нынешний lifecycle и добавить optional launchAttempt, не вводя сразу новый глобальный state machine.

**Совместимость.** Старые pending записи считать legacy/неизвестного происхождения. При рестарте не запускать автоматически все pending: показать recovery выбор с доказательством последней попытки. Перезапуск процесса — новая попытка с отдельным бюджетом, не невидимый retry. Для аварии между spawn и commit понадобится отдельная восстанавливаемая запись identity процесса; неизвестный PID нельзя убивать без проверки принадлежности и start time.

**Приёмка.** Fault injection до spawn, после spawn, при записи map, при регистрации hook, при cleanup и при рестарте host. Fake PTY доказывает stop+await-exit после commit failure. Тест с собственным безвредным subprocess доказывает отсутствие оставшегося процесса после отмены. Повтор operationId не запускает второй экземпляр. Частичный room-create возвращает список successes/failures и доступное действие продолжения.

### A04. Разделить Pause и Stop и поставить общий барьер действий

Покрытие: R4, O5, O7, часть UX-3 и R14. Приоритет P1; размер L; риск высокий. Зависимости: A03; A23 для UI.

**Инвариант.** После подтверждения паузы доставки не отправляется ни один ранее отложенный Enter. После подтверждённого Stop комнаты/работы не возникает новых Parley-mediated submit/resume/spawn до явного Resume. Закрытый caller не может мутировать работу.

**Минимальное решение.** Ввести generation/cancellation token на queued wake и launch. Перед набором и непосредственно перед Enter повторять guard; pause отменяет ожидающие попытки. Не стирать чужой ввод в терминале: если Parley уже напечатал свой указатель, отмечать его как отменённую попытку и очищать только при доказуемом владении буфером. Уже принятый моделью ход пауза не отменяет. Для Stop добавить устойчивое control state работы/комнаты с revision, закрыть новые admission, отменить queued операции, остановить принадлежащие цели PTY, дождаться результатов. MCP mutations проверяют live caller и control state под той же блокировкой, что и изменение. Чтения после close разрешить отдельным явным правилом.

**Модули/API.** wake-service.ts:366–409,653–663; pty/type-and-submit.ts:83–122; sessions-service.ts:456–464,508–559,582; core/mcp/tools.ts:168–171,600–625,773–778,847–875,978–1000. Новые room/work control методы возвращают per-session stopped/failed/unreachable и количество оставшихся in-flight действий.

**Совместимость.** Нынешний Pause назвать «пауза автоматической доставки»; individual Stop/Close сохранить с точной семантикой. Устойчивый Stop должен переживать restart, в отличие от текущего memory-only pause. Старые клиенты не могут обходить control guard. Ответ «остановлено» только после барьера; при частичном отказе показывать частичный результат. Native действия вне Parley остаются в границах разрешений CLI, см. A17.

**Приёмка.** Fake timers: pointer → pause → timer не порождает Enter. Конкурентные stop/spawn, close/send, stop/commit-launch не проходят за барьер. После restart работа остаётся остановленной. Проверить активного ребёнка и внука, зависший PTY, ошибку stop, пользовательский ввод и уже отправленный ход. Ни один тест не запускает настоящий агент.

### A05. Сохранять структуру черновика и адресатов без переинтерпретации

Покрытие: R2, UX-1. Приоритет P1 для маршрутизации; размер S–M; риск средний. Зависимости: нет; используется A06.

**Инвариант.** serialize → restore сохраняет одновременно текст, тип сегментов и recipients. Простой текст @s02 не становится адресатом только из-за remount.

**Минимальное решение.** Хранить versioned draft: segments(text|mention), recipientIds, roomId/workId. Chips — явная адресация; plain text остаётся plain text. Разбор typed/paste/restore должен иметь одну политику. Перед send строить to из структуры, показывать итоговый режим «всем / выбранным», валидировать существование адресатов. Исчезнувший участник даёт понятное требование пересмотреть адресацию, а не молчаливое расширение до broadcast.

**Модули/API.** packages/desktop/src/renderer/components/rooms/mention-editor.ts:34–64,119–136; Composer.tsx:107–114,129–135,159–163; renderer/store/ui.ts:224–232. Вынести encode/decode draft из DOM helpers в чистую функцию.

**Совместимость.** Legacy draft содержит только текст, поэтому прежние chips восстановить достоверно нельзя. Без сохранённых recipients безопаснее восстановить обычный текст и показать, что адресатов следует выбрать заново, чем угадывать их из @. Не отправлять такой черновик автоматически; не менять ранее отправленные сообщения.

**Приёмка.** Регрессия из аудита «Всем: @s02 проверит API, остальные пишут тесты» остаётся broadcast после remount. Смешанный chip+plain mention не меняет получателей. Проверить paste, смену комнаты, повторное открытие приложения, удалённого участника, send failure и несколько одинаковых mentions.

### A06. Отделить исходящие сообщения от нового черновика

Покрытие: R14, UX-2. Приоритет P2, рядом с A05; размер M; риск средний. Зависимости: A05; idempotency на rooms.send.

**Инвариант.** Текст отправленного пользователем сообщения остаётся доступен до подтверждения сохранения сервером или явного удаления пользователем. Новый draft не затирается при отказе старого send.

**Минимальное решение.** Перед очисткой composer перенести typed payload в устойчивый outbox с clientMessageId и состоянием queued/sending/failed/committed. Host rooms.send дедуплицирует по work+sender+clientMessageId и проверяет digest содержимого. После ошибки показывать Retry/Copy/Edit отдельно от текущего draft. После потери ответа запрос статуса/повтор того же ID возвращает тот же messageId. Для native Chat send, где нет такого idempotent vendor API, не обещать безопасный автоматический resend: сохранить текст и состояние «доставка неизвестна», предложить ручную проверку.

**Модули/API.** Composer.tsx:155–164; renderer/store/ui.ts:224–232; chat/ChatView.tsx:192–207; protocol rooms.send и core messages. Подтверждение означает сохранение сообщения, не получение/исполнение агентом.

**Совместимость.** Новый optional clientMessageId сначала допускается для старых клиентов, но гарантированный Retry доступен только новым. Outbox scoped по work/room; при удалении работы требуется обработать несданные тексты в UI. Не восстанавливать старое A поверх набранного B.

### A12. Развести получение сообщений, подтверждение и выполнение

Покрытие: R10, O6; вторичное замечание об однократном pointer. Приоритет P2, до долгих автономных цепочек; размер L; риск высокий. Зависимости: A04, A13, A14.

**Инвариант.** Потеря ответа check_inbox не уничтожает возможность повторно получить то же поручение. Повтор уведомления не означает разрешение повторно выполнить уже завершённую операцию.

**Минимальное решение.** check_inbox выдаёт стабильную ограниченную пачку с receiptId/message IDs/cursor; не помечает её обработанной до ack_inbox. Повтор незавершённого receipt возвращает ту же пачку. Хранить отдельно announced, fetched, acknowledged; task completion — самостоятельный report, а не синоним ack. Показать человеку непродвинувшиеся receipts. Wake повторяет только безопасное уведомление по backoff и бюджету; при пользовательском вводе/blocked не вводит Enter повторно, а переводит попытку в needs-attention с ручным Retry. Мутации по поручению используют operation IDs, чтобы повторная доставка не повторяла spawn/proposal автоматически.

**Модули/API.** core/mcp/tools.ts:825–834,1119–1125; work/delivery.ts:112–114; host/wake/wake-service.ts:392–433. Message delivery metadata per-recipient; receipt принадлежит caller и фиксированной пачке. Срок lease управляет повторной выдачей, не удалением сообщения.

**Совместимость.** Старый check_inbox read semantics не менять незаметно для активной старой сессии. Новый contract version/инструмент и bootstrap объявляют ack. Legacy read flags сохраняются как historical fetched, не как доказательство обработки. Не переотправлять массово всю старую историю при миграции; replay доступен явно. At-least-once visibility допустима; exactly-once рассуждения и исполнения модели не обещается.

**Приёмка.** Разорвать synthetic MCP transport после записи receipt до ответа; retry возвращает те же IDs. Повтор ack идемпотентен, чужой receipt отклонён. Crash между fetch/ack, lease expiry, manual input и blocked не теряют текст и не создают бесконтрольный wake loop. Статусы UI соответствуют наблюдаемым событиям.

### A13. Фиксировать получателей broadcast в момент отправки

Покрытие: R10, O4; часть T1/O8. Приоритет P2; размер M; риск средний. Зависимости: нет; согласовать с A12/A15.

**Минимальное решение.** Хранить recipientIds, audienceKind и membershipRevision при send. Для broadcast развернуть текущий состав один раз под lock. ### A14. Ограничить контекст и транспорт без переписывания всего storage

**Приёмка.** Создание команды из двух новых членов запускает ровно два запрошенных CLI, а создание пустой work — ноль. Включение существующих подходящих sessions не дублирует процессы. Клавиатурный путь делает тот же transfer с теми же guards. Один неуспешный provider не скрывает успешно созданные записи. Tests используют stubs, не настоящие CLI.

### A26. Сделать тестовый gate детерминированным и полным по доступным слоям

Покрытие: QA-V2, QA-V3; инженерное качество основной части. Приоритет P2; размер M; риск низкий–средний. Зависимости: A03/A28 для lifecycle dispose.

**Инвариант.** Завершение теста означает завершение его subprocess/finalizers/watchers. Type assertions действительно type-checkятся. Зелёный статус после retry не скрывает первый провал.

**Минимальное решение.** В cli-work tests immutable fixture context на каждый тест; execFile с AbortSignal/ограничением времени, tracking принадлежащих тесту процессов и ожиданием close. Vitest timeout не считать отменой процесса. В SessionsService expose dispose/idle barrier, который дожидается finishExited и watcher cleanup; afterEach удаляет tmp только после него. Заменять произвольные sleeps наблюдаемыми событиями/fake clocks там, где это действительно таймерная логика. Причину core timeout исследовать с instrumentation: каскад из-за mutable globals в аудите — сильная гипотеза, не окончательно доказанный порядок событий.

**Модули/API.** core/src/cli-work.test.ts:16–19,37–47,70–104; host/src/sessions/sessions-service.test.ts:117–122,627–637; sessions-service.ts:168–185; .github/workflows/ci.yml:56–60; test tsconfig/Vitest конфигурация; desktop E2E setup.

**CI/совместимость.** Добавить отдельный noEmit test typecheck для expectTypeOf/типовых assertions; не включать тесты в production emit. Electron E2E на контролируемом runner с подставными CLI и запретом network/model execution. Закрепить Node/pnpm и чистый frozen install, исключить унаследованные @harnas symlinks. Отдельно публиковать first-pass failure и flake rate; временный quarantine только с owner/issue и ограниченным перечнем, не blanket retry как доказательство качества.

**Приёмка.** Намеренно неверный type assertion ломает gate. Timeout subprocess не оставляет процесс и не меняет следующий fixture ID. Уборка temp не пересекается с finishExited. Целевые flaky tests повторно выполняются в изолированных условиях до устранения причины; вся suite не гоняется бесконечно без нового сигнала. E2E PATH ведёт только на stubs, окружение HOME/config и project dirs временные, safety guard проверяет root до destructive setup/teardown.

### A27. Контрактная матрица вендоров и отдельный live acceptance gate

Покрытие: QA-V1; внешняя проверка Vendor-V1–V7; критерии продукта. Приоритет P1 как пробел доказательств, не автоматически P1-дефект поведения; размер M; риск низкий offline/управляемый live. Зависимости: A07–A10, A23/A24.

**Инвариант.** Для каждой поддержанной версии явно разделены: утверждение официальной документации, безопасная локальная проверка CLI/parser, fixture проверка Parley и наблюдение настоящей сессии.

**Минимальное решение.** Compatibility manifest закрепляет CLI version range и требуемые возможности. Offline suite использует безопасные --version/--help/config-schema только после проверки команды; fixtures native logs/notify/MCP metadata не должны содержать пользовательские secrets. Проверять build args для fresh, quiet child, resume, custom home, permissions и missing/unsupported flags. Матрица «не проверено» — допустимый честный результат.

**Отдельный live сценарий, только с новым разрешением.** Маленький disposable Git project и заданные максимумы turns/launches/usage. Сначала один Claude и один Codex; затем одна смешанная команда: общая задача, DM и broadcast, уточнение посреди работы, proposal/rework/accept, stop/resume, финальный review package. Проверить initial/quiet/resume instruction markers, authoritative binding, отсутствие extra sessions/повторных поручений и сохранность human constraints. Human controls остаются доступными. В отчёте сохранить обезличенные transcript excerpts и измерения, а не только «модель ответила OK».

**Модули/основания.** TODOS.md:30–82; desktop/e2e/codex.spec.ts:14–17; e2e/global-setup.ts:51–54; vendor adapters и version probes. В срезе аудита безопасно наблюдались Claude 2.1.287, Codex 0.156.1; это не автоматически будущая support matrix.

**Совместимость и риск.** Новый CLI version автоматически не объявляется поддержанным по совпадению имени команды. Contract mismatch отключает затронутую оптимизацию/функцию с понятным fallback, а не весь terminal. Live gate не запускается в обычном CI и не расходует подписку без согласования. Нельзя проверять отсутствие task loss одним вопросом «ты понял?»: нужны проверяемые outputs/operation records.

**Приёмка.** Release checklist содержит заполненные клетки и evidence refs. Различить «offline pass», «live pass», «unsupported», «not run». Зафиксировать лимит и фактический расход каждого разрешённого live прогона. Настоящий cache эффект и сохранение system policy требуют наблюдения соответствующего пути; argv test подтверждает только построение аргументов.

### A28. Отменять wait_for и освобождать наблюдателей

Покрытие: вторичное замечание оркестрации, TODOS.md:194–200. Приоритет P2; размер S–M; риск низкий–средний. Зависимости: A04/A26.

**Инвариант.** Отмена MCP request, close session или shutdown host прекращает принадлежащие запросу watch/timer и не оставляет их ждать до 30 минут.

**Минимальное решение.** Протянуть request AbortSignal из MCP extra.signal через wait_for к watch-map, race ожидание с abort, cleanup в finally, исключить повторный resolve после cancel. Session lifecycle disposer владеет зарегистрированными waits; close/shutdown вызывает cancel+await cleanup. Проверку текущего состояния и подписку выполнить без окна потери события — snapshot/revision перед и после subscribe либо общий read/watch primitive.

**Модули/API.** core/mcp/tools.ts обработчик wait_for; work/watch-map и связанные timers; host lifecycle dispose. В исходном аудите отсутствие cancellation integration установлено чтением/TODO; новый resource leak под реальной нагрузкой не измерялся.

**Совместимость.** Нормальный long wait продолжает работать; отмена возвращает стандартный cancellation result без ложного task failure. Timeout — отдельный результат, не завершение задачи. Никаких новых фоновых polls или model turns.

**Приёмка.** Сотни synthetic wait→cancel возвращают число watchers/timers/file handles к baseline. Event одновременно с cancel даёт ровно одно завершение. Close во время ожидания освобождает ресурс; shutdown await действительно дожидается cleanup. Event между первым read и subscribe не теряется.

### A29. Свести документацию и диагностику к проверяемым контрактам

Покрытие: O8, T1; документационные разделы основного и всех приложений; secondary observability. Приоритет P2; размер M; риск низкий. Зависимости: проходит через остальные пакеты, не ждёт их полного завершения.

**Инвариант.** В README/guide/tool descriptions/UI одна семантика, а статус «реализовано» не смешан с TODO, WIP и live verified. Диагностика объясняет переходы без копирования всей переписки.

**Минимальное решение.** Исправить обещание «seen only by those named» в core/work/guide.ts:141–143: в нынешней trusted project room адресат определяет inbox/wake, а не конфиденциальность. Компактный get_map A14 снижает лишнюю экспозицию, но это не доказательство полной privacy. Если private rooms понадобятся позднее, нужен полный access-control review всех history/search/export/map endpoints и файловой модели, а не скрытие UI. Добавить короткий contract index с invariants, source module, тестом, supported versions и status. Большие README/TODOS разбить по назначению без потери ссылок; закрытые TODO переносить в evidence/changelog, WIP specs маркировать отдельно. Не генерировать мегадокумент на каждый prompt.

**Наблюдаемость.** Структурированные события work/room/session/launchAttempt/deliveryReceipt/taskRevision/operationId; transition from→to, reason code, timestamp и outcome. Метрики queue depth, launch failures, stale locks, unacked age, stop barrier failures, snapshot bytes, budget rejection, binding ambiguity и active watcher count. Free text task/log bodies выключены по умолчанию; correlation IDs достаточно для большинства расследований. Диагностический export описывает completeness и redaction.

**Модули/API.** core/work/guide.ts:141–143; mcp/tools.ts:473–490,909–917; README/TODOS/specs; host service events, protocol errors и desktop attention. Формировать tool description/annotations из общей typed metadata там, где это устраняет реальное дублирование; не превращать документацию в дополнительный runtime слой.

**Совместимость.** Честное уточнение DM semantics не удаляет историю. Existing users получают краткую заметку о прежнем поведении и изменениях A13/A14. Наблюдаемость не должна увеличивать модельный контекст: технические события хранятся отдельно и извлекаются по запросу.

**Приёмка.** Для каждого публичного обещания есть реализующая проверка или явная пометка advisory/planned/unverified. Через IDs можно проследить send→receipt→wake→launch→report→review без раскрытия текста. Документирована native subscription/permissions модель без обещания правового одобрения, совместимости всех вендоров или гарантии трудоустройства.

## 4. Будущие capabilities, navigator и knowledge — отдельная дорожка

Это предложения к активным спецификациям, не список дефектов реализованного router. Работу других сессий не требуется начинать заново. Полезно согласовать с ними следующие интерфейсы до расширения реализации; в рамках этой задачи сообщения им не отправлялись.

### F01. Один resolver, разные представления каталога

Основание: A10/A22; docs/specs/2026-10-02-capabilities-design.md. Приоритет P2 после исправления scanner; размер M; риск средний.

Использовать один effective capability resolver для UI и navigator. UI может показывать human-invocable команды и установленное, но отключённое содержимое с явным статусом. Модельный поиск получает только model-invocable и доступное её provider/profile/worktree. Stable skill identity включает source/version hash; display name недостаточно. Для lead find_skill(for=sessionId) ищет именно каталог указанного участника и проверяет его существование/доступность, а не отдаёт lead каталог всех провайдеров.

Предлагаемый API: resolveCapabilities(sessionContext) → versioned snapshot; findSkill(query, targetSessionId?, limit) → bounded metadata и source refs. Body загружается native механизмом участника. Lead пересылает ID/path/hash и цель применения, а не полный текст skill всем агентам. Shared index живёт вне модельного контекста; его наличие не означает shared model cache.

Миграция: UI сначала переключается на resolver за feature flag, сравнение старого/нового результата сохраняется только диагностически. Принятие: disabled/чужие skills не предлагаются; разные worktree дают соответствующий каталог; смена версии инвалидирует index; native загрузка совпадает с найденным hash или сообщает об изменении.

### F02. Navigator как ограниченный локальный поиск

Основание: docs/specs/2026-10-03-skill-navigator-design.md; A09/A22. Приоритет P3 opt-in до измерений; размер M; риск средний–высокий из-за native contracts.

Сохранить предложенный локальный BM25 по name/description, default top-5 и cap-10, без отдельного LLM/router network call, embeddings и hook на каждый prompt. Ограничить query/result bytes; дать явный no-match. Для русского запроса основная модель может сформулировать английский query, но fallback должен быть ограничен одной корректирующей попыткой/локальными aliases, а не открытой цепочкой повторных запросов. Новое обычное «есть сообщения» не должно заново запускать подбор, если taskRevision не менялась и skill уже выбран.

Перед подавлением native skill listing доказать, что выбранный skill всё ещё может быть загружен. User-disabled skill и skill, скрытый Parley только из listing, — разные состояния. Нельзя считать Codex skills.config disabled эквивалентом «не печатать описание», пока это не подтверждено контрактом. Claude names-only/experimental budget — optional optimization с version gate, а не опора корректности. Отключение jev, если пользователь включил режим navigator, допускается только проверенным session-local способом; глобальные settings не менять.

Миграция/fallback: default off, один переключатель на work/session, сохранённый native режим. При неподдержанном контракте вернуться к native listing и показать, что оптимизация отключена. Не оставлять одновременно полный native каталог и ещё один огромный navigator каталог без измерения overhead. Tool schema стабильна; не вписывать все изменившиеся skill names в описание на каждом ходе. Принятие: multilingual/no-match/ambiguous/disabled/large-skill fixtures плюс разрешённый F05; качество и безопасность важнее минимального текста.

### F03. Память и знания с происхождением и областью действия

Основание: раздел skills/knowledge основного аудита, A08/A14/A16. Приоритет P3 после надёжной доставки; размер L; риск высокий для качества решений.

Не считать .omc/.omx development memory готовой runtime-памятью Parley. Начать с task-local facts/decisions/artifact refs, а не глобального knowledge dump. Запись: id, scope(work/room/task), origin, sourceRefs, evidenceHash, taskRevision, status(proposed/verified/accepted/superseded), updatedAt/validity. Утверждение агента не становится user constraint или accepted fact без соответствующего provenance. При конфликте показывать обе версии/основание и текущий authority; не молча выбирать последнее summary.

Retrieval отдаёт ограниченные excerpts с references и причиной релевантности. Полные тела доступны по demand, повторные загрузки дедуплицируются в пределах известных content hashes. После compaction bootstrap восстанавливает current task revision, constraints, approvals, pending work и ссылки на доказательства; не всю историю. Stable policy не включает меняющуюся memory. Нативные SKILL.md остаются native форматом; agent roles — task assignments, а не новый слой огромных системных промптов.

Совместимость: старые summaries импортируются как agent-reported unverified, без автоматического доверия. Принятие: устаревшая memory не перебивает новое human amendment; документ с инструкцией не меняет authority; восстановление сохраняет запреты/открытые вопросы; room isolation и byte budget выполняются. Реальную экономию чтений оценивать F05.

### F04. Capability management отдельным пользовательским действием

Основание: WIP capabilities design, A10/A17/A20/A22. Приоритет P3 после read-only catalogue; размер M–L; риск высокий для install/remove/share.

Сначала read-only inspect/refresh. Установка, отключение, удаление, sharing и scope change требуют конкретного preview: какой native source, какая версия, какие settings/files меняются, для новых или уже работающих сессий, нужен ли restart. Реализовывать через поддержанный native CLI/config contract, с атомарной записью/backup и минимальным diff; не переписывать credential файлы и не копировать secrets между вендорами. Объём разрешения привязан к показанной операции, не к широкому «управлять всеми skills».

Миграция: конфигурации разных providers не унифицируются насильно. Неподдержанный write operation остаётся ссылкой на native workflow. Rollback возможен только для app-owned изменений и не отменяет внешние последствия установки. Принятие: dry-run diff соответствует применённому, reject ничего не меняет, выключенный user plugin не включается для router, running sessions показывают effective vs pending config, export проходит synthetic secret-redaction tests.

### F05. Доказать экономию на принятом результате

Основание: C1–C5, QA-V4, исходный benchmark раздел. Приоритет P2 для любых заявлений об экономии; размер M; риск низкий offline, бюджетируемый live. Зависимости: A21/A27, F01/F02.

Сравнивать одинаковый Parley с stock native skills и с navigator при одинаковых provider/model/effort/CLI/plugin hashes/task/team/permissions. Вариант с jev — отдельная ось, не подмена native baseline. Единица сравнения — принятая задача всей команды, включая main sessions, native subagents, retries и человеческие исправления. Считать input/output/cache read/write, tool-result bytes, skill lookup/load, no-match, дубли загрузок, messages/fanout, launches, compactions и время до приёмки. Неизвестное поле — unknown; для Codex ненаблюдаемый cacheWrite не выдавать за нулевое потребление.

Набор должен покрывать no-skill, очевидный/неоднозначный skill, русский запрос, несколько skills, смешанную room, DM/broadcast, mid-task amendment, stop/resume, disabled/unavailable skill, no-match и compaction. Разделить cold/warm cache, фиксировать интервалы и reset; random warm-hit не считать преимуществом router. Около 15 prompts достаточно для smoke-test, но не для сильного статистического обещания. Показать paired differences, медиану и хвосты, исключения и полноту данных.

Gate: качество/соблюдение ограничений не хуже baseline; снижение ресурса не съедено retry/fanout/tool overhead; пустой поиск ограничен; запрещённые skills не предлагаются. Целевой процент экономии назначать только после baseline. В этой задаче live A/B не проводился, факт экономии не заявляется.

Очередь 1 может содержать маленькие безопасные части A04 до полной схемы Stop, но продукт не должен объявлять общий барьер готовым раньше полной приёмки.

### Предлагаемые решения продукта по умолчанию

1. Trusted local project team, с честной общей видимостью conversation; privacy между hostile agents — отдельная будущая функция.
2. Native permission profile наследуется, override только явный и видимый; login/trust остаются у native CLI.
3. Стабильная политика в privileged channel; task/summary/knowledge — данные с происхождением. Не отключать prompt snapshot/cache оптимизации автоматически.
4. Plan coordination advisory, кроме явно проверяемых Parley-mediated approvals; окончательная приёмка привязана к review package.
5. Navigator default off до compatibility и economic gate. Никакого дополнительного model router и глобального переписывания настроек.

Эти defaults позволяют приступить к большинству fixes без большой продуктовой развилки. Более сильные обещания — запрет любых native действий до Accept, приватные комнаты, точный hard денежный потолок — требуют отдельного проекта и не должны появляться в интерфейсе раньше реализации своей границы.

## 7. Проверки плана и ограничения

Для составления плана использованы сохранённые результаты исходного аудита. Повторного полного аудита, live model calls, платных benchmark или реализации не выполнялось. В рамках текущего этапа выполнены: узкая read-only сверка HEAD/status; чтение исходных findings и WIP design выводов из аудита; автоматическая проверка наличия всех 55 строк coverage и всех 29 A/5 F пакетов; проверка ссылок на существующие обозначения; сохранение отдельного отчёта в Library.

Из исходного аудита сохраняется evidence baseline: в изолированной копии на Node 22 прошли builds всех пакетов, desktop typecheck/lint и protocol test typecheck; полный первоначальный прогон — 358 test files, 6947 tests, 6944 pass/3 fail. Core 1675/1677, protocol 81/81, host 686/687, desktop 4502/4502. Целевые повторы показали нестабильность, описанную QA-V2, а не доказали отсутствие проблемы. Эти цифры не являются прогоном будущих исправлений. Разрушающие probes из аудита выполнялись только на собственных временных fixtures; fake PTY не запускал модели.

План не устанавливает, какие функции могли появиться после зафиксированного среза в параллельных рабочих сессиях. Перед реализацией каждого пакета нужен короткий rebase/check затронутых interfaces, а не повтор всего аудита. Реальные user secrets, OAuth state и живые conversation prompts не читались для этого плана.
