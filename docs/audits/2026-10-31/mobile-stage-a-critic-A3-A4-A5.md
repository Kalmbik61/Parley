# Ревью критика: A3, A4, A5 мобильного приложения (этап A)

Дата: 2026-10-31. Критик: s-179 (Opus), только чтение, по исходникам. Предмет: `feat/mobile-stage-a` на `fbbcec7c` —
`packages/noise` (A3), `packages/relay` (A4), `packages/push-gateway` (A5). Текст перенесён ведущим s-174 из отчёта
критика без изменений по существу. Прогон критика: noise 64, relay 25, push-gateway 24 — зелёные. Docker-сборку
критик проверить не смог: демон не запущен.

**Итог.** Блокеров нет. Major — 4, minor — 9.

## Major

### M1 (A4). Relay: без аутентификации можно занять все соединения с одного IP

- **Где.** `packages/relay/src/server.ts:265-279`.
- **Почему.** Проверка — только глобальный `open >= maxConnections` (по умолчанию 2000). Предела на число
  одновременных соединений с одного IP нет, а лимитер считает только кадры `connect` и `pair`, не upgrade.
- **Опыт.** Relay с `maxConnections` 20, 20 простаивающих WS на `/v1/connect` с 127.0.0.1 → `/v1/host` моста получает
  HTTP 503. Каждый сокет живёт до `firstFrameMs` (10 с), значит в боевом режиме хватает ~200 переподключений в секунду
  с одного адреса, чтобы мосты и телефоны всех маршрутов получали 503. Спека §14 допускает отказ в обслуживании только
  от оператора relay, а не от любого из интернета.
- **Исправление.** Предел одновременных соединений на IP (например, 16) до `handleUpgrade`; upgrade тоже расходует
  лимит; `open++` до `handleUpgrade` (сейчас параллельные upgrade проскакивают сверх предела); `firstFrameMs` ≈ 5 с.

### M2 (A4). Relay: таблицу маршрутов можно забить навсегда

- **Где.** `server.ts:155`, `limits.ts:43`, `store.ts:66`.
- **Почему.** Ключ `newRoute` — полный адрес клиента, IPv6 по /64 не сворачивается (за Caddy адрес клиента IPv6 как
  есть). Маршруты не истекают, а `MAX_ROUTES = 10 000` — общий потолок.
- **Сценарий.** С ротацией внутри одной /64 создаются 10 000 мусорных маршрутов (по 5 на адрес). Они пишутся на диск и
  переживают перезапуск. После этого мост владельца после сброса (новый `routeId`) получает `rate_limited`, и relay
  непригоден для новых парингов до ручной чистки. Попутно каждый `createRoute` синхронно переписывает весь JSON с
  `fsync` (до ~1,5 МБ), и цикл событий блокируется.
- **Исправление.** IPv6-ключ по /64 (заодно `::ffff:`); сборка мусора: маршруты без устройств, к которым не было
  `hello` за 24 ч, и маршруты с `lastSeen` старше N дней; отложенная запись в store.

### M3 (A5). Шлюз: JWT не обновляется после 403 от APNs, сбой ничем не виден

- **Где.** `jwt.ts:36-44`, `server.ts:97-104`, `apns.ts:68-73`.
- **Почему.** Кэш держится по стенным часам `t - cached.at < 50 мин` и ничем не сбрасывается. 403
  (`ExpiredProviderToken` / `InvalidProviderToken`) превращается в 502, но токен остаётся в кэше. Если часы сервера
  шагнули назад (коррекция NTP), разность отрицательная, и токен старше часа живёт дальше: каждый push → 403 → 502 у
  всех пользователей, пока часы не догонят. При неверных Key ID / Team ID — то же навсегда. В лог не пишется ничего.
- **Исправление.** Возраст токена — по монотонным часам; читать в памяти `reason` из тела ответа APNs; при 403
  Expired/InvalidProviderToken сбросить кэш и повторить один раз, но не чаще раза в 20 мин (иначе
  `TooManyProviderTokenUpdates`); писать в лог агрегированные коды status/reason без токенов.

### M4 (A5). Шлюз: лимит на токен обходится регистром hex

- **Где.** `limits.ts:45`, `server.ts:95`, `packages/protocol/src/remote/frames.ts:56`.
- **Почему.** `APNS_TOKEN_RE` пропускает `[0-9a-fA-F]`, а лимитер хранит ключ как есть. Тот, кто знает чужой токен,
  шлёт тот же токен в разных регистрах: каждый вариант — новое окно «1 за 3 с / 60 в час». Принятие риска в спеке §6.5
  этим ломается (если APNs принимает hex в любом регистре — проверить в A24).
- **Исправление.** Приводить токен к нижнему регистру до лимитера и до запроса в APNs, либо принимать только
  `^[0-9a-f]{64}$`.

## Minor

- **m1 (A5).** Лимит по IP обходится, ловушка в README (`server.ts:25-32`, README «Docker»): IPv6 по полному адресу;
  `::ffff:` не снимается; README даёт `-p 8080:8080` (HTTP на всех интерфейсах) и одновременно велит `TRUST_PROXY=1` за
  прокси — `X-Forwarded-For` можно подделать прямым запросом. Исправление: /64, `-p 127.0.0.1:8080:8080`, явное
  предупреждение.
- **m2 (A5).** APNs 400 → 400 (`server.ts:102`): `BadDeviceToken`, `DeviceTokenNotForTopic` — постоянная проблема
  токена, мост её не стирает и push падает вечно; `BadTopic`, `TopicDisallowed` — ошибки конфигурации шлюза.
  Исправление: токенные причины → 410, ошибки конфигурации → 502 (нужен `reason`, см. M3).
- **m3 (A5).** `readBody` (`server.ts:35-52`) не слушает `close` / `aborted`: при обрыве клиента промис висит до
  `requestTimeout`. Исправление: `resolve(null)` на `close`.
- **m4 (A3 → A7).** `CipherState` после ошибки расшифровки остаётся рабочим (`cipher.ts:67-75`); по Noise nonce не
  сдвигается — верно, но §7.7 требует закрыть сессию. Для A7: флаг `failed` в транспортной обёртке.
- **m5 (A3 → A7/A8).** `FrameCodec.encode` сжимает всё от 1024 байт (`codec.ts:62-68`); кадр, где смешаны секрет и
  подконтрольный атакующему текст, даёт оракул длины в духе CRIME. Для `credentials` и всего с токенами —
  `encode(frame, {compress: false})`. Мелочь: `compressMin` не проверяется (NaN молча выключает сжатие).
- **m6 (A4).** Вытесненный управляющий сокет ещё до 30 с обрабатывает `devices` / `offer` (`server.ts:124-145`) и
  перезаписывает список нового моста. Исправление: игнорировать кадры, если `registry.host(host.routeId) !== host`.
- **m7 (A4).** Потолок памяти трубы (`pipe.ts:102`): до 4 МиБ на направление, `from` не на паузе, глобального потолка
  нет. Лучше pause/resume по `bufferedAmount` или меньший потолок.
- **m8 (A4).** Каждое `hello` моста (`touch`) и каждый `devices` — синхронная перезапись файла с `fsync`
  (`store.ts:72-122`). Сделать отложенную запись.
- **m9 (A4, A5).** Нет `.dockerignore`: в контекст уходит весь репозиторий; `COPY packages/<p>` кладёт симлинки хоста и
  устаревший `tsbuildinfo`. Исправление: `.dockerignore` с `node_modules`, `dist`, `*.tsbuildinfo`, `.parley`, `.git`.

Мелочь вне находок: схема допускает `count: 0` → алерт «0 waiting»; мост по §9.2 такое не шлёт.

## Проверено и верно

**A3 noise.** Токены IK и IKpsk0 по Noise §5.3 и §9 (psk = MixKeyAndHash первым; при psk `e` делает MixHash и MixKey;
`s` — EncryptAndHash, на чтении DHLEN+16). Соответствие es/se ключам. Имя протокола ровно 32 байта (граница
подтверждена вектором cacophony). Порядок split и роли send/receive. SAS по `h` после msg2. Любая ошибка → `failed`,
ключи стёрты. Nonce: отказ на 2⁶⁴−1, `shouldClose` на 2³², неудачная расшифровка nonce не сдвигает. Алиасинга буферов
нет. x25519 бросает на нулевом общем секрете, тест на точку малого порядка есть. HKDF по RFC 5869 сверен. FrameCodec:
потолки, распаковка кусками, ошибка залипает. Нет запасного пути через `Math.random`. sha256 векторов закреплён.

**A4 relay.** Сравнение хэшей за постоянное время. TOFU маршрута. Строгие кадры zod. `maxPayload` 65 599,
`perMessageDeflate` выключен. Лимиты `connect`, `pair` и нераспознанного кадра до поиска. Случайный 96-битный
`stream`. Машина ожидания и трубы корректны (закрытие сторон, 2 ч, простой 60 с при ping 25 с). Журнал без
идентификаторов и секретов. store 0600, атомарный rename. XFF за Caddy верен. Образ не под root.

**A5 push-gateway.** Строгая схема без свободного текста, внедрение в `:path` невозможно. Тело ≤ 4 КиБ, таймауты.
Лимит IP до чтения тела, лимит токена после схемы. ES256 (ieee-p1363, `kid`, `iss`, `iat`, проверка P-256). Разные хосты
APNs для sandbox и production. 410 наружу как есть. Токены, тела и IP не логируются. Без ключа сервис не стартует.
Образ не под root.
