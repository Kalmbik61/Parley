Проверка: код прочитан целиком; три находки подтверждены опытом на стабах против собранного `dist` (скрипты — вне

## Major

### M1 (A1b). `proposal.plan` уносит на телефон весь план комнаты, вместе с `argv` и `env` проверок

- **Где.** `packages/protocol/src/remote/projection.ts:184` — `proposal: r.proposal ?? null`;
  `packages/protocol/src/remote/projection.test.ts:62` — обход запретных ключей нарочно не заходит в `plan`
  (`if (k !== 'plan') keys(x, out)`).
- **Почему так.** В любой комнате не в режиме `free` решение ведущего хранит полный план:
  `room.proposal = {…, kind: 'decision', plan: RoomPlan}` (`core/src/work/proposals.ts:94-102`). Снимок окна
  (`windowMapBase`, `core/src/work/context-pages.ts:516`) у комнат только укорачивает строки, план не убирает.
- **Сценарий.** Автономная комната ждёт Go человека. В снимке телефона:
  - `items[].scope`, `criteria`, `note`, `evidence`, `log`;
  - `autonomous.checks[].argv`, `cwd`, `env` (`CheckSpec`, `core/src/work/types.ts:333-341`: «полный allowlist
    переменных»), `inputs`;
  - `attempts` с ветками, sha, манифестами, квитанциями и логами; `ops`.

  Это противоречит §5.5 («текстов… планов телефон не получает»). Размер такого снимка S7 не мерил.
- **Исправление.** Проецировать решение как `{id, kind, from, text, rev, at, planId, planRev}`, без `plan`. Если
  экрану понадобится план — короткая выжимка `{goal, items: [{id, title, status}]}` и никогда `autonomous`. Экрану
  Decision в D1 нужен только `text`. В тесте убрать пропуск `plan` и добавить в FORBIDDEN `env`, `argv`,
  `autonomous`, `log`.

### M2 (A6b). События хоста без `remote-policy-1` уходят подписчикам раньше проверки признака

- **Где.** `packages/remote/src/host-link.ts:228` — проверка признака в `.then` промиса ответа на `hello`
  (микрозадача). События того же куска данных идут синхронно через `handleEvent` → `emit` (`:270`).
- **Опыт.** Стаб старого хоста отвечает на `hello` без признака и тем же `write` шлёт `activity.changed` и
  `settings.changed`. Подписчики получили по порядку: `host:activity.changed (status=offline)`,
  `host:settings.changed (status=offline)`, `status:incompatible`. Вызовов к стабу — 0: вызовы закрыты, события — нет.
- **Риск.** Старый хост ничего не фильтрует (это и есть случай «второй границы нет», §4.1). Остаётся только фильтр A8
  и его привязка к статусу. Кэш активности тоже наполняется от непроверенного хоста.
- **Исправление.** Разбирать ответ на `hello` синхронно в цикле разбора кадров: ставить флаг `verified` до разбора
  следующего кадра; до него отбрасывать все события (без кэша и без `emit`). Тест: `hello` без признака и события в
  одном куске → ни одного события подписчикам.

### M3 (A6b). `stop()` не останавливает подключение в пути: после остановки связь выходит в `online`

- **Где.** `packages/remote/src/host-link.ts:283` — `stop()` закрывает только сокет из `socket`. Сокет `net.connect`
  до события `'connect'` нигде не хранится; обработчик `'connect'` (`:215`) не проверяет `stopped`; `connect()`
  проверяет `stopped` после чтения токена, но не после `net.connect`.
- **Опыт.** `start()`, через 1 мс `stop()`. Через 300 мс: статус `online`, стаб получил `hello` и `works.list`, сокет
  открыт, `call()` после `stop()` работает.
- **Та же причина:** `start → stop → start`, пока читается токен, даёт два `connect()`. Проигравший сокет остаётся
  открытым и зарегистрированным на хосте навсегда: его `.then` для `hello` выходит по `socket !== sock` и сокет не
  закрывает.
- **Исправление.**
  - хранить ссылку `connecting` и закрывать её в `stop()`;
  - в `'connect'`: `if (stopped || connecting !== sock) { sock.destroy(); return; }`;
  - счётчик поколений для `connect()`;
  - закрывать сокет везде, где обработчик `hello` или `works.list` видит `socket !== sock`.

## Minor

### m1 (A6a). Запросы одного соединения сокета управления идут параллельно; `stop` не ждёт идущих

- **Где.** `packages/remote/src/control.ts:237` — `for (const raw of messages) void handle(raw)`.
- **Сценарий.** Ответы приходят не по порядку (опыт: id 3 раньше id 2). Окно шлёт `devices.revoke` и сразу `stop`:
  `stop` отвечает и вызывает `callbacks.stop()`, пока `devices.revoke` ещё пишет `devices.json`.
- **Исправление.** Последовательная обработка на соединение или учёт идущих вызовов; на `stop` — не принимать новые,
  дождаться идущих, дождаться записи ответа (колбэк `write`), затем остановка.

### m2 (A6a). `push.test` не принимает `{deviceId}`

- **Где.** `packages/remote/src/control.ts:141` — разбор `{}`; спека §5.3 — `push.test {deviceId}`.
- **Опыт.** `push.test {deviceId}` → `bad_request`.
- **Исправление.** Параметры `{deviceId}` (форма `controlRevokeParams`) и передача в `pushTest`.

### m3 (A1). Адрес relay в `configure` — свободная строка

- **Где.** `packages/protocol/src/remote/pairing.ts:56` — `relayUrl: z.string().min(1).max(64)` без проверки вида;
  `controlStatusResult.relayUrl` — до 128.
- **Сценарий.** Мусор попадает в `remote.json` и всплывает только при сборке QR.
- **Исправление.** Проверять как `host[:port]` через `isValidRelayHost` (или явно задать форму `ws(s)://`), пределы
  выровнять.

### m4 (A1). Строки от телефона принимают управляющие и bidi-символы

- **Где.** `pairing.ts:6` — `pairMsg1Payload` (`name`, `platform`, `app`); `frames.ts` — `client.info`.
- **Сценарий.** Имя показывается в диалоге Мака «Allow '<name>' (unverified)?». U+202E или перевод строки искажают
  диалог визуально; защищает SAS, но текст диалога врёт.
- **Исправление.** refine: без `\p{Cc}\p{Cf}\p{Zl}\p{Zp}`, обрезка пробелов.

### m5 (A1). У `relayIncomingFrame` нет обязательного `device` для `kind: 'connect'`

- **Где.** `packages/protocol/src/remote/relay.ts:73` — `device` необязательный при любом `kind`.
- **Сценарий.** Проверка «устройство relay = ключ из msg1» (§7.5) опирается на `device`. A7 может её пропустить,
  если поля нет.
- **Исправление.** Размеченное объединение: `connect` — `device` обязателен, `pair` — без `device`.

### m6 (A1). Схемы b64 проверяют длину и алфавит, но не канонический вид

- **Где.** `packages/protocol/src/remote/relay.ts:28`.
- **Сценарий.** Две разные строки дают один id или токен; при сравнении строк в одном месте и байт в другом — промах
  (отказ в обслуживании, без обхода).
- **Исправление.** refine через `b64urlDecode` — он уже строгий.

### m7 (A1). Остальные свободные строки

- `pairing.ts:45` `pairFailedEvent.reason` → перечисление (`bad-psk`, `timeout`, `no-ack`, `denied`, `offer_closed`);
- `pairing.ts:23` `credentials.relays` и `frames.ts:41` `hello.relays` → проверка `isValidRelayHost`.

### m8 (A1b). `stuck` и `creator` роя копируются ссылкой, без выбора полей

- **Где.** `projection.ts:159` (`stuck: s.stuck ?? null`), `:168` (`creator: w.creator`).
- **Сценарий.** Новое поле хоста молча уходит в проекцию или ломает строгую схему.
- **Исправление.** Явный выбор полей. `stuck.detail` (команда или текст вопроса) — текст по замыслу (`needReason`);
  записать в спеке как единственный разрешённый текст кроме заголовков и `proposal.text`.

### m9 (A6b). `HostCallError` теряет `data` ошибки

- **Где.** `packages/remote/src/host-link.ts:267`.
- **Сценарий.** §5.4: `data` пропускается телефону для известных `reason` (`HOST_ERROR_REASONS`). A9 не сможет его
  передать.
- **Исправление.** Нести `data` в `HostCallError`.

### m10 (A6b). Предел строки 8 МиБ даёт тихую петлю переподключения

- **Где.** `packages/remote/src/host-link.ts:254` — `LineDecoder` с `MAX_LINE_BYTES = 8 МиБ`.
- **Сценарий.** `works.list` или `works.changed` больше 8 МиБ (в S6 уже 4,4 МБ сырыми) → `destroy` → переподключение
  → то же; мост навсегда в `starting` / `offline` без понятной причины.
- **Исправление.** Отдельная запись `host.line_too_long` в лог и причина в статусе.

### m11 (A6a). Лог обрезает строку до вырезания секретов

- **Где.** `packages/remote/src/log.ts:22` — обрезка до 200 знаков; вырезание зарегистрированных секретов — `:39`.
- **Сценарий.** Секрет, попавший на границу обрезки, оставляет в `bridge.log` своё начало.
- **Исправление.** Сначала вырезать секреты, потом обрезать.

### m12 (A6a). `start()` удаляет чужой живой `control.sock`

- **Где.** `packages/remote/src/control.ts:244` — `rm(socketPath)` без условий.
- **Сценарий.** Второй экземпляр моста молча перехватывает сокет управления первого.
- **Исправление.** Сначала попробовать подключиться; ответил — отказ (один экземпляр; это может взять A22, но
  примитив не должен затирать живой сокет).

### m13 (A6a, к A7). Нет последовательной записи «прочитать — изменить — записать»

- **Где.** `packages/remote/src/files.ts` — только атомарная запись.
- **Сценарий.** Отложенная запись `lastTs` после `devices.revoke` возвращает отозванное устройство на диск.
- **Исправление.** По m-2048 писатель `devices.json` один — A7; ему всё равно нужна очередь записей на файл.

### Мелочи

- **A2.** `packages/host/src/client.ts:38` — `remoteMayReceive` считает ответом любой кадр с числовым `id` без
  `event`. Сейчас хост не шлёт клиентам запросов, поэтому это верно. Для глубины защиты требовать ровно одно из
  `result` / `error` и отсутствие `method`.
- **A6a.** `detail` и `target` журнала не ограничены. Предел (например, 256) не даст случайно записать полный текст.

## Проверено и верно

**A2.**
- Роль задаётся один раз в `handleHello`; повторный `hello` получает `unknown_method`.
- Кадры до `hello` отклоняются, флаг `rejected` закрывает соединение для следующих кадров.
- Белый список проверяется по сырому имени до `parseIncoming`: имена со свойств прототипа (`constructor`,
  `__proto__`) безопасны; запрос и уведомление различаются по числовому `id`. Уведомления вне списка отбрасываются и
  пишутся в лог (в этапе A список пуст). `checkRemoteParams` — через `hasOwnProperty`; `rooms.resolveProposal` требует
  целый `rev ≥ 0`.
- Отправка: `send` фильтрует разобранный кадр, `sendLine` разбирает ровно эту строку и не пропускает строки из
  нескольких кадров и со встроенным переводом строки.
- Все пути к клиенту идут через `client.send` / `sendLine`, запросов хоста к клиенту нет. Проверены
  `context.broadcast`, повтор при регистрации (`activity.changed`, `host.notice`), `feed-service`, `pty.ts`,
  `backlog.ts`, `browser-endpoint`.
- `hello.features` клиента `remote` сужены до `compact-works` и `rooms-mail`: мост не становится окном для
  браузерного агента и не считается в `actionsShown`; проверка `name === 'desktop'` в `browser-endpoint` не задета.
  `hello.methods` для `remote` ⊆ `REMOTE_METHODS ∪ {hello}`; `remote-policy-1` добавлен в той же правке.
- `always` в `feed.decide` хост применяет только при непустых `suggestions` (`hooks/decisions.ts:53`). Поведение
  Telegram от подключённых клиентов не зависит.
- Тесты покрывают все шесть кейсов приёмки.

**A1.**
- `parsePairUrl`: строгий префикс, только известные поля, повторы отвергаются, точные длины, канонический b64url,
  строгий адрес relay и диапазон порта; тексты ошибок без значений (`s` — секрет).
- `relayUrlFor` ошибается только в сторону `wss://`, никогда в сторону открытого текста.
- Схемы push-шлюза и данных push строгие, без свободных строк; `push.register` — шестнадцатеричный токен и перечисление
  `env`.
- Вход `remote` без Node: правила ESLint; проекция берёт тип хоста только `import type`.

**A1b.** Нет `task`, `summary`, `history`, `metrics`, `agentPlan`, `plans`, `planEffects`, `resources` и текстов роя;
`revision` по умолчанию 0; без `compact` счётчики `null`.

**A6a.**
- Атомарная запись: временный файл с `O_EXCL` и правами 0600, `chmod` после umask, `fsync` файла и каталога,
  переименование, временный файл удаляется при сбое.
- Права проверены опытом: `control.token` — 600, `control.sock` — 600, каталог — 0700.
- Токен сравнивается за постоянное время. Авторизация синхронна до любого вызова: склеенные в один кусок `hello` с
  неверным токеном и `devices.revoke` дали 0 отзывов.
- Ответ уходит после завершения обработчика; незарегистрированные обработчики — `not_ready`.
- Лог вырезает значения по ключу и зарегистрированные секреты; токена в логе нет. Журнал ротируется на 5 МБ в один
  архив.

**A6b.**
- Вызовы закрыты по умолчанию: к старому хосту — 0 вызовов.
- Эпоха `<случайный bootId>:<n>`; снимок и активность сбрасываются при подключении и при закрытии; ждущие вызовы при
  закрытии получают `host_offline`.
- Поздние ответы старого сокета отбрасываются по тождеству сокета.
- Защита по `revision`: более новый `works.changed` не откатывается поздним ответом `works.list`.
- `host.token` перечитывается на каждое подключение и регистрируется как секрет лога; `works.list` повторяется с
  отступом, пока статус `starting`.
