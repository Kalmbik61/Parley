## 3. A18a — мастер установки relay по SSH

### Major

#### R1. Ключ с парольной фразой: запрос фразы недостижим, мастер падает

- **Где.** `packages/desktop/src/main/relay-setup/ssh.ts`:
  - парольная фраза распознаётся только в обработчике события `error`: `/passphrase/i.test(error.message)`;
  - `client.connect` обёрнут в `try` / `catch`, а `catch` отдаёт `{ kind: 'error', message }`.
- **Почему.** ssh2 1.17.0 разбирает `privateKey` синхронно внутри `connect()`:
  - `lib/client.js:259-261`: `throw new Error('Cannot parse privateKey: …')`;
  - `keyParser.js:496/848`: «Encrypted … private key detected, but no passphrase given».

  Исключение уходит в `catch`, а не в событие `error`. Получается `error` → `failed(null, …)` → `end()`.
- **Сценарий.**
  - Человек выбирает ключ `id_ed25519`, защищённый фразой (у ключей на Маке это обычно так).
  - Вместо фазы `need-passphrase` он видит сбой «Cannot parse privateKey: Encrypted OpenSSH private key detected,
    but no passphrase given», и сеанс закрыт.
  - Неверная фраза даёт ту же ошибку разбора, тоже без повторного запроса.
  - В `service.test.ts:317` этот путь проверен только с поддельным `connect`, который сам возвращает
    `passphrase-required`. На стенде случая нет.
- **Почему major.** Безопасности это не вредит: ничего не уходит, сеанс закрыт. Но выбор «ключ из ~/.ssh» не
  работает для обычного защищённого ключа, а заявленный в плане поток недостижим. Обходной путь — ssh-agent.
- **Исправление.**
  - В `catch` вокруг `client.connect` тоже проверять `/passphrase/i` и отдавать `passphrase-required`. Неверная
    фраза при уже заданной `secrets.passphrase` → снова `passphrase-required` с пометкой «wrong passphrase».
  - Тест на настоящем ssh2: зашифрованный ключ из `ssh-keygen -N secret` → `passphrase-required`, затем с фразой →
    дальше к ключу хоста.

### Minor

- **R2. Секреты живут в памяти main после конца прогона.**
  - Где: `service.ts`, `lastSecrets`. `end()` чистит `session.input.secrets`, но копия всех трёх секретов в
    `lastSecrets` живёт до следующего `begin`, то есть пока окно открыто.
  - Это противоречит комментарию «Credentials live in main memory for one run» и плану («только на один прогон»).
  - Исправление: обнулять `lastSecrets` после последней записи лога прогона — в конце `execute` и `failed`, по
    таймауту и при `cancel`.
- **R3. В окне секреты держатся всё время соединения.**
  - Где: `RelaySetupDialog.tsx` — `wipeSecrets()` вызывается после `await setup.call('begin'…)`, а `begin`
    включает подключение и разведку (до ~20 с и дольше). Если вызов бросил `bad_input`, поля не стираются до
    закрытия окна.
  - Исправление: собрать запрос, стереть состояние, потом `await`. При `bad_input` человек вводит пароль заново —
    это нормально.
- **R4. `begin` и `cancel` рвут идущий прогон.**
  - Где: `service.ts` — `begin` начинает с безусловного `end()`, `cancel` тоже вызывает `end()`; `running` они не
    проверяют. В окне Escape или закрытие диалога во время «Run» шлёт `cancel`.
  - Сценарий: соединение рвётся посреди `apt-get install` или `docker compose up`. Шаги идемпотентны, повтор
    доводит дело, но сервер остаётся в промежуточном состоянии, а человек не видит, на каком шаге остановились.
  - Исправление: пока `running`, `begin` отвергать, а `cancel` выполнять после текущего шага, с событием `step`
    «stopped».
- **R5. Хвост stdin после `sudo -S`.**
  - Где: `ssh.ts` `createShell` — пароль идёт в stdin `sudo -S`. Если sudo его не прочтёт (кэш или правило
    `NOPASSWD`), строка достанется команде.
  - Сейчас ни одна команда плана stdin не читает (base64 и `sha256sum` — из конвейера, `while read` — из `grep`,
    `apt-get` неинтерактивен), поэтому вреда нет.
  - Защита на будущее: `sh -c 'exec </dev/null; …'` внутри `sudo`.
- **R6. Пароль sudo под чужим login shell.**
  - Где: внешняя строка `sudo -S -p '' sh -c '…'` разбирается login shell пользователя. Для `sh`, `bash` и `zsh`
    кавычки `shQuote` верны. Для `fish` внутри одинарных кавычек `\\` и `\'` — экранирования.
  - Сейчас тела в base64 и шаблоны без `\\`, поэтому вреда нет. Но ограничение стоит записать в комментарий
    `shQuote`, иначе будущий шаблон с `\\` сломается у пользователя с `fish`.
- **R7. Caddy не закреплён по digest.**
  - Где: `templates.ts` `COMPOSE_CADDY` и `packages/relay/deploy/compose.yml` — `image: caddy:2`, плавающий тег.
  - Relay ставится по digest версии Parley, а соседний контейнер с TLS и портами 80/443 — по тегу. Повторный
    прогон через `--remove-orphans` подтянет не тот Caddy, что проверяли.
  - Исправление: `caddy:2@sha256:…` в шаблоне (и в README), обновление — вместе с digest relay при выпуске.
- **R8. Частный IPv4 и sslip.**
  - Где: `service.ts` `makePlan` — для адреса без домена берётся первый IPv4 хоста, частный тоже
    (`192-168-1-10.sslip.io`).
  - Сценарий: человек подключился к серверу по адресу в локальной сети. План ставит Caddy, сертификат не
    выпускается, проверка здоровья падает только в конце, с общим советом про DNS и firewall.
  - Исправление: частный или CGNAT IPv4 без своего домена → план `blocked` с текстом «This address is not
    reachable from the internet: enter the server's public address or your own domain».

### Мелочи

- **Перезапись `docker.list`.** `/etc/apt/sources.list.d/docker.list` перезаписывается, если Docker не стоит. Если
  человек раньше добавил репозиторий с другими параметрами, но Docker не поставил, его файл заменится.
  Предлагаю `test -e` с заметкой в плане.
- **Нет проверки отправителя IPC.** `relay-setup:call` и `relay-setup:event` не смотрят на окно-отправителя, в
  отличие от главного IPC (остров ограничен `ISLAND_METHODS`). Так же устроен `remote:call`. Если у острова тот же
  preload, ему доступен мастер. Стоит закрыть оба канала для острова.
- **Нет «не в sudoers».** Пароль `sudo` верен, но пользователь не в sudoers → снова `need-sudo`, без объяснения.

### Проверено и верно

- **Учётные данные (приёмка 8).**
  - Пароль, фраза и пароль sudo приходят в main через `relay-setup:call`, проверяются (`input.ts` `secret`: одна
    строка, ≤ 512, без `\0\r\n`) и живут в объекте сеанса.
  - В ответах окну их нет: фазы без секретов, неожиданные ошибки → `setup_failed` без текста (`ipc.ts`).
  - Строки вывода и лог маскируются `redactSecrets` до отправки и записи. Лог `relay-setup.log` — 0600, каталог —
    0700.
  - В Keychain и на диск ничего не пишется. Ключ из `~/.ssh` читает main, окно знает только имена файлов
    (`listPrivateKeys`).
  - Тест `service.test.ts:273` грепает лог, события и ответы.
- **Ключ хоста (приёмка 6).**
  - `hostVerifier` ssh2 срабатывает на обмене ключами, до `userauth`. Неизвестный ключ отвергается, пароль не
    уходит. Человеку показывают отпечаток SHA256.
  - `trust()` пишет `[host]:port type SHA256:…` в `~/.parley/remote/known_hosts`, переподключение принимает только
    этот отпечаток.
  - Смена ключа → `hostkey-changed` и `end()` до аутентификации. `trust()` отказывается заменить известный ключ.
- **Проверка ввода до подключения (приёмка 7).** `validateInput` в `begin` до `connect`:
  - хост — имя по меткам или IP без `%`; порт 1–65535; пользователь `^[a-z_][a-z0-9_-]{0,31}$`;
  - домен — только метки и не IP;
  - файл ключа — имя без пути, не `.pub`;
  - тип входа и действие — из перечня.

  Ничего не обрезается молча.
- **Построение команд.**
  - Всё идёт как `sh -c <shQuote>`, под `sudo -n` или `sudo -S -p ''`; NUL отвергается.
  - Переменные части проверены и заключены в кавычки: образ по `REFERENCE` плюс `shQuote`, порты — числа, домен
    проверен.
  - `distro`, `codename`, `arch` берутся из фиксированных таблиц `probe.ts`, а не из вывода сервера. `INSTALL_DIR`
    — константа.
  - Тела файлов — `printf %s '<base64>' | base64 -d > file`. `.env` секретов не содержит: домен, образ, режим,
    порты.
- **Чужие конфиги.**
  - nginx и Apache не трогаются, выдаётся сниппет. `X-Forwarded-For` задаётся, а не дописывается.
  - Правила `ufw` добавляются только если их нет и записываются в `ufw-rules`. Remove удаляет только записанные,
    по шаблону `^[0-9]{1,5}/tcp$`.
  - В режиме proxy relay слушает только `127.0.0.1`. Caddy держит 80/443, relay наружу не открыт (`expose`).
- **Remove и Roll back (приёмка 4).**
  - Remove: `down`, затем правила, затем `rm -rf /opt/parley-relay`. Тома удаляются только при отмеченном
    «delete data», план при этом перестраивается и показывается заново.
  - Roll back: файлы из `previous/`. `.env` с сервера перепроверяется (`addressFromEnv`) перед проверкой здоровья.
  - На стенде: маркер в `/data` переживает обновление, откат и Remove без данных; удаление с данными стирает том.
- **Заглушка digest.** `image.ts` `isImagePublished()` ложно при нулевом digest → установка `blocked` в
  `makePlan`, а `run` отвергает заблокированный план. В приложении образ берётся только из `pinnedImageRef()`
  (`createAppRelaySetup`), переменной окружения для подмены нет. Стенд передаёт свой образ через зависимости
  сервиса.
- **Проверка здоровья.**
  - С Мака через `net.fetch` Electron, то есть с системным хранилищем сертификатов.
  - `configure` моста — только после 200. В режиме proxy — после «Check».
- **Dockerfile и compose.**
  - `--ignore-scripts` у `pnpm deploy` убирает запуск скриптов при сборке — это безопаснее.
  - `${RELAY_IMAGE:-parley-relay}` и порты из `.env` с прежними значениями по умолчанию: ручная установка по README
    не меняется. Значения в `.env` мастер пишет только проверенные.
  - Контейнер relay — под `node`, `/data` — том.
- **Неподдерживаемая ОС (приёмка 9).** Разведка без привилегий (`cat /etc/os-release`, `uname -m`, `id -u`,
  `sudo -n true`) → `unsupported` и `end()` до любых изменений. На стенде — Alpine.

**Пробел стенда.** Приёмка 1 требует TLS-проверки здоровья с сертификатом тестового ACME (Pebble). Его нет:
проверка здоровья на стенде — запрос к контейнеру изнутри сервера (README, «What the stand does not cover»). Цепочка
«Let's Encrypt → `net.fetch` с системной проверкой → `configure`» проверена только тестами с подставным fetcher.
Предлагаю перед выпуском прогнать её один раз на настоящем VPS с опубликованным образом — это и так шаг человека
вместе с публикацией digest.
