# План: запущенные shell-процессы в тулбаре сессии

**Goal:** Показывать в правой части тулбара сессии краткую сводку запущенных команд и по нажатию — безопасный список процессов, принадлежащих PTY этой сессии.

**Behaviour:** Хост периодически получает дерево процессов от PID PTY и рассылает структурированный снимок; окно отображает только имя исполняемого файла и безопасные метаданные. Никаких аргументов командной строки или полного командного текста в UI/API не передаётся. Обновление работает для Claude и Codex, но для Codex классификация приблизительная и должна быть обозначена как таковая.

**Исходные факты:**
- PID PTY доступен в `packages/host/src/pty/pty-manager.ts` через `PtyHandle.pid`.
- `packages/desktop/src/main/diagnostics/processes.ts` уже строит дерево по `ppid` одним вызовом `ps`; его текущая строковая выдача предназначена для архива диагностики, а не для UI.
- `ChatToolbar` присутствует над Chat и Terminal (`packages/desktop/src/renderer/chat/ChatToolbar.tsx`), рядом с ним уже есть кнопка активных агентов.
- Предварительная проба: Claude позволяет точнее выделить дочерние команды; у Codex процессы служебной инфраструктуры могут выглядеть как пользовательские команды. argv не показывать (см. ограничение безопасности в `processes.ts` и backlog b-030).
- Измерения предыдущей разведки: 66–88 мс на `ps` при примерно 880 процессах (3 замера). Это ориентир, не гарантия и не критерий производительности.
- Живой замер 2026-11-09 (17 PTY Parley и проба Codex на `gpt-6-luna`, читались только `pid`, `ppid`, `etime`, `ucomm`):
  - `comm` на macOS отдаёт подменённый `argv[0]` и `process.title`: при `exec -a 'fake-title --token=SECRETVALUE/abc' sleep` в `comm` вся эта строка, при `process.title = 'node-title --token=…'` — `node-title --to`. `ucomm` в обоих случаях даёт `sleep` и `node`, но обрезан до 16 символов и дополнен пробелами.
  - При `LANG=ru_RU.UTF-8` колонки `%cpu` и `%mem` приходят как `0,4`, и `Number()` даёт `null`. С `LC_ALL=C` — `0.4`.
  - Claude в простое: корень PTY (`ucomm` — версия CLI, `2.1.319`), потомки `node` (MCP), `caffeinate`, `mcp-server-darwi`, `node → node → node`. Команды идут под `zsh`, и он остаётся живым: `zsh → docker, head`.
  - Codex в простое: корень PTY `node` → `codex` → `node`, `node → node_repl`, `codex-code-mode-`. Команды: `sleep 25` — прямой потомок `codex` без `zsh`; `sleep 25 | cat` — `zsh → sleep, cat`; `node -e …` — прямой потомок `node`, по имени не отличается от MCP-сервера.
  - Codex, служебное: при старте `git → git → git-remote-http` (39 и 68 с в двух пробах) и `zsh → zsh → zsh → zsh, tail` (около секунды); в ходе работы кратко `sandbox-exec`, `bash → bash → bash → dirname` и лишние `node`.

**Решения для v1:**
1. Сбор выполняется на хосте, который владеет PTY; окно не запускает `ps` и не читает системные процессы напрямую.
2. Опрос раз в 2 секунды только пока хотя бы один клиент подписан на процессные сведения живой сессии. Для нескольких сессий один снимок `ps` на тик, не отдельный процесс на каждую сессию.
3. UI показывает чип `N shell` и раскрываемый список. В строке: имя исполняемого файла, elapsed time, CPU и память, если корректно разобраны. Имя берётся только из `ucomm` (на macOS до 16 символов); `comm` монитор не запрашивает: в нём бывает подменённый `argv[0]` и `process.title`.
4. Не считать корень Claude/Codex командой. Классификатор идёт от корня PTY по дереву, проходит сквозь служебные процессы и берёт целиком поддерево первого процесса-команды:
   - все провайдеры, кроме `codex` (семейство Claude): процесс-команда — shell (`sh`, `bash`, `zsh`, `dash`, `fish`, `ksh`, `csh`, `tcsh`);
   - `codex`: процесс-команда — всё, кроме `node`, `node_repl` и имён с префиксом `codex`.

   Известные ошибки Codex, поэтому его список помечается как приблизительный: прямой `node`-потомок скрыт, даже если это команда человека (`node -e …`; у `pnpm test` видна только часть ниже `node`), а `git` при старте и служебные `zsh`, `bash` кратко видны. У Claude кратко виден shell хука, и постоянно виден MCP-сервер, если он запущен через shell-обёртку.
5. v1 не обещает описания фоновой задачи Claude: hook `background_tasks` сейчас не является живым универсальным источником и разбор событий отбрасывает `command`. Поддержка описаний — отдельное решение после безопасного дизайна данных.
6. Время и метрики — только наблюдаемые значения `ps`; при недоступности или ошибке опроса UI скрывает/помечает данные как недоступные, но не показывает текст ошибки ОС.

## Этапы и задачи

### Этап A — структурированный сбор и тесты на хосте

**Файлы (ориентир):**
- `packages/host/src/pty/pty-manager.ts` — доступ к PID и живым PTY оставить через существующий интерфейс. Диагностику в `packages/desktop` этап не трогает (см. «Доработка этапов A и B», п. 5).
- Новый модуль сервиса, например `packages/host/src/pty/process-monitor.ts` и тест — опрос, выбор потомков, фильтр provider и управление таймером.

**Критерии:**
- Один запуск `ps` даёт структурированные строки для всех активных PTY; PID/PPID используются для дерева, поля числовые и валидируются.
- В результирующей схеме нет argv, command line, окружения или текста команд; тест подтверждает, что секретоподобная строка из argv не может попасть в результат.
- Исключаются процессы корня агента и известные служебные процессы. Тестовые деревья для Claude/Codex фиксируют ожидаемые включения и исключения.
- Параллельный/медленный опрос не запускает неограниченное число процессов `ps`; ошибка или таймаут не ломает PTY и не оставляет таймер/подписчиков.
- Опрос стартует при первом подписчике и останавливается при последнем; остановка хоста очищает таймер.

### Этап B — протокол, подписки и жизненный цикл

**Файлы (ориентир):**
- `packages/protocol/src/methods.ts` (+ тесты протокола) — добавить запрос/ответ подписки и уведомление снимка либо эквивалентный узкий интерфейс.
- `packages/host/src/methods/` и `packages/host/src/methods/index.ts` — подключить обработчики и рассылку.
- Связанные индексы методов/возможностей и тесты — только если этого требует существующий механизм совместимости.

**Критерии:**
- Подписка привязана к `SessionRef`; клиент может отписаться; отключение клиента снимает все его подписки.
- Новый подписчик получает начальный снимок; далее уведомления содержат заменяющий полный снимок с монотонной ревизией или эквивалентной защитой от перестановки ответов.
- Выход/перезапуск PTY очищает или заменяет снимок, старый PID не продолжает отображаться.
- Старый хост/неподдерживаемый метод не ломает открытие Chat/Terminal; UI корректно скрывает функцию.
- Число подписчиков и активных интервалов ограничено действующими PTY и клиентами; повторная подписка идемпотентна.

### Этап C — окно: store/hook и безопасная модель

**Файлы (ориентир):**
- Новый модуль в `packages/desktop/src/renderer/terminal/` для состояния/подписки и unit-тестов.
- `packages/desktop/src/shared/strings.ts` — пользовательские английские строки.
- `packages/desktop/src/renderer/chat/ChatToolbar.tsx` и `.test.tsx` — вставить компонент рядом с кнопкой активных агентов.

**Критерии:**
- Подписка активна только для отображаемой вкладки живой сессии и снимается при смене/закрытии вкладки и размонтировании.
- Чип отсутствует при отсутствии данных/поддержки; раскрытие показывает пустое, загрузочное и недоступное состояния без ошибок или технических путей.
- В строке отображаются только безопасное имя, elapsed time и доступные CPU/память; нет title/tooltip с argv или сырой строки `ps`.
- Для Codex заметно обозначено, что список может включать служебные процессы; это не представляется как полный/точный список команд.
- В длинных именах список остаётся в пределах окна; доступно с клавиатуры, aria-label и роли корректны.

**Уточнения лида (после приёмки доработки A и B):**
- Поддержка определяется через `useHostSupports('processes.subscribe')`. В `BASELINE_METHODS` и `REQUIRED_METHODS` (`renderer/lib/capabilities.ts`) метод не добавлять: старый хост не должен считаться неполным.
- Новое событие и вызовы идут через тот же `bridge`, что в `renderer/terminal/use-terminal.ts`: `call` и `on`.
- Ответ `not_found` при подписке означает, что живого PTY нет, а не ошибку: чип скрыт, в журнал и UI не выводить. Подписка повторяется, когда сессия снова становится живой.
- Подписка живёт на сокете. После переподключения к хосту подписаться заново (образец — `pty.attach` в `use-terminal.ts`, строки около 423).
- Ревизия монотонна только внутри одного запуска хоста, а после его перезапуска начинается заново. Поэтому последняя принятая ревизия сбрасывается при каждой новой подписке, иначе снимки нового хоста отбрасывались бы как устаревшие.
- Чип ведёт себя как соседний `N agents running`: при `available: true` и нуле процессов его нет, как нет и при `available: false`. Пока список раскрыт, чип не исчезает, а список показывает пустое или недоступное состояние: иначе фокус клавиатуры потерялся бы вместе с кнопкой.
- Число в чипе — `processes.length`.
- Строк в списке может быть много: на живом замере 17 у одной сессии с тестами, поэтому список прокручивается.

### Этап D — интеграционная проверка и документация

**Файлы:** тесты host/protocol/renderer, при необходимости сценарий существующего E2E; `CHANGELOG.md` только по принятому порядку проекта.

**Критерии:**
- Тесты проверяют цикл подписка → снимок → изменение → выход PTY → отписка, несколько сессий и несколько клиентов.
- Проверить вручную Claude и Codex: запускаемые `sleep`/локальная безопасная тестовая команда появляются и исчезают; аргументы не отображаются. Зафиксировать Codex false positives как известное ограничение.
- Typecheck, затронутые тесты и lint соответствующих пакетов проходят.
- Измерить длительность общего опроса на обычной машине и зафиксировать фактический результат, не превращая разведочный замер в обещание.

**Уточнения лида (после приёмки этапа C):**
- Правка этапа C: `S.chat.processes.approximate` говорит только о лишних процессах, а Codex может и не показать команду. Текст: `Approximate list: it may include Codex helper processes and miss some commands.`
- Интеграционный тест хоста — через настоящий сокет и настоящий `HostConnection`-подобный клиент, по образцу существующих тестов сервера, с `ps`-заглушкой: подписка → начальный снимок → изменение → выход PTY (`available: false`) → отписка; две сессии; два клиента; обрыв клиента снимает подписку; неподдерживаемый метод у хоста без монитора отвечает `unknown_method`.
- E2E — новый `packages/desktop/e2e/session-processes.spec.ts` по образцу `e2e/shell.spec.ts` и `e2e/chat-hooks.spec.ts`: отдельный `PARLEY_HOME`, агент-заглушка через `PARLEY_CLAUDE_BIN`, запускающая дочерний `zsh` с `exec -a "fake --token=SECRET-PROBE" sleep`. Проверки: чип появляется и исчезает; список показывает `sleep`; весь текст окна и DOM списка не содержат `SECRET-PROBE`. Снимок экрана с раскрытым списком сохранить в `docs/audits/2026-11-09/session-processes-chip.png`. Запускать только этот файл.
- Живой хост и установленный `/Applications/Parley.app` не трогать: не перезапускать, не завершать процессы вне своего теста.
- Замер: 10 опросов настоящего `ps` без заглушки, в отчёте медиана, максимум и число строк `ps`. Цифры записать в `docs/audits/2026-11-09/session-processes-measure.md`.
- `CHANGELOG.md`: одна запись на английском в `## Unreleased` → `### Added`, с известным ограничением Codex.
- Проверка с настоящими Claude и Codex остаётся за лидом.

## Доработка этапов A и B (по живому замеру 2026-11-09)

Этапы A и B лежат в рабочем дереве незакоммиченными и не приняты. Этап C начинается только после приёмки этой доработки. Файлы: `packages/host/src/pty/process-monitor.ts` и `.test.ts`, `packages/host/src/methods/processes.ts` и `.test.ts`, `packages/protocol/src/processes.ts`, откат в `packages/desktop/src/main/diagnostics/`.

Дефекты текущего кода, воспроизведённые временным тестом с `ps` на 100 мс: подписчик, пришедший во время опроса, удваивает цепочку таймера (18 вызовов `ps` за 10 интервалов вместо 10, цепочки не схлопываются); после `stop()` при живом подписчике опрос продолжается (9 вызовов за 10 интервалов); после отписки последнего клиента срабатывает ещё один лишний `ps`.

1. **Колонки и локаль.** `PS_ARGS = ['-axo', 'pid,ppid,%cpu,%mem,rss,etime,ucomm']`, `ps` запускается с `env: { ...process.env, LC_ALL: 'C' }`. Имя — `ucomm` после `.trim()`; `processName` и `PROCESS_NAME_MAX` убрать.
2. **Классификатор** — решение 4, один обход дерева с предикатом «процесс-команда» по провайдеру. `SERVICE_COMMS` убрать: этих имён на живых деревьях нет. `approximate` остаётся `provider === 'codex'`.
3. **Один путь опроса.** Вместо `runOnce`, `refreshNow` и флага `polling`:
   ```ts
   function schedule() {
     if (timer !== null || inFlight !== null || subscriberCount() === 0) return;
     timer = setTimeout(() => { timer = null; void pollNow(); }, intervalMs);
     timer.unref?.();
   }
   function pollNow(): Promise<void> {
     if (inFlight !== null) return inFlight;
     if (timer !== null) { clearTimeout(timer); timer = null; }
     inFlight = poll().catch(logFailure).finally(() => { inFlight = null; schedule(); });
     return inFlight;
   }
   ```
   `refresh()` — это `pollNow()`. `subscribe` зовёт `schedule()`. Отписка последнего снимает таймер. `stop()` снимает таймер и очищает подписчиков, чтобы идущий опрос не возобновил расписание.
4. **Опрос и рассылка.** `ps` запускается, только если есть живой PTY с подписчиком. Рассылка заново читает `deps.livePtys()` после `ps`: снимок вышедшего PTY не должен прийти после `available: false`. Сбой, таймаут или ненулевой код `ps` доставляются подписчикам живых PTY как `null`: сигнатура слушателя `(ref, snapshot: ProcessSnapshot | null)` (решение 6).
5. **Парсер.** Изменения в `packages/desktop/src/main/diagnostics/` откатить: `parsePs` никто, кроме его же тестов, не использует, а хосту он недоступен. Типизированный парсер один, в хосте. Архив диагностики сохраняет свой регексп и `comm`, поэтому разные `PS_ARGS` у хоста и окна намеренны; это отметить комментарием в мониторе. Правку про разрыв строки между чанками не делать: вывод склеивается целиком до разбора.
6. **Этап B.** `null` от монитора публикуется как `available: false`. Комментарий к `SessionProcess.name` описывает `ucomm`, а не basename.

**Критерии:**
- Тест на настоящем `ps` (пропуск на `win32`): дочерний `bash -c '(exec -a "fake --token=SECRET-PROBE" sleep 30) & wait'`, корень — `process.pid`, провайдер `claude`. Снимок содержит `sleep`, не содержит `SECRET-PROBE`, а `cpuPct` — число. Отчёт подтверждает, что при `comm` вместо `ucomm` тест падает. Старый тест с токеном, которого нет во входных данных, заменён этим.
- Тест на `env.LC_ALL === 'C'` в вызове `spawn`.
- Фикстуры деревьев — из раздела «Исходные факты»: Claude в простое и Codex в простое дают пустой доступный снимок; `zsh → docker, head` даёт три строки; у Codex прямой `sleep` виден, `zsh → sleep, cat` даёт три строки, прямой `node` скрыт, `node → sh → vitest` даёт `sh` и `vitest`; провайдер `custom-claude-api` классифицируется как Claude.
- Регрессионные тесты с `ps`, занимающим ненулевое время: подписчик во время опроса — не больше 10 вызовов `ps` за 10 интервалов; `stop()` во время опроса и отписка последнего клиента во время опроса — 0 вызовов после; `refresh()` во время опроса ждёт его завершения, а новый подписчик получает снимок; нет ни одного живого PTY с подписчиком — `ps` не запускается; сбой `ps` — подписчик получает `null`, клиент — `available: false`.
- `git diff --quiet -- packages/desktop/src/main/diagnostics/` проходит.
- Тесты `src/pty/process-monitor.test.ts` и `src/methods/processes.test.ts` в `packages/host`, `tsc` и `eslint` по изменённым файлам: в отчёте фактический вывод, чужие ошибки названы отдельно.

## Порядок исполнения

1. Этап A — сначала утвердить тип результата и критерии классификации; отдельные тесты парсера и фильтра.
2. Этап B — протокол и lifecycle; проверить совместимость старого окна/хоста.
3. Этап C — подписка окна и UI.
4. Этап D — интеграционная проверка и документация.

Этапы последовательны: renderer нельзя начинать до готового интерфейса протокола. При реализации каждый этап выдаётся отдельной ограниченной задачей, тесты запускает ведущий после этапа.

## Риски и не-входит

- Классификация процессов по дереву не универсальна: оболочки, detached/nohup и реализация CLI могут менять родительство; Codex в частности даёт ложные строки.
- `ps` — снимок, не трассировка: очень короткие команды могут не попасть в выборку.
- Не показывать argv, env, cwd, полный путь исполняемого файла или исходные строки `ps`; вопрос добавления безопасных подписей команд потребует отдельного threat review.
- Не входит: завершение процессов из UI, управление командами, журналирование истории запусков, отображение shell-команд из hook/rollout, точная классификация всех провайдеров.

## Impact card

- **Goal:** быстро видеть активность shell-команд сессии.
- **Behaviour:** периодический безопасный снимок процессов в тулбаре; Codex приблизительный.
