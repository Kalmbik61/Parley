# A3 — исполнение без подтверждения

- **Исполнитель:** senior-only. Причина: граница записи, отмена, восстановление после рестарта, конкуренция планов.
- **Зависимости:** A2.
- **Сначала прочитать:** `00-common.md`; Спека §3, §5.2 («Правило»), §5.3 целиком, §5.9, §10 (AU-02…AU-16, AU-21);
  План §2, A3; отчёт и коммиты A2.

## Цель

При допуске из A2 и включённом флаге вызов `propose_*` исполняет действие сам и отвечает модели настоящим итогом.
При любом другом допуске всё работает как раньше.

## Что есть сейчас

- `propose*` → `setPending` (`assistant-service.ts:455-467`) → карточка `active`, событие `needs_confirmation`,
  ответ «Shown to the person as a card».
- Клик → `decide` (`:1440-1487`) → `cards.claim` → `applyMessage` / `applyRoom` / `applyDecision` /
  `applyRoomDecision` или `startPlan` → `runPlan`.
- `cards.put` и `cards.claim` — отдельные транзакции (`cards.ts:106-144`).
- `running` (один план за раз) проверяется до `await preparePlan` и не перепроверяется (`:1138-1146`, `:1198-1200`).
- `apply*` возвращают `applied: boolean` — это решение по карточке, а не итог действия.

## Шаги

Иди блоками; каждый блок — со своими тестами.

1. **Схема и хранилище.** Миграция в реестре `MIGRATIONS` (`packages/core/src/work/db.ts:308`): два столбца в
   `assistant_cards` — ход исполнения (JSON) и `result_state`. В `cards.ts`:
   - `CardVia` += `'auto'`; в `packages/protocol/src/assistant.ts:199` — то же в `assistantDecidedViaSchema`;
   - `putDecided(card, via, now)` — одна транзакция: вытеснение активных карточек того же источника и вставка строки
     сразу в состоянии `decided` с `decided_via`, ходом `recorded`, `result_state = 'pending'`;
   - запись хода: `started: k`, `confirmed: k`;
   - условный переход `result_state`: `pending → taken_by_run`, `pending → sent_as_message` (возвращает, удалось ли).
2. **Точка исполнения** (Спека §5.3, участок 2). Одна синхронная функция без `await`, вызывается после всей
   подготовки: правило §5.2 (допуск, флаг сейчас, запуск действителен, для job — `running` и Request не частичный, не
   вытеснен, не отменён), политика плана (блок 6), захват слота плана, `putDecided`, `recordCard`. Не прошла —
   обычный путь с `setPending`.
3. **Слот плана.** Один владелец; захват в точке исполнения и в `decide` перед `claim`; освобождение в `finally`.
4. **Срок вызова.** `AUTO_CALL_MS = 40_000` от начала обработки вызова; все ожидания получают остаток. До точки
   исполнения срок вышел — `Not started`, действия нет. После — `Still running` с id карточки.
5. **Структурный итог.** Исполнение возвращает
   `{ status: 'done' | 'partial' | 'not_done' | 'unknown', effects, retry: 'safe' | 'unsafe', reason }` (таблица в
   Спеке §5.3). `run-plan.ts` отдаёт итог по шагам и пишет ход (`started` перед эффектом шага, `confirmed` после).
   Существующий путь клика продолжает работать на `applied`/`error`: его поведение и тесты не меняются.
6. **Политика плана** (Спека §5.9). Таблица классов шагов: все нынешние виды — `auto`. План с видом шага, которого
   таблица не знает, или с шагом класса `click` целиком идёт обычной карточкой.
7. **`action_status { id }`.** Новый инструмент чтения: описание в `core/src/mcp/assistant.ts`, имя в
   `ASSISTANT_TOOL_NAMES` (`assistant-endpoint.ts`), в `JOB_TOOL_ALLOWLIST` и `JOB_CANCEL_SAFE_TOOLS`. Ждёт конца
   действия в пределах `AUTO_CALL_MS`; отдаёт итог только запуску, создавшему карточку; при выдаче окончательного
   итога переводит `result_state` в `taken_by_run`. Повторный вызов возвращает тот же итог.
8. **Стоп и отмена.** Отмена job или хода после точки исполнения план не останавливает. Остановка плана — отдельный
   обратный вызов (метод для него делает A6): запрещает следующие шаги, идущий шаг доводится.
9. **Итог без получателя.** Когда действие закончилось, итог `pending`, а создавший запуск не жив — либо когда
   запуск заканчивается при готовом итоге `pending` — сервис зовёт новую необязательную зависимость
   `deliverOutcome(card, outcome)`. Здесь она только объявляется и вызывается; реализацию даёт W2.
10. **Рестарт.** При старте сервиса автоматические карточки без закрытия классифицируются по ходу (таблица в Спеке
    §5.3) и закрываются с исходом `not_done`, `unknown` или `done`. Если job, создавший карточку, был `running`, его
    резюме `needs_confirmation` содержит этот исход, `result_state` становится `taken_by_run`. Иначе — вызов
    `deliverOutcome`.
11. **Где автоматической карточки нет.** Она не уходит в проекцию телефона (`cards.changed`, `host.ts:1034-1037`), в
    уведомления (`notifications/ingest.ts`), в мост Telegram (`telegram/assistant-bridge.ts`). Событие
    `needs_confirmation` по ней не возникает; `decided` — одно, после закрытия.

## Тесты

Каждый сценарий — тест в `assistant-service.test.ts`, `cards.test.ts`, `run-plan.test.ts`, тестах уведомлений и моста:

- AU-02, AU-04, AU-05, AU-06, AU-08, AU-09, AU-10, AU-11, AU-12, AU-13, AU-16;
- AU-14 на хосте: стоп во время шага — шаг доведён, следующие не начаты; отмена job после точки исполнения план не
  останавливает;
- AU-15 (а–г) для случая «job шёл»; для «job закончился» — что вызван `deliverOutcome` с верным исходом;
- AU-21 в части `taken_by_run`: итог получен через `action_status` → `deliverOutcome` не вызван; повторный
  `action_status` возвращает то же;
- слушатель карточек получает по автоматической карточке ровно одно событие;
- `link_request` на Request с автоматически исполненной карточкой — отказ;
- миграция: база прежней версии поднимается, старые строки карточек читаются.

- Методы окна, значок, журнал — A6.
- Слежение и служебные сообщения — W1, W2.
