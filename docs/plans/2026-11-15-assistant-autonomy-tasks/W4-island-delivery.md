# W4 — остров: доставка служебного итога

- **Исполнитель:** junior; senior-ревью (один итог — один путь доставки).
- **Зависимости:** W3, A8.
- **Сначала прочитать:** `00-common.md`; Спека §6.1, §6.3 («Где служебного нет», «Занятость Live», «Остров»), §6.5
  (RW-03, RW-10, RW-13, RW-14, RW-19, RW-22, RW-23), §9; План §3, W4; отчёт W2 (`AssistantRequestView.origin`).

## Цель

Итог служебного Request остров доставляет человеку ровно один раз: голосом Live, если Live острова активен, иначе —
карточкой сразу и обычной озвучкой. Служебные Request не попадают в статусы Live и во вход чужих job.

## Сначала сверить

Может ли обычная озвучка острова произнести произвольный текст вне хода разговора: `speaker.ts`, очередь речи
острова (`island/assistant/speech-queue.ts`), `store.ts` (`canSpeak`, `:211-213`). Если готового входа нет — добавь
в `store.ts` одно действие «произнести текст», на существующей очереди; новый движок озвучки не заводить.

## Что есть сейчас

- `island/live/delegation.ts`: `refresh()` читает `requests.list` (`:175-208`), `toResultInput` (`:76-90`), статусы
  и контекст моста собираются из всех открытых Request (`:192-194`, `:219`), занятость для автозакрытия —
  `:168-173`.
- `core/src/voice-live/speech-queue.ts`: состояния `queued`, `submitted`, `played`, `unknown`, `dropped`; карточка
  итога показывается через `CARD_AFTER_MS`; отметка доставки ставится после успешной отправки.
- `core/src/voice-live/status.ts`: статус на каждый открытый Request.

## Шаги

1. **Происхождение.** `toResultInput` несёт `origin` (`view.origin ?? 'island'` — у старого хоста поля нет).
2. **Исключения.** Служебные Request не входят: в статусы (`status.ts`), в `context.openRequests` моста
   (`delegation.ts:192-194`, `bridge.ts:130-131`), в счётчик «проверяю» (`checking`).
3. **Занятость Live.** Для автозакрытия занятостью считается служебный Request, только если его job идёт или итог
   ждёт озвучки; ждущий в очереди job — нет.
4. **Состояние служебного итога** (схема в Спеке §6.3, «Остров»):
   - `queued` → `submitted` → `played` при активном Live острова — существующий путь;
   - Live закрылся до `played` → обратно в `queued`;
   - Live острова не активен → `shown`: остров открывается, карточка итога показывается сразу, текст уходит в
     обычную озвучку, если включено «Speak answers»;
   - проверка «Live активен» и перевод состояния — в одном синхронном участке;
   - отметка доставки (`requests.ack`) — только из `played` или `shown`.
   Итоги человеческих Request ведут себя как раньше: их ветки не трогать.
5. **`watchNote`.** Строка из состояния хоста показывается строкой уведомления острова (как `notice`), пропадает при
   следующем ходе.
6. **Строки** — в `strings.ts`.

## Тесты

`delegation.test.ts`, `live/store.test.ts`, `core/src/voice-live/*.test.ts`, `AssistantView.test.tsx`,
`assistant/store.test.ts`:

- RW-10 (остров): служебный Request не даёт `thinking.append` статуса и не попадает в `context.openRequests`;
- RW-03: Live острова не активен → карточка сразу, обычная озвучка вызвана один раз, отметка доставки поставлена;
  при старте Live итог не звучит;
- RW-13: голосовая сессия хоста активна (телефон), Live острова нет → второй путь;
- RW-14 и RW-23: Live закрылся в состоянии `submitted` до `played` → итог показан вторым путём один раз; Live
  открылся, пока итог в `queued` → первый путь; ни в одном порядке событий нет двух доставок и нет потери;
- RW-22 (остров): служебный Request ждёт в очереди job — Live закрывается по тишине; готовый итог приходит вторым
  путём;
- RW-19 (остров): итог служебного Request от хоста проходит оба состояния Live;
- старый хост: Request без `origin` ведёт себя как раньше;
- `watchNote` показана и снята.
