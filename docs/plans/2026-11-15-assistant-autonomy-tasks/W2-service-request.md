# W2 — служебный Request и очередь

- **Исполнитель:** senior-only. Причина: durable-хранилище Request, ворота очереди речи, порядок общей очереди job и
  то, что служебное не должно утечь в чужие каналы.
- **Зависимости:** W1, A3.
- **Сначала прочитать:** `00-common.md`; Спека §5.3 («Кому достаётся итог», «Рестарт хоста»), §6.1, §6.2 («Выключение
  режима»), §6.3 («Request», «Очередь и пределы», «Где служебного нет», «Занятость Live»), §6.5 (RW-04, RW-10,
  RW-11, RW-12, RW-21, RW-22), §10 (AU-15, AU-21); План §3, W2; отчёты A3 и W1 (`deliverOutcome`, `onWatchEvent`).

## Цель

Событие слежения и итог действия без получателя превращаются в служебный Request разговора `island` с job
происхождения `system`. Служебное не мешает человеческим поручениям и не видно вне острова.

## Шаги

1. **`requests.ts`.** Внутренний вход `SubmitRequestInput` получает `origin: 'island' | 'system'` (по умолчанию
   `island`). RPC `requests.submit` поле не принимает: острову создавать служебные Request нельзя. Служебный Request:
   - ключ `originKey` из `['host', '<вид>:<проект>:<работа>:<сессия>:<ключ события>']`; для итога действия — id
     карточки;
   - создаётся сразу связанным как независимый (`link_kind`), ворота не держит;
   - исключается **в SQL, до `LIMIT`** из `openBefore` и из любых выборок «открытые поручения».
   `AssistantRequestView` получает `origin` (`protocol/src/assistant.ts`).
2. **`request-link.ts`.** Цель `link_request` с происхождением `system` — отказ.
3. **`job-context.ts`, `request-status.ts`.** Служебных в выводе нет.
4. **`jobs.ts`.**
   - при выборе из очереди служебный job запускается, только если нет ждущего человеческого;
   - одновременно идёт не больше одного служебного; в очереди — не больше пяти ждущих событий слежения;
   - новое событие той же сессии заменяет ждущее: прежний Request помечается неактуальным;
   - переполнение снимает старейшее ждущее событие слежения (итоги действий не снимаются) и сообщает наружу для
     `watchNote`;
   - срок жизни 5 минут от создания: не начат — job закрывается готовым текстом без прогона. Для этого — завершение
     job без прогона, доступное только происхождению `system`.
5. **Итог действия одним получателем.** Реализация `deliverOutcome` из A3: одной транзакцией перевести
   `result_state` карточки `pending → sent_as_message` и создать служебный Request с ключом — id карточки. Переход не
   удался — ничего не создавать.
6. **Событие слежения.** Реализация `onWatchEvent` из W1 в `host.ts`: флаг читается в том же синхронном участке, что
   создаёт Request; выключен — Request не создаётся.
7. **Выключение режима** (обёртка `settings.set`, сделана в A6): снять слежения (`clear()`), отменить без доставки
   ждущие служебные Request о событиях слежения; идущий пересказ не трогать; итоги действий не трогать.
8. **Чужие каналы.** Job происхождения `system` не проецируется телефону (`protocol/src/remote/voice.ts`,
   `jobs.changed` в `host.ts:1029-1033`) и не создаёт уведомлений (`notifications/ingest.ts`, `onJob`).

Вход и промпт самого прогона делает W3; здесь job происхождения `system` в тестах исполняет подставной исполнитель.

## Тесты

- `requests.test.ts`: RW-04 (повтор события — тот же Request; другое событие — новый); служебный не держит ворота
  более старого итога; девять служебных не вытесняют человеческое поручение из `openBefore`; RPC-схема не принимает
  `origin`.
- `request-link.test.ts`: вытеснение служебного — отказ.
- `job-context.test.ts`, `request-status.test.ts`: служебных нет.
- `jobs.test.ts`: RW-11 (человеческий раньше служебных; один идущий; пять ждущих; замена по сессии; снятие
  старейшего); RW-22 на хосте (5 минут в очереди — закрыт готовым текстом, прогона не было).
- `assistant-service.test.ts`: AU-21 (итог взят через `action_status` — сообщения нет; job отменён до получения —
  одно сообщение; повтор — второго нет); AU-15 для случая «job закончился» — сообщение с исходом по записям хода;
  RW-21 (все пять пунктов выключения режима).
- тесты уведомлений и проекции телефона: RW-12.
