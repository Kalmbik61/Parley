**Цель этапа.** Новый режим комнаты `autonomous` поверх механизма плана verified, в котором после Go человека один полный цикл проходит без человека: попытка исполнителя → проваленная проверка → попытка починки → прошедшие проверки → интеграция на точном SHA → `verified` → карточка завершения человеку. Перезапуск хоста посреди любого шага заканчивается безопасной остановкой с продолжением по явному действию человека, без повторения внешних действий. Исчерпание бюджета — явный незавершённый результат.

**Не входит в этап.** Зонды DOM, шрифтов, SVG и анимаций (этап 2); совет из трёх голосов и соподписи; комнаты направлений и холст; профиль прав для сети и учётных данных; автопродолжение после перезапуска без человека; парковка на лимите подписки; расширение истории `evidence` у обычного verified (бэклог b-001 остаётся отдельным пунктом).

**Tech Stack:** TypeScript, pnpm-монорепо (`@parley/core`, `@parley/host`, `@parley/desktop`), vitest.

## 1. Что берём из verified и что добавляем

Берём как есть (`packages/core/src/work/plans.ts`, `types.ts`): `RoomPlan` с `rev` и CAS; `PlanItem` с `criteria`, `after[]`, статусами `waiting | ready | in_progress | done | blocked | verified | returned`, `log`; `recalculate` (`plans.ts:292–313`); транзитивный сброс зависимых при возврате (`plans.ts:529–551`); `plan-effects.ts` как образец долговечной доставки с ключами и `occurrence`; `propose_completion` и карточки решения и завершения в окне; снимки плана `plan-snapshots.ts`.

Добавляем:
1. Режим `autonomous` в `RoomMode` (`types.ts:174`), четвёртый по порядку после `verified`.
2. Записи плана: попытка, манифест передачи, квитанция, спецификация и прогон проверки, журнал операций, бюджет со счётчиками, интеграция (п. 2).
3. Движок на хосте — единственный мутатор автономного плана и единственный, кто создаёт и закрывает сессии комнаты (п. 3). Инструменты агентов в автономной комнате идут через канал агента на хост, как `create_session`, а не пишут карту сами (п. 7).
4. Запускатель проверок на чистом закреплённом checkout точного SHA с замороженными входами (п. 4).
5. Интеграционная ветка: `verified` только после слияния и проверок на интегрированной голове (п. 5).
6. Бюджет: пределы, долговечные счётчики, резервы, сигнатура прогресса (п. 6).
7. Граница записи: изолированный репозиторий на попытку, движок как единственный посредник git, песочница у исполнителя и у запускателя; спайк — жёсткие ворота для каждого провайдера (п. 8).
8. Роли: новых встроенных ролей нет (поправка p-04); инструкции ведущему автономной комнаты даёт раздел «Role in the room» брифа и `guidance` (п. 7).
9. Окно: минимум (п. 9).

## 2. Модель данных

Новые поля — в `map.json` рядом с планом; `parseMap` подставляет пустые значения старым картам (`map.ts:339`), `validateMap` проверяет форму по образцу `planEffects`. Большие тексты (хвосты вывода проверок, передачи, артефакты) — в файлах под `.parley/works/<id>/autonomous/<planId>/`, в карте только пути, хэши и сводки.

```ts
// types.ts
export type RoomMode = 'free' | 'checklist' | 'verified' | 'autonomous';
export const ENGINE = 'engine';   // актор движка в log и в правилах плана, рядом с HUMAN/SYSTEM/PARLEY

export interface AutonomousPlan {               // RoomPlan.autonomous, только при mode === 'autonomous'
  budget: AutonomousBudget;
  checks: CheckSpec[];                           // заморожены при Go
  coverage: Record<number, Record<number, Array<string | 'verifier'>>>; // item → criterion index → требуемые checkId и/или вердикт проверяющего
  criteriaVersion: Record<number, number>;      // пункт → текущая версия критериев, ≥ 1; при Go движок пишет 1 для каждого пункта; растёт только через amendment (п. 2); ключи канонические, как у coverage
  integration: Integration;
  attempts: PlanAttempt[];
  ops: AutonomousOp[];                           // журнал операций с внешним эффектом
  halted: { reason: 'budget' | 'no_progress' | 'stuck' | 'restart' | 'confinement' | 'human'; at: string; detail: string } | null;
  seq: { attempt: number; receipt: number; check: number; op: number };
}

export interface PlanAttempt {
  id: string;                                    // at-0001
  item: number; n: number;                       // пункт и номер попытки по пункту
  planRev: number; criteriaVersion: number;      // под какую ревизию и версию критериев сдана
  worker: string | null;                         // сессия исполнителя (null до записи sessionId)
  verifier: string | null;                       // сессия проверяющего качественных критериев
  branch: string; baseSha: string;               // ветка попытки и голова интеграции, от которой она ответвлена
  sha: string | null;                            // коммит захвата, созданный движком в engine.git; HEAD клона не читается и не доверяется
  tree: string | null;                           // дерево захвата; tree == tree(baseSha) → попытка без изменений
  submissionKey: string | null;                  // хэш манифеста без sha, задан исполнителем до действий сервера
  status: 'starting' | 'running' | 'submitted' | 'checking' | 'accepted' | 'queued' | 'integrated' | 'returned' | 'blocked' | 'aborted' | 'superseded';
  manifest: HandoffManifest | null; receipt: Receipt | null;
  checks: string[];                              // CheckResult.id
  failureSignature: string | null;               // см. п. 6
  startedAt: string; endedAt: string | null;
  log: { at: string; by: string; status: PlanAttempt['status']; note: string | null; op: string | null }[];
}

export interface HandoffManifest {
  version: 1;
  sha: string | null;                            // null при сдаче; дописывает движок после захвата
  criteriaVersion: number;
  dependsOn: string[];                           // id принятых попыток зависимостей, из брифа
  coverage: 'covered' | 'partial' | 'failed' | 'unstarted';
  scope: string; facts: string[]; hypotheses: string[]; notFound: string[]; gaps: string[];
  text: string;                                  // до 4096 знаков
  artifacts: { path: string; sha256: string; storedAs: string }[]; // путь в дереве захвата, хэш, копия под .parley/…/attempts/<id>/; при сдаче storedAs обязан быть '' (агент не выбирает путь копии), путь копии относительно каталога попытки пишет квитанция (редакция 8)
  hash: string;                                  // sha256 канонического JSON манифеста без поля hash
  submittedAt: string;
}

export interface Receipt {
  id: string; attemptId: string; manifestHash: string; sha: string; criteriaVersion: number;
  valid: boolean; reason: string | null; at: string;
}

export interface CheckSpec {
  id: string;                                    // ck-spec-01
  item: number;
  argv: string[];                                // без оболочки
  cwd: string;                                   // относительно checkout
  env: Record<string, string>;                   // полный allowlist переменных
  inputs: { path: string; blob: string }[];      // замороженные входы: файлы тестов, конфиги раннера, фикстуры, package.json и lock — blob на baseSha Go
  timeoutMs: number;
  frozenAt: string;
}

export interface CheckResult {
  id: string; specId: string; attemptId: string;
  sha: string; argvHash: string; envHash: string; inputsOk: boolean;
  verdict: 'pass' | 'fail' | 'error' | 'not_verified';
  by: string;                                    // ENGINE или сессия-проверяющий
  exitCode: number | null; summary: string; outputTail: string | null; // путь к файлу хвоста
  at: string; durationMs: number;
}

export interface Integration {
  branch: string; baseSha: string;
  verifiedHead: string;                          // последняя голова, на которой все проверки интегрированных пунктов прошли
  candidateHead: string | null;                  // голова после слияния, ещё не проверенная
  queue: string[];                               // attemptId в порядке приёма
  suspended: { reason: string; attemptId: string; at: string } | null;
}

export interface AutonomousBudget {
  limits: { attemptsPerItem: number; repairWaves: number; minutesPerAttempt: number; sessions: number; concurrent: number };
  spent: { attempts: number; repairWaves: number; sessions: number; verifiers: number; minutes: number; launches: number };
  reservations: { key: string; kind: 'session' | 'launch'; attemptId: string; at: string }[]; // снимаются по op done/failed
}

export interface AutonomousOp {
  key: string;                                   // op-0001; идемпотентный ключ эффекта
  kind: 'create-session' | 'launch' | 'close-session' | 'stop-session' | 'clone' | 'capture' | 'merge' | 'noop-integration' | 'merge-abort' | 'check' | 'copy-artifacts' | 'cleanup' | 'resume';
  attemptId: string | null;
  payload: Record<string, unknown>;              // что именно: sessionId, sha, branch, specId…
  state: 'intended' | 'done' | 'failed';
  at: string; settledAt: string | null; result: Record<string, unknown> | null;
}
```

Правила записей:
- **Попытка не перезаписывается.** Новая попытка по пункту — новая запись с `n + 1`.
- **Коммит делает движок** (итог задачи 0: под Codex `.git` клона только для чтения, под Claude Code он под контролем исполнителя). Исполнитель сдаёт манифест без `sha`; движок отгораживает попытку (`stop-session`), захватывает рабочее дерево клона из собственного репозитория `engine.git` с доверенной конфигурацией (`GIT_DIR=engine.git`, `GIT_WORK_TREE=<клон>`, свой индекс, `GIT_CONFIG_GLOBAL/SYSTEM=/dev/null`, `core.hooksPath` пустой, `core.fsmonitor=false`, `commit.gpgsign=false`), пишет `commit-tree` с родителем `baseSha`, автором `attempt at-…` и ключом операции в сообщении, и дописывает `sha` и `tree` в попытку и манифест. Хуки, фильтры, fsmonitor и подпись из `.git` клона не исполняются (проверено, `gates/engine-capture.out`). Голову клона движок не читает. **Попытка без изменений** (`sha == baseSha`, а шире — `sha` уже содержится в текущем `verifiedHead`) допустима при валидном манифесте и свежих прогонах: так сдаются уже выполненные пункты и повторные подтверждения после отката регрессии; интеграция такой попытки — операция `noop-integration` без слияния (п. 5).
- **Квитанция привязана к `submissionKey`.** Повторная сдача с тем же `submissionKey` идемпотентна: тот же результат и та же квитанция (в том числе после потерянного ответа). Другой манифест для той же попытки — отказ `handoff-conflict`.
- **Артефакты копируются до квитанции** из дерева захвата (`git cat-file` в `engine.git`), не из файлов клона, в `.parley/works/<id>/autonomous/<planId>/attempts/<attemptId>/` с хэшем; замороженные входы проверяются по тому же дереву; квитанция `valid` только если все копии записаны и хэши совпали. Уборка клона попытки артефакты не трогает; они живут до завершения или отмены плана.
- **Доказательство пункта** (`PlanItem.evidence`) ставит движок после `integrated`: текст с `sha`, `verifiedHead`, `criteriaVersion`, идентификаторами квитанции и прогонов; `artifacts` — пути копий.
- **Критерии меняются только через amendment плана** (`propose_decision` с `planId`, рост `rev`, принятие человеком). Движок применяет его атомарно под одним `updateMap`: `criteriaVersion` изменённых пунктов растёт; у них **и у всех транзитивно зависимых** пунктов попытки в любом нефинальном статусе (`starting … queued`) → `superseded` с `stop-session`/`close-session` (операции — после записи), принятые и интегрированные → `superseded`, `evidence = null`, записи очереди сняты; если кандидат интеграции принадлежит затронутому пункту — `candidateHead` сбрасывается на `verifiedHead`; ожидающее предложение завершения снимается (`room.proposal.kind === 'completion'` → `null`, как в `plans.ts:533`); пункты → `ready`/`waiting` по `recalculate`. Одновременные amendments разрешает CAS по `rev` (есть).
- **Поздний дефект** (возврат проверяющего или человека по `verified`-пункту) ссылается на попытку в `log`, не меняя её; пункт → `returned`, новая попытка; транзитивно зависимые отгораживаются тем же атомарным правилом, что и amendment: все их попытки в нефинальных статусах → `superseded` с остановкой сессий, записи очереди сняты, кандидат при необходимости сброшен, предложение завершения снято, `evidence = null`. **`dependsOn` проверяется трижды:** при сдаче, при приёме проверок (`accepted`) и перед слиянием; попытка, чьи `dependsOn` перестали быть принятыми, → `superseded` на любом из этих шагов.
- **`completing` недостижимо**, пока `halted !== null`, очередь не пуста или есть пункт не в `verified`.

## 3. Движок

Место: `packages/host/src/rooms/autonomous-engine.ts` (хост); чистые правила переходов — `packages/core/src/work/autonomous.ts` без файлов и процессов (как `resource-policy.ts`), чтобы тестировать заглушками.

Принципы (P09, P16–P18): состояние меняет только движок под `updateMap`; агенты предлагают действия через канал агента; каждая мутация проверяет актора, попытку, `rev`, `criteriaVersion`, статус и ключ операции; переходы — в `attempt.log` со ссылкой на `op`.

### 3.1. Протокол операций (A13, A14)

Любой внешний эффект — создание и запуск сессии, закрытие, клон попытки, слияние, его откат, прогон проверки, копирование артефактов, уборка — идёт в три шага: **намерение** (`ops.push({state: 'intended'})` под `updateMap`) → **эффект** → **завершение** (`state: 'done' | 'failed'`, `result`). Ключ операции кладётся в эффект там, где это возможно: метка сессии содержит `attemptId`, `CreateSessionInput.requestedBy = ENGINE`, сообщение слияния содержит `op.key` и `attemptId`. Повтор операции с тем же ключом не создаёт второго эффекта: движок сначала ищет свидетельство (сессия с такой меткой в карте, коммит слияния с таким ключом в ветке) и завершает старое намерение, а не исполняет новое.

Порядок у запуска попытки: `attempt{status: 'starting'}` + `op create-session intended` → `SessionsService.create` → `op done` с `sessionId`, `attempt.worker` → `op launch intended` → `launch` → `op done`, `attempt{status: 'running'}`. Падение между шагами оставляет намерение, которое сверка при старте хоста закрывает по свидетельству.

### 3.2. Цикл по пункту

1. **Запуск попытки.** Пункт `ready`, бюджет позволяет (п. 6), резерв взят: движок создаёт исполнителя (`SessionsService.create` с отложенным запуском, изолированный клон от головы интеграции — п. 5 и п. 8, роль с правом записи, провайдер из списка поддерживаемых — п. 8), добавляет его в комнату (`addMember`) **до** `launch`, чтобы лимиты комнаты в `resource-policy` учитывали сессию (редакция 8, m-279), запускает и пишет бриф из плана: цель, пункт, критерии версии N, `baseSha`, факты и артефакты принятых попыток зависимостей с их `attemptId` (для `dependsOn`), структура манифеста, список замороженных входов, запреты.
2. **Сдача.** Исполнитель вызывает `attempt_submit(attemptId, submissionKey, manifest)` → канал агента → движок: статус `running`; `criteriaVersion` текущая; `dependsOn` совпадает с принятыми попытками зависимостей; `text ≤ 4096`. Отказ — с причиной, без смены статуса. Успех — `op stop-session` (процессы исполнителя остановлены, дерево стабильно) → `op capture` (п. 2 «Коммит делает движок») → проверка `sha` потомок или равен `baseSha`, замороженных входов и артефактов по дереву захвата → `op copy-artifacts` → квитанция → `submitted` → письмо исполнителю «квитанция rc-… записана» → `op close-session`. Повтор с тем же `submissionKey` возвращает тот же результат; поздняя сдача по попытке в `aborted/superseded/returned` отклоняется (`attempt-fenced`).
3. **Проверка.** `checking`. Исполняемые проверки пункта — запускатель (п. 4) на `sha`. Качественные критерии (`coverage` → `'verifier'`) — сессия-проверяющий: создаётся тем же протоколом, с ролью только для чтения (Codex `sandbox_mode="read-only"`, `approval_policy="never"`; Claude — роль чтения с песочницей, предварительно), другого семейства или размера модели, чем исполнитель (умолчание; один вендор допустим — ответ 7). Работает **только по артефактам** в собственном каталоге движка без кода кандидата: манифест, дифф `baseSha..sha` из `engine.git`, копии артефактов, выводы прогонов; код кандидата не исполняет — если критерий требует запуска, это спецификация для запускателя. Вызывает `attempt_verify(attemptId, sha, criterion, verdict, note)`; по завершении закрывается движком так же, как исполнитель. Покрытие: каждый обязательный критерий имеет хотя бы один требуемый результат; отсутствующий, `error` или `not_verified` результат **блокирует** приём (A01, A18) — пункт не принимается, пробелы перечисляются в карточке. Все требуемые `pass` и `dependsOn` всё ещё принятые → `accepted`; устаревший `dependsOn` → `superseded`; иначе `returned` с перечнем проваленных проверок и вердиктов.
4. **Починка.** `returned` при `n < attemptsPerItem` → новая попытка от текущего `verifiedHead` с брифом: прежние факты, проваленные проверки с хвостами вывода, вердикты проверяющего, что менять нельзя (замороженные входы). При `returned` и `n == attemptsPerItem` → пункт `blocked`, карточка человеку. Успешная последняя разрешённая попытка принимается. Сигнатура прогресса — п. 6.
5. **Интеграция.** `accepted` → атомарно с этим `queued` и в `integration.queue`. Статус пункта остаётся `in_progress`: зависимые не освобождаются, `completing` не наступает (п. 5).
6. **Приём пункта.** Единственный путь к `verified` — `integrate` (задача 2): по `integrated` попытке с полным покрытием на интегрированной голове он ставит пункт `verified`, пишет `evidence`, зависимые становятся `ready` через `recalculate`. `verifyPlanItem` в режиме `autonomous` отказывает всем акторам, включая `ENGINE` (редакция 7, рецензия m-156).
7. **Завершение.** Все пункты `verified`, очередь пуста, `halted === null` → `completing` → движок вызывает `propose_completion` от имени ведущего с `verifiedHead`, перечнем проверок, бюджетом (потрачено/осталось). Приёмка — человек (ответ 5). Отказ человека — возврат пункта (п. 2 «Поздний дефект»).

### 3.3. Сессии

- Создаёт, запускает, останавливает и закрывает только движок (`SessionsService.create/launch/stop/close`, `sessions-service.ts:165–198`), через протокол операций. Текст правил `guidance.ts`/`guide.ts`/`skill.ts` получает исключение: «в автономной комнате сессии закрывает движок по решению Go».
- Лимиты `resource-policy.ts` действуют как есть: отказ при резерве → `halted: budget`, порог не обходится.
- Застрявший исполнитель или проверяющий (`stuck`, 0.21.0): ждём до `minutesPerAttempt`, затем `op stop-session` → `aborted` с причиной, письмо ведущему, карточка человеку; попытка-замена только после `aborted`, прежняя отгорожена (`attempt-fenced`). `stuck: approval` у исполнителя автономной комнаты (запрос разрешения файлового инструмента вне cwd у Claude Code) — не вопрос человеку, а тот же `aborted` по таймауту: отвечать некому по замыслу режима. Уточнение (редакция 8): это остановка плана по п. 6 — `op stop-session` → `halt(reason: 'stuck')`; `aborted` ставится всем активным попыткам правилом остановки, отдельного правила точечного прерывания нет; замена — после «Продолжить» человеком (задача 8).

### 3.4. Перезапуск хоста и продолжение (A14, P16, P18)

При старте хоста движок **сверяет** план с миром, ничего не исполняя:
- `ops` в `intended`: `create-session` — ищет сессию с меткой попытки в карте (есть → `done`, нет → `failed`); `launch` — по `lifecycle`; `merge` — по **идентичности коммита**: голова ветки интеграции имеет родителей `[verifiedHead, sha попытки]` и ключ операции в сообщении (есть → `done`, `candidateHead` = эта голова; идёт слияние или голова иная → `merge-abort`/`reset --hard verifiedHead`, `failed`); `check` → `failed` (прогон не доверяется); `copy-artifacts` — по файлам и хэшам; `close-session`/`stop-session` — по `lifecycle`.
- Попытки `starting/running/checking` → `aborted: restart`, их сессии остановлены; `submitted` с валидной квитанцией остаются `submitted` (проверка перезапускается после продолжения); `accepted/queued` остаются.
- **Правило кандидата одно:** кандидат принадлежит движку; если коммит слияния подтверждён по идентичности, `candidateHead` сохраняется и **полностью перепроверяется** (все спецификации интегрированных пунктов и кандидата, качественные критерии по правилу §5) до любого движения очереди; `verifiedHead` сдвигается только после этой перепроверки. Если прогоны прошли до падения, но `verifiedHead` не записан — та же перепроверка (идемпотентно). Если коммит не подтверждён — `reset --hard verifiedHead`, попытка возвращается в `queued`.
- План → `halted: restart`, карточка человеку «Продолжить?». **Продолжение** — явное действие человека (кнопка на карточке → `op resume`): движок сначала завершает перепроверку сохранённого кандидата (если есть), затем перезапускает проверки `submitted`, заводит новые попытки взамен `aborted` (в счёт бюджета) и возобновляет очередь. Автопродолжение без человека — не в этапе.
- Неожиданная голова ветки попытки или интеграции никогда не принимается как доказательство: доверенное — только `sha` из манифеста и `verifiedHead` из карты.

## 4. Запускатель проверок (A06, A16, P10)

`packages/host/src/rooms/check-runner.ts`: `run(spec: CheckSpec, sha: string, attemptId) → CheckResult`.
1. **Чистый закреплённый изолированный checkout:** `git clone --no-hardlinks --no-checkout <engine.git> <…/checks/<attemptId>/<specId>>` без alternates (источник — bare-репозиторий движка `attemptsEngineGitPath(projectPath, workId)` = `<workDir>/engine.git`, где лежат захваты попыток и ветка интеграции; редакция 7, задача 4) и `git checkout --detach <sha>`; у checkout свои `.git`, ссылки **и копии объектов** (жёстких ссылок на объекты проекта нет: запись в объект клона не меняет объект проекта); `git status --porcelain` обязан быть пустым; иначе `error`.
2. **Замороженные входы:** для каждого `spec.inputs` blob файла в дереве `sha` сравнивается с `blob` из Go; расхождение → прогон не запускается, попытка → `returned` с причиной «изменены замороженные входы проверок» (так ловится правка тестов, конфигурации раннера, фикстур, `package.json`/lock).
3. **Запуск под песочницей:** тесты исполняют код кандидата, поэтому `spawn` идёт через обёртку `sandbox-exec` с профилем `(allow default) (deny file-write* (with send-signal SIGKILL)) (allow file-write* (subpath <checkout>) (subpath <checkout-tmp>) (subpath "/dev"))` (`gates/runner-profile-kill.sb`): нарушитель убивается до записи. **Обнаружение** — после прогона запускатель опрашивает журнал ядра за окно прогона: `log show --start <начало> --end <конец> --predicate '(subsystem == "com.apple.sandbox.reporting" OR sender == "Sandbox") AND eventMessage CONTAINS "deny(1)"'` (редакция 7: отчёты sandboxd в этой системе появляются не всегда, строки ядра `sender == "Sandbox"` — всегда и персистентно; свёрнутые строки «N duplicate reports for Sandbox: …» тоже считаются нарушением; метки времени для `log` — секунды без дробной части); строка с путём вне корней прогона → `error: запись вне корня (журнал песочницы)` независимо от кода выхода кандидата; журнал называет только имя исполняемого файла, pid и путь, поэтому фильтр fail-closed (редакция 7): строка, не атрибутированная процессу прогона или его потомкам, в узком окне прогона тоже даёт `error` (с пометкой «unattributed»; ложные срабатывания от параллельной активности хоста допустимы — движок повторяет прогон на том же `sha`); по той же причине движок исполняет прогоны на хосте строго по одному — параллельные прогоны отравляли бы друг друга строками журнала (редакция 8) (проверено для прямого и дочернего нарушителя с маскирующим родителем, `gates/runner-denial-log.out`). Завершение по сигналу без строки журнала → `error: завершён сигналом`, без диагноза. Без обёртки или без доступа к журналу прогон не запускается (`error`), план → `halted: confinement`. Linux (`bwrap`) не проверен и в этапе не поддерживается. Аргументы массивом без оболочки; `env` — только из `spec.env` (без `ANTHROPIC_*`, `CLAUDE_CODE_*`, `OPENAI_*`, ключей; отдельный `HOME` под checkout — удобство, не граница); лимит времени `timeoutMs`; лимит вывода (хвост 64 КиБ в файл). Код 0 без строк журнала → `pass`, иной код → `fail`; тайм-аут, невозможность запуска, непустой `status`, строка журнала, сигнал → `error`.
4. **Идентичность прогона:** `argvHash`, `envHash`, `inputsOk`, `sha` — в `CheckResult`; прогон на другом `sha` или с другим `argvHash` для критерия не считается.
5. **Уборка** checkout после прогона (`op cleanup`); хвост вывода остаётся файлом.

Спецификации проверок пишутся при Go и видны человеку в карточке Go (кто пишет первый набор — вопрос 1 в §12). `coverage` требует для каждого критерия хотя бы одну спецификацию или вердикт проверяющего; план без полного покрытия не принимается на Go.

## 5. Интеграционная ветка (A17)

При Go движок создаёт ветку `autonomous/<planId>` от `baseSha` и её worktree (`createWorktree`); `verifiedHead = baseSha`.

- **База попытки — голова интеграции,** не база проекта, и **репозиторий попытки изолирован** (п. 8): вместо worktree с общим `.git` (`attachWorktreePlan` берёт `baseBranchOf(projectPath)`, `sessions-service.ts:958`; `mergeWorktree` вливает в `info.base`, `worktree.ts:965`) движок делает `git clone --no-hardlinks` (без alternates) ветки интеграции на `verifiedHead` в каталог попытки: объекты копируются, а не делятся жёсткими ссылками. Расширение хоста: `CreateSessionInput.workspace: { kind: 'clone'; path: string; branch: string; sha: string }`, `WorkSession.workspace` рядом с `worktree`, `launch` берёт `cwd` из него, бриф описывает клон. Панель Changes клоны попыток не показывает (этап 1); дифф попытки читает движок.
- **Посредник git — движок:** после сдачи `git fetch <clone> +refs/heads/<branch>:refs/attempts/<attemptId>` в репозитории проекта, затем проверка, что `sha` достижим из этой ссылки и равен `baseSha` или его потомок. Слияние — в worktree ветки интеграции, принадлежащем движку: `git merge --no-ff <sha>` закреплённого коммита с ключом операции в сообщении; `mergeWorktree` не используется. Рабочее дерево интеграции — одноразовый клон движка из `engine.git`: перед каждым слиянием `reset --hard verifiedHead` и `clean -fdx`, при неисправности клон удаляется и пересоздаётся; если и это не удалось — `halted` с подробностью; `suspended` в этапе не пишется (редакция 9).
- **Очередь:** по одному; перед слиянием — третья проверка `dependsOn` (п. 2); `op merge intended` → `git merge --no-ff <sha>` → `candidateHead` → прогон спецификаций **интегрированных пунктов и текущего кандидата** на `candidateHead` (не всех в очереди: проверки ещё не влитого пункта требуют его реализации и дали бы ложный провал) → качественная перепроверка по правилу ниже → всё `pass` → `verifiedHead = candidateHead`, попытка `integrated`, пункт `verified` (п. 3.2 ш. 6). **Уже содержащийся `sha`** (равен текущему `verifiedHead` или его предок, например B сдала без изменений на H, пока A довела голову до H1): слияние даёт «already up to date» и двухродительского коммита не будет, поэтому движок пишет `op noop-integration` вместо `merge`, прогоняет спецификации и качественные критерии кандидата и интегрированных пунктов на текущем `verifiedHead`, и при успехе ставит `integrated` без сдвига головы; восстановление для `noop-integration` коммита слияния не ищет, а перепроверяет по тому же правилу кандидата. Любой провал → `op merge` остаётся `done`, но `git reset --hard verifiedHead` (`op merge-abort`), `candidateHead = null`, очередь `suspended`.
- **Разбор провала (редакция 9):** любой провал на кандидате — проваленная спецификация или вердикт проверяющего, в том числе принадлежащие ранее интегрированному пункту — это дефект кандидата: попытка `returned: integration` (`returnAttempt`), новая попытка от `verifiedHead` с проваленными проверками и diff в брифе. Обоснование: `verifiedHead` не сдвинулся и ветка возвращена на него, поэтому `evidence` прежних пунктов остаётся истинным; «регрессия» — изменение кандидата, ломающее проверенный пункт на слитом дереве, и чинит её исполнитель кандидата. `lateDefect` — только для позднего дефекта, заявленного человеком после приёмки (п. 2). Сигнатура провала — проваленные `specId:verdict`, `criterion:verdict` и причина `integration` (у конфликта — `conflict`); два одинаковых подряд блокируют пункт правилом `no_progress`. Очередь после возврата кандидата продолжается следующей попыткой.
- **Качественные критерии:** в этапе 1 на `candidateHead` до сдвига `verifiedHead` проверяющий переподтверждает **все** обязательные качественные критерии интегрированных пунктов **и** кандидата. Сужение по владению файлами не годится: экран A вызывает помощник из `scope` пункта B, B меняет помощник — файлы A не тронуты, поведение A изменилось; правило по глобам этого не видит. Узкое правило возможно только с моделью зависимостей и влияния, которой в этапе нет.
- **Конфликт** слияния → `merge-abort`, попытка `returned: conflict`, новая попытка одного исполнителя от `verifiedHead`; очередь продолжается (редакция 9).
- Финальное слияние `autonomous/<planId>` в базу проекта — человек после приёмки, как сегодня в Changes (ветка интеграции — обычный worktree движка, он виден панели). Клоны попыток убираются после `integrated` или в конце плана; артефакты — уже скопированы (п. 2).

## 6. Бюджет и остановки (A15, P21)

Пределы — в решении Go; счётчики `spent` и `reservations` — в карте, переживают перезапуск. Резерв берётся перед `create-session`/`launch` (`kind: 'session' | 'launch'`), снимается по `op done/failed`, учитываются исполнители **и** проверяющие, повторы и одновременные запуски (`concurrent`). Минуты считаются по `startedAt/endedAt` попыток плюс время прогонов.

Остановки, все с `halted` и карточкой человеку, без новых сессий: превышен любой предел; отказ `resource-policy`; `stuck` сверх времени; **нет прогресса**: `failureSignature = sha256(sorted(specId:verdict) + sorted(criterion:verdict) + нормализованные причины отказа)`; две подряд попытки по пункту с равной сигнатурой → пункт `blocked` без третьей попытки; изменившаяся сигнатура — прогресс, попытки продолжаются до `attemptsPerItem`. `n == attemptsPerItem` блокирует только после `returned`; `accepted` на последней попытке принимается. Остановка никогда не выглядит как успех (п. 2, последний пункт).

## 7. Инструменты агентов, права и роли

- Новые инструменты только в комнатах `autonomous`: `attempt_submit(attemptId, submissionKey, manifest)` (без `sha`: его создаёт движок захватом), `attempt_verify(attemptId, sha, criterion, verdict, note)`, `attempt_status(attemptId?)`. Первые два **не пишут карту в процессе MCP**: они шлют запрос в хост по каналу агента (`/agent/attempts`, образец — `session-endpoint.ts`), хост проверяет токен сессии, актора и состояние и мутирует карту через движок. `attempt_status` — чтение с пагинацией как у `get_map`.
- Унаследованные `plan_submit`, `plan_verify`, `plan_update` в комнате `autonomous` отвечают отказом `RoomRuleError('autonomous plan is driven by the engine')` — проверка в `plans.ts` по `plan.mode`, а не только в `plan-tools.ts`, чтобы обход через другой вход был невозможен. `set_room_mode('autonomous')` — ведущий поднимает как сегодня (`plans.ts:605–620`), понижает только человек.
- **Ответственность за пункт стабильна, назначение на попытку — переменное.** В автономном плане `PlanItem.owner = ENGINE` и `PlanItem.verifier = ENGINE` при предложении плана (правила `liveOwner`/`participant` расширяются сентинелом `ENGINE` только для `mode === 'autonomous'`); фактические сессии исполнителя и проверяющего — в `PlanAttempt.worker/verifier`; переназначение не меняет `rev`. `verifyPlanItem` в этом режиме отказывает всем, включая `ENGINE`: `verified` ставит только `integrate` (п. 3 шаг 6), и это записывается в `log` попытки.
- Amendment плана: только ведущий через `propose_decision` с `planId` и `rev`, принимает человек; применение — п. 2.
- **Предложение автономного плана (редакция 7).** Ведущий вызывает `propose_decision` с черновиком плана, как в verified; в комнате `autonomous` черновик дополняется `AutonomousDraft { budget: limits; checks: { id, item, argv, cwd, env, inputs: string[] (пути), timeoutMs }[]; coverage }`. Ядро проверяет черновик (`validateAutonomousDraft` в `plans.ts`: владелец и проверяющий каждого пункта — `ENGINE`; ключи `coverage` ⊆ пункты, индексы критериев в границах `criteria`; `checkId` уникальны, покрытие ссылается только на существующие `checks` или `'verifier'`; лимиты бюджета — безопасные положительные целые) и **не пишет карту**: инструмент шлёт черновик на хост по каналу агента (`/agent/attempts`, действие `propose-plan`). Хост дополняет git-фактами (`integration.branch = parley/<work>/integration/<planId>`, `baseSha` — голова базовой ветки проекта, `verifiedHead = baseSha`, `candidateHead = null`, `queue = []`, blob каждого входа на `baseSha`, `frozenAt`), пишет `criteriaVersion = 1` для каждого пункта, нулевые `spent`, пустые `attempts/ops/reservations`, `seq` нули — и записывает предложение через движок (`proposed`). Инварианты маршрута (проверяются тестами задач 3 и 4): хост заново проверяет живого ведущего, режим комнаты и ожидаемый `rev` по аутентифицированной сессии — проверка ядра не является авторитетом; у каждого критерия каждого пункта непустое покрытие, и проверки, на которые ссылается `coverage[item]`, принадлежат этому пункту (`check.item === item`); git-факты и blob закрепляются в предложении, которое видит человек, и принятие использует именно этот снимок, а не перечитывает сдвинувшуюся базовую ветку; повтор или сбой запроса к хосту не создаёт частичного или двойного предложения (идемпотентный `requestKey` считает ядро: sha256 канонического JSON `{roomId, planId ?? null, rev ?? null, text, draft}` — текст решения входит в ключ, чтобы исправление формулировки не считалось повтором; хост отвечает тем же результатом на повтор с тем же ключом по открытому предложению, а после возврата предложения та же пара ключ/содержимое — новый раунд решения). ## 8. Граница записи (ответ 4, A16, P22)

Сегодня граница не обеспечена: для Claude Code `--disallowedTools Edit,Write,NotebookEdit` ставится только ролям чтения (`launch.ts:398`), исполнитель сохраняет оболочку; worktree делит с проектом каталог `.git` (ссылки, объекты), и дифф попытки не видит записей вне worktree. Прежняя формулировка «ссылки могут остаться записываемыми, но в базу пишет только движок» противоречива и снимается. Граница этапа:

1. **Изолированный репозиторий попытки.** Исполнитель работает в клоне ветки интеграции с собственным хранилищем объектов (`git clone --no-hardlinks`, без alternates: свои `.git`, объекты, ссылки и индекс), а не в worktree; каталог проекта и его `.git` находятся вне корня записи, и ни один файл объектов не общий. Движок — единственный посредник git: он забирает коммиты из клона `fetch`-ом (п. 5), сам пишет в ветку интеграции, и только человек вливает её в базу. `git update-ref`, `git push`, `git -C <проект>` из клона упираются в песочницу, а не в договорённость.
2. **Песочница исполнителя по провайдеру** (проверено задачей 0 на macOS 15.3). Codex 0.162.0 — `-c sandbox_mode="workspace-write" -c sandbox_workspace_write.exclude_slash_tmp=true -c sandbox_workspace_write.exclude_tmpdir_env_var=true -c approval_policy="never"` с `cwd` = клон; `.git` клона при этом только для чтения (коммитит движок). Claude Code 2.1.309 — файл настроек сессии `{"sandbox":{"enabled":true,"failIfUnavailable":true,"allowUnsandboxedCommands":false,"autoAllowBashIfSandboxed":true}}`, режим `acceptEdits`, переменная `TMPDIR` = каталог попытки (единственный разрешённый каталог вне клона, убирается вместе с ним); поддержка Claude Code как исполнителя **предварительная** до реализации правила «запрос разрешения = `aborted`» (§3.3). Каталоги попыток и checkout — не под `/tmp` и не под `$TMPDIR` (оба входят в корни записи по умолчанию): `<проект>/.parley/works/<id>/autonomous/<planId>/attempts/<attemptId>/` (`.parley/` в `.gitignore`).
3. **Песочница запускателя** (п. 4): обёртка `sandbox-exec` с профилем `send-signal SIGKILL` ограничивает запись каталогом checkout, журнал `com.apple.sandbox.reporting` даёт обнаружение.
4. **Жёсткие ворота — задача 0, пройдены** (`docs/audits/2026-10-24/write-boundary-gates.md`, скрипты и выводы в `gates/`); повторяются скриптом `scripts/gates/write-boundary.sh` при смене версий CLI. Тесты побегов: запись через оболочку по абсолютному пути вне корня; симлинк внутри корня наружу; `git update-ref refs/heads/autonomous/<planId>` и `git push` в репозиторий проекта; `git -C <проект> commit`; модуль-кандидат, пишущий наружу во время прогона; **правка объекта или pack-файла на месте внутри клона** — байты и `git fsck` одноимённого объекта проекта не изменились (проверка изоляции хранилища, а не только путей). Ожидание — отказ песочницы или отсутствие влияния на проект, событие в `log`. Провайдер, не прошедший ворота, исключается из исполнителей (`halted: confinement` при Go с таким провайдером); если не проходит запускатель или ни один провайдер — этап останавливается до решения человека (перепланирование), а не принимает задокументированный побег.

## 12. Риски этапа

- Граница записи проверена только на macOS с текущими версиями CLI; Claude Code как исполнитель и проверяющий — предварительно (файловые инструменты вне cwd задают вопрос, а не отказывают); на другой платформе или версии ворота повторяются скриптом до запуска.
- Изолированные клоны вместо worktree: `--no-hardlinks` копирует объекты (на репозитории Parley это десятки мегабайт на попытку и на прогон; уборка после `integrated` обязательна), клоны не видны панели Changes, хосту нужен новый вид рабочего каталога сессии (`workspace`); это добавляет объём задаче 7 и правке `launch`.
- Объём хоста: движок, канал агента, запускатель и интеграция — четыре новых модуля; оценка объёма — после задачи 2 исполнителями.
- `map.json` растёт: в карте только хэши, пути и сводки; хвосты и артефакты — файлы.
- Переподтверждение всех качественных критериев после каждого слияния стоит сессии проверяющего на интеграцию (один проверяющий получает все критерии разом, не по сессии на пункт); при `k` пунктах это `k` интеграций × один проверяющий. Дешевле только с моделью влияния — следующие этапы.
- Один вендор у исполнителя и проверяющего допустим (ответ 7): риск коррелированных ошибок снижают исполняемые проверки и разные размеры моделей.
- **Время жизни потомков кандидата (редакция 7, рецензия m-227).** Запускатель ограничивает возврат из прогона (ожидание по exit, дренаж stdio, kill группы) и ищет сирот через `lsof` по каталогу прогона (найдены → убиты, `error: orphan-descendants`; `lsof` недоступен → `error`, fail-closed). Потомок, сделавший `setsid`, сменивший cwd за пределы каталога прогона и закрывший дескрипторы, не находится: на macOS `ps` не показывает окружение и сессии, `pgrep -s` отсутствует. Его записи вне корней всё равно блокирует унаследованный профиль seatbelt — не ограничено только время жизни. Платформенный супервизор процессов — вне этапа.
- **Навыки агента в клоне попытки (задача 7, m-328).** `installAgentSkill` рассчитан на worktree с общим gitdir проекта (исключение через `.git/info/exclude` проекта); в изолированный клон навыки не устанавливаются, иначе захват движка забрал бы файлы хоста в дерево попытки. Исполнители в клоне получают бриф «Clone» и канал MCP, но не файлы навыков. Для пилота с реальными агентами (§11) проверить, достаточно ли брифа; при необходимости — установка навыков вне дерева клона или исключение путей хоста при захвате (отдельное решение).
