# Spec: слой данных (jsonl-сессии Claude Code)

Статус: **подтверждено 2026-09-01** на 335 реальных файлах (557 МБ, 111 196 записей),
Claude Code `2.1.247`. Снимок наблюдения — `docs/schema/` (README там же описывает
прогон и очистку). Прежняя редакция этого файла была набором гипотез; расхождения
перечислены в конце.

## Источник

- Корень: `~/.claude/projects/`. Каталог строго read-only.
  `~/.claude/.credentials.json` не читать НИКОГДА.
- Формат недокументирован и ломается между релизами Claude Code.

### Раскладка на диске (подтверждено, 335/335 файлов)

```
~/.claude/projects/
  <project-slug>/                                  слаг = cwd с заменой / и . на -
    <session-id>.jsonl                             47  — НАСТОЯЩАЯ сессия
    sessions-index.json                             3  — старый кэш Claude Code, не источник истины
    MEMORY.md                                       9  — не наши данные
    <session-id>/
      subagents/
        agent-<agentId>.jsonl                      13  — подсессия субагента
        agent-<agentId>.meta.json                       — её метаданные
        workflows/
          wf_<runId>/
            agent-<agentId>.jsonl                 240  — подсессия агента внутри workflow
            agent-<agentId>.meta.json
            journal.jsonl                          35  — журнал workflow, НЕ сессия
      workflows/
        wf_<runId>.json                                 — дескриптор workflow
```

**Главное следствие:** «1 файл = 1 сессия» неверно. Сессия — это файл
`<project-slug>/<session-id>.jsonl`; подсессии — **отдельные файлы** рядом, а не
записи внутри. Дискриминатор — путь, а не содержимое: всё под `<session-id>/subagents/`
относится к сессии `<session-id>`.

Связи проверены на 253/253 файлах субагентов:

- каждая запись в `agent-<agentId>.jsonl` несёт `sessionId` **родительской** сессии;
- `agentId` в записях равен `<agentId>` из имени файла;
- `isSidechain: true` у 100% записей файлов субагентов и у 0% записей главных файлов —
  то есть это признак файла, а не способ группировки внутри файла.

## Правила извлечения

**Заголовок сессии.** Последняя по порядку запись `custom-title` (`customTitle`) или
`ai-title` (`aiTitle`) с нужным `sessionId`. Записи append-only и дублируются (2 887
записей на 47 сессий) — брать именно последнюю. Покрытие 47/47 сессий; у сессии
всегда ровно один из двух типов, никогда оба. **Глобальная сшивка по чужим файлам не
нужна.** Fallback, если заголовка нет: `lastPrompt` последней записи `last-prompt`,
затем первая пользовательская реплика.

**Мета.** `cwd`, `gitBranch`, `version`, `sessionId` присутствуют на 100% записей
`user` / `assistant` / `attachment`. Достаточно первой попавшейся.

**Длительность.** min/max `timestamp` по записям файла. Заголовочные и служебные записи
(`custom-title`, `ai-title`, `last-prompt`, `bridge-session`, записи journal)
таймстемпа не имеют — по ним время не считать.

**Модель.** `message.model` на записях `assistant` (100% присутствия). Наблюдались
`claude-opus-5`, `claude-fable-5`, `claude-opus-4-8`, `claude-sonnet-5` и `<synthetic>`.
`<synthetic>` — служебные сообщения, из подсчёта `primaryModel` исключать.

**Инструменты.** Блоки `type:"tool_use"` в `message.content[]` (топ: Bash, Read, Edit,
Write, mcp__*).

**Подсессии.** Не разбор `parentUuid`, а обход каталога `<session-id>/subagents/`:

- задача подсессии — `description` из `agent-<agentId>.meta.json`; там же
  `agentType`, `name`, `toolUseId`, `spawnDepth`;
- у workflow-агентов (240 из 253) meta содержит только
  `{"agentType":"workflow-subagent","spawnDepth":1}` — ни описания, ни `toolUseId`.
  Для них задача = первый текстовый блок в файле агента;
- `toolUseId` находится среди `tool_use` родительской сессии в 13/253 случаев (ровно
  у неworkflow-агентов) — это точка привязки к главной цепочке; для остальных якоря нет;
- `spawnDepth` всегда 1: вложенных субагентов в данных нет, но парсер не должен на это
  закладываться;
- `journal.jsonl` — не подсессия. Это лог workflow: `started` / `result` по `agentId`;
- `<session-id>/workflows/wf_<runId>.json` — дескриптор workflow (`workflowName`,
  `summary`, `status`, `phases`, `agentCount`, `durationMs`), пригоден как группировка
  подсессий; читать опционально.

## Требования к core

1. **Streaming**: построчное чтение, файл не грузится в память целиком (самый большой
   реальный файл — 53 МБ).
2. **Толерантность**: битая/оборванная строка (живая сессия пишется прямо сейчас) —
   норма; фиксируется счётчиком, не роняет парсер. В снимке 0 битых строк, но
   гарантии нет.
3. **Версионированный адаптер**: `adapter-v1` для схемы Claude Code 2.1.x; raw-запись →
   typed `SessionRecord`; ни одно поле не обязательное; неизвестные поля сохраняются.
   При поломке формата после релиза — новый адаптер, старый остаётся.
4. **Schema-report** как встроенная возможность core (порт `observe()`): по нему
   диагностируется расхождение после апдейтов. Известный дефект прототипа: `observe()`
   рекурсирует в мапы с динамическими ключами (`snapshot.trackedFileBackups.<путь>`) и
   раздувает отчёт — в core такие ключи схлопывать.
5. **Watcher**: fs.watch по `~/.claude/projects` с debounce; инкрементальный ре-парс
   только изменённого файла. Учитывать, что изменение файла субагента должно
   инвалидировать и его родительскую сессию.
6. **Контракт**: core — отдельный пакет; наружу только JSON в stdout
   (`harnas-core index --json`, `harnas-core session <id> --json`) и typed API для tui.

## Модель данных (наружу)

- `SessionIndex[]`: id, project (слаг), projectPath (из `cwd`), cwd, gitBranch, version,
  title, titleSource (`custom` | `ai` | `prompt`), startedAt, endedAt, durationMs,
  records, models{}, tools{}, primaryModel, subsessionCount, provider
  (`claude` | `codex` | `glm`).
- `SessionTree`: mainChain + subsessions[] {agentId, agentType, name, task, workflowRunId,
  models[], startedAt, endedAt, records, anchorToolUseId?}.

## Тестовые данные

- 2-3 реальных файла сессий, анонимизированных (пути, тексты реплик заменить),
  закоммиченных как фикстуры; обязательно с парой `agent-*.jsonl` + `.meta.json` и
  одним `journal.jsonl`, чтобы дерево подсессий покрывалось.
- Синтетика: оборванная последняя строка; сессия без заголовка (только `last-prompt`);
  `agent-*.jsonl` без соседнего `.meta.json`; записи без timestamp; пустой файл;
  `<synthetic>` как единственная модель.

## Что разошлось с прежними гипотезами

| Гипотеза (было) | Реальность (2.1.247) |
|---|---|
| Заголовок — записи `type:"summary"` | Типа `summary` нет. Заголовок — `custom-title` / `ai-title` |
| Summary в соседнем файле, сшивать глобально по `leafUuid` | Сшивка не нужна: 47/47 заголовков лежат в своём файле. `leafUuid` существует, но у `last-prompt` и указывает на последнюю реплику |
| Подсессии — записи `isSidechain:true` внутри файла сессии | Подсессии — отдельные файлы в `<session-id>/subagents/`. В главных файлах `isSidechain:true` не встречается ни разу |
| Якорь подсессии — подъём по `parentUuid` до несайдчейнового предка | Подъём невозможен (предка нет в файле). Привязка — путь + `agentId`; точка в цепочке — `meta.toolUseId`, и только у 13/253 |
| Задача подсессии — первая реплика | Для 13 агентов есть `meta.description` (точнее). Первая реплика — fallback для workflow-агентов |
| 1 файл = 1 сессия, `sessionId` уникален | 335 файлов = 47 сессий + 253 субагента + 35 журналов; `sessionId` повторяется во всех файлах поддерева |
