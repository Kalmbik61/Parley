# Spec: слой данных (jsonl-сессии Claude Code)

Статус: **гипотезы, не проверенные на реальных данных**. Первые две задачи fix_plan
(запуск экспортёра + сверка schema-report) обязаны подтвердить или поправить этот файл
ДО написания кода парсера. После сверки обновить статус на «подтверждено <дата>».

## Источник

- `~/.claude/projects/<slug>/<session-id>.jsonl` — по файлу на сессию.
- Каталог строго read-only. `~/.claude/.credentials.json` не читать НИКОГДА.
- Формат недокументирован и ломается между релизами Claude Code.

## Предполагаемая структура записи

- Мета (на записях цепочки): `sessionId`, `cwd`, `gitBranch`, `version`, `timestamp`, `uuid`, `parentUuid`.
- `type` — как минимум: `summary`, `user`, `assistant`; реальный список даст schema-report.
- Имя сессии: записи `type:"summary"` с полем `summary` (возможно `title`).
  Иногда summary лежит в СОСЕДНЕМ файле и ссылается на `leafUuid` — сшивать глобально
  по всем файлам (двухпроходный алгоритм: собрать все summary → раздать по сессиям,
  чей набор uuid содержит leafUuid). Гипотеза: leafUuid указывает на последнюю запись
  цепочки; парсер использует superset (все uuid сессии) — это надёжнее.
- Длительность: min/max по timestamp записей.
- Подсессии: записи с `isSidechain: true`; якорь — подъём по `parentUuid` до первого
  несайдчейнового предка. Защита от циклов обязательна (guard-счётчик).
- Модель: `message.model` на записях assistant; бейдж подсессии — уникальные модели
  её записей; primaryModel сессии — самая частая.
- Инструменты: блоки `type:"tool_use"` в `message.content[]`.

## Прототип

`tools/claude-export.mjs` — рабочий standalone-прототип всей этой логики (потоковое
чтение, толерантность к битым строкам, schema-report, дерево сайдчейнов, сшивка
summary). Портировать его логику в typed-модули packages/core, НЕ переписывать с нуля.
Известный нюанс прототипа: при `--limit` сшивка summary видит только обработанные
файлы — в core сшивка всегда глобальная.

## Требования к core

1. **Streaming**: построчное чтение, файл не грузится в память целиком.
2. **Толерантность**: битая/оборванная строка (живая сессия пишется прямо сейчас) —
   норма; фиксируется счётчиком, не роняет парсер.
3. **Версионированный адаптер**: `adapter-v1` для наблюдаемой схемы; raw-запись →
   typed `SessionRecord`; ни одно поле не обязательное; неизвестные поля сохраняются.
   При поломке формата после релиза Claude Code — новый адаптер, старый остаётся.
4. **Schema-report** как встроенная возможность core (порт `observe()`): по нему
   диагностируется расхождение после апдейтов Claude Code.
5. **Watcher**: fs.watch по `~/.claude/projects` с debounce (файл дописывается
   пачками); инкрементальный ре-парс только изменённого файла.
6. **Контракт**: core — отдельный пакет; наружу только JSON в stdout
   (`harnas-core index --json`, `harnas-core session <id> --json`) и typed API для tui.

## Модель данных (наружу)

- `SessionIndex[]`: id, project, cwd, gitBranch, version, summary, startedAt, endedAt,
  durationMs, records, models{}, tools{}, primaryModel, subsessionCount, provider ("claude" | "codex" | "glm").
- `SessionTree`: mainChain + subsessions[] {anchorUuid, task, models[], startedAt, endedAt, records}.

## Тестовые данные

- 2-3 реальных файла сессий, анонимизированных (пути, тексты реплик заменить),
  закоммиченных как фикстуры.
- Синтетика: оборванная последняя строка; summary в соседнем файле; сайдчейн-сирота
  (parentUuid не находится); записи без timestamp; пустой файл.
